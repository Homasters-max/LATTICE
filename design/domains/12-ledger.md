# 12. ledger — журнал, коммит, индекс, хранилище

**Назначение.** Хранить все ревизии в одном append-only журнале и давать быстрый доступ к текущему состоянию через
вычисляемый индекс.

**Зависит от:** [10-kernel](10-kernel.md), [13-rules](13-rules.md) (проверка при коммите). **Используют:** все.

## Модель

### 1. Журнал — единственный источник истины

- Одна строка — одна ревизия (канонический JSON) + служебное `seq`. Только дописывание.
- Ничего не мутирует: новая версия — новая строка; отмена — факт или утверждение.
- В журнал пишется всё: объекты проекта, типы, правила, факты, вызовы конвейера, оценки, вердикты, прогоны стенда.
- Одно хранилище может держать несколько пространств имён; проект читает свои и импортированные (CT-02).

### 2. Коммит — всё или ничего

```text
commit(rows[], by) →
  1. заполнить заголовки (at, seq, id для новых, version = текущая + 1)
  2. отбросить no-op (то же тело, что у текущей ревизии; уже существующее значение)
  3. правила hard для каждой строки — на состоянии «индекс + уже принятые строки этого коммита»
  4. все прошли → дописать строки и обновить индекс; хотя бы одна нет → ничего не писать, вернуть нарушения
```

- Идентификатор коммита — хэш канонического массива его строк; пишется в `seq`-метку строк (`commit`).
- Проверка версии — compare-and-set: ожидаемая текущая версия передаётся явно; расхождение → конфликт, не перезапись.
- Один писатель на хранилище (файл-замок); читателей — сколько угодно.

### 3. Индекс — вычисляемое состояние

Индекс ничего не знает сверх журнала и пересобирается из него. Руками не правится.

| Раздел индекса | Содержимое |
|---|---|
| `revisions` | `id@version` → смещение в журнале, хэш |
| `latest` | `id` → последняя версия, живой ли |
| `byType` | тип → id объектов |
| `grain` | тип → ключ зерна → id (только живые) |
| `aliases` | алиас → канонический (сжатые цепочки) |
| `facts` | тип факта → ключ факта → текущий факт; накапливаемые — списком |
| `consumers` | `id@version` / `id` → кто ссылается (обратные ссылки) |
| `trust` | факт → `{grounding, epistemic}` (вычисляет [14-trust](14-trust.md)) |
| `snapshots` | значение snapshot'а → статус (`fresh` / `stale` / `broken`) по запросу |

Вычисляемые атрибуты (как `@property` в Python): последняя версия, доверие, статус snapshot'а — **не пишутся в
журнал**.

### 4. Пересборка детерминирована

`rebuild()` дважды на одном журнале даёт побайтно одинаковый индекс (канонический JSON, стабильный порядок).
Это регрессионная проверка системы (эффект E6 первого запуска).

### 5. Порт хранилища

```ts
interface Store {
  append(rows: Revision[]): Promise<void>        // атомарно; вызывает только ledger после проверки
  scan(fromSeq?: number): AsyncIterable<Revision> // по порядку seq
  lock(): Promise<Release>                        // один писатель
  saveIndex?(ix: IndexBlob): Promise<void>        // кэш индекса, необязательно
  loadIndex?(): Promise<IndexBlob | null>
}
```

Первый адаптер — `store-jsonl` ([30](30-adapters.md)): `ledger.jsonl` + `index.json` в каталоге данных проекта.
Позже — SQLite / PostgreSQL; раскладка в Anchor Modeling — механическая проекция (анкер — сущность, атрибут — поле
тела во времени, tie — факт с ≥ 2 ролями, knot — значения закрытых списков).

## Операции

| Операция | Вход → выход |
|---|---|
| `commit(rows, by, expect?)` | → `{ok, ids, commit}` или `{violations}` |
| `get(ref)` | → ревизия (через `resolve`, [11](11-identity-grain.md)) |
| `history(id)` | → все ревизии объекта |
| `facts(type, where?)` | → текущие факты по ключу / накопленные |
| `find(type, where?)` | → живые объекты типа (фильтр по полям тела) |
| `consumers(ref)` | → кто ссылается |
| `rebuild()` | → индекс |

## Инварианты

1. Журнал только растёт; строка, однажды записанная, не меняется.
2. Индекс = функция журнала: `rebuild(ledger) == index`.
3. В журнале нет строк, не прошедших правила `hard` на момент коммита.

## Решения

| ID | Решение | Почему |
|---|---|---|
| LG-01 | Один append-only журнал JSONL на хранилище; пространства имён внутри | просто, переносимо, история бесплатно |
| LG-02 | Текущее состояние, доверие, статусы — вычисляемый индекс | одна истина; индекс можно перестроить и сменить |
| LG-03 | Коммит атомарен; правила `hard` проверяются на состоянии с учётом строк того же коммита | план слияния и новая версия типа — одним шагом |
| LG-04 | Порядок — `seq`; `at` — для людей и доверия | время на разных машинах не совпадает |
| LG-05 | Хранилище — порт; первый адаптер JSONL | смена хранилища без смены модели |
| LG-06 | Compare-and-set по версии; один писатель | нет потерянных обновлений |
| LG-07 | Пересборка побайтно детерминирована | проверка целостности и регрессии |
| LG-08 | Вызовы, оценки, вердикты — тоже в журнале | аудит и воспроизведение конвейера |

## Вопросы для grilling

1. **Объём журнала:** события конвейера (оценки с баллами по 200 карточкам) быстро растут. Отдельный сегмент
   (`runtime.jsonl`) или один файл? Рекомендация: один логический журнал, физически сегменты по префиксу типа —
   решение адаптера, не модели.
2. **Несколько проектов в одном хранилище или хранилище на проект** с импортом общих библиотек? Рекомендация:
   хранилище на проект + общее хранилище `std` только для чтения; один писатель — проще.
3. **Кэш индекса** на диске — сразу или пересборка при старте? Рекомендация: пересборка, пока журнал < 50 МБ;
   кэш — когда станет медленно.

## Вне объёма

- Репликация, распределённая запись, подписи строк.
