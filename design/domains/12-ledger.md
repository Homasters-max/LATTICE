# 12. ledger — журнал, коммит, индекс, хранилище

**Назначение.** Хранить все ревизии в одном append-only журнале и давать быстрый доступ к текущему состоянию через
вычисляемый индекс.

**Зависит от:** [10-kernel](10-kernel.md), [11-identity-grain](11-identity-grain.md) (`resolve`, область зерна),
[13-rules](13-rules.md) (проверки при коммите). **Используют:** все; catalog — коммит обновления `std` ([15](15-catalog.md)).

## Модель

### 1. Журнал — единственный источник истины

- Одна строка — одна ревизия (канонический JSON) + заголовок строки. Только дописывание.
- Ничего не мутирует: новая версия — новая строка; отмена — факт или утверждение.
- В журнал пишется всё: объекты проекта, типы, правила, факты, вызовы конвейера, оценки, вердикты, прогоны стенда.
- Хранилище — на проект: пространство проекта (одно в v1) и неизменные копии `std` и импортированных блоков ([15](15-catalog.md),
  ADR-4); общего хранилища на чтение нет (LG-11).
- Порядок — только `seq` (LG-04); `at` — для людей.

**Заголовок строки** (T113) — служебные поля вне объекта; заголовок объекта (`id`, `type`, `version`, `at`, `by`) —
[10-kernel](10-kernel.md) §1.

| Поле | У каких строк | Что |
|---|---|---|
| `seq` | каждая | целое, позиция в журнале; строго возрастает, плотность не обещается (LG-14); назначает адаптер при `append` |
| `commit` | каждая | хэш коммита — хэш канонического массива ревизий коммита без полей строки и без маркера (KR-06) |
| `kernel` | маркер | версия ядра, проверками которой прошёл коммит ([13](13-rules.md) RL-12) |
| `key` | маркер, если задан | ключ идемпотентности коммита; задаёт вызывающий (id вызова, вердикт, источник + версия импорта) |

**Маркер коммита** `core/commit` (T114, тип генезиса) — последняя строка каждого коммита, тело
`{hash, rows}`: `hash` = `commit` строк коммита, `rows` — число строк до маркера; `id` — `#…` из тела. Строки после
последнего маркера — оборванная запись, не коммит.

**Сегменты со сроком** (T115, ADR-3). События исполнения пишутся в тот же журнал и поток `seq`, но в сегменты со
сроком хранения по типу; проекции доменов их не читают (исключение — раздел индекса `executions` для проверок коммита, §3,
ADR-3); сегмент истекает только целиком, строка внутри — никогда.

| Тип строк | Сегмент | Срок |
|---|---|---|
| `std/execution` | исполнение | горизонт replay — насколько старый вызов система обязуется воспроизвести ([22](22-run.md)) |
| `std/measurement` | исполнение | тот же |

- Число — замером первого запуска (как LG-09); до замера сегменты **не истекают**. Механизм истечения — вопрос 2.
- Значения, на которые ссылается трасса (тексты — значения по хэшу, T-4; промпты стадий — в `params` закреплённого
  `pipeline@n`, шаблоны judge — `prompt_hash`), лежат в основном журнале и не истекают. Копия кампании стенда `.lattice/bench/<run>` (T138) — вне журнала, сроки ADR-3 её не касаются.

### 2. Коммит — всё или ничего

```text
commit(rows: Draft[], by, key?) →                        // Draft, Row — §5; expect — поле Draft
  0. t = seq хвоста, до которого дочитан индекс; key уже есть в индексе `keys` → вернуть прежний результат,
     ничего не писать
  1. входная проверка ядра; заголовки: at = clock.now(), id новых без id = newId(namespace, ids.ulid())
     (id, выданный стадией вызова, сохраняется — [22](22-run.md)), version = текущая + 1 ([10](10-kernel.md));
     строки пакета импорта сохраняют заголовок поставщика ([15](15-catalog.md) §1)
  2. отбросить no-op: сущность — то же тело под тем же type@n (ADR-2); факт — тот же ключ и value;
     значение уже есть в хранилище, но пространство by его не держит → вместо no-op строка core/holds (10-kernel §7)
  3. нет зарегистрированных значений: строка содержит известное значение секрета → отказ всего коммита (T-12)
  4. expect: сущность с текущей версией > 1 — Draft.expect обязателен и равен текущей; иначе конфликт. Факты — без CAS
  5. проверки ядра и hard-правила: построчные — на префиксе «индекс + уже принятые строки этого коммита»;
     относительные (count, grain-unique, unique-within, regrain-plan, acyclic, extends-chain, ref-exists) —
     на итоге «индекс + все строки коммита» ([13](13-rules.md) §2)
  6. всё прошло → store.append(строки + маркер core/commit, expect = {id: Draft.expect}, tail = t); обновить индекс → {ok, ids, commit}
     conflict по хвосту → дочитать индекс scan(t + 1) и повторить шаги 0–5 (до 3 раз, затем {conflict}; ADR-31)
     хотя бы одно нарушение → ничего не писать, вернуть нарушения {row, rule, message} (RL-11)
```

- Повтор с тем же `key` возвращает прежний результат, даже если строки другие (10-kernel, «Когда запись — no-op»).
- В один коммит — только объекты, между которыми нужна строгая согласованность (LG-03): смена зерна типа + план
  слияния ([11](11-identity-grain.md) GR-03), новая версия типа + перевод. Остальное — отдельными коммитами.
- Шаги 0–5 считаются на индексе на хвосте `t`; `append` атомарно сверяет `tail` и `expect` (истина, ADR-31): коммит,
  вставший между чтением и записью, вызывает повтор шагов 0–5 на дочитанном индексе. Так атомарны ключ
  идемпотентности, `grain-unique`, `count`, `unique-within` и `expect`; шаг 4 — ранний отказ.
- **Порядок строк в коммите исход не меняет:** построчная проверка судит строку по тому, что до неё (право, вид,
  версия), относительная — по итогу коммита; перестановка строк с разными `id` даёт тот же результат (тест S1).
  Так `learn` пишет `[+Z, −Y]` в решение из 7 членов в любом порядке.
- **Открытие хранилища:** сверка хэша генезиса как звена цепочки генезиса ядра ([10](10-kernel.md) KR-16, KR-19,
  ADR-34); строки после последнего маркера переносятся в `.lattice/recovered/` и отрезаются до `rebuild()`. Пересборка
  и так читает весь журнал, поэтому `open()` заодно сверяет у каждого коммита `hash` маркера с его строками и
  строгий рост `seq`; расхождение — отказ открытия с адресом первого расходящегося коммита (LG-19). С кэшем индекса
  (LG-09) сверяется дочитываемый хвост.

### 3. Индекс — вычисляемое состояние

Индекс ничего не знает сверх журнала и пересобирается из него; сегменты читает только раздел `executions`. Руками
не правится.

| Раздел индекса | Содержимое |
|---|---|
| `revisions` | `id@version` → `seq`, хэш; физический адрес — внутри адаптера |
| `latest` | `id` → последняя версия (последняя по `seq`), живой ли |
| `byType` | тип → id объектов |
| `grain` | тип → ключ зерна → id (только живые) в области зерна: пространство автора или `store` (ADR-27) |
| `aliases` | алиас → канонический (сжатые цепочки); только `core/alias` в силе (ADR-8) |
| `facts` | тип факта → ключ факта → текущий факт (последний по `seq`); накапливаемые — списком |
| `consumers` | `id@version` / `id` → кто ссылается (обратные ссылки) |
| `trust` | цель (факт или ревизия) → результат `trust()`: `{basis, epistemic, support, groups, overruled?, policy}` (проекцию подключает [14-trust](14-trust.md)) |
| `snapshots` | значение snapshot'а → статус (`fresh` / `stale` / `broken`); `stale` — и через отменённый алиас (GR-15) |
| `keys` | ключ идемпотентности → `{commit, ids}` |
| `executions` | id вызова → `{кортеж исполнения ([22](22-run.md) §1), status, seq}` — только живые сегменты; читают только проверки коммита (`ref-exists`, `learning-gate`, [13](13-rules.md) §2), не проекции доменов (ADR-3) |

Вычисляемые атрибуты (как `@property` в Python): последняя версия, доверие, статус snapshot'а — **не пишутся в
журнал**.

**Проекции подключаемые** (T170, N-32): раздел индекса — проекция `{name, version, apply(row, ix)}`, чистая функция
строки коммита и текущего индекса (запреты — §4). Разделы таблицы, кроме `trust`, — проекции этого домена; `trust` —
проекция [14](14-trust.md). Список проекций передаёт `open()` корень сборки ([04](../04-architecture.md) §4); имена и
версии проекций — поле `projection` кэша индекса.

### 4. Пересборка детерминирована

`rebuild()` дважды на одном журнале даёт побайтно одинаковый индекс (каноническая форма — KR-06, ADR-1; стабильный
порядок). Это регрессионная проверка системы (эффект E6 первого запуска).

- **Запреты для кода проекции:** не вызывает `clock` / `ids`, не зависит от порядка параллельного обхода, не читает
  сегменты; `snapshots` при пересборке всегда пересчитывается, из прежнего индекса не берётся.
- **`rebuild --check`:** (1) пересборка с нуля против текущего индекса, который коммиты ведут приращениями; (2) при
  смене кода проекции — против сохранённого индекса прежней версии проекции (вместо миграции индекса). Расхождение —
  первый расходящийся раздел §3 и ключ. Прогон — минимум на двух платформах (Windows, Linux).
- **Эталонные журналы-фикстуры** с проверенным ожидаемым индексом по всем разделам §3, заморожены: побайтное
  совпадение доказывает воспроизводимость, фикстуры — правильность.
- **Кэш индекса** — `IndexBlob {projection, seq, data}`: `loadIndex` сверяет `projection` с кодом проекции и `seq` с
  хвостом журнала, дочитывает `scan(seq + 1)`; не сошлось — пересборка. `saveIndex` — после коммита, не часть его
  успеха. Пока не сработал триггер LG-09, кэш не пишется: индекс пересобирается при открытии.

### 5. Порты хранилища и времени

Контракт портов — здесь (ADR-24); реализации и проводка — [30-adapters](30-adapters.md).

```ts
interface Store {
  append(rows: Omit<Row, "seq">[], expect?: Expect, tail?: number): Promise<number> // атомарно: CAS + строки + маркер; seq назначает адаптер; → seq первой строки
  scan(from?: number, to?: number): AsyncIterable<Row>  // по порядку seq; from, to — включительно; только целые коммиты
  history?(id: string): AsyncIterable<Row>              // ревизии объекта, если адаптер умеет быстрее scan
  saveIndex?(ix: IndexBlob): Promise<void>              // кэш индекса (§4), необязательно
  loadIndex?(): Promise<IndexBlob | null>
}
type Expect = Record<string, number>                    // {id: ожидаемая текущая версия}
type Draft  = { type: string; id?: string; body: Json; expect?: number }  // строка до коммита — вход commit: без заголовков; type без @n — последняя версия (type-latest);
                                                        // expect — версия изменяемой сущности, прочитанная из view
type Row    = { id: string; type: string; version: number; at: string; by: string; body: Json   // ревизия ([10] §1)
                seq: number; commit: string; kernel?: string; key?: string }                   // + заголовок строки (§1)
type IndexBlob = { projection: string; seq: number; data: unknown }

interface LedgerView {                                  // чтения индекса на seq («Операции»); View стадий — [22] §2
  seq: number
  get(ref: Ref): Row | null;  history(id: string): AsyncIterable<Row>
  facts(type: string, where?: Json): Row[];  find(type: string, where?: Json): Row[];  consumers(ref: Ref): Ref[]
}
interface Clock { now(): string }                       // UTC, мс — поле at
interface Ids { ulid(): string }                        // для newId (10-kernel)
```

**Контракт `Store`** (проверяют общие контрактные тесты; каждый адаптер — `store-jsonl`, `store-memory` — проходит
тот же набор, T-10):
- `append` атомарен: после успешного возврата все строки коммита с маркером долговечны; при отказе — ни одной.
- CAS: последний `seq` журнала ≠ `tail` или текущая версия хоть одного `id` из `expect` отличается → отказ
  `conflict`, ничего не записано (ADR-31).
- Один писатель: адаптер сериализует `append` своим замком с владельцем (процесс / сессия) и сроком; просроченный
  замок снимается; чужой непросроченный замок — ожидание со сроком, затем отказ `locked` (ADR-31). **Ограждение:**
  перед записью `append` сверяет, что замок всё ещё свой и не просрочен, иначе `locked`, ничего не записано —
  писатель, проспавший срок, не допишет строки, посчитанные на старом хвосте (контрактный тест, LG-06). Хранилище — только локальный диск; сетевые ФС не поддерживаются.
- Видимость: `scan` отдаёт только строки коммитов с маркером; читатель не видит часть идущего `append`.
- `seq` — целое, строго возрастает; пропуски допустимы (истёкший сегмент, отрезанный хвост); физический адрес
  (смещение, файл сегмента) порт не раскрывает.

`Clock` и `Ids` — единственные источники времени и новых ULID: операции ядра получают их аргументами; стадии получают
через `Deps` (T133) только `ids` — часов у стадий нет, `at` ставит коммит; в тестах — детерминированные реализации.

Первый адаптер — `store-jsonl` ([30](30-adapters.md)): `ledger.jsonl` в каталоге данных проекта; `index.json` — когда
включён кэш. Позже — SQLite / PostgreSQL (триггер — LG-09); раскладка в Anchor Modeling — механическая проекция
(анкер — сущность, атрибут — поле тела во времени, tie — факт с ≥ 2 ролями, knot — значения закрытых списков).

## Операции

| Операция | Вход → выход |
|---|---|
| `open()` | → хранилище: сверка генезиса (звено цепочки, ADR-34), отрезанный хвост → `.lattice/recovered/`, сверка маркеров и роста `seq`, индекс (кэш или пересборка) |
| `commit(rows, by, key?)` | → `{ok, ids, commit}` · `{conflict}` · `{violations}` · `{locked}` |
| `get(ref)` | → ревизия (через `resolve`, [11](11-identity-grain.md)) |
| `history(id)` | → все ревизии объекта (`store.history` или `scan`) |
| `facts(type, where?)` | → текущие факты по ключу / накопленные |
| `find(type, where?)` | → живые объекты типа (фильтр по полям тела) |
| `consumers(ref)` | → кто ссылается |
| `rebuild({check?})` | → индекс · с `check` — первый расходящийся раздел и ключ (§4) |

## Инварианты

1. Журнал только растёт; строка, однажды записанная, не меняется; сегмент со сроком истекает только целиком.
2. Индекс = функция журнала: `rebuild(ledger) == index`; строки сегментов входят только в раздел `executions`.
3. В журнале нет строк, не прошедших проверки ядра и правила `hard` на момент коммита.
4. Каждый коммит заканчивается маркером `core/commit`; строки без маркера не читаются и не входят в индекс.
5. `seq` строго возрастает.
6. В журнале нет зарегистрированных значений секретов; PII — допущение без проверки (KR-14).

## Решения

| ID | Решение | Почему |
|---|---|---|
| LG-01 | Один append-only журнал на хранилище; пространства имён внутри; единственное исключение — сегмент со сроком истекает целиком | просто, переносимо, история бесплатно; события исполнения не копятся вечно. v0.4 · ADR-3 · Q-09 C-2, Q-28 C-3 |
| LG-02 | Текущее состояние, доверие, статусы — вычисляемый индекс | одна истина; индекс можно перестроить и сменить |
| LG-03 | Коммит атомарен; построчные проверки — на префиксе коммита, относительные (`count`, `grain-unique`, `unique-within`, `regrain-plan`, `acyclic`, `extends-chain`, `ref-exists`) — на его итоге; перестановка строк с разными `id` исход не меняет; несколько объектов в одном коммите — только при строгой согласованности между ними | план слияния и новая версия типа — одним шагом (GR-03); прочее — отдельными коммитами. «С учётом строк коммита» было двусмысленно: на префиксе `[+Z, −Y]` в решение из 7 отклонялся, `[−Y, +Z]` — нет. v0.4 · T-9 · Q-23 C-1 · v0.5 · CA-F28 |
| LG-04 | Порядок — только `seq`; `at` — для людей | время на разных машинах не совпадает; верно, пока путь записи один (LG-06). v0.4 · T-6 · П-1 · Q-24 C-1…C-3 |
| LG-05 | Хранилище — порт `Store` с контрактом здесь (ADR-24); первый адаптер JSONL; контракт проверяют общие тесты на каждом адаптере, включая `store-memory`; вход коммита — `Draft` (без заголовков, `expect?`), хранимая строка — `Row`, `scan` включительно | смена хранилища без смены модели; одна реализация не проверяет контракт; строка стадии и строка журнала — разные типы, CAS — против чтения стадии. v0.4 · ADR-24 · T-10 · Q-21 C-3, Q-25 C-3, C-4 · C2c Q4 |
| LG-06 | Один писатель — замок адаптера с владельцем и сроком, только локальный диск; `append` перед записью сверяет, что замок свой и не просрочен (ограждение); CAS `expect {id: version}` обязателен для сущности версии > 1, факты без CAS | один писатель не даёт коммитам перемешаться; CAS ловит потерянное обновление по устаревшему чтению; по отдельности ни один не защищает от сбоя другого; без ограждения писатель, проспавший срок, дописал бы строки после снятия его замка. v0.4 · T-9 · Q-26 C-1…C-3 · v0.5 · CA-F44 |
| LG-07 | Пересборка побайтно детерминирована; `rebuild --check` — с нуля против приращённого индекса и против прежней проекции, на ≥ 2 платформах; эталонные фикстуры | повтор в одном процессе не ловит расхождение приращений и платформ; совпадение — ещё не правильность. v0.4 · Q-22 C-4 · Q-27 C-2…C-4 |

## Вопросы для grilling

v0.3 вопросы 1–3 закрыты в v0.4 — LG-10, LG-11, LG-09.

1. **Прогон частями** (RN-03, вариант (б) ADR-19): трасса и контрольные точки — отдельными коммитами, видимость
   вызова — завершающим фактом. Отложено; триггер — появился `exec` или вызовы дольше нескольких минут. Тогда же —
   правка LG-03 для вызова ([22](22-run.md)).
2. **Истечение сегмента:** операция порта или адаптера, кто и когда её вызывает; хэш коммита, часть строк которого
   истекла, перепроверить нельзя — сверять только маркер. Отложено; триггер — объём сегментов заметно влияет на p95
   пересборки (LG-09) или на диск. Рекомендация: операция адаптера `expire(segment)` по явной команде, не фоном.

## Вне объёма

- Репликация, распределённая запись, подписи строк.
- Запись в `.lattice/` мимо хоста и синхронизация каталога — допущение модели угроз: каталог пишет только хост, он в
  `.gitignore` и вне облачной синхронизации; ловится только то, что видно `open()` (LG-19), — умышленно посчитанный
  хэш маркера не ловится.
- Сетевые файловые системы (LG-06).
- Миграция индекса — вместо неё пересборка и `rebuild --check` (LG-07).
- Сравнение содержимого при повторе ключа идемпотентности (LG-13).
