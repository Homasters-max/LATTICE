# 13. rules — правила, контракты, проверка

**Назначение.** Единственное, что ограничивает поведение (P2). Правило — объект (данные), который параметризует примитив проверки ядра; сверх правил ядро безусловно держит небольшой набор проверок ядра (T134).

**Зависит от:** [10-kernel](10-kernel.md), [11-identity-grain](11-identity-grain.md) (`grain-unique`, `regrain-plan`). **Используют:** ledger (коммит), catalog (публикация), compose (проверка решения), run (контракты стадий, гейт обучения), lint.

## Модель

### 1. Правило — объект

```json
{ "id": "std/rule.solution-size", "type": "core/rule@1", "version": 1, "by": "…",
  "body": {
    "level": "hard",
    "check": "count",
    "params": { "fact": "std/member", "role": "group", "max": 7 },
    "message": "Решение — не больше 7 членов; больше — разбить потребность",
    "doc": "Размер группы решения: не больше 7 членов",
    "examples": { "pass": [{ "facts": ["… 7 × std/member одной group"] }],
                  "fail": [{ "facts": ["… 8 × std/member одной group"] }] }
  } }
```

Поля тела `core/rule`: `level` (`hard` / `soft`), `check` (примитив §2 или `capability`, п. 3), `params`, `message`, `doc`, `examples`, `when` — необязательны все, кроме `level` и `check`.

- Тип закрепляет свои правила: `rules: [{"$ref": "std/rule.solution-size@1"}]` (пример — у типа факта `std/member`, [21](21-compose.md)).
- **Наследование (ADR-12):** правила родителя берутся из закреплённой версии — `extends` у типа — ссылка `id@n` (у типов `refs: pin`, правило `ref-policy`, [15](15-catalog.md)); наследник только добавляет правила и сужает: его правила ⊇ правил родителя `@n`, схема не слабее. Закрытость схемы (`additionalProperties`) считается по объединению свойств всей цепочки `extends`: закрытая схема родителя не отклоняет собственные поля наследника; «не слабее» — по полям родителя (ADR-12).
- Изменить правило = новая версия правила + новая версия типа, которая на неё ссылается. Ревизия проверена ровно теми правилами, что закреплены в её `type@n`, и кодом примитивов версии ядра — `kernel` маркера коммита ([12](12-ledger.md) §1, T113) — проверку можно повторить (`revalidate`).
- `hard` — при коммите, нарушение отклоняет коммит. `soft` — в `lint`, результат — находка (T44). **Находка** — результат проверки, который коммит не отклоняет: `soft` в `lint` и нарушение проверки выбора `check` в вызове (выбор отклонён, коммит вызова идёт, [21](21-compose.md) §5); форма — оболочка нарушения (§2) + уровень.
- **`examples {pass, fail}`** — при публикации версии правила ядро прогоняет их: каждый `pass` правило пропускает, каждый `fail` — отклоняет. При публикации версии типа — все закреплённые правила совместно выполнимы на `pass`-примерах этих правил. Правило без `examples` допустимо.
- **`when: {path, eq}`** — условие: правило действует, только если значение по пути тела проверяемой строки равно `eq`. У факта путь может начинаться с роли (`group.form`) — значение текущей ревизии объекта в этой роли. Так тип выражает согласованность поля с фактами (`form` решения, ADR-17), не заводя примитив под один тип.
- **Схема тела** (`schema` у `core/type`, T125, ADR-9) — сахар: компилируется в правило примитива `schema` с уровнем из поля; у общих типов (`core`, `std`, импортируемые, T172) обязательна, закрыта и `hard` — не умолчание ([10](10-kernel.md), ADR-9). Лестница для проектного типа: нет схемы → `soft` → `hard` новой версией типа; если прежние ревизии новой схеме не соответствуют — только с планом для них. Измерения `grain` — `required` в схеме ([11](11-identity-grain.md)).

### 2. Проверки ядра и примитивы (код ядра)

**Реестр проверок** (T189, ADR-38) — каждая проверка ядра и каждый примитив объявляет, где и к чему применяется; коммит ([12](12-ledger.md) §2, шаг 5) берёт из реестра проверки своего входа и фазы, и только их. Поля записи реестра:

| Поле | Значения | Что |
|---|---|---|
| `scope` | `row` · `commit` | `row` — строку судят по виду «индекс + строки коммита до неё» (`overlay.at(i)`), `commit` — по итогу «индекс + все строки коммита» (`overlay.total()`); перестановка строк с разными `id` исход не меняет (LG-03) |
| `phase` | `write` · `publish-type` · `publish-rule` | `write` — каждая строка; `publish-type` — строка — ревизия `core/type`; `publish-rule` — ревизия `core/rule` |
| `appliesTo` | `author` · `copy` · `genesis` (по умолчанию — все) | источник строки по виду входа коммита (T187): `copy` — строки поставщика, `genesis` — строки генезиса; строки намерений любого входа — источник `author` ([12](12-ledger.md) §2); исключение — называет источник, а не `key` |

**Проверки ядра (T134)** — безусловные: не параметризуются правилом и не отключаются типом (T-16).

| Проверка | `scope` | `phase` | `appliesTo` | Что проверяет |
|---|---|---|---|---|
| `owner` | `row` | `write` | `author`, `copy` | право записи строки — вызов проекции полномочий `view.authority.mayWrite(row, view.seq)` ([10](10-kernel.md) §7, ADR-40); строки входа `genesis` судит не `owner`, а сверка хэша генезиса как звена цепочки ([10](10-kernel.md) KR-16, KR-19): ревизию пишет владелец пространства или допущенный, допуск различает `create` и `edit`, у типов `refs: follow` `edit` не действует — только предложение ([15](15-catalog.md) CT-14); факт — по `writers` типа в пространстве роли `target`; `{purpose}` — по сессии; ревизия `core/session` — только с `by` = она сама ([14](14-trust.md) §1); допуск `core/grant {declare: true}` не-человеку — отказ ([15](15-catalog.md) CT-13); самоустановление первого коммита пространства (ADR-33); копия — против её собственного пространства ([15](15-catalog.md) CT-10) |
| `immutable` | `row` | `write` | все | у неизменяемых нет версии > 1 |
| `grain-unique` | `commit` | `write` | все | ключ зерна уникален среди живых сущностей типа в области зерна (пространство автора или `store`, ADR-27), включая сущность, которую коммит делает живой (`split`) ([11](11-identity-grain.md)) |
| `ref-policy` | `row` | `write` | все | ссылки на объекты типа с `refs: pin` закреплены (`id@n`) |
| `roles` | `row` | `write` | все | роли факта объявлены типом, их объекты нужных типов (наследник — только при ролях контракта, ADR-12) |
| `content-pin` | `row` | `write` | все | у `content`-типов все ссылки тела закреплены `id@n` ([10](10-kernel.md) §2) |
| `kind` | `row` | `write` | все | новая ревизия сохраняет вид объекта — `identity` и `mutable` типа ([10](10-kernel.md) §2, T-16) |
| `type-latest` | `row` | `write` | `author` | `type` новой строки — последняя версия своего типа с учётом строк коммита (новая версия типа и строки под ней — одним коммитом). Входы `copy` (импорт, обновление `std` — заголовок поставщика, ADR-4) и `genesis` её не проходят. Без неё ужесточение `writers` или `schema` новой версией типа обходится записью под старой `type@n` (RL-16) |
| `extends-chain` | `commit` | `publish-type` | все | цепочка `extends` ацикличная с учётом строк коммита, глубина ≤ 4 ([10](10-kernel.md) §6) |
| `regrain-plan` | `commit` | `publish-type` | все | любое изменение состава или порядка `grain` или области `grain_scope` несёт полный план ([11](11-identity-grain.md) GR-18) |
| совместимость схемы | `row` | `publish-type` | все | новая схема общего или `content`-типа принимает всё прежнее, иначе план или новый `id` ([10](10-kernel.md)) |
| совместимость наследования | `row` | `publish-type` | все | правила ⊇ родителя `@n`, схема не слабее по полям родителя, закрытость — по объединению свойств цепочки `extends`, `writers` ⊆, `inForce` не слабее — порядки значений [10](10-kernel.md) §7 (ADR-12) |
| `examples` | `row` | `publish-rule`, `publish-type` | все | п. 1 — на виде `fromRows()` (ниже) |

**Примитивы** — параметризуются правилом `core/rule`; `phase` у всех — `write` (правило закреплено в типе строки), `appliesTo` — все.

| Примитив | `scope` | Что проверяет | Параметры |
|---|---|---|---|
| `schema` | `row` | форма тела (подмножество JSON Schema: type, required, properties, enum, pattern, items, additionalProperties) | `schema` |
| `ref-exists` | `commit` | каждая `$ref` тела разрешается — единственный владелец проверки ссылок ([10](10-kernel.md) инвариант 5, [12](12-ledger.md) §2 ссылаются сюда); ссылка на событие исполнения — по разделу индекса `executions` ([12](12-ledger.md) §3): при коммите вызова там нет — нарушение (вердикт на вызов старше горизонта не принимается); при `revalidate` ссылка в истёкший сегмент — находка «не проверяемо» | `pinned?` — требовать `@n` |
| `ref-type` | `row` | ссылка по пути указывает на объект нужного типа или наследника — наследника только при ролях, объявленных в контракте (ADR-12) | `path`, `type` |
| `acyclic` | `commit` | граф по факту или по ссылкам без циклов (решение-граф, ADR-18); с `role` — в пределах объекта этой роли у проверяемой строки | `fact` / `path`, `role?` |
| `contract` | `row` | цепочка стадий согласована по контрактам (п. 3) — правило типа конвейера | — |
| `unique-within` | `commit` | значение поля уникально в группе | `path`, `scope` |
| `count` | `commit` | число действующих фактов вида `fact`, где в роли `role` тот же объект, что у проверяемой строки (без `role` — в любой роли), в пределах. Направление: строку вида `fact` с `value: false` (окончание) не проверяет `max`, строку вида `fact` с `value` ≠ `false` — `min`; строки других типов (ревизия `std/solution` со сменой `form`) — оба предела. Строка, уменьшающая нарушение, не отклоняется (RL-17) | `fact`, `role?`, `min?`, `max?` |
| `learning-gate` | `row` | строка обучения `from: verdict` принимается, только если её `via` — сессия вердикта (`by` вердикта; контракт `via` — [22](22-run.md) §6, ADR-47) и сессия вердикта — (а) `purpose: verdict` и `bench` строки — засчитанный прогон кортежа вызова (T200), то есть `bench` = `countedRun(view, tuple)` для кортежа `verdict.execution` (ниже, ADR-42); или (б) `purpose: simulate` и в индексе есть метка копии `std/bench-copy` (T180, [23](23-bench.md) §3). Прочие `purpose` — отказ (перечень разрешённых, RL-18, ADR-29). При `revalidate` вызов в истёкшем сегменте — находка «не проверяемо», не нарушение (RL-12); на какой прогон опиралась строка, видно по `bench`. Какие поля `std` читает — перечень [04](../04-architecture.md) §1, часть версии ядра (ADR-35) | `from?` — путь к вердикту |

**Засчитанный прогон** (T200) — одна чистая функция замороженного ядра `countedRun(view, tuple) → ref std/bench-run | null` (ADR-42; прогоны, планы и метку копии читает `view.events`), единственное определение: последний по `seq` прогон `std/bench-run`, чей `tuple` совпадает с `tuple` (`sameTuple`, ниже), по плану `candidate` с `base` на регрессионный план, действующий на `seq` этого плана — последний по `seq` среди регрессионных планов, записанных владельцем пространства на `seq` их записи ([23](23-bench.md) §1), — если он `pass`; более поздний `fail` того же кортежа закрывает. **Совпадение кортежей** `sameTuple(a, b)` — равенство `setup@n`, `code`, `prompts`, `policy` (T131; `kernel` записан, но не сравнивается, [22](22-run.md) §1): одно правило для гейта и стенда — модуль `run/tuple.matches` его вызывает, а не повторяет. Её читают `learning-gate`, `learn` ([22](22-run.md) §6), отметка пакета выдачи «проверен стендом» ([22](22-run.md) §4) и стенд ([23](23-bench.md)) — копий запроса нет: `bench ≠ null` в пакете ⇔ гейт принимает строку обучения этого вердикта.

**Вид проверки** (`CheckView`, T190, ADR-39) — контракт у rules (ADR-24): синхронные чтения, ровно перечень [04](../04-architecture.md) §1 (ADR-35), не шире.

```ts
interface CheckView {                            // rules/types; импортирует только kernel/types — Revision, Authority
  seq: number                                    // у overlay.at(i) — условный seq строки i ([12] §3)
  revision(ref: Ref): Revision | null            // revisions + latest; следующая ссылка — через aliases в силе
  latest(id: string): { version: number; live: boolean } | null
  grain(type: string, scope: string, key: string): string | null   // раздел grain ([11] §1)
  canonical(id: string): string | null           // aliases в силе
  facts(type: string, key?: Json): Revision[]    // текущие / накопленные
  events(type: string): Array<{ row: Revision; seq: number }>      // byType + revisions: события типа по seq —
                                                 // прогоны, планы, метка копии (countedRun, learning-gate)
  referrers(ref: Ref): Ref[]                     // смена типа сущности перепроверяет ссылающихся (§4)
  execution(id: string): { tuple: Json; status: string; seq: number } | null   // executions, живые сегменты
  typeChain(type: Ref): Revision[]               // цепочка extends закреплённых версий
  authority: Authority                           // [10] §7 — проекция, вида проверок не читает (без цикла)
}

type Check = {                                   // запись реестра и её код; rules/types
  name: string; scope: "row" | "commit"; phase: "write" | "publish-type" | "publish-rule"
  appliesTo: Array<"author" | "copy" | "genesis">
  run(input: { rows: Revision[]; i?: number; view: CheckView; params?: Json;
               fromRows(rows: Revision[]): CheckView }): Array<{ row: number } & Details>
}                                                // i и view = overlay.at(i) — у scope: row; view = overlay.total() — у commit
type Details   = { message: string; path?: string; expected?: Json; got?: Json; with?: Ref; diff?: Json }
type Violation = { row: string; rule: string } & Details   // оболочку собирает коммит (ниже)
```

`Revision` — ревизия ядра ([10](10-kernel.md) §1, «Операции»), не хранимая строка `Row` ledger: у строк `overlay` и `fromRows()` нет `commit`, их `seq` — условный, только для порядка ([12](12-ledger.md) §3), а rules не импортирует `ledger/types` ([04](../04-architecture.md) §2).

Адаптеры вида — у ledger ([12](12-ledger.md) §3): индекс на `seq`, `overlay(ix, rows)` и **`fromRows(rows)`** = `overlay(пустой индекс, rows).total()` — вид из строк без хранилища. Проверка `examples` получает построитель `fromRows` аргументом `run` (rules не импортирует ledger, [04](../04-architecture.md) §2); тесты каждой проверки и примитива берут его из точки входа `kernel-v1`.

Набор примитивов и проверок ядра — часть замороженного ядра и растёт только с его версией (ADR-32); код проверок ядра — `src/rules/kernel-checks/` ([04](../04-architecture.md) §1, §6). **Критерий нового примитива:** тот же выход нужен в нескольких пространствах и не выражается параметром существующего. Правило, которое не выражается примитивами, — способность уровня `soft` (п. 3).

**Нарушение** — одна оболочка на все проверки: `{row, rule, message}` + детали по виду проверки (`Violation`, выше). Проверка отдаёт номер строки и детали, оболочку собирает коммит: `row` — адрес строки во входе коммита (`drafts[i]`, `rows[i]`, `delta[i]`, строки намерений — `intents[j]`), при `revalidate` — `id@n`, у `fromRows()` — `rows[i]`; `rule` — `id@n` объекта-правила или имя проверки ядра (её версия — `kernel` маркера коммита, T113). Детали: `schema`, `ref-*`, `count` — `path`, `expected`, `got`; `grain-unique` — `with`, `diff` ([11](11-identity-grain.md)); прочие — `path`.

### 3. Способности и контракты

```json
{ "id": "std/stage.bm25", "type": "std/capability@1",
  "body": { "title": "BM25 по карточкам пула",
            "input": {"$ref": "std/ctx@1"}, "output": {"$ref": "std/ctx@1"},
            "reads": ["needs[].norm", "needs[].pool"], "writes": ["needs[].scores.bm25"], "uses": [], "emits": [],
            "impl": { "adapter": "builtin", "name": "lens/stages/bm25.ts",
                      "pins": { "package": "lattice@0.4.0", "hash": "sha256:…" } },
            "determinism": "deterministic" } }
```

**Способность** (`std/capability`, T68) — объект с контрактом и ссылкой на реализацию. Тело: `title`; `input` и `output` — закреплённые ссылки на типы (у стадий — `std/ctx@1`, [22](22-run.md)); `reads` / `writes` — пути `ctx`, которые стадия читает и дополняет (T132); `uses` — порты `Deps`, которые она вызывает (`judge`, `composer`, `source`; порта `exec` в v1 нет — [22](22-run.md) RN-42): рантайм отказывает на старте, если порта нет в `setup.ports` ([22](22-run.md) RN-27); `emits` — типы строк, которые стадия готовит для коммита вызова (`needs[].rows`, T156): строку другого типа рантайм отклоняет как ошибку стадии, типов блоков (с `card`, T66) в `emits` нет — проверка `contract` ([22](22-run.md) RN-36); `impl` — адаптер, имя и закрепление кода; `determinism` (T-3): `deterministic` — функция `ctx`, `params` и `view`; `ports` — ходит во внешнее через порты `Deps`, для replay вызовы записаны в `calls` ([22](22-run.md) §7); у способности `check:` — только `deterministic` (RL-07). Сигнатура стадии (`Stage`, T96) и зависимости `Deps` (T133) — [22](22-run.md) §2.

- **Закрепление кода (`impl.pins`, T-2):** версия пакета + хэш модуля. Решает хэш модуля: рантайм отказывает исполнять способность, если хэш не совпадает; версия пакета — справочно, релиз, не тронувший модуль, способность не останавливает ([22](22-run.md) RN-34). Хэш модуля берётся из манифеста кода (T193), который генерирует сборка; `impl.name` — ключ модуля в манифесте, путь от `src/` ([30](30-adapters.md) §2); зерно `code` кортежа — модуль (ADR-42). Вызов пишет хэш в `code` (кортеж исполнения T131 — [22](22-run.md)).
- **Калиброванные параметры (`calibrated`, ADR-45):** пути `params`, чьи значения — калиброванный порог `CalibratedThreshold {value, calibrated_for: {adapter, model, prompt_hash, bench} | null, call: score | verify | choose, onMismatch: refuse | mark}` (T198, привязка — T136). Способность объявляет их в контракте; рантайм сверяет `calibrated_for` с портом из `setup` и `describe().prompts[call]` обобщённо — не по имени стадии — и поступает по `onMismatch` ([22](22-run.md) RN-10). Сверка — одна чистая функция `checkCalibration(threshold, ident) → ok | uncalibrated | mismatch`; её же зовут читатели калиброванных порогов вне `params` конвейера — `candidates.min_p` политики ([14](14-trust.md) §4) в `recall` и `aliasCandidates`. При `mark` читатель идёт как без калибровки и пишет заметку `<параметр>: calibration-mismatch`. Порог без калибровки — `calibrated_for: null`: поведение «не откалиброван» задаёт стадия ([20](20-lens.md) LN-07, [21](21-compose.md) CP-05).
- **Совместимость (T46), номинальная:** выход A совместим со входом B, если это тот же тип или его наследник по `extends`, совместимый по контракту (ADR-12). `compatible` сравнивает `id` типов без версии. Структурная (по схеме) — не в v1 ([03](../03-python-lessons.md), RL-05).
- **`contract` (ADR-18)** — проверка цепочки стадий конвейера при его публикации: каждое чтение (`reads`) записано раньше — входом конвейера или `writes` предыдущей стадии; `emits` ни одной стадии не содержит типа блока; вход конвейера — вход первой стадии, выход — выход последней. Конвейер v1 — линейная цепочка; решение-граф проверяет `acyclic`, не `contract`.
- **Правило-способность (ADR-11):** `check: "capability"`, `params: {capability: {"$ref": "…@n"}}` — только `soft`, способность закреплена `@n` и объявлена детерминированной; результат — находка-отчёт. Всё, что должно держаться в коммите, — проверка ядра или примитив.

### 4. Где проверяются правила

| Момент | Уровень | Что |
|---|---|---|
| коммит | `hard` | проверки реестра для вида входа и фазы (§2); правила, закреплённые в `type@n` записываемых ревизий и фактов (с цепочкой `extends`); одно нарушение — отклонён весь коммит |
| смена типа сущности ([10](10-kernel.md) KR-10) | `hard` | в том же коммите перепроверяются ссылающиеся (`referrers`, [12](12-ledger.md)): следующие ссылки с `ref-type`, текущие факты с типизированными ролями; кроме смены «вниз по `extends`» (к наследнику) |
| публикация версии типа или правила | `hard` | `regrain-plan`, совместимость схемы и наследования, `examples` (§2) |
| публикация конвейера | `hard` | `contract` (п. 3) |
| стадия `check` конвейера | `hard` правила решения | размер, контракты, происхождение членов (CP-06) |
| `lint` (по запросу, в CI проекта) | `soft` | тип без схемы, на объекты которого ссылаются другие пространства; необязательное измерение `grain` («пустое измерение»); раскачка членства, большие группы, устаревшие snapshot'ы, следующие ссылки на выведенные объекты; правила-способности |

## Операции

| Операция | Вход → выход |
|---|---|
| `checks(batchKind, phase)` | → записи реестра проверок, которые коммит применяет к этому входу и фазе (§2); отдельной операции проверки строк нет — её место шаг 5 коммита ([12](12-ledger.md) §2, ADR-38) |
| `countedRun(view, tuple)` | → засчитанный прогон кортежа или `null` (§2, T200) |
| `sameTuple(a, b)` | → совпадение кортежей исполнения по `setup@n`, `code`, `prompts`, `policy` (§2) |
| `checkCalibration(threshold, ident)` | → `ok` · `uncalibrated` · `mismatch` (§3) |
| `lint(scope?)` | → находки `soft` — отчёт на `seq` (ADR-10) |
| `compatible(outType, inType)` | → bool; по `id` без версии |
| `revalidate(commit, {rules: "pinned" \| "current"})` | → нарушения + отличия от исходного вердикта + `kernel` записанный и текущий; по умолчанию — закреплённые правила, текущее ядро |

## Инварианты

1. Каждая строка коммита проходит проверки реестра своего источника и фазы (§2) и все `hard`-правила своего `type@n` с цепочкой `extends`; иначе отклонён весь коммит.
2. Правила наследника ⊇ правил родителя `@n`, схема не слабее; `extends` закреплён `id@n`.
3. Версия правила или типа не публикуется, если её `examples` не выполняются или закреплённые правила несовместны.
4. Правило вне примитивов не бывает `hard`.
5. Способность не исполняется, если хэш её модуля расходится с `impl.pins`.
6. В опубликованном конвейере каждое чтение стадии записано раньше.
7. Исход проверки коммита не зависит от порядка строк с разными `id` (LG-03).
8. Коммит применяет ровно проверки реестра для своего вида входа и фазы; исключение из проверки — только значение `appliesTo` в реестре (ADR-38).
9. Проверки читают только `CheckView` — перечень [04](../04-architecture.md) §1; засчитанный прогон вычисляет одна функция `countedRun` (ADR-39, ADR-42).

| RL-01 | Правило — объект `core/rule` с уровнем `hard` / `soft` | ограничения — данные (P2) |
