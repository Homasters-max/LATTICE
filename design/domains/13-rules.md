# 13. rules — правила, контракты, проверка

**Назначение.** Единственное, что ограничивает поведение (P2). Правило — объект (данные), который параметризует
примитив проверки ядра.

**Зависит от:** [10-kernel](10-kernel.md). **Используют:** ledger (коммит), catalog (публикация), compose (проверка
решения), lint.

## Модель

### 1. Правило — объект

```json
{ "id": "std/rule.solution-size", "type": "core/rule@1", "version": 1, "by": "…",
  "body": {
    "level": "hard",
    "check": "max-members",
    "params": { "fact": "core/member", "role": "group", "max": 7 },
    "message": "Решение — не больше 7 членов; больше — разбить потребность",
    "doc": "Группа достаточна и минимальна (T82)"
  } }
```

- Тип закрепляет свои правила: `rules: [{"$ref": "std/rule.solution-size@1"}]`; правила наследуются по `extends`.
- Изменить правило = новая версия правила + новая версия типа, которая на неё ссылается. Ревизия проверена ровно
  теми правилами, что закреплены в её `type@n` — проверку можно повторить.
- `hard` — при коммите, нарушение отклоняет коммит. `soft` — в `lint`, результат — находка (T44).

### 2. Примитивы проверки (код ядра)

| Примитив | Что проверяет | Параметры |
|---|---|---|
| `schema` | форма тела (подмножество JSON Schema: type, required, properties, enum, pattern, items) | `schema` |
| `ref-exists` | каждая `$ref` тела разрешается | `pinned?` — требовать `@n` |
| `ref-type` | ссылка по пути указывает на объект нужного типа (или наследника) | `path`, `type` |
| `ref-policy` | ссылки на объекты типа с `refs: pin` закреплены (`id@n`) | — (из типа цели) |
| `roles` | роли факта объявлены типом, их объекты нужных типов | — (из типа) |
| `grain-unique` | уникальность ключа зерна | — (из типа) |
| `regrain-plan` | публикация типа с суженным зерном несёт полный план | — |
| `immutable` | у неизменяемых нет версии > 1 | — |
| `owner` | ревизию пишет владелец пространства или допущенный | — ([15](15-catalog.md)) |
| `max-members` | группа не больше N членов | `fact`, `role`, `max` |
| `acyclic` | граф по факту или по ссылкам без циклов | `fact` / `path` |
| `contract` | рёбра графа совместимы по контрактам | — (п. 3) |
| `unique-within` | значение поля уникально в группе | `path`, `scope` |
| `count` | число фактов данного вида в пределах | `fact`, `min`, `max` |

Набор примитивов — часть ядра и растёт только с его версией. Правило, которое не выражается примитивами, — см.
вопрос 2.

### 3. Контракты способностей

```json
{ "id": "std/stage.bm25", "type": "std/capability@1",
  "body": { "title": "BM25 по карточкам пула", "input": {"$ref": "std/ctx@1"}, "output": {"$ref": "std/ctx@1"},
            "impl": { "adapter": "builtin", "name": "lens.bm25" }, "determinism": "deterministic" } }
```

- Контракт = `input` и `output` — закреплённые ссылки на типы.
- **Совместимость (T46), номинальная:** выход A совместим со входом B, если это тот же тип или его наследник по
  `extends`. Структурная (по схеме) — вопрос grilling (PY-Q1).
- Проверка графа (`contract`): для каждой связи `from → to` выход `from` совместим со входом `to`; вход графа — вход
  первой стадии, выход — выход последней.

### 4. Где проверяются правила

| Момент | Уровень | Что |
|---|---|---|
| коммит | `hard` | всё, что закреплено в типах записываемых ревизий |
| публикация версии типа | `hard` | `regrain-plan`, совместимость наследования |
| стадия `check` конвейера | `hard` правила решения | размер, контракты, происхождение членов (CP-06) |
| `lint` (по запросу, в CI проекта) | `soft` | раскачка членства, большие группы, устаревшие snapshot'ы, следующие ссылки на выведенные объекты |

## Операции

| Операция | Вход → выход |
|---|---|
| `validate(rows, state)` | → нарушения `hard` |
| `lint(scope?)` | → находки `soft` |
| `compatible(outType, inType)` | → bool |

## Решения

| ID | Решение | Почему |
|---|---|---|
| RL-01 | Правило — объект `core/rule` с уровнем `hard` / `soft` | ограничения — данные (P2) |
| RL-02 | Схема тела — добровольное правило (`schema`), не часть ядра | тело открыто, как `__dict__` |
| RL-03 | Правила параметризуют фиксированный набор примитивов ядра | предсказуемо, проверяемо, без произвольного кода |
| RL-04 | Тип закрепляет правила ссылкой `@n` | проверку ревизии можно повторить |
| RL-05 | Контракт — ссылки на типы; совместимость номинальная через `extends` | просто; структурная — позже |
| RL-06 | Находки `soft` не пишутся в журнал — это отчёт | журнал — факты, а не диагностика |

## Вопросы для grilling

1. **Находки lint** — отчёт или события в журнале (чтобы видеть, когда появились и исчезли)? Рекомендация: отчёт; в
   журнал — только решения по находкам (факты).
2. **Правило вне примитивов** (например, «у нормы есть тест») — пользовательская проверка как способность
   (`check: capability`, реализация вне ядра)? Рекомендация: да, но только `soft` — `hard` остаётся в ядре.
3. **Наследование правил:** наследник может ослабить правило родителя? Рекомендация: нет — только добавить.
