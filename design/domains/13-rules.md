# 13. rules — правила, контракты, проверка

**Назначение.** Единственное, что ограничивает поведение (P2). Правило — объект (данные), который параметризует
примитив проверки ядра; сверх правил ядро безусловно держит небольшой набор проверок ядра (T134).

**Зависит от:** [10-kernel](10-kernel.md), [11-identity-grain](11-identity-grain.md) (`grain-unique`,
`regrain-plan`). **Используют:** ledger (коммит), catalog (публикация), compose (проверка решения), run (контракты
стадий, гейт обучения), lint.

## Модель

### 1. Правило — объект

```json
{ "id": "std/rule.solution-size", "type": "core/rule@1", "version": 1, "by": "…",
  "body": {
    "level": "hard",
    "check": "count",
    "params": { "fact": "std/member", "role": "group", "max": 7 },
    "message": "Решение — не больше 7 членов; больше — разбить потребность",
    "doc": "Размер группы решения: не больше 7 членов",
    "examples": { "pass": [{ "facts": ["… 7 × std/member одной group"] }],
                  "fail": [{ "facts": ["… 8 × std/member одной group"] }] }
  } }
```

Поля тела `core/rule`: `level` (`hard` / `soft`), `check` (примитив §2 или `capability`, п. 3), `params`, `message`,
`doc`, `examples`, `when` — необязательны все, кроме `level` и `check`.

- Тип закрепляет свои правила: `rules: [{"$ref": "std/rule.solution-size@1"}]` (пример — у типа факта `std/member`,
  [21](21-compose.md)).
- **Наследование (ADR-12):** правила родителя берутся из закреплённой версии — `extends` у типа — ссылка `id@n`
  (у типов `refs: pin`, правило `ref-policy`, [15](15-catalog.md)); наследник только добавляет правила и сужает: его
  правила ⊇ правил родителя `@n`, схема не слабее.
- Изменить правило = новая версия правила + новая версия типа, которая на неё ссылается. Ревизия проверена ровно
  теми правилами, что закреплены в её `type@n`, и кодом примитивов версии ядра из заголовка коммита (`kernel`,
  [10](10-kernel.md)) — проверку можно повторить (`revalidate`).
- `hard` — при коммите, нарушение отклоняет коммит. `soft` — в `lint`, результат — находка (T44).
- **`examples {pass, fail}`** — при публикации версии правила ядро прогоняет их: каждый `pass` правило пропускает,
  каждый `fail` — отклоняет. При публикации версии типа — все закреплённые правила совместно выполнимы на
  `pass`-примерах этих правил. Правило без `examples` допустимо.
- **`when: {path, eq}`** — условие: правило действует, только если значение по пути тела проверяемой строки равно
  `eq`. У факта путь может начинаться с роли (`group.form`) — значение текущей ревизии объекта в этой роли. Так тип
  выражает согласованность поля с фактами (`form` решения, ADR-17), не заводя примитив под один тип.
- **Схема тела** (`schema` у `core/type`, T125, ADR-9) — сахар: компилируется в правило примитива `schema` с уровнем
  из поля; у `core`, `std` и импортируемых типов обязательна, закрыта и `hard` ([10](10-kernel.md)). Лестница для
  проектного типа: нет схемы → `soft` → `hard` новой версией типа. У общего типа `soft` → `hard` — только с планом
  для ревизий, которые новой схеме не соответствуют. Измерения `grain` — `required` в схеме
  ([11](11-identity-grain.md)).

### 2. Проверки ядра и примитивы (код ядра)

**Проверки ядра (T134)** — безусловные: не параметризуются правилом и не отключаются типом (T-16).

| Проверка | Когда | Что проверяет |
|---|---|---|
| `owner` | каждая строка коммита | ревизию или факт пишет владелец пространства или допущенный; `writers` типа — по цепочке `by` → сессия → участник (ADR-6, [15](15-catalog.md)) |
| `immutable` | каждая строка коммита | у неизменяемых нет версии > 1 |
| `grain-unique` | каждая строка коммита | ключ зерна уникален среди живых сущностей типа в области зерна (пространство автора или `store`, ADR-27) ([11](11-identity-grain.md)) |
| `ref-policy` | каждая строка коммита | ссылки на объекты типа с `refs: pin` закреплены (`id@n`) |
| `roles` | каждая строка коммита | роли факта объявлены типом, их объекты нужных типов (наследник — только при ролях контракта, ADR-12) |
| `regrain-plan` | публикация версии типа | любое изменение состава или порядка `grain` несёт полный план ([11](11-identity-grain.md)) |
| совместимость схемы | публикация версии типа | новая схема общего или `content`-типа принимает всё прежнее, иначе план или новый `id` ([10](10-kernel.md)) |
| совместимость наследования | публикация версии типа | правила ⊇ родителя `@n`, схема не слабее, `writers` ⊆, `inForce` не слабее (ADR-12) |
| `examples` | публикация версии правила или типа | п. 1 |

**Примитивы** — параметризуются правилом `core/rule`.

| Примитив | Что проверяет | Параметры |
|---|---|---|
| `schema` | форма тела (подмножество JSON Schema: type, required, properties, enum, pattern, items, additionalProperties) | `schema` |
| `ref-exists` | каждая `$ref` тела разрешается | `pinned?` — требовать `@n` |
| `ref-type` | ссылка по пути указывает на объект нужного типа (или наследника) | `path`, `type` |
| `acyclic` | граф по факту или по ссылкам без циклов (решение-граф, ADR-18); с `role` — в пределах объекта этой роли у проверяемой строки | `fact` / `path`, `role?` |
| `contract` | цепочка стадий согласована по контрактам (п. 3) | — |
| `unique-within` | значение поля уникально в группе | `path`, `scope` |
| `count` | число действующих фактов вида `fact`, где в роли `role` тот же объект, что у проверяемой строки (без `role` — в любой роли), в пределах | `fact`, `role?`, `min?`, `max?` |
| `learning-gate` | факт обучения `from: verdict` — только если вердикт не из сессии стенда и у его кортежа (T131) есть `bench-run pass` по плану с `base` на регрессионный план, или вердикт выведен `simulate-consumer` (T139, ADR-29) | `from?` — путь к вердикту |

Набор примитивов и проверок ядра — часть ядра и растёт только с его версией. **Критерий нового примитива:** тот же
выход нужен в нескольких пространствах и не выражается параметром существующего. Правило, которое не выражается
примитивами, — способность уровня `soft` (п. 3).

**Нарушение** — одна оболочка на все проверки: `{row, rule, message}` + детали по виду проверки. `rule` — `id@n`
объекта-правила или имя проверки ядра (её версия — `kernel` в заголовке коммита). Детали: `schema`, `ref-*`,
`count` — `path`, `expected`, `got`; `grain-unique` — `with`, `diff` ([11](11-identity-grain.md)); прочие — `path`.

### 3. Способности и контракты

```json
{ "id": "std/stage.bm25", "type": "std/capability@1",
  "body": { "title": "BM25 по карточкам пула",
            "input": {"$ref": "std/ctx@1"}, "output": {"$ref": "std/ctx@1"},
            "reads": ["needs[].norm", "needs[].pool"], "writes": ["needs[].scores.bm25"],
            "impl": { "adapter": "builtin", "name": "lens.bm25",
                      "pins": { "package": "lattice-lens@0.4.0", "hash": "sha256:…" } },
            "determinism": "deterministic" } }
```

**Способность** (`std/capability`, T68) — объект с контрактом и ссылкой на реализацию. Тело: `title`; `input` и
`output` — закреплённые ссылки на типы (у стадий — `std/ctx@1`, [22](22-run.md)); `reads` / `writes` — пути `ctx`,
которые стадия читает и дополняет (T132); `impl` — адаптер, имя и закрепление кода; `determinism` (T-3). Сигнатура
стадии `(ctx, params, deps) → Promise<ctx>` и зависимости `Deps` (T133) — [22](22-run.md).

- **Закрепление кода (`impl.pins`, T-2):** версия пакета + хэш модуля. Рантайм отказывает исполнять способность,
  если код не совпадает с `pins`; прогон пишет версию пакета в вызов (кортеж исполнения T131 — [22](22-run.md)).
- **Совместимость (T46), номинальная:** выход A совместим со входом B, если это тот же тип или его наследник по
  `extends`, совместимый по контракту (ADR-12). `compatible` сравнивает `id` типов без версии. Структурная (по
  схеме) — вопрос grilling (PY-Q1).
- **`contract` (ADR-18)** — проверка цепочки стадий конвейера при его публикации: каждое чтение (`reads`) записано
  раньше — входом конвейера или `writes` предыдущей стадии; вход конвейера — вход первой стадии, выход — выход
  последней. Конвейер v1 — линейная цепочка; решение-граф проверяет `acyclic`, не `contract`.
- **Правило-способность (ADR-11):** `check: "capability"`, `params: {capability: {"$ref": "…@n"}}` — только
  `soft`, способность закреплена `@n` и объявлена детерминированной; результат — находка-отчёт. Всё, что должно
  держаться в коммите, — проверка ядра или примитив.

### 4. Где проверяются правила

| Момент | Уровень | Что |
|---|---|---|
| коммит | `hard` | проверки ядра на каждой строке; правила, закреплённые в `type@n` записываемых ревизий и фактов (с цепочкой `extends`); одно нарушение — отклонён весь коммит |
| смена типа сущности ([10](10-kernel.md) KR-10) | `hard` | в том же коммите перепроверяются потребители (`consumers`, [12](12-ledger.md)): следующие ссылки с `ref-type`, текущие факты с типизированными ролями; кроме смены «вниз по `extends`» (к наследнику) |
| публикация версии типа или правила | `hard` | `regrain-plan`, совместимость схемы и наследования, `examples` (§2) |
| публикация конвейера | `hard` | `contract` (п. 3) |
| стадия `check` конвейера | `hard` правила решения | размер, контракты, происхождение членов (CP-06) |
| `lint` (по запросу, в CI проекта) | `soft` | тип без схемы с внешними потребителями; необязательное измерение `grain` («пустое измерение»); раскачка членства, большие группы, устаревшие snapshot'ы, следующие ссылки на выведенные объекты; правила-способности |

## Операции

| Операция | Вход → выход |
|---|---|
| `validate(rows, state)` | → нарушения `hard` (оболочка §2) |
| `lint(scope?)` | → находки `soft` — отчёт на `seq` (ADR-10) |
| `compatible(outType, inType)` | → bool; по `id` без версии |
| `revalidate(commit, {rules: "pinned" \| "current"})` | → нарушения + отличия от исходного вердикта + `kernel` записанный и текущий; по умолчанию — закреплённые правила, текущее ядро |

## Инварианты

1. Каждая строка коммита проходит проверки ядра и все `hard`-правила своего `type@n` с цепочкой `extends`; иначе
   отклонён весь коммит.
2. Правила наследника ⊇ правил родителя `@n`, схема не слабее; `extends` закреплён `id@n`.
3. Версия правила или типа не публикуется, если её `examples` не выполняются или закреплённые правила несовместны.
4. Правило вне примитивов не бывает `hard`.
5. Способность не исполняется, если код расходится с `impl.pins`.
6. В опубликованном конвейере каждое чтение стадии записано раньше.

## Решения

| ID | Решение | Почему |
|---|---|---|
| RL-01 | Правило — объект `core/rule` с уровнем `hard` / `soft` | ограничения — данные (P2) |
| RL-02 | Схема тела — поле `schema` типа, сахар для правила примитива `schema` с уровнем; у `core`/`std`/импортируемых — обязательна, закрыта, `hard`; проектный тип — лестница «нет → `soft` → `hard`», у общего `soft` → `hard` — с планом | без схемы нет контракта для потребителей; лестница — дёшево начать. v0.4 · ADR-9 · T-13 · Q-30 C-2, C-3 |
| RL-03 | Правила параметризуют фиксированный набор примитивов ядра | предсказуемо, проверяемо, без произвольного кода |
| RL-04 | Тип закрепляет правила ссылкой `@n`, родителя — `extends` `id@n`; наследник только добавляет и сужает | проверку ревизии можно повторить; наследник не ослабляет родителя. v0.4 · ADR-12 · Ф-6 · Q-32 C-2 · v0.3 вопрос 3 |
| RL-05 | Контракт способности — ссылки на типы + `reads`/`writes`; совместимость номинальная через `extends` с контрактом, по `id` без версии; `contract` — для цепочки стадий, `acyclic` — для решения-графа | просто; структурная — позже. v0.4 · T-3 · ADR-12 · ADR-18 · Q-32 C-3, Q-33 C-3 |
| RL-06 | Находка, которую можно пересчитать по журналу на `seq`, — отчёт, в журнал не пишется; непересчитываемая — факт (тип — [30](30-adapters.md)) | журнал — факты, а не диагностика. v0.4 · ADR-10 · v0.3 вопрос 1 |
| RL-07 | Правило вне примитивов — только `soft`, способностью `check: capability@n` с `determinism` | `hard` без кода ядра — произвольный код в коммите. v0.4 · ADR-11 · Q-31 C-1 · v0.3 вопрос 2 |
| RL-08 | Гейт обучения — примитив `learning-gate`, закреплённый в `rules` типов фактов обучения `std` ([22](22-run.md)) | барьер на необратимом переходе, держит коммит для любого писателя; ядро не знает смысла фактов обучения. v0.4 · ADR-29 · T-16 · D04 Q4 |
| RL-09 | Проверки ядра (T134) безусловны и отделены от параметризуемых примитивов | инвариант держат тип и коммит, а не стадия. v0.4 · T-16 · Q-29 C-3 |
| RL-10 | `examples {pass, fail}` правила прогоняются при публикации; правила типа совместно выполнимы | правило-данные без проверки на примерах публикуется вслепую. v0.4 · T-13 · Q-29 C-2 |
| RL-11 | Одна оболочка нарушения `{row, rule, message}` + детали по виду проверки | запись ведут агенты: отказ называет строку, правило и место. v0.4 · Q-30 C-4 · GR-04 · D04 Q2 |
| RL-12 | `revalidate(commit)` — повтор проверки на закреплённых или текущих правилах и текущем ядре; код старых примитивов не хранится | видно, меняет ли новое ядро или правило вердикт; версия ядра — в заголовке. v0.4 · Q-32 C-2 · T-11 · D04 Q3 |
| RL-13 | Условие правила `when: {path, eq}`; у факта путь может начинаться с роли | согласованность поля с фактами без примитива под один тип. v0.4 · ADR-17 · D04 Q5 |
| RL-14 | Новый примитив — когда выход нужен в нескольких пространствах и не выражается параметром; `max-members` сведён к `count` с `role` | набор примитивов не растёт бесконтрольно. v0.4 · Q-31 C-2 · D04 Q1 |
| RL-15 | Код способности закреплён `impl.pins` (пакет + хэш модуля); рантайм отказывает при расхождении | закрепление доходит до исполняемого кода. v0.4 · T-2 · Q-14 C-4 |
