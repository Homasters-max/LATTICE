# 21. compose — потребности, решения, выбор

**Назначение.** Превратить задачу в атомарные потребности, найти для каждой сохранённое решение или собрать новое
из кандидатов LENS — только из блоков LATTICE (P6), с причиной-цитатой для каждого члена.

**Зависит от:** [10-kernel](10-kernel.md) (факты, значения), [11-identity-grain](11-identity-grain.md)
(`std/alias-candidate`, `std/distinct`), [12-ledger](12-ledger.md) (статус snapshot'а, коммит), [13-rules](13-rules.md)
(`count`, `acyclic`, `when`, способности), [14-trust](14-trust.md) (`trust()`, `policy.candidates`),
[15-catalog](15-catalog.md) (допуск, `core/deprecate`), [20-lens](20-lens.md) (кандидаты, карточки, порт `judge`,
`std/term`, `normalize`); контракт стадий и `Ctx` — [22](22-run.md). Порты `composer` и `source` определяет этот домен
(ADR-24, §8); реализации — [30](30-adapters.md). **Используют:** run (стадии, `materialize`, проверки выбора при
обучении), bench (серая зона, матрица E4), adapters.

## Модель

### 1. Объекты

| Объект | Тип | Вид | Тело / роли | Зерно, ключ, `writers` |
|---|---|---|---|---|
| потребность | `std/need` | сущность | `{scope: ref, label, terms: [ref]}` | — (ключ потребности — индекс) |
| подсказка | `std/cue` | факт | `{of: {target: need \| блок@n \| term}, value: "текст", from?, policy?, match?}` | ключ `[target, norm(value)]`; `any` |
| решение | `std/solution` | сущность | `{need: ref, form: "set" \| "graph"}` | `[need]` — одно решение на потребность |
| член решения | `std/member` (`extends core/member@1`) | факт | `{of: {group: solution, member: блок}, value: true \| false, reason, found_by, from?, policy?}` | ключ `[group, member]`; `grant` — владелец или допущенный |
| связь | `std/link` | факт | `{of: {group: solution, from: блок, to: блок}, value: true \| false}` | ключ `[group, from, to]`; как у `std/member` |
| snapshot | `core/snapshot` | значение | `{of: solution, members: [ref@n], links: [[from@n, to@n]]}` | содержимое |
| пробел | `std/gap` | событие | `{need, scope, kind: "absent" \| "coverage", places?: [Place], note?}` | — |

Ссылкой: различие `std/distinct` и кандидат в алиас `std/alias-candidate` — [11](11-identity-grain.md) §6.

- **Потребность** — единица повторного использования (P7). Её формулировки — подсказки: одна потребность — много
  перефразировок.
- **Ключ потребности** (T80) = `hash(область, отсортированные id терминов)` — индекс для поиска похожих, не identity
  и не фильтр (§3); identity — ULID.
- **Подсказка** (T72) — один механизм для трёх целей: перефраз потребности, алиас блока (к ревизии `блок@n`,
  LN-10), синоним термина (`std/term`, [20](20-lens.md)). Ключ `[target, norm(value)]`: тот же текст из разных
  сессий — один факт, подтверждения — утверждения к нему. В силе при основании ≥ `observed` ([14](14-trust.md) §7);
  путь выученной подсказки к `observed` — обучение ([22](22-run.md)).
- **Решение** отвечает на **потребность, а не на задачу**: иначе разрастается до «всего, что понадобилось». Решение
  **достаточно** (по нему можно ответить) и **минимально** (у каждого члена своя причина, которую не покрывают
  остальные). Код проверяет размер, происхождение и цитаты; достаточность и минимальность — вердикты потребителя
  ([22](22-run.md) §6), не правило.
- **Член решения** — свой тип `std/member`, наследник `core/member` с ролью `group` только `std/solution`. Состав
  доменов (`core/member`) пишет владелец; состав решений — Composer и обучение по допуску
  `core/grant {create: ["std/member"]}` ([15](15-catalog.md)). Допуск задаётся по типу — поэтому типы разные.
  `found_by: "lens" | "self-search" | "verdict"` — как член попал в решение (обучение читает, [22](22-run.md)).
- **Роль `member` — ссылка по политике `refs` типа блока** ([15](15-catalog.md) §4): знание — следующая (`id`),
  способность — закреплённая (`id@n`, правило `ref-policy`). Версию знания закрепляет только snapshot. Поэтому
  правка нормы не заводит новый факт членства: ключ `[group, member]` тот же, доверие членства сохраняется, `count`
  не видит норму дважды; устаревание ловит статус snapshot'а и `recheck` (CP-18). Новая версия способности —
  перезакрепление владельцем решения, как везде (`pin`).
- **Строки обучения** — `std/member` и `std/cue` с `from` (вердикт), `policy@rev` и `bench` (засчитанный прогон,
  [22](22-run.md) RN-24); в `rules` обоих типов — гейт
  `learning-gate` по `from` ([13](13-rules.md) §2, [22](22-run.md) §6, ADR-29).
- **След сопоставления** (`match`, T186, CP-25): подсказка, которую записала стадия по сопоставлению — `recall`
  (формулировка признана той же, §3) или `recheck` («подсказка верна для `@n`?», §4), — несёт `match: {by: "judge" | "composer", p?, port: {adapter, model, prompt_hash?}}` — как
  `std/alias-candidate` (там та же тройка названа `judge`, [11](11-identity-grain.md) §6); в ключ не входит. У формулировки новой потребности и у строк
  обучения (`from`) поля нет. Трасса вызова истекает с сегментом, подсказка — нет: после замены judge видно, какие
  связи провёл прежний оценщик и с каким `p` (P13).
- Членство — факты: состав калибруется вердиктами без новых версий решения (P4). Snapshot фиксирует, что именно
  было выдано; его статус (`fresh` / `stale` / `broken`) вычисляет индекс `snapshots` ([12](12-ledger.md)). `stale` —
  и когда действующие `std/member`/`std/link` решения ≠ `members`/`links` snapshot'а: выученное обучением доходит до
  повтора веткой `stale` — новым snapshot'ом (CP-20).
- **Форма** — явное поле (ADR-17): `set` — знания, набор без связей; `graph` — способности, связи ацикличны. Граф
  из одной вершины законен. Решение-граф — не конвейер (ADR-18): его snapshot не тело составной способности.

### 2. Правила типов — инвариант держит коммит

Правила закреплены в типах (T-16): их проверяет коммит любого писателя — стадии `check`, обучения, `materialize`
вне вызова.

| Тип | Правило | Что держит |
|---|---|---|
| `std/member` | `std/rule.solution-size`: `count {fact: std/member, role: group, max: 7}` | не больше `max` действующих членов в решении; `max` калибрует стенд |
| `std/member` | `learning-gate {from}` | строка обучения (`from` — вердикт) принимается только за гейтом (ADR-29, [22](22-run.md) §6) |
| `std/member` | `schema {required: [from]}`, `when: {path: value, eq: false}` | член удаляется только строкой обучения: `value: false` без вердикта — отказ для любого писателя ([22](22-run.md) RN-25) |
| `std/cue` | `learning-gate {from}` | то же для подсказки из вердикта |
| `std/solution` | `count {fact: std/link, role: group, max: 0}`, `when: {path: form, eq: set}` | у набора нет связей (смена формы на `set`) |
| `std/link` | `count {fact: std/link, role: group, max: 0}`, `when: {path: group.form, eq: set}` | связь в наборе — отказ |
| `std/link` | `acyclic {fact: std/link, role: group}` | граф решения без циклов |
| `std/gap` | `schema` (`places` — `minItems: 1`), `when: {path: kind, eq: coverage}` | дыра покрытия несёт место в источнике |

`select` и граница обучения читают `max` из `solution-size` закреплённой версии `std/member`, а не несут своё число.
Концы связи ⊆ членов решения — проверка выбора (§5), примитива под неё нет.

### 3. Путь одной потребности

```text
frame ─► recall ─┬─ fresh, доверие ок, не пустое ─────────────────► deliver (без LENS)
                 ├─ stale ─► recheck изменённых членов (+ граф) ─► новый snapshot ─► deliver
                 ├─ broken ─► LENS по сохранённой потребности ─► select (замена пропавшего)
                 └─ нет ─► LENS ─┬─ кандидаты ─► select ─┬─ выбрано ─► check ─► deliver
                                 └─ no-match ─┐          └─ none-fit ─┐
                                              └─────────► self-search (внутри LATTICE)
                                                              ├─ найдено ─► выбор (found_by: self-search) ─► check
                                                              ├─ дубль потребности с решением ─► промах B
                                                              └─ нет ─► source.find: место живого блока → found (промах B);
                                                                        прочие места → gap coverage; нет → gap absent
```

**Повтор решения (`recall`).** Кандидаты в «ту же потребность» — потребности области с тем же ключом (кроме
отказанных `std/distinct` и тех, чью подсказку с этой формулировкой отверг вердикт — [22](22-run.md) §6) ∪ top-N (5) потребностей области по BM25 над их подсказками. Ключ — индекс, не фильтр:
перефраз, для которого `lexicon` вывел другие термины, тоже доходит до сравнения (T-8).

1. Точный повтор нормализованного текста подсказки **в силе** (≥ `observed`, [14](14-trust.md) §7) кандидата → та
   же (`by: exact`). Подсказка не в силе — только шаг 2: связь, которую однажды провёл judge, пересматривается
   текущим judge с его порогом и `calibrated_for`, а не закрепляется как точный повтор (CP-21).
2. Иначе один вызов `judge.verify` (`state` один, пара «формулировка A — формулировка кандидата B»: та же ли
   потребность).
   Лучший `p` ≥ `same_hi` → та же (`by: judge`, `p`); `same_lo…same_hi` → подтверждает Composer
   (`kind: confirm-same`, `by: composer`); ниже `same_lo` — новая потребность.
3. Ещё одна потребность выше `candidates.min_p` (§6) → кандидат `std/alias-candidate` для пары (не слияние, ADR-8,
   §6); порог кандидатов один для сущностей и потребностей, `same_hi` — только «та же потребность».
   `candidates.calibrated_for` расходится с judge из `setup` — порог неоткалиброван: кандидат пишется, как без
   калибровки (§6), в трассе — `candidates: uncalibrated`; вызов не отклоняется.
4. **Без `calibrated_for`** (T136) judge «ту же» сам не выносит: всё ≥ `same_lo` подтверждает Composer, в трассе —
   `recall: uncalibrated` (как LN-07).

Параметры стадии: `same_hi` 0,85, `same_lo` 0,5 — до калибровки на перефразах стенда (пары «та же / другая»
с трудными отрицательными примерами проекта, обе ошибки, `dev`; [23](23-bench.md)); `top_n` 5; `calibrated_for`
`{adapter, model, prompt_hash, bench}` — рантайм отказывает при расхождении с judge из `std/setup` ([22](22-run.md),
ADR-28). Повтор решения — названное исключение ADR-13: выдача без поиска обратима, ошибку ловит вердикт
(`same_need: false` → утверждение −1 на подсказку-формулировку, [22](22-run.md) §6). Доверие решения при повторе — [14](14-trust.md) §5, §7:
сводка `overruled`, `contested` или `rejected` — заново через LENS; иначе ≥ `observed` — выдать, `inferred` — выдать с
пометкой. Член, который не проходит правило выдачи (выведен, перекрыт, [14](14-trust.md) TR-15), — как `broken`.
Пустое решение `recall` не выдаёт: повтор — всегда через LENS (CP-20).
Формулировка, признанная той же, — подсказка к потребности (`inferred`) со следом `match` (CP-25); новая потребность —
сущность и подсказка.

### 4. Стадии compose

Каждая стадия — способность `std/stage.<имя>` ([13](13-rules.md) §3): `(ctx, params, deps) → Promise<ctx>`,
`reads`/`writes` — пути `Ctx` ([22](22-run.md) §2), код закреплён `impl.pins`. Пути — внутри `needs[]`, кроме
`request.*`. `rows` — строки для коммита вызова (ADR-19; имя поля — [22](22-run.md)).

| Стадия | Кто | Что делает | `reads` | `writes` |
|---|---|---|---|---|
| `frame` | Composer (`frame`) | задача → 1…`max_needs` (5) атомарных потребностей: одна потребность — одна область; междоменная задача → несколько | `request.task`, `request.scope` | `text`, `scope` |
| `frame.single` | код | задача → одна потребность: `text` — `request.task`, `scope` — `request.scope`; без Composer — стадия базовых линий стенда ([23](23-bench.md) BN-15, CP-22) | `request.task`, `request.scope` | `text`, `scope` |
| `recall` | код + judge (+ Composer `confirm-same`) | §3 | `norm`, `scope`, `terms` | `key`, `need`, `recall` (`solution`, `snapshot`, `status`, `by`, `p`), `rows`, `done` |
| `recheck` | Composer (`recheck`) + код | `stale`: только изменённые члены — «всё ещё отвечает?»; для `graph` — затем `acyclic` и совместимость концов связей (выход `from` → вход `to`, [13](13-rules.md) §3) на новом snapshot'е; подсказки в силе прежней ревизии этих членов — «верна для `@n`?», «да» → `std/cue` на `блок@n` ([22](22-run.md) §6) | `recall` | `recall`, `selection`, `done`, `rows` |
| `select` | Composer (`select`) | потребность + кандидаты (карточки, `trust`, `marks`) → 1…`max` членов с причиной-цитатой, или `none-fit`; при `threshold: uncalibrated` отказ — здесь | `norm`, `candidates`, `outcome`, `recall` | `selection` |
| `self-search` | код + Composer (`self-search`) | при `none-fit` или `no-match`: расширить область до всех доменов пространства и `source.grep` — найденное код пишет в `found`, Composer выбирает только из него; перед `absent` — `judge.verify` против потребностей пространства с непустым решением (дубль → промах B, члены — в `found`); не нашлось — `source.find`: места сверяются с `source.locate` живых блоков пространства — блок, чьё место пересекается с найденным, идёт в `found` (промах B, CP-26), кроме уже отвергнутых выбором `candidates` — их место покрыто; прочие места → `coverage`, нет мест → `absent`; Composer отверг и найденное — `absent` | `norm`, `scope`, `outcome`, `selection` | `found`, `selection`, `rows` |
| `check` | код | проверка выбора (§5) | `selection`, `candidates`, `found` | `findings`, `done` |
| `materialize` | код | выбор без нарушений `check` → строки решения, `std/member` (роль `member` — по `refs` типа блока, CP-18), `std/link`, snapshot с `@n` (операция `materialize`) | `selection`, `findings`, `recall` | `rows`, `solution` (`{ref, snapshot}` — для `deliver`, [22](22-run.md) §4) |

Граф-форма исполняется (`exec`) только после `check`; первый запуск — без `exec` ([22](22-run.md), ADR-19).
Коммит вызова собирает рантайм: стадия `materialize` кладёт строки в `rows`, сама не пишет (§ Операции).

### 5. Закрытый мир (P6) и проверка выбора

Composer получает кандидатов и может сослаться **только на них** или на найденное self-search. `found` пишет код —
по ответу `source.grep`, по месту `source.find`, пересекающемуся с местом живого блока (CP-26), и по членам дубля
потребности, — не Composer: в режиме агента (`composer-caller`) агент набор не объявляет. Стадия `check`:

1. каждый `members[].ref` ∈ `candidates` ∪ `found`, закреплён `@n` и проходит правило выдачи (жив, не в
   `policy.lens.exclude`, [14](14-trust.md) TR-15);
2. оба конца каждой `links[]` ∈ `members`;
3. каждый `task_only[]` ∈ `candidates` ∪ `found`;
4. каждая `reason` — хотя бы одна цитата «…», и каждая цитата — нормализованная (правила `normalize`,
   [20](20-lens.md)) подстрока текста карточки `ref@n`: `title` и `summary`, без подсказок — их писали потребители;
   причина, чьи цитаты — только `title` целиком, — находка `soft` «цитата — только заголовок» (выбор не отклоняет,
   CP-24);
5. число членов ≤ `max` правила `solution-size`; для `graph` — `acyclic` и совместимость концов.

Нарушение отклоняет выбор целиком: строк решения нет, нарушения — находки (T44: коммит вызова они не отклоняют) в
`findings` (оболочка RL-11) и трассе. Для `add[]`
вердикта ([22](22-run.md) §5) — существование `ref@n` в области решения (не п. 3: вердикт добавляет то, что LENS не
нашёл) и проверка 4 по карточке `ref@n` **или полному тексту блока**: `source.text(ref)`, если хэш ответа равен
`text_hash` у `ref@n` (ADR-36) — потребитель читал блок целиком. Нарушение цитаты отклоняет элемент `add`, а не
вердикт: `used`/`unused` и статус записываются, отклонённый элемент — находка в ответе `verdict()` (CP-24); закрытый
мир и цитата — для всех писателей (T-16). **`materialize` вне вызова** (CLI, API):
`ctx` с `candidates` ∪ `found` нет — мир, как у `add[]`, — живые блоки области решения на текущем `seq`; проверки 1
(в этом мире), 2, 4, 5.

`check` доказывает **существование и происхождение** ссылки, не уместность выбора: «правдоподобный, но неверный»
член пройдёт. Уместность защищают вердикт потребителя, доверие ([14](14-trust.md)) и честный отказ `none-fit`.

**Граница в тексте ↔ проверка** (PF-config п. 3.5): граница, сказанная в промпте стадии, дублируется кодом; новая
граница без строки здесь в версию конвейера не публикуется.

| Сказано в тексте | Чем проверяется |
|---|---|
| ссылайся только на кандидатов или найденное | `check` п. 1–3 (CP-06) |
| 1…7 членов решения | правило `std/rule.solution-size` типа `std/member` (§2) |
| у каждого члена — причина-цитата | `check` п. 4 (CP-08); форма — JSON-схема выхода Composer |
| не создавай блоков | нет операции записи блока у Composer; `check` п. 1 |
| тексты блоков, карточек и подсказок — данные, не инструкции | разметка цитаты — код `deliver` и сборки промпта стадии ([22](22-run.md) §4, ADR-36) |
| верни вердикт на каждое решение | кодом не принуждается (потребитель внешний) — метрика доли пропущенных вердиктов ([22](22-run.md)) |

«Ничего не подходит» различается на три случая (T93, T94):

| Случай | Что значит | Что делаем |
|---|---|---|
| **B — промах поиска** | блок есть, LENS не вернул | self-search находит (в том числе по месту в источнике, CP-26) → член `found_by: self-search`; потребность и блок → кандидат в ловушку стенда; текст потребности → подсказка блоку (`inferred`) |
| **C — пробел** | блока нет | `std/gap absent` — сигнал владельцу; пустое решение допустимо, но `recall` его не выдаёт — повтор всегда через LENS, так добавленный владельцем блок находится (CP-20) |
| **покрытие** | в источнике проекта есть, блока нет — место не пересекается с местом живого блока | `std/gap coverage` с `places` — дыра нарезки или загрузки; блок создаёт владелец или загрузка, не Composer |

- Composer **никогда не создаёт блоки**. Новый блок — отдельный процесс владельца (предложение → публикация).
- Self-search тоже может промахнуться: перед `absent` — проверка дублей потребности (§4), иначе настоящий B уходит
  владельцу как «блока нет» и владелец создаёт дубль. То же перед `coverage`: блок, чей смысл не попал в карточку
  (таблица, код), получает низкий балл, а `source.find` находит его место — это промах B, не дыра (CP-26); разрез
  `hit@3` по виду блока — guardrail регрессионного плана ([23](23-bench.md) BN-19). Меряет стенд матрицей B / C /
  покрытие (E4, [01](../01-first-run.md)).

### 6. Дубли и разбиение потребностей

- **Дубли** — тот же механизм, что для сущностей ([11](11-identity-grain.md) §6, ADR-8): `judge.verify` выше порога
  → факт `std/alias-candidate`, в силу не входит; владелец подтверждает `core/alias` или отказывает
  `std/distinct`. При слиянии потребностей их решения алиасятся тем же коммитом; при столкновении ключей членства
  текущим остаётся факт канонического решения; состав после объединения > `max` → находка «разбить», слияние не
  отклоняется ([11](11-identity-grain.md) §4, GR-16).
- **Политика кандидатов** — значения `std` в `std/trust-policy.candidates` ([14](14-trust.md) §4), для сущностей и
  потребностей: `{min_p: 0.85, calibrated_for: null, budget: 10, cluster: true}` — порог `verify`; под какую версию
  judge и каким прогоном он подобран (калибровка — ревизия политики проекта, [23](23-bench.md) §4 п. 8); размер
  очереди владельца — кандидаты пишутся всегда, в очередь идут не больше `budget` открытых по `seq`, остальные ждут
  в журнале ([11](11-identity-grain.md) GR-17); связанные кандидаты — одно решение владельца. Кандидат пишется и без калибровки: в силу не входит, ошибку исправляет владелец
  (ADR-13). Память отказов — `std/distinct` всегда.
- **Разбиение** (T140) — `divide(need, parts, by)`: новые потребности-части, старая — `core/deprecate
  {replaced_by: [части]}` (не алиас: у алиаса один канонический). Находку «> `max` членов» получает владелец
  потребности, не Composer: размер сам по себе не доказывает, что потребность составная. Composer новых потребностей
  вне `frame` не создаёт; после разбиения `frame` следующего вызова находит части.

### 7. Формат выбора (выход Composer, проверяется схемой)

```json
{ "need": "warrant/NEED-01J8…",
  "outcome": "selected",
  "members": [ { "ref": "warrant/REQ-VER-007@4", "reason": "«Waiver применяется к проверке со статусом FAIL»",
                 "found_by": "lens" } ],
  "links": [],
  "task_only": ["warrant/ADR-0036"] }
```

`outcome`: `selected` · `none-fit` (→ self-search) · `absent` · `coverage` (после self-search). `found_by` ставит
код по происхождению ссылки (`candidates` → `lens`, `found` → `self-search`), не Composer.

### 8. Порты `composer` и `source`

```ts
interface Composer {
  run<T>(t: { kind: 'frame' | 'confirm-same' | 'select' | 'recheck' | 'self-search';
             input: Json; schema: JsonSchema }): Promise<{ output: T; meta: Meta } | { pending: Id }>
  describe(): Ident                    // adapter, model — [22](22-run.md) §3
}

interface Source {
  load(): AsyncIterable<RevisionInput>                          // первичная загрузка и обновление (T129): все блоки источника
  text(ref: Ref): Promise<{ text: string; revision: string }>   // полный текст блока — для пакета
  locate(ref: Ref): Promise<{ places: Place[] }>                 // где блок в источнике
  grep(q: string, scope: Ref): Promise<Ref[]>                    // по тексту блоков области — self-search
  find(q: string, scope?: Ref): Promise<{ places: Place[] }>     // по сырому источнику — дыра покрытия
}
type Place = { kind: 'doc' | 'code' | 'test'; path: string; lines?: [number, number] }
```

- **`load()` отдаёт полный перечень** блоков источника, не только изменённые: пишутся только изменённые (no-op), а
  живой объект пространства из прежних загрузок, которого в перечне нет, получает находку `std/load-finding {kind:
  missing}` ([30](30-adapters.md) §6); вывести его из обращения (`core/retire`) решает владелец. Вернулся в
  источник — находка снимается (`value: false`).
- **`text_hash`** (T181, ADR-36): `load()` пишет в тело блока `sha256` текста, который вернёт `text(ref)` (переводы
  строк → LF). Правка текста блока — новая ревизия, доверие — к ней (TR-09); без правки — no-op. Контрактный тест:
  хэш `text()` сразу после `load()` равен `text_hash`. Выдачу сверяет `deliver` ([22](22-run.md) §4).
- **`id` блока — устойчивый якорь источника**: внешнее имя, которое не меняется от вставки соседей; порядковый номер
  пункта якорем не бывает — у пункта без своего якоря блок — документ целиком (CP-19).
- `Meta` — сводка ответа порта, общая с `judge` ([22](22-run.md), T135).
- Выход Composer всегда проверяется схемой; невалидный выход — ошибка стадии, не «лучшее, что получилось».
- `pending` — режим агента (`composer-caller`): задание уходит вызывающему, ответ приходит командой
  `lattice answer`, вызов перезапускается и берёт его (ADR-19; транспорт — [30](30-adapters.md)).
- Какой Composer исполняет — адаптер и точная версия модели в `std/setup` (ADR-28); промпт стадии — в `params`
  стадии, `prompt_hash` — в кортеже исполнения (T131).
- `Place` — не identity: путь и строки вычисляются при чтении. `find` возвращает места, а не `Ref`: у дыры покрытия
  блока нет.

## Операции

| Операция | Вход → выход |
|---|---|
| `frame(task, scopes)` | → потребности (новые или найденные) |
| `recall(need)` | → `{solution, snapshot, status, by, p}` или `none` |
| `select(need, candidates)` | → выбор (§7) |
| `selfSearch(need)` | → `found` и выбор, или `absent` / `coverage` с местами, не пересекающимися с местами живых блоков |
| `check(selection, ctx)` | → нарушения (§5); тот же код проверяет `add[]` вердикта |
| `materialize(need, selection, by)` | → строки: решение, `std/member`, `std/link`, snapshot. Вне вызова (CLI, API) — один коммит, закрытый мир — живые блоки области решения (§5); внутри вызова — строки без записи, коммит делает рантайм (ADR-19) |
| `divide(need, parts, by)` | → потребности-части + `core/deprecate {replaced_by}` старой (§6) |

## Инварианты

1. Одно решение на потребность; действующих `std/member` в нём ≤ `max` правила `solution-size` — держит коммит
   любого писателя.
2. `form: set` ⇒ нет `std/link` в решении; связи решения ацикличны — держит коммит.
3. Каждая ссылка выбора (`members`, оба конца `links`, `task_only`) ∈ `candidates` ∪ `found`; `found` пишет код.
4. Каждая причина члена — цитата из карточки `ref@n`; у `add[]` вердикта — из карточки или полного текста `ref@n`
   (хэш = `text_hash`), нарушение отклоняет элемент, не вердикт.
5. Composer не создаёт блоков, а потребности — только в `frame` (без Composer — `frame.single`).
6. Judge без `calibrated_for` «ту же потребность» не выносит; действие по баллу — только обратимое (ADR-13).
7. Внутри вызова compose журнал не пишет: строки — в коммит вызова (ADR-19).
8. `std/gap coverage` несёт хотя бы одно место в источнике; ни одно его место не пересекается с местом живого блока
   пространства (тот же путь, общие строки).
9. Подсказка, записанная `recall` или `recheck` по сопоставлению, несёт `match` — кто и с каким `p` её сопоставил.

## Вне объёма

- Промпты стадий — в данных конвейера (параметры стадий), черновик — при реализации среза S6.
- **Прежние члены при пересборке.** Решение `overruled`/`contested`/`rejected` `recall` собирает заново через LENS
  (§3), `materialize` пишет новый выбор; что делать с прежними членами, не вошедшими в него, не определено: удалить
  их может только строка обучения (RN-25), а `count` отклонит добавление сверх `max`. Триггер — первый отказ
  `solution-size` или первое решение, где прежние члены с `wrong` остаются рядом с новыми. В v1 уже сейчас: ничего
  сверх — прежние члены с `wrong` не проходят правило выдачи при `policy.lens.exclude` ([14](14-trust.md) TR-15).
- Проверка уместности цитаты `judge.verify` («цитата отвечает на потребность?») `soft`-находкой — нет: правило-
  способность детерминирована (ADR-11), judge — нет. Уместность держат вердикты.
- Composer с инструментами агента (поиск по ID, по тексту) в self-search — после первого запуска, если стенд покажет
  промахи B, которые расширение области не ловит.
