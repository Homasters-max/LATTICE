# 14. trust — факты, утверждения, доверие

**Назначение.** Ответить «насколько этому верить» для любой ревизии и любого факта — вычислением из утверждений,
а не присвоенным статусом (P5).

**Зависит от:** [10-kernel](10-kernel.md), [12-ledger](12-ledger.md) (журнал, индекс фактов), [15-catalog](15-catalog.md)
(владелец, допуски). Раздел индекса `trust` — проекция, которую подключает этот домен: 12 перечисляет раздел, но от
14 не зависит (механизм подключаемых проекций — [04](../04-architecture.md) §4, N-32).
**Используют:** lens (ранжирование и пометки), compose (повтор решений), run (обучение), bench (эталоны), adapters
(хост открывает сессию).

## Модель

### 1. Участники, сессии, реестр

| Объект | Тело | Зачем |
|---|---|---|
| `core/actor` (сущность) | `{kind: human \| agent \| machine, name, model?}`; `model` обязателен при `kind: agent` | кто пишет; вид задаёт вес и группу независимости |
| `core/session` (сущность) | `{actor: ref@n \| null, claimed?, claimed_via?, os_user?, started, ended?, purpose, software?}` | сеанс участника; единица «последнего утверждения» |

- Каждая ревизия несёт `by` = сессия ([10](10-kernel.md) §1).
- **Реестр участников** (ADR-25). Вид участника и право декларанта берутся из реестра владельца пространства, а не
  из тела записи самого участника: `core/actor` — ревизии пространства проекта, их пишет владелец или допущенный
  ([15](15-catalog.md) «Кто что пишет»); детализацию `model` задаёт владелец. Декларант — допуск `core/grant {declare:
  true}` ([15](15-catalog.md) CT-13) — только участнику `kind: human`: допуск не-человеку не действует (находка lint),
  решающее «−» даёт только человек (T-1). Участник вне реестра получает вес и основание уровня `agent`.
- Сессию открывает хост-процесс, а не пишущий участник ([22](22-run.md), [30](30-adapters.md)); он же ставит
  `purpose` и `software`. **Ревизию `core/session` пишет хост**, её `by` — она сама (самоссылка, как у `core/genesis`);
  проверка `owner` пропускает `core/session` только с таким `by` ([13](13-rules.md) §2). Участник вне реестра —
  `actor: null` и `claimed` — имя из `--as` ([30](30-adapters.md) §3); группа — `(agent, unknown)`.
- **Личность — заявление вызывающего**; хост её не проверяет, но пишет в сессию наблюдённое им самим:
  `claimed_via` (T178) — как участник назван (`flag` — `--as` без терминала, `env` — `LATTICE_ACTOR`, `tty` — `--as` в
  интерактивном терминале с подтверждением) и `os_user` — хэш имени пользователя ОС процесса с солью — `origin`
  пространства (T144): совпадение пользователя видно, имени в журнале нет (KR-14). Участника `kind: human` называет
  только `tty`: `env` и `flag` с человеком — отказ ([30](30-adapters.md) §3). Так агент, запущенный из оболочки
  владельца, не пишет от имени владельца, а подмену видно по журналу постфактум («Вне объёма»). Хост пишет оба поля
  у каждой своей сессии; их нет только у сессий, которые хост не открывал, — `core/genesis` и сессий пакета `std`.
- `purpose` — строка, обязательна; значения — **закрытый перечень** хоста ([30](30-adapters.md) §3): новое значение —
  строка таблицы там и решение, питает ли оно доверие. Этот домен резервирует `bench`: сессия стенда, её утверждения
  в доверие не входят (её вердикты не питают обучение — [22](22-run.md), [23](23-bench.md), ADR-29). `simulate`
  резервирует 23-bench: потребитель-симулятор, только в копии кампании, там считается как рабочая сессия
  ([23](23-bench.md) §3). Прочие значения резервируют их владельцы. Доверие читает `purpose` **перечнем
  разрешённых**: утверждения сессий перечня, кроме `bench`, входят в доверие; значение вне перечня — не входит
  (TR-12).
- `software` (`core/session.software`) — `имя@версия` программы, которой действует участник `machine` (парсер). Смена версии — новая сессия
  того же участника, не новый участник: иначе две группы независимости при коррелированных ошибках одного парсера.
- **Группа независимости** (ADR-26) — единица независимых подтверждений: `human` и `machine` — участник, `agent` —
  пара `(kind, model)`. Разные сессии одной группы поддержку не увеличивают. Группа `(agent, unknown)` — участники
  вне реестра — никому не «другая»: её голоса не дают `observed` и не входят в окно удаления членства (TR-16).
- **Реестр читается на `seq` голоса.** Вид и модель участника, владелец пространства цели и декларант для
  утверждения (и для голоса автора) — какими они были на `seq` этого утверждения, как допуск при записи (ADR-6):
  `core/session.actor` — закреплённая `actor@n`. `transfer`, отзыв `declare`, уточнение `model` действуют на
  следующие голоса и не переписывают прошлое доверие (TR-13).
- Владелец пространства (`owner`) — участник или список участников ([15](15-catalog.md) §1); владелец — любой член
  списка.

### 2. Утверждение

```json
{ "id": "warrant/01J8…", "type": "core/assert@1", "version": 1, "by": "warrant/SES-…",
  "body": { "of": { "target": {"$ref": "warrant/01J8…member-fact"} }, "value": 0.5, "reason": "used in answer" } }
```

- `target` — любой факт или ревизия. Следующая ссылка на ревизию разрешается при коммите: индекс относит
  утверждение к `id@n` на `seq` утверждения — правка объекта не переносит голос на новую ревизию (TR-13).
  **Основание — на одну ревизию или факт**, не на часть тела: составное тело, поля
  которого пришли из источников разной надёжности, делится на факты своих авторов. Норма WARRANT: ревизия парсера —
  только извлечённые поля; `summary` — отдельный факт автора `agent` о ревизии (тип проекта, определяет адаптер,
  [30](30-adapters.md)); алиасы — `std/alias-candidate` (ADR-8).
- `value` — надёжность −1…1. `reason` необязателен; при принятии предложения — обязателен ([15](15-catalog.md) CT-11).
- `via` — исходная сессия, когда утверждение пишет посредник (сессия `learn`, [22](22-run.md)); учёт — по `via ?? by`
  (ADR-5). Утверждения обучения — наследник `std/learned-assert` (`via` обязателен, `from` — вердикт, [22](22-run.md)
  §6); «утверждения» здесь — `core/assert` и его наследники.
- **Автор факта или ревизии неявно утверждает её с надёжностью +1.** Отдельного утверждения автора не пишется; голос
  автора идёт в основание, не в сумму спора (§3).
- Утверждения копятся ([10](10-kernel.md) §7, исключение); текущее выбирает этот домен:
  - **голос сессии** — её последнее утверждение по цели (переобуться можно, накрутить повтором нельзя);
  - **голос группы**: `human`, `machine` — последнее утверждение участника; `agent` — среднее голосов сессий группы
    (одна свежая сессия модели не переворачивает её прежние);
  - владелец пространства цели и декларант — последнее утверждение **участника** (ADR-5).
- Держание `core/holds` — провенанс, не голос ([10](10-kernel.md) §7).

### 3. Доверие — две оси

**Основание (`basis`)** — откуда известно: кем и как создана запись и сколько независимых групп её подтвердило.
Выбирается высшее выполненное:

| Значение | Условие (пороги — политика, §4) |
|---|---|
| `declared` | действующее «+» (последнее явное `core/assert` участника, не утверждение обучения) человека-владельца пространства цели или допущенного декларанта |
| `derived` | автор — `machine`, запись получена детерминированным разбором внешнего источника (документ, правило); сессия несёт `software` |
| `observed` | «+» от ≥ `observe_groups` разных групп независимости, из них ≥ 1 не из группы автора |
| `inferred` | иначе: поддержка только от LLM-агентов или одной группы |

- **Порядок** `declared > derived > observed > inferred`: за `declared` отвечает владелец; ошибка `derived`
  воспроизводима и ловится проверкой разборщика; `observed` — независимые группы, но без ответственного; `inferred` —
  одиночный голос. Довод дизайна, опоры в базе знаний нет — пересмотр по данным стенда.
- **Вывод не отмывает основание.** Запись, выведенная из вердиктов (обучение, [22](22-run.md)), узнаётся по `from`
  (вердикт); её основание считается по этой таблице, как у любой записи: автор — сессия вердикта ([22](22-run.md) §6),
  подтверждения — утверждения и вердикты других групп. `derived` ей недоступно: `learn` — машина, но не разбор
  источника; вид сессии `learn` записи не передаётся. `declared` — только «+» человека-владельца или декларанта
  явным `core/assert`: утверждение обучения (`std/learned-assert`) из вердикта владельца — обычный голос его группы
  (TR-17).
- «Сколько подтвердило» читается из поля `groups` выхода `trust()`, а не через `basis` (эталоны стенда, `std/cue`, §7).

**Состояние спора (`epistemic`)** — есть ли спор:

| Значение | Условие |
|---|---|
| `contested` | суммы «+» и «−» обе ≥ `contest_min`; или раскачка — историзуемый факт переключался ≥ `oscillation_cycles` раз |
| `rejected` | «−» ≥ `resolve_min`, «+» < `contest_min` — независимые группы отвергли (TR-14) |
| `unresolved` | модуль суммы < `resolve_min` |
| `settled` | иначе — итог «+» |

Условия проверяются сверху вниз; первое выполненное — значение.

Сумма = Σ голос группы × вес (ключ весов, §4) по группам, **кроме группы автора**. Голос автора в сумму не входит:
свежая запись одного автора — `unresolved`, пока её не подтвердит другая группа.

**Перекрытие владельцем.** «−» человека-владельца пространства цели или декларанта явным `core/assert` решающее:
`trust()` отдаёт `overruled: {by, at}`, какой бы ни была остальная поддержка. «−» агента-владельца и «−» из вердикта
владельца (`std/learned-assert`, например `wrong`) — обычные голоса в сумме (TR-17).

### 4. Политика доверия — объект типа `std/policy`

```json
{ "id": "std/trust-policy", "type": "std/policy@1",
  "body": { "weights": {"human": 1.0, "machine": 1.0, "agent": 0.5},
            "observe_groups": 2, "contest_min": 0.5, "resolve_min": 0.5, "oscillation_cycles": 2,
            "lens": {…}, "candidates": {…},
            "calibration": { "add_min_verdicts": 1, "verdict_weights": {…}, "removal_window": {"n": 3, "m": 5} } } }
```

| Поле | Что | Переопределяет проект |
|---|---|---|
| `weights` | вес голоса по ключу `kind` → `kind/model` → `kind/model@namespace` (берётся самый точный заданный); числа — допущение, калибрует стенд | да |
| `observe_groups` | порог `observed` | да |
| `contest_min`, `resolve_min`, `oscillation_cycles` | пороги спора | да |
| `lens` | `{exclude, mark}` — какие состояния доверия LENS исключает до judge и какие помечает ([20](20-lens.md)) | да |
| `candidates` | политика кандидатов в алиас: порог (ADR-13) и `calibrated_for` — под какую версию judge и каким прогоном он подобран (T136; расходится с judge из `setup` — кандидаты как без калибровки, [22](22-run.md) RN-35), бюджет — размер очереди владельца, не предел записи ([11](11-identity-grain.md) GR-17), кластер — одно решение, память отказов `std/distinct` (GR-12) | да |
| `calibration` | правила обучения ([22](22-run.md) RN-05): `add_min_verdicts`, `verdict_weights`, окно удаления членства `removal_window` (ADR-20) | только `std` |

- Значения `lens`, `candidates`, `verdict_weights` задают их потребители — [20](20-lens.md), [21](21-compose.md),
  [22](22-run.md); здесь — форма.
- Своя политика у каждого пространства имён (`namespace.policy`, [15](15-catalog.md)); по умолчанию —
  `std/trust-policy`. До второго проекта WARRANT ссылается на `std/trust-policy`. Ссылка **закреплена** `id@n`
  (`refs: pin`, [15](15-catalog.md) CT-16): `lattice update` с новой ревизией политики её не меняет; смена —
  ревизия пространства владельцем, `policy@n` входит в кортеж исполнения, и прежний `pass` стенда её не покрывает
  ([22](22-run.md) §1, RN-24).
- Тип политики — `std/policy`, не тип генезиса: ядро политику не читает (ADR-35); новый ключ — новая версия
  `std/policy` по совместимости схемы общего типа. Ядро проверяет только, что ссылка `namespace.policy`
  разрешается; цель не `std/policy` (или наследник) — `trust()` отказывает, политика не подменяется.
- **Чья политика считает.** Доверие в хранилище считает политика проекта-владельца хранилища — `policy` его
  единственного пространства ([15](15-catalog.md) §1) — для всех целей,
  включая копии `core`, `std` и импортированных пространств; доверие, посчитанное поставщиком, — справочное
  (T-7). Выход `trust()` несёт `policy: id@version`; смена политики — ревизия и пересчёт
  индекса, журнал не меняется.

### 5. Доверие составных вещей

- **Решение** (T82): доверие каждого членства отдельно; сводка решения — наименьшее основание среди членств; из
  состояний — худшее: `overruled` > `contested` > `rejected` > `unresolved` > `settled` (перекрытое членство
  поднимается в сводку).
- **Блок:** основание ревизии (кто и как написал) + утверждения на ревизию. Вердикты пишут утверждения на членства,
  не на блок: вердикты решений, где блок участвовал, — справка `explain`, в доверие блока не входят (иначе петля:
  доверие блока → выдача → вердикты → доверие блока).
- **Способность:** то же; вердикты исполнения — справка `explain`.

### 6. Чем доверие не является

- **Балл judge не превращается в утверждение.** Оценка — событие `std/measurement`, влияет на выдачу, но не на доверие.
- Число вызовов не является доверием: «18 000 оценок» ничего не говорит без вердиктов.
- Держание значения (`core/holds`) — не голос.
- Доверие не затухает со временем: устаревание решает статус snapshot'а (изменились версии членов или состав решения), а не возраст.
- Доверие не хранится — пересчитывается в индексе при каждом новом утверждении по затронутой цели.

### 7. Как доверие используется

**Балл решает только обратимое действие** (ADR-13). Действие по баллу judge без участника допустимо, только если оно
обратимо и дёшево и его ошибку ловит последующий вердикт (потребителя или стенда); остальное решает правило,
владелец или вердикт. Названное исключение — повтор решения (`recall`): выдача без поиска с полями `by: exact / judge
/ composer` и баллом `p`, доля серой зоны — в отчёте стенда ([23](23-bench.md)). Порог — по `max(scores.judge)`
закреплённой версии judge, не по `fused` ([20](20-lens.md)). Для сущностей тот же приём запрещён: похожесть даёт
только кандидата в алиас (`std/alias-candidate`, ADR-8, [11](11-identity-grain.md) GR-06).

| Где | Правило |
|---|---|
| повтор решения (`recall`) | по сводке решения (§5): `overruled`, `contested` или `rejected` → заново через LENS и Composer; иначе (`settled`, `unresolved`) — по основанию: ≥ `observed` → выдать без поиска (`by`, `p`), `inferred` → выдать с пометкой «не подтверждено». Пустое решение `recall` не выдаёт — всегда через LENS (TR-14) |
| правило выдачи — все пути | блок выдаётся, только если жив (не выведен из обращения) и его доверие не в `policy.lens.exclude`; пометки — `policy.lens.mark` и `deprecated`. Применяют LENS (пул), `recall` (член не проходит → как `broken`: LENS по сохранённой потребности), проверка `add[]` вердикта и `materialize` (TR-15) |
| выдача LENS | доверие — пометка и фильтр по `policy.lens` (правило выдачи), не множитель к баллу (порядок решает стенд); перекрытое — исключается до judge ([20](20-lens.md)). Перекрытое при `support.plus` ≥ `contest_min` от других групп — находка `lint` владельцу: иначе ошибка владельца самозапечатывается — нет выдач, нет вердиктов (TR-04) |
| эталоны стенда | решения `observed` / `declared` — кандидаты в эталоны; сессии стенда доверие не питают |
| алиасы, подсказки | `core/alias` — управляющий факт: `inForce: write` — в силе по праву записи (`writers`, ADR-6), кандидат в силу не входит (ADR-8); `std/cue` — `inForce: {basis: observed}` |

## Операции

| Операция | Вход → выход |
|---|---|
| `assert(target, value, reason?, via?, by)` | → событие `core/assert` |
| `trust(target)` | → `{basis, epistemic, support: {plus, minus}, groups, overruled?: {by, at}, policy}` — то же хранит раздел индекса `trust` ([12](12-ledger.md) §3) |
| `explain(target)` | → голоса групп, из каких утверждений они взяты, и веса — почему такое доверие |

`support.plus` / `support.minus` — взвешенные суммы «+» и «−» голосов групп без группы автора; `groups` — число групп
независимости с «+», не считая группы автора; `policy` — `id@version` политики, которая считала.

## Инварианты

1. Доверие не пишется в журнал: `trust()` — функция журнала и политики; пересборка индекса даёт тот же результат.
2. Разные сессии одной группы независимости не увеличивают поддержку; голос автора не входит в сумму спора.
   Прошлое доверие меняется только новыми утверждениями или ревизией политики: реестр, владелец и декларант
   читаются на `seq` голоса (TR-13).
3. `derived` — только детерминированный разбор внешнего источника; запись, выведенная из вердиктов, — не `derived`,
   её основание — по таблице §3 с автором — сессией вердикта.
4. `declared` и перекрытие (`overruled`) дают только явные `core/assert` человека-владельца пространства цели или
   допущенного декларанта (декларант — только `human`), не утверждения обучения (TR-17).
5. Вид участника и право декларанта читаются из реестра владельца пространства; участник вне реестра — уровня `agent`.
6. В доверие входят утверждения сессий только перечисленных `purpose` ([30](30-adapters.md) §3), кроме `bench`;
   значение вне перечня — не входит (TR-12).

## Решения

| ID | Решение | Почему |
|---|---|---|
| TR-01 | Доверие вычисляется из утверждений по двум осям и в один балл не сводится: решения сочетают оси правилами §7 | основание и спор — разные вопросы; балл прятал бы, какое условие не выполнено. v0.4 · И-1 · ADR-14 (`basis`) |
| TR-02 | Автор неявно утверждает +1 — голос в основание, не в сумму спора; утверждения копятся, текущее — последнее сессии (владельца и декларанта — участника), учёт по `via ?? by` | повтор в сессии не удваивает голос; самоотчёт автора не закрывает спор; от накрутки новыми сессиями защищает TR-03. v0.4 · ADR-5 · T-15 · И-6, И-7, И-12 |
| TR-03 | Независимость — по группам: участник для `human`/`machine`, `(kind, model)` для `agent`; голос группы: участник — последнее, `agent` — среднее голосов сессий; вес — по иерархическому ключу | подтверждения одной модели на том же evidence коррелированы; среднее не даёт одной сессии перевернуть группу; ключ растёт без смены журнала. v0.4 · ADR-26 · И-8, И-9 · D07 Q3 · v0.3 вопросы 1–2 · v0.5 · CA-F09: `(agent, unknown)` — никому не «другая» группа (TR-16) |
| TR-04 | «−» человека-владельца пространства цели или декларанта решающее — `overruled: {by, at}`; «−» агента-владельца — голос в сумме | владелец отвечает за своё пространство; агент-владелец ошибается как агент. v0.4 · T-1 · ADR-6 · И-11, И-13 · v0.5 · CA-F43: перекрытое при «+» других групп ≥ `contest_min` — находка `lint` владельцу |
| TR-05 | Пороги — объект политики пространства имён; доверие в хранилище считает политика проекта-владельца, выход несёт `policy`; правила обучения — только `std` | разные проекты — разная строгость; одно хранилище — одна политика, чужой расчёт справочный. v0.4 · T-7 · И-14, И-15 · D07 Q1 · v0.5 · ADR-35: тип политики — `std/policy` |
| TR-06 | Баллы judge и число вызовов — не доверие | P5; закон Гудхарта — балл, ставший целью, перестаёт мерить; баллы разных версий judge несравнимы; «может ≠ имеет право». v0.4 · ADR-13 · И-16 |
| TR-07 | `derived` — только детерминированный разбор внешнего источника; запись из вердиктов — не `derived`, основание — по таблице §3, автор — сессия вердикта; версия разборщика — `session.software`, участник тот же | нормы, разобранные парсером, надёжнее пересказа LLM, но детерминизм — не правильность; вывод не отмывает основание, но и не заперт на `inferred`: подтверждения других групп дают `observed`. v0.4 · T-15 · И-2, И-4 · R4 Q5 · C2b 2·Q2 |
| TR-08 | Затухания доверия во времени нет | устаревание решает статус snapshot'а (изменились версии членов или состав, CP-20), а не время. v0.4 · v0.3 вопрос 3 |
| TR-09 | Основание — на одну ревизию или факт; составное тело из источников разной надёжности делится на факты своих авторов; тип такого факта — проекта | одна запись не несёт двух оснований; `std`-тип — со вторым адаптером. v0.4 · И-5 · R4 Q6 · D07 Q2 |
| TR-10 | Балл решает только обратимое и дешёвое действие, ошибку которого ловит вердикт; `recall` — названное исключение | правило проверяется в каждом новом месте, где балл решает. v0.4 · ADR-13 · T-14 · И-17 |
| TR-11 | Вид участника и декларант — из реестра владельца; декларант — только `human`; сессию открывает и пишет хост (`by` — она сама); вне реестра — `actor: null`, `claimed`, уровень `agent`; хост пишет наблюдённое — `claimed_via` и `os_user`; `human` называет только `tty` | самозаявленный `kind: human` дал бы агенту вес 1,0; решающее «−» — только человек (T-1); сессия не может ждать записи владельцем. v0.4 · ADR-25 · И-10 · C2b 1·Q4 · v0.5 · CA-F01; `os_user` — хэш с солью `origin` (KR-14) |
| TR-12 | `purpose` — строка из закрытого перечня хоста; домен резервирует `bench`: сессии стенда доверие не питают; доверие читает `purpose` перечнем разрешённых — значение вне перечня не питает | стенд меряет, а не голосует. Отсрочка «перечисление — когда прочтёт второй потребитель» уже сработала: значения читают 14, 20, 22, 23 и гейт; новый `purpose: eval` тихо голосовал бы и учил. v0.4 · T-5 · 23-bench/И-10 · D07 Q7 · v0.5 · CA-F50 |
| TR-13 | Вид, модель, владелец и декларант для голоса — на `seq` голоса; `core/session.actor` — `actor@n`; следующая цель утверждения на ревизию — `id@n` на `seq` утверждения | иначе `transfer` или уточнение `model` тихо переписывают доверие всей истории: перекрытия прежнего владельца исчезают, одна группа задним числом распадается на две; время привязано так же, как допуск при записи (ADR-6). v0.5 · CA-F06, CA-F33 |
| TR-14 | Состояние спора `rejected` — «−» ≥ `resolve_min` при «+» < `contest_min`; `recall` — полная таблица по сводке решения: `overruled`/`contested`/`rejected` → заново, иначе по основанию; пустое решение — всегда через LENS | `settled` без знака: три `wrong` от разных групп давали `settled`, и `recall` отдавал отвергнутое бесконечно; для `unresolved` — состояния свежей записи — правила не было. Новое значение — в словаре `policy.lens`, LENS помечает отвергнутое тем же механизмом. v0.5 · CA-F16, CA-F36 |
| TR-15 | Одно правило выдачи: жив и не в `policy.lens.exclude`, пометки — `mark` и `deprecated`; применяют LENS, `recall`, `add[]`, `materialize` | приоритет «владелец > доверие > балл» держался только на пути LENS: повтор отдавал перекрытые и выведенные нормы. v0.5 · CA-F15 |
| TR-16 | `(agent, unknown)` никому не «другая» группа: не даёт `observed`, не входит в окно удаления | опечатка в `--as` давала самоподтверждение одного агента: `observed`, `settled` и `recall` без поиска. v0.5 · CA-F09 |
| TR-17 | `declared` и решающее «−» дают только явные `core/assert` владельца-человека или декларанта; утверждения обучения из его вердиктов — голос его группы | учёт по `via ?? by` делал любое «−» из вердикта владельца — даже `unused` («возможно лишнее») — решающим `overruled` вопреки окну ADR-20. v0.5 · CA-F35 |

## Вне объёма

- Криптографическая подпись утверждений.
- **Снятие голосов подменённой сессии** (сессия, чья личность оказалась подменой, F01): голоса на `seq` голоса
  остаются (TR-13), отзыв `declare` их не снимает. Механизм — утверждение владельца «сессии X…Y недействительны» или
  пересчёт без них — когда понадобится. Триггер — первая обнаруженная подмена (видна по `claimed_via` и `os_user`).
  В v1 уже сейчас: сессия несёт `claimed_via`, `os_user` и `actor@n`.
- Аутентификация участника — порт окружения. Допущение модели угроз (ADR-25): личность в сессии — заявление
  вызывающего, хост её не проверяет. На нём стоят `owner`, `declared`, решающее «−» (`overruled`), декларант, группы
  независимости и гейт обучения (`purpose`). Граница хоста: `human` — только `--as` в терминале с подтверждением;
  `LATTICE_ACTOR` агенту задаёт оркестратор на процесс, в профиле человека его нет ([30](30-adapters.md) §3).
  Подмену видно постфактум — по `claimed_via` и `os_user` сессии; предотвращения нет. Восстановление владения при
  утрате — через хост или адаптер.
- Общий `std`-тип для полей LLM-обогащения (как `summary`) — когда он понадобится второму адаптеру (TR-09).
