# 15. catalog — пространства имён, владельцы, публикация, потребители

**Назначение.** Кто что может менять, как новая версия становится доступной и как это расходится по потребителям
без скрытого глобального изменения поведения.

**Зависит от:** [10-kernel](10-kernel.md), [11-identity-grain](11-identity-grain.md), [12-ledger](12-ledger.md)
(коммит, `keys`, LG-11), [13-rules](13-rules.md). **Используют:** все пишущие операции; trust (кто владелец,
декларант), run (обновление `std`, `std/setup`); adapters (проекты).

## Модель

### 1. Пространство имён и проект

```json
{ "id": "warrant/namespace", "type": "core/namespace@1",
  "body": { "name": "warrant", "owner": {"$ref": "warrant/ACT-maintainer"},
            "imports": ["core", "std"], "policy": {"$ref": "std/trust-policy"},
            "doc": "Нормы и агенты проекта WARRANT" } }
```

- Тело `core/namespace` (тип генезиса): `name`, `owner`, `imports`, `policy`, `doc` — описаны здесь; неизменное поле
  `origin` и правило «точка в имени — часть имени, без иерархии» — [10](10-kernel.md) §1. Локальное имя `namespace`
  зарезервировано: объект пространства лежит в нём самом.
- **Проект** = пространство имён + хранилище + настройка исполнения `std/setup` (конвейер и адаптеры портов с
  моделями, один объект на пространство, [22](22-run.md), ADR-28) + проводка `lattice.config.json`
  ([30](30-adapters.md) §2, [04](../04-architecture.md) §5). Ядро о проектах не знает (P10).
- `owner` — участник или группа участников: ссылка или список ссылок на `core/actor`; владелец — любой член списка
  (реестр — [14](14-trust.md), ADR-25).
- `imports` — какие пространства проект читает; поле есть **только** в `core/namespace`, в конфигурации его нет.
  В v1 допустимы только `core` и `std`: импорт открывает пространство целиком, а зависеть от всей модели другого
  проекта нельзя. Связь проект→проект — через перенос блока в `std` (CT-12); публичное подмножество пространства —
  по триггеру второго проекта, которому нужен чужой блок. Писать можно только в своё пространство.
- `core` поставляется кодом, `std` — данными в пакете LATTICE. Их объекты попадают в хранилище проекта **импортом**
  (CT-08, CT-09): неизменные копии строк с тем же `id`, версией и хэшем, пакет замкнут по ссылкам тела и заголовка
  (ADR-4, [10](10-kernel.md) инвариант 5); пространство с тем же именем и другим `origin` отклоняется.

**Коммит обновления `std`** (при `init` и новой версии пакета, CT-10):
- копии сохраняют заголовок поставщика: `by` — сессия пакета `std/release-<версия>`, та же `version`; правило `owner`
  проверяет копию против её собственного пространства `std` — его `core/namespace`, участники и сессии пришли в
  замыкании. Шаг 1 коммита заголовки копий не назначает ([12](12-ledger.md) §2);
- коммит целиком (маркер, `key` = источник + версия импорта) подписывает сессия, которую хост открывает от имени
  владельца **проекта**: принять обновление — его акт;
- если новая версия `std` меняет зерно типа, в тот же коммит входит план перезерновки пространств проекта — строки
  владельца проекта по обычному `owner`; без плана для пространств с коллизиями обновление не публикуется в этом
  хранилище ([11](11-identity-grain.md) GR-14, ADR-7).

### 2. Кто что пишет

| Что | Кто | Правило |
|---|---|---|
| ревизии объектов пространства | владелец или допущенный (`core/grant`) | `owner` (hard) |
| типы и правила пространства | владелец | `owner` + допуск на `core/type` |
| управляющие факты: `core/grant`, `core/retire`, `core/deprecate` (и `core/alias`, [11](11-identity-grain.md)) | владелец пространства **цели** или допущенный на этот тип факта | `writers` типа факта, проверяет `owner` ([10](10-kernel.md) §7, ADR-6) |
| накопительные факты: утверждения `core/assert`, подсказки `std/cue` | любой участник с доступом к хранилищу | факт живёт **в пространстве автора**, ссылается куда угодно |
| предложение ревизии | любой | событие `core/proposal`; ревизию пишет владелец |

- **Текущий управляющий факт** — последний по `seq` с этим ключом среди записей допущенных `writers` ([10](10-kernel.md)
  §7). Факт стороннего писателя с тем же ключом (`retire`, `alias`, `member … false`) текущий не подменяет — правило
  `owner` его не пропускает.
- **Допуск** — факт `core/grant` `{of: {actor, namespace}, value: {create?: [типы], edit?: [типы], declare?: true}}`:
  `create` — создавать объекты типа, `edit` — писать ревизии чужих объектов типа, `declare` — быть декларантом
  (T119, ADR-25). Например, агентам WARRANT: `{create: ["std/need", "std/solution", "std/member", "std/link"]}` —
  создавать потребности и решения с составом, но не нормы и не состав доменов (`core/member`, [21](21-compose.md));
  подсказки `std/cue` пишет любой. У типов `refs: follow` (нормы, знания) `edit` не действует: правка чужого — только
  через `core/proposal`, массово — пакетом предложений.
- **Смена владельца** — ревизия `core/namespace` с новым `owner`, которую принимает новый владелец (двусторонний акт,
  ADR-25). Восстановление при утрате — через хост, «Вне объёма».

Это и есть P4: **тело говорит владелец, факты — кто угодно.** Агент не может переписать норму, но может утверждать,
что она пригодилась или нет, — и это меняет доверие, а не норму.

### 3. Публикация и версии

- Коммит владельца = публикация. Опубликованная ревизия неизменна (KR-03).
- Предложение: `core/proposal` `{target: ref, body, reason}` → владелец принимает или отклоняет. **Принятие** —
  ревизия цели + утверждение `core/assert {of: {target: proposal}, value: 1, reason}` с обязательным `reason`: что
  проверено. **Отклонение** — утверждение −1 на предложение.
- Три правила из концепции: **версия неизменна; новую выпускает только владелец; потребитель сам решает, когда
  переходить.**

### 4. Ссылки и потребители

| Политика типа (`refs`) | Что обязаны делать ссылки на его объекты | Типы |
|---|---|---|
| `pin` | быть закреплёнными `id@n` (правило `ref-policy`, hard) | способности, включая правило-способность `check` ([13](13-rules.md) RL-07); конвейеры, типы, правила |
| `follow` | могут быть следующими `id` | знания, домены, термины, потребности |

- **Способности всегда закреплены.** Новая версия блока ничего не меняет у потребителей, пока они сами не
  перезакрепят ссылку. Подписки «@current» для исполняемых блоков нет — это та скрытая глобальная связь, от которой
  концепция защищается. Закреплена и реализация: рантайм отказывает, если код не совпадает с `impl.pins`
  ([13](13-rules.md) §3, T-2).
- **Знания могут следовать.** Решение ссылается на норму без версии; snapshot при выдаче закрепляет версии; изменение
  нормы делает snapshot `stale` — это видно, а не тихо.
- **Индекс потребителей** отвечает: где используется `X@3`, кто следует за `X`, какие версии в ходу — в пределах
  своего хранилища. Потребителей в других хранилищах поставщик не видит.

### 5. Жизненный цикл

| Событие | Как | Последствия |
|---|---|---|
| новая версия | ревизия владельца | закреплённые потребители — без изменений; следующие — видят новую; lint: «есть новая версия» для закреплённых |
| устаревание | факт `core/deprecate` `{object, replaced_by?}` | объект жив; LENS помечает, не понижает ([20](20-lens.md)); lint: «перейдите на …» |
| вывод из обращения | факт `core/retire` `{object}` | не живой; следующие — `broken`; LENS не выдаёт. Закреплённые ссылки на **данные** работают (строки неизменны); код исполняется только при совпадении `impl.pins` и без отзыва версии (CT-05) |
| миграция | потребитель пишет новые ревизии с новыми закреплениями | `migrate --from X@3 --to X@4` запускает **потребитель** в своём хранилище: готовит ревизии или предложения; то же тело под новой версией типа — новая ревизия ([12](12-ledger.md) §2, ADR-2). Поставщик публикует `core/deprecate {replaced_by}` и, для несовместимой версии, карту перехода; сам `migrate` не выполняет |

**Вывод старой версии способности** (ADR-15). В v1, пока у способности один проект-потребитель, владелец выводит
старую версию согласованным переходом: сам переводит потребителей на новую, затем `core/retire`. Триггер пересмотра —
второй проект-потребитель: тогда строгий `pin` и вывод по политике — `retire` с датой, после неё закреплённые ссылки
на выведенную реализацию — `broken` с подсказкой `replaced_by`.

## Операции

| Операция | Вход → выход |
|---|---|
| `publish(rows, by)` | → коммит ([12](12-ledger.md)) с правилом `owner` |
| `propose(target, body, by)` / `accept(proposal, reason, by)` / `reject(proposal, reason?, by)` | → событие; ревизия цели + утверждение ±1 на предложение |
| `grant(actor, namespace, {create?, edit?, declare?}, by)` | → факт `core/grant` |
| `deprecate(ref, replacedBy?, by)` / `retire(ref, by)` | → факты (владелец пространства цели) |
| `consumers(ref)` / `usage(id)` | → потребители по версиям в пределах хранилища |
| `migrate(from, to, by)` | → ревизии или предложения потребителям; запускает потребитель |
| `update(package, by)` | → коммит обновления `std` (§1): копии + план перезерновки, `key` = источник + версия |

## Инварианты

1. Каждая строка коммита проходит `owner`: ревизию пишет владелец её пространства или допущенный, управляющий факт —
   допущенный `writers` его типа; копия импорта проверяется против своего пространства из замыкания.
2. `imports` задан только в `core/namespace` и в v1 содержит только `core`/`std`.
3. Копия импорта совпадает с оригиналом по `id`, версии и хэшу; пакет замкнут; другой `origin` при том же имени —
   отказ.
4. Ссылка на объект типа `refs: pin` закреплена `@n`.
5. Правка чужого объекта типа `refs: follow` — только через `core/proposal`.

## Решения

| ID | Решение | Почему |
|---|---|---|
| CT-01 | Пространство имён — объект с владельцем, импортами, политикой доверия; `imports` — только здесь, в v1 — только `core`/`std` | мультипроектность без знания ядра о проектах; `core`/`std` — конформист к опубликованному языку LATTICE, версии идут параллельно; совладение (shared kernel) между пространствами не допускается. v0.4 · ADR-28 · T-7 · Q-42 C-2, C-3 · Q-43 C-3 |
| CT-02 | Проект читает свои и импортированные пространства, пишет только в своё | изоляция; общие блоки — без форка: копия неизменна, тот же `id` и хэш. v0.4 · ADR-4 · Q-43 C-2 |
| CT-03 | Ревизии — владелец или допущенный; остальные — предложения; `owner` — участник или группа, смена — двусторонний акт | owner-controlled; владение не теряется и не захватывается односторонне. v0.4 · ADR-25 · Q-42 C-4 |
| CT-04 | Накопительные факты и утверждения живут в пространстве автора; управляющие — пишут допущенные `writers` цели, текущий — среди допущенных | любой может свидетельствовать, никто не переписывает чужое; свидетельства видны в своём хранилище, обмен между проектами — вне v1. v0.4 · ADR-6 · T-1 · Q-44 C-2 · Q-45 C-2, C-3 |
| CT-05 | Удаления нет; устаревание и вывод из обращения — факты; индекс потребителей в пределах хранилища | закреплённые ссылки на данные вечны, видно, кто держит; код — `impl.pins` и согласованный вывод (ADR-15), строгий `pin` с датой — со второго проекта. v0.4 · ADR-15 · T-2 · Q-46 C-3 · Q-47 C-3, C-4 |
| CT-06 | Политика ссылок типа: способности (и правило-способность `check`) — только `pin` | нет скрытого глобального изменения поведения; `pin` закрепляет и код (`impl.pins`). v0.4 · ADR-11 · T-2 |
| CT-07 | Миграцию запускает потребитель в своём хранилище; поставщик публикует `deprecate` и карту перехода | концепция v0.2, правило 3; поставщик не видит чужих хранилищ. v0.4 · T-7 · ADR-2 · Q-47 C-2 |
| CT-08 | `core` — код, `std` — данные пакета, импортируются в хранилище проекта копией | один механизм версий для библиотеки и проекта. v0.4 · ADR-4 |
| CT-09 | Общие блоки между проектами копируются неизменными строками при импорте; общего хранилища на чтение нет | проект самодостаточен; один источник истины — [12](12-ledger.md) LG-11. v0.4 · ADR-4 · v0.3 вопрос 1 |
| CT-10 | Коммит обновления `std`: копии сохраняют заголовок поставщика и проходят `owner` по своему пространству; коммит подписывает сессия владельца проекта; план перезерновки — в том же коммите | провенанс копии не теряется, хэш совпадает с поставщиком; без исключений в правиле ядра; принять обновление — акт владельца проекта. v0.4 · ADR-7 · ADR-4 · D06 Q1 |
| CT-11 | Принятие предложения — ревизия цели + `core/assert` +1 на предложение с обязательным `reason` | видно, что проверено; симметрично отклонению; без нового типа. v0.4 · Q-44 C-1 · D06 Q2 |
| CT-12 | Блок проекта становится общим только через `std`: новая сущность в `std` + `core/deprecate {replaced_by}` старой; `id` не переносится; `lib.<имя>` — с публичным подмножеством | `id` не переезжает между пространствами (ADR-4); в v1 `imports` — только `core`/`std`. v0.4 · D06 Q3 · v0.3 вопрос 2 |
| CT-13 | Декларант — допуск `core/grant {declare: true}` от владельца пространства | право не самозаявлено; реестр — у владельца. v0.4 · ADR-25 · v0.3 вопрос 3 |
| CT-14 | Допуск различает `create` и `edit`; у типов `refs: follow` `edit` не действует — только предложение | допуск на тип не обходит согласование норм и знаний. v0.4 · T-1 · Q-44 C-3 |

## Вопросы для grilling

Открытых нет: v0.3 вопросы 1–3 закрыты в v0.4 — CT-09, CT-12, CT-13.

## Вне объёма

- Аутентификация участников — порт окружения (агент, CLI), не модель.
- Восстановление владения при утрате — через хост / адаптер; допущение: хост честно передаёт личность (ADR-25).
- Обмен утверждениями о `std`-блоках между проектами — в v1 доверие к общему блоку у каждого проекта своё.
- Публичное подмножество пространства и импорт проект→проект — по триггеру (CT-01, CT-12).
