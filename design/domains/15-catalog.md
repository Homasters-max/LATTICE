# 15. catalog — пространства имён, владельцы, публикация, ссылающиеся

**Назначение.** Кто что может менять, как новая версия становится доступной и как это расходится по ссылающимся без скрытого глобального изменения поведения.

**Зависит от:** [10-kernel](10-kernel.md), [11-identity-grain](11-identity-grain.md), [12-ledger](12-ledger.md) (коммит, `keys`, LG-11), [13-rules](13-rules.md). **Используют:** все пишущие операции; trust (кто владелец, декларант), run (обновление `std`, `std/setup`); adapters (проекты).

## Модель

### 1. Пространство имён и проект

```json
{ "id": "warrant/namespace", "type": "core/namespace@1",
  "body": { "name": "warrant", "owner": {"$ref": "warrant/ACT-maintainer"},
            "imports": ["core", "std"], "policy": {"$ref": "std/trust-policy@1"},
            "doc": "Нормы и агенты проекта WARRANT" } }
```

- Тело `core/namespace` (тип генезиса): `name`, `owner`, `imports`, `policy`, `doc` — описаны здесь; неизменное поле `origin` и правило «точка в имени — часть имени, без иерархии» — [10](10-kernel.md) §4. Локальное имя `namespace` зарезервировано: объект пространства лежит в нём самом.
- `policy` — политика доверия пространства ([14](14-trust.md) §4), закреплённая `id@n`: тип `std/policy` — `refs: pin` (§4). Обновление `std` новой ревизии политики её не меняет; смена — ревизия `core/namespace` владельцем, и `policy@n` входит в кортеж исполнения ([22](22-run.md) §1): прежний `pass` стенда новую политику не покрывает (CT-16, ADR-29).
- **Проект** = одно пространство имён (v1; несколько — по триггеру второго) + хранилище + настройка исполнения `std/setup` (конвейер и адаптеры портов с моделями; действующая — объект `<пространство>/setup`, прочие — базовые линии стенда, [22](22-run.md) RN-29, ADR-28) + проводка `lattice.config.json` ([30](30-adapters.md) §2, [04](../04-architecture.md) §5). Ядро о проектах не знает (P10).
- `owner` — участник или группа участников: ссылка или список ссылок на `core/actor`; владелец — любой член списка (реестр — [14](14-trust.md), ADR-25).
- **Первый коммит пространства** (`init`, ADR-33) — самоустановление: первая ревизия `core/namespace` и участники её `owner` одним коммитом, сессия коммита — сессия одного из них; проверка `owner` пропускает его, пока проектного пространства в хранилище нет ([13](13-rules.md) §2). Дальше — обычный `owner`.
- `imports` — какие пространства проект читает; поле есть **только** в `core/namespace`, в конфигурации его нет. В v1 допустимы только `core` и `std`: импорт открывает пространство целиком, а зависеть от всей модели другого проекта нельзя. Связь проект→проект — через перенос блока в `std` (CT-12); публичное подмножество пространства — по триггеру второго проекта, которому нужен чужой блок. Писать можно только в своё пространство.
- `core` поставляется кодом, `std` — данными в пакете LATTICE. Их объекты попадают в хранилище проекта **импортом** (CT-08, CT-09): неизменные копии строк с тем же `id`, версией и хэшем, пакет замкнут по ссылкам тела и заголовка (ADR-4, [10](10-kernel.md) инвариант 5) и несёт **все ревизии** каждого объекта замыкания после имеющейся в хранилище — версия копии всегда следующая (LG-06 без исключений); пространство с тем же именем и другим `origin` отклоняется.

**Коммит обновления `std`** (при `init` и новой версии пакета, CT-10) — коммит входа `copy {rows, signer, key, intents?}` ([12](12-ledger.md) §2, T187, ADR-38):
- копии (`rows`) сохраняют заголовок поставщика: `by` — сессия пакета `std/release-<версия>`, та же `version`; правило `owner` проверяет копию против её собственного пространства `std` — его `core/namespace`, участники и сессии пришли в замыкании. Шаг 1 коммита заголовки строк входа `copy` не назначает ([12](12-ledger.md) §2), `type-latest` их не проверяет — исключение названо видом входа в реестре проверок ([13](13-rules.md) §2);
- коммит целиком (маркер, `key` = `std@<версия>#<хэш релиза>`) подписывает `signer` — сессия, которую хост открывает от имени владельца **проекта**: принять обновление — его акт; повтор с другим содержимым (другой план перезерновки) — отказ `differs` с адресом прежнего коммита ([12](12-ledger.md) LG-20), а не молчаливое «уже обновлено»;
- **подлинность `std` — подлинность пакета LATTICE** (CT-18): правило `owner` проверяет только согласованность копии с её собственным пространством `std` из того же замыкания, не происхождение — `origin` пространства `std` — публичная константа, а сессия пакета проходит `owner` самоссылкой. Происхождение держит хэш релиза — `sha256` канонической формы всех строк пакета `std` этой версии целиком, а не импортируемой в это хранилище части: хост сверяет его с константой своего кода (как хэш генезиса, KR-16) до коммита — не совпал, в том числе у пакета, пересобранного под той же версией, — отказ; принятый хэш остаётся в ключе коммита обновления;
- если новая версия `std` меняет зерно типа, в тот же коммит входит план перезерновки пространства проекта — намерения `merge` входа `copy` (`intents`), строки владельца проекта по обычному `owner`; без плана для пространств с коллизиями обновление не публикуется в этом хранилище ([11](11-identity-grain.md) GR-14, ADR-7).

### 2. Кто что пишет

Здесь — понятия владения и допусков; исполнитель модели прав — одна проекция замороженного ядра `authority.mayWrite` ([10](10-kernel.md) §7, ADR-40), её вызывает проверка `owner` ([13](13-rules.md) §2). Строка таблицы, допуск или исключение, которых нет в `mayWrite`, не действуют.

| Что | Кто | Правило |
|---|---|---|
| ревизии объектов пространства | владелец или допущенный (`core/grant`) | `owner` (hard) |
| типы и правила пространства | владелец | `owner` + допуск на `core/type` |
| управляющие факты: `core/grant`, `core/retire`, `core/deprecate` (и `core/alias`, [11](11-identity-grain.md)) | владелец пространства **цели** или допущенный на этот тип факта | `writers` типа факта, проверяет `owner` ([10](10-kernel.md) §7, ADR-6) |
| факты, открытые всем (`writers: any`): утверждения `core/assert`, подсказки `std/cue`, кандидаты `std/alias-candidate` | любой участник с доступом к хранилищу | факт живёт **в пространстве автора**, ссылается куда угодно |
| предложение ревизии | любой | событие `core/proposal`; ревизию пишет владелец |

- **Текущий управляющий факт** — последний по `seq` с этим ключом среди записей допущенных `writers` ([10](10-kernel.md) §7); допуск проверен при коммите — отзыв `core/grant` прежних записей не меняет. Факт стороннего писателя с тем же ключом (`retire`, `alias`, `member … false`) текущий не подменяет — правило `owner` его не пропускает.
- **Допуск** — факт `core/grant` `{of: {actor, namespace}, value: {create?: [типы], edit?: [типы], declare?: true}}`: `create` — создавать объекты типа, `edit` — писать ревизии чужих объектов типа, `declare` — быть декларантом (T119, ADR-25). Например, агентам WARRANT: `{create: ["std/need", "std/solution", "std/member", "std/link"]}` — создавать потребности и решения с составом, но не нормы и не состав доменов (`core/member`, [21](21-compose.md)); подсказки `std/cue` пишет любой. У типов `refs: follow` (нормы, знания) `edit` не действует: правка чужого — только через `core/proposal`, массово — пакетом предложений; отказ даёт `owner` при записи (CT-14 — внутри `mayWrite`). Допуск `declare` не-человеку отклоняется при записи (CT-13).
- **Смена владельца** — двусторонний акт (ADR-25) без исключений в проверке `owner`: старый владелец пишет `core/proposal` ревизии `core/namespace` с новым `owner`; новый отвечает `core/assert +1` на предложение; ревизию пишет старый владелец операцией `transfer`, которая без «+1» нового отказывает. До ревизии действует старый владелец. Ревизия `owner` в обход `transfer` (без «+1» нового на предложение) — находка lint. Восстановление при утрате — через хост, «Вне объёма».

Это и есть P4: **тело и управляющие факты — владелец, открытые всем факты — кто угодно.** Агент не может переписать норму, но может утверждать, что она пригодилась или нет, — и это меняет доверие, а не норму.

### 3. Публикация и версии

- Коммит владельца = публикация. Опубликованная ревизия неизменна (KR-03).
- Предложение: `core/proposal` `{target: ref, body, reason}` → владелец принимает или отклоняет. **Принятие** — ревизия цели + утверждение `core/assert {of: {target: proposal}, value: 1, reason}` с обязательным `reason`: что проверено. **Отклонение** — утверждение −1 на предложение.
- Три правила из концепции: **версия неизменна; новую выпускает только владелец; владелец ссылающегося объекта сам решает, когда переходить.**

### 4. Ссылки и ссылающиеся

| Политика типа (`refs`) | Что обязаны делать ссылки на его объекты | Типы |
|---|---|---|
| `pin` | быть закреплёнными `id@n` (правило `ref-policy`, hard) | способности, включая правило-способность `check` ([13](13-rules.md) RL-07); конвейеры, типы, правила; политики доверия (`std/policy`, CT-16) |
| `follow` | могут быть следующими `id` | знания, домены, термины, потребности |

- **Способности всегда закреплены.** Новая версия блока ничего не меняет у ссылающихся, пока их владельцы не перезакрепят ссылку. Подписки «@current» для исполняемых блоков нет — это та скрытая глобальная связь, от которой концепция защищается. Закреплена и реализация: рантайм отказывает, если код не совпадает с `impl.pins` ([13](13-rules.md) §3, T-2).
- **Знания могут следовать.** Решение ссылается на норму без версии; snapshot при выдаче закрепляет версии; изменение нормы делает snapshot `stale` — это видно, а не тихо.
- **Индекс ссылающихся** (T63, `referrers`) отвечает: где используется `X@3`, кто следует за `X`, какие версии в ходу — в пределах своего хранилища. Ссылающихся в других хранилищах поставщик не видит.

### 5. Жизненный цикл

| Событие | Как | Последствия |
|---|---|---|
| новая версия | ревизия владельца | закреплённые ссылающиеся — без изменений; следующие — видят новую; lint: «есть новая версия» для закреплённых |
| устаревание | факт `core/deprecate` `{object, replaced_by?}` | объект жив; LENS помечает, не понижает ([20](20-lens.md)); lint: «перейдите на …» |
| вывод из обращения | факт `core/retire` `{object: id}` | не живой; следующие — `broken`; LENS не выдаёт. Закреплённые ссылки на **данные** работают (строки неизменны); код исполняется только при совпадении `impl.pins` и без отзыва версии (CT-05) |
| отзыв версии (T174) | факт `core/retire` `{object: id@n}` | код ревизии `id@n` не исполняется (рантайм — отказ на старте); чтение `id@n` работает; остальные версии объекта живы |
| миграция | владелец ссылающихся объектов пишет новые ревизии с новыми закреплениями | `migrate --from X@3 --to X@4` запускает **владелец ссылающихся** в своём хранилище: готовит ревизии или предложения; то же тело под новой версией типа — новая ревизия ([12](12-ledger.md) §2, ADR-2). Поставщик публикует `core/deprecate {replaced_by}` и, для несовместимой версии, карту перехода; сам `migrate` не выполняет |

**Вывод старой версии способности** (ADR-15). В v1, пока на способность ссылается один проект, владелец выводит старую версию согласованным переходом: сам переводит ссылающихся на новую, затем отзывает старую — `core/retire` на `id@n`. Триггер пересмотра — второй проект, ссылающийся на способность: тогда строгий `pin` и вывод по политике — `retire` с датой, после неё закреплённые ссылки на выведенную реализацию — `broken` с подсказкой `replaced_by`.

### 6. Очередь владельца

Что ждёт решения владельца пространства (T185, CT-17) — считается из журнала, не хранится. Очередь толкует вердикты, кандидатов, пробелы и находки — знание run, identity, compose и rules, которые catalog по матрице ([04](../04-architecture.md) §2) не зовёт. Поэтому её собирает `cli/` (команды `explain <пространство>`, `lint`) из чистых функций доменов `pending(namespace, seq)` — каждая отвечает за свой вид; здесь — состав очереди и функция `pending` своего вида (предложения без ответа).

| Вид | Что ждёт | Откуда | `pending` — домен |
|---|---|---|---|
| вердикты, ждущие `pass` | вердикт принят, строки обучения не записаны — гейт отказал ([22](22-run.md) §6); «не выучится» — вердикты кортежа, который установленным кодом не прогнать | вердикты `purpose: verdict` с непустым выводом правил обучения, без коммита `learn`, с живым вызовом | [22](22-run.md) |
| кандидаты в алиас | в очереди (`budget`) и ждущие в журнале ([11](11-identity-grain.md) GR-17) | `std/alias-candidate` без `core/alias` и `std/distinct` | [11](11-identity-grain.md) |
| пробелы | `std/gap` (`absent`, `coverage`) по потребностям пространства ([21](21-compose.md) §5) | события `std/gap` | [21](21-compose.md) |
| находки стенда | «калибровка устарела», «перемерить той же настройкой» ([23](23-bench.md) BN-18) | события после `state` калибровки и засчитанного прогона | [23](23-bench.md) |
| находки `lint` | `soft`-находки правил владельцу | отчёт `lint` на `seq` | [13](13-rules.md) (`lint`) |
| предложения | `core/proposal` без ответа ±1 владельца (§3) | предложения без утверждения | этот домен |

По каждому виду — счёт и возраст старшего по `at`. `lattice explain <пространство>` показывает очередь целиком, `lint` — строкой сводки. Порогов нет: очередь видна, а не принуждается; владелец в отъезде — это видно по возрасту, а не по тишине.

## Операции

Глубина домена — в операциях с логикой: `update`, `migrate`, `transfer`, `setPolicy`. Остальное — **сборка строк** для входа коммита `author` ([12](12-ledger.md) §2): отдельного пути записи у них нет, право проверяет `owner` (`authority`).

| Операция с логикой | Вход → выход |
|---|---|
| `update(package, by)` | → вход `copy {rows, signer, key, intents?}` обновления `std` (§1): копии + план перезерновки, `key` = `std@<версия>#<хэш релиза>`; хэш сверен с константой кода до коммита |
| `migrate(from, to, by)` | → ревизии или предложения ссылающимся; запускает их владелец |
| `transfer(namespace, proposal, by)` | → ревизия `core/namespace` с `owner` из предложения; только от текущего владельца и при «+1» нового на предложение (§2) |
| `setPolicy(namespace, policy@n, by)` | → ревизия `core/namespace` с новой `policy`; цель не `std/policy` (или наследник) — отказ до коммита: иначе следующее `open()` отказало бы всему хранилищу ([12](12-ledger.md) LG-27, [14](14-trust.md) §4) |

| Сборка строк (`Draft[]` входа `author`) | Что собирает |
|---|---|
| `propose` / `accept` / `reject` | событие `core/proposal`; ревизия цели + утверждение ±1 на предложение |
| `grant(actor, namespace, {create?, edit?, declare?})` | факт `core/grant` |
| `deprecate(ref, replacedBy?)` / `retire(ref)` | факты (владелец пространства цели); `retire` на `id@n` — отзыв версии, на `id` — вывод объекта |

| Чтение | Вход → выход |
|---|---|
| `referrers(ref)` / `usage(id)` | → ссылающиеся по версиям в пределах хранилища (чтение раздела индекса `referrers`) |
| `pending(namespace, seq)` | → предложения без ответа владельца (§6); очередь целиком собирает `cli/` из `pending` доменов |

## Инварианты

1. Каждая строка коммита проходит `owner`: ревизию пишет владелец её пространства или допущенный, управляющий факт — допущенный `writers` его типа; копия импорта проверяется против своего пространства из замыкания.
2. `imports` задан только в `core/namespace` и в v1 содержит только `core`/`std`.
3. Копия импорта совпадает с оригиналом по `id`, версии и хэшу; пакет замкнут; другой `origin` при том же имени — отказ.
4. Ссылка на объект типа `refs: pin` закреплена `@n`.
5. Правка чужого объекта типа `refs: follow` — только через `core/proposal`.

## Решения

| ID | Решение | Почему |
|---|---|---|
| CT-01 | Пространство имён — объект с владельцем, импортами, политикой доверия; `imports` — только здесь, в v1 — только `core`/`std` | мультипроектность без знания ядра о проектах; `core`/`std` — конформист к опубликованному языку LATTICE, версии идут параллельно; совладение (shared kernel) между пространствами не допускается. v0.4 · ADR-28 · T-7 · Q-42 C-2, C-3 · Q-43 C-3 |

## Вне объёма

- Аутентификация участников — порт окружения (агент, CLI), не модель.
- Восстановление владения при утрате — через хост / адаптер; допущение: личность — заявление вызывающего, хост её не проверяет, но пишет `claimed_via` и `os_user` ([14](14-trust.md) «Вне объёма», ADR-25).
- Обмен утверждениями о `std`-блоках между проектами — в v1 доверие к общему блоку у каждого проекта своё.
- Публичное подмножество пространства и импорт проект→проект — по триггеру (CT-01, CT-12).
