# 15. catalog — пространства имён, владельцы, публикация, потребители

**Назначение.** Кто что может менять, как новая версия становится доступной и как это расходится по потребителям
без скрытого глобального изменения поведения.

**Зависит от:** [10-kernel](10-kernel.md), [11-identity-grain](11-identity-grain.md), [13-rules](13-rules.md).
**Используют:** все пишущие операции; adapters (проекты).

## Модель

### 1. Пространство имён и проект

```json
{ "id": "warrant/namespace", "type": "core/namespace@1",
  "body": { "name": "warrant", "owner": {"$ref": "warrant/ACT-maintainer"},
            "imports": ["core", "std"], "policy": {"$ref": "warrant/trust-policy"},
            "doc": "Нормы и агенты проекта WARRANT" } }
```

- Локальное имя `namespace` зарезервировано: объект пространства лежит в нём самом.
- **Проект** = пространство имён + хранилище + конфигурация `lattice.config.json` (адаптеры, конвейер, каталог
  данных). Ядро о проектах не знает (P10).
- `imports` — какие пространства проект читает. Писать можно только в своё.
- `core` поставляется кодом, `std` — данными в пакете LATTICE; при `init` и обновлении они дописываются в хранилище
  проекта только для чтения (сессия `std/release-<версия>`).

### 2. Кто что пишет

| Что | Кто | Правило |
|---|---|---|
| ревизии объектов пространства | владелец или допущенный (`core/grant`) | `owner` (hard) |
| типы и правила пространства | владелец | `owner` + допуск на `core/type` |
| факты и утверждения | любой участник с доступом к хранилищу | факт живёт **в пространстве автора**, ссылается куда угодно |
| предложение ревизии | любой | событие `core/proposal`; ревизию пишет владелец |

**Допуск** — факт `core/grant` `{of: {actor, namespace}, value: {types: ["std/need", "std/solution", "std/cue"]}}`:
например, агентам WARRANT разрешено создавать потребности и решения, но не нормы.

Это и есть P4: **тело говорит владелец, факты — кто угодно.** Агент не может переписать норму, но может утверждать,
что она пригодилась или нет, — и это меняет доверие, а не норму.

### 3. Публикация и версии

- Коммит владельца = публикация. Опубликованная ревизия неизменна (KR-03).
- Предложение: `core/proposal` `{target: ref, body, reason}` → владелец принимает (ревизия с `proposal` в теле
  или отдельным фактом) или отклоняет (утверждение −1 на предложение).
- Три правила из концепции: **версия неизменна; новую выпускает только владелец; потребитель сам решает, когда
  переходить.**

### 4. Ссылки и потребители

| Политика типа (`refs`) | Что обязаны делать ссылки на его объекты | Типы |
|---|---|---|
| `pin` | быть закреплёнными `id@n` (правило `ref-policy`, hard) | способности, конвейеры, типы, правила |
| `follow` | могут быть следующими `id` | знания, домены, термины, потребности |

- **Способности всегда закреплены.** Новая версия блока ничего не меняет у потребителей, пока они сами не
  перезакрепят ссылку. Подписки «@current» для исполняемых блоков нет — это та скрытая глобальная связь, от которой
  концепция защищается.
- **Знания могут следовать.** Решение ссылается на норму без версии; snapshot при выдаче закрепляет версии; изменение
  нормы делает snapshot `stale` — это видно, а не тихо.
- **Индекс потребителей** отвечает: где используется `X@3`, кто следует за `X`, какие версии в ходу.

### 5. Жизненный цикл

| Событие | Как | Последствия |
|---|---|---|
| новая версия | ревизия владельца | закреплённые потребители — без изменений; следующие — видят новую; lint: «есть новая версия» для закреплённых |
| устаревание | факт `core/deprecate` `{object, replaced_by?}` | объект жив; LENS понижает; lint: «перейдите на …» |
| вывод из обращения | факт `core/retire` `{object}` | не живой; закреплённые ссылки работают; следующие — `broken`; LENS не выдаёт |
| миграция | потребитель пишет новые ревизии с новыми закреплениями | инструмент `migrate --from X@3 --to X@4` готовит ревизии/предложения для каждого потребителя |

## Операции

| Операция | Вход → выход |
|---|---|
| `publish(rows, by)` | → коммит с правилом `owner` |
| `propose(target, body, by)` / `accept(proposal, by)` / `reject(proposal, by)` | → события и ревизии |
| `grant(actor, namespace, types, by)` | → факт `core/grant` |
| `deprecate(ref, replacedBy?, by)` / `retire(ref, by)` | → факты |
| `consumers(ref)` / `usage(id)` | → потребители по версиям |
| `migrate(from, to, by)` | → ревизии или предложения потребителям |

## Решения

| ID | Решение | Почему |
|---|---|---|
| CT-01 | Пространство имён — объект с владельцем, импортами, политикой доверия | мультипроектность без знания ядра о проектах |
| CT-02 | Проект читает свои и импортированные пространства, пишет только в своё | изоляция; общие блоки без копирования |
| CT-03 | Ревизии — владелец или допущенный; остальные — предложения | owner-controlled |
| CT-04 | Факты и утверждения живут в пространстве автора | любой может свидетельствовать, никто не переписывает чужое |
| CT-05 | Удаления нет; устаревание и вывод из обращения — факты; индекс потребителей | закреплённые ссылки вечны, видно, кто держит |
| CT-06 | Политика ссылок типа: способности — только `pin` | нет скрытого глобального изменения поведения |
| CT-07 | Миграцию делает потребитель; LATTICE распространяет версии, но не навязывает | концепция v0.2, правило 3 |
| CT-08 | `core` — код, `std` — данные пакета, дописываются в хранилище проекта | один механизм версий для библиотеки и проекта |

## Вопросы для grilling

1. **Хранилище на проект + общая `std`** ([12](12-ledger.md), вопрос 2) — общие блоки между проектами копируются строками при импорте или
   читаются из общего хранилища? Рекомендация: копируются неизменными строками (значения и ревизии совпадают по
   `id` и хэшу) — проект самодостаточен.
2. **Блок проекта → в библиотеку**: как способность из `warrant` становится общей? Рекомендация: новая сущность в
   `std` (или `lib.<имя>`) + `core/deprecate` старой с `replaced_by`; не перенос `id`.
3. **Декларант** — отдельная роль (человек, который вправе ставить `declared`, не будучи владельцем)?
   Рекомендация: да, через `core/grant` `{value: {declare: true}}`.
