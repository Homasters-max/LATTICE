# 11. identity & grain — идентичность, зерно, дубли, слияние

**Назначение.** Гарантировать P8: ни одного тихого схлопывания и ни одного тихого дубля. Определить, что значит
«та же самая сущность», и что происходит, когда это определение или тело объекта меняется.

**Зависит от:** [10-kernel](10-kernel.md). **Используют:** ledger (`resolve`, индекс `grain`), rules (`grain-unique`, `regrain-plan`), catalog, compose (потребности, решения), CLI и хост (загрузка, [30](30-adapters.md)).

## Главная идея

Identity и «одинаковость» — **разные вещи** (как `id()` и `==` в Python):

| | Identity (`id`) | Зерно (ключ зерна) |
|---|---|---|
| что | «это тот же объект во времени» | «это то же самое по смыслу владельца» |
| откуда | выдаётся один раз (ULID / внешнее имя) | вычисляется из тела по списку измерений типа |
| меняется | никогда | когда меняется тело или определение зерна |
| роль | ссылки, история, доверие | запрет дублей, «найди или создай» |

Поэтому изменение зерна **никогда не меняет identity**. Оно может только обнаружить, что две разные сущности теперь
выглядят одинаково. Что с ними делать, решает владелец явно.

## Модель

### 1. Зерно

```json
// тип
{ "id": "std/domain", "type": "core/type@1", "version": 2,
  "body": { "identity": "assigned", "mutable": true, "grain": ["name", "language"],
            "schema": { "required": ["name", "language", "code"] } } }

// сущность — в пространстве проекта
{ "id": "warrant/01J8…A", "type": "std/domain@2", "version": 1,
  "body": { "name": "lifecycle", "language": "ru", "code": "LCY" } }
```

- `grain` — пути в теле. Ключ зерна = `hash(id типа, [значения измерений по порядку grain])` (T26).
- Нет `grain` — тип не проверяет дубли по содержимому (только семантически, п. 6).
- Измерения `grain` — `required` в `schema` типа (правило `schema`, hard). Тип, у которого измерение не обязательно,
  получает от lint находку soft «пустое измерение»; отсутствующее измерение входит в ключ как отдельное значение
  `null`, не «равно любому».
- **Область уникальности** (`grain_scope`, T124, ADR-27) — пространство имён автора сущности: индекс `grain` — по
  `(namespace, тип, hash)` ([12](12-ledger.md)). `grain_scope: store` — одна сущность на всё хранилище; для
  справочников пространства `std` (единицы). Домен (`std/domain`, T75) — группа блоков проекта: область — пространство
  проекта, поэтому поля `project` у домена нет — его задаёт пространство.
- Ключ считается по **текущей** версии определения зерна у типа и хранится в индексе.

### 2. Значения — схлопываются автоматически и это правильно

Значение (`identity: content`) равно своему содержимому. Две записи с одинаковым содержимым — **один объект**
(интернирование, T29). Это не потеря данных: они одинаковы по определению. Повторная запись значения, которое
пространство уже держит, — no-op; значение, которое есть в хранилище, но пространство сессии его не держит, — шаг
коммита пишет держание `core/holds` ([10](10-kernel.md) §7). В обоих случаях тело одно, ссылки обеих сторон
указывают на один `#hash`.

### 3. Сущности — никогда не схлопываются сами

**Правило `grain-unique` (hard):** среди живых сущностей типа ключ зерна уникален в области зерна (п. 1). Три случая,
один механизм. Нарушение — одной формы во всех случаях: `{rule: "grain-unique", with: <id>, diff: [пути]}` (детали
оболочки нарушения `{row, rule, message}`, [13](13-rules.md) §2) — с кем
совпал ключ и какими путями тела (вне зерна) сущности различаются.

**Случай A — создание.** Новая сущность получает ключ, который уже есть в области → коммит отклонён с нарушением
`grain-unique`. Операция `ensure(type, body, by)` = «найди или создай» (как `sys.intern`): возвращает существующую
сущность вместо ошибки и её **не меняет** — расхождение тела показывает `differs: [пути]`. Гонку двух `ensure` одного
ключа закрывает CAS по хвосту журнала: шаги коммита, включая `grain-unique`, повторяются на дочитанном индексе
([12](12-ledger.md) §2, ADR-31); второй `ensure` того же ключа в одном
коммите получает строку первого. При `grain_scope: store` найденная сущность может быть из другого пространства
(единица `kg` из `std`).

**Случай B — владелец меняет тело одной сущности** (твой пример: убрал измерение у объекта):

```text
было:   D1 {name: lifecycle, language: ru}      D2 {name: lifecycle, language: null}
правка: D1 → {name: lifecycle, language: null}  ключ D1 == ключ D2
```

Новая версия D1 отклоняется (`grain-unique`, `with: D2`). Владелец выбирает одно:

| Выбор | Что происходит |
|---|---|
| **слить** | только если D1 и D2 в одном пространстве и у пишущего право на обе (ADR-6): коммит — версия D1 не пишется; факт `core/alias` {alias: D1, canonical: D2} — всё, что ссылалось на D1, разрешается в D2 |
| **различить** | оставить или добавить измерение, которое их различает |
| **отменить** | правка не делается |

**Случай C — владелец меняет определение зерна у типа** (убрал, добавил или переставил измерения `grain`):

1. Новая версия типа — это публикация. Перед коммитом ядро делает **перезерновку** (T33): пересчитывает ключи всех
   живых сущностей типа по новому `grain`.
2. **Отчёт о коллизиях:** наборы сущностей с одинаковым новым ключом в одной области, например
   `{lifecycle/ru, lifecycle/en}`.
3. Коммит новой версии типа проходит **только с планом**: для каждого набора — `merge` (канонический + алиасы),
   `distinguish` (вернуть измерение или задать другое) или отказ от изменения зерна. Правило `regrain-plan` (hard)
   — при любом изменении состава или порядка измерений: коллизий может не быть, но проверку проходит каждая смена.
4. План исполняется в том же коммите: версия типа + факты `core/alias` — всё или ничего.

**Смена зерна общего (`std`) типа** (ADR-7): сущности перезерновываются **по пространствам** — коллизии в каждом
пространстве разрешает план его владельца (ADR-6, ADR-25). Без плана для пространств с коллизиями новая версия типа
не публикуется в этом хранилище. Пока у `std` один потребитель, план согласуется напрямую; кто подписывает коммит
обновления `std` — [15](15-catalog.md).

### 4. Слияние — алиасы, а не переписывание

- Слияние = факт `core/alias` `{of: {alias: A, canonical: B}, value: true}`, ключ факта — `[alias]`. Пишет владелец
  пространства или допущенный (`writers`, ADR-6); это подтверждение, кандидат — отдельный тип (п. 6, ADR-8).
- A и B — в одном пространстве; B — живая сущность и сама не алиас (набор сливается звездой на одного
  канонического); канонический-алиас в плане — отказ.
- История A не переписывается. Ревизии A остаются; закреплённые ссылки `A@n` разрешаются в ревизии A.
- Следующие ссылки на A (`A` без версии) разрешаются в B. Индекс хранит карту алиасов в силе (цепочки сжимаются,
  циклы запрещены правилом `acyclic`).
- Факты о A (членства, утверждения, подсказки) при вычислении доверия и состава учитываются как факты о B. `merge`
  перепроверяет hard-правила этих фактов на разрешённом виде — в том же коммите (T-16).
- **Обратимо:** разделение (T32) — владелец пишет `core/alias {value: false}`; A снова живая, её факты снова её.
  Утверждение «−1» на факт алиаса влияет на доверие, но алиас не отменяет. Разделение проверяет `grain-unique`: ключ
  A, пока она была алиасом, оставался в индексе `grain`, коллизия → отказ или `distinguish`. Snapshot'ы, чьи ссылки
  разрешались через отменённый алиас, становятся `stale` ([12](12-ledger.md)); lint soft — «ссылка на бывший алиас».
- Канонический — по плану; по умолчанию — старейший: меньший `seq` первой ревизии (T-6). «Больше потребителей» —
  подсказка в отчёте о коллизиях, не умолчание.

### 5. Что с ревизиями, закреплёнными на старой версии типа

Ревизия сущности закрепляет `type@n`, по которому её проверяли. После новой версии типа старые ревизии **остаются
валидными по своей версии**. Для уникальности зерна используется ключ по текущему определению (п. 1) — поэтому
перезерновка проверяет все живые сущности сразу. Перевод ревизий на новую версию типа — новые версии сущностей
(по мере правки или пакетом), не условие публикации; то же тело под `type@n+1` — новая ревизия, не no-op (ADR-2;
перевод — `migrate`, [15](15-catalog.md)).

### 6. Семантические дубли

Разные ключи, один смысл («archive» и «архивация»). Ядро их не видит. Их ищет LENS ([20](20-lens.md)) — после
коммита, не внутри `ensure` (identity lens не импортирует, [04](../04-architecture.md) §2):

- после `ensure` и импорта хост вызывает операцию LENS `aliasCandidates(ids, by)`: `judge.verify("A и B — одно и то
  же?")` по карточкам кандидатов той же области, отдельным коммитом;
- выше порога → **кандидат в алиас** — факт `std/alias-candidate` (T123, ADR-8): ключ `[alias, canonical]`,
  `value: {p}` — балл `judge.verify` (версия judge — в `std/measurement` вызова `aliasCandidates`), `writers: any` —
  кандидат следующего писателя той же пары становится текущим; в силу не входит; индексы `aliases`, `grain` и
  `resolve` его не видят. Владелец подтверждает кандидата фактом `core/alias` — или отказывает фактом `std/distinct`;
- кандидат **открыт**, пока для пары нет `core/alias` в силе и нет `std/distinct {value: true}`; бюджет
  `candidates.budget` считает открытых кандидатов на владельца пространства цели (роль `alias`); `value: false` у
  кандидата нет — отказ пишется `std/distinct`;
- никакого автоматического слияния: балл решает только обратимое (ADR-13). Порог, бюджет на владельца, кластер как
  одно решение — политика кандидатов `core/trust-policy.candidates` (T142, [14](14-trust.md)); один механизм — для
  сущностей и потребностей ([21](21-compose.md)).

**Различие** (`std/distinct`, T81) — память отказов:

```json
{ "of": { "a": {"$ref": "warrant/01J8…A"}, "b": {"$ref": "warrant/01J8…C"} }, "value": true }
```

Пара симметрична: `a < b` по `id` (ядро нормализует); ключ — `[a, b]`; `writers` — те же, кто может написать
`core/alias` для этой пары. Политика кандидатов не предлагает пару повторно; `value: false` снимает отказ.

## Операции

| Операция | Вход → выход |
|---|---|
| `grainKey(type, body)` | → hex или `null` (нет `grain`) |
| `ensure(type, body, by)` | → `{id, created: bool, differs: [пути]}`; найденную не меняет |
| `regrain(typeRevision)` | → `{collisions: [[id…]], unaffected: n}` — по областям зерна |
| `merge(plan, by)` | → факты `core/alias` + перепроверка hard-правил затронутых фактов (в коммите) |
| `split(aliasFact, by)` | → факт `core/alias {value: false}` (в коммите, с проверкой `grain-unique`) |
| `resolve(ref)` | → ревизия (через алиасы в силе и последнюю версию) или `broken` |

## Инварианты

1. Среди живых сущностей типа ключи зерна уникальны в области зерна (пространство автора или `store`).
2. Ни одна операция не меняет `id` и не переписывает ревизии; `ensure` не меняет найденную сущность.
3. Граф алиасов ацикличен; у алиаса ровно один канонический — живой, не алиас, в том же пространстве.
4. Публикация изменённого зерна без полного плана невозможна.
5. Индексы и `resolve` видят только `core/alias` в силе; кандидат (`std/alias-candidate`) на них не влияет.

## Решения

| ID | Решение | Почему |
|---|---|---|
| GR-01 | Значения интернируются автоматически; значение, которое пространство не держит, — `core/holds`, не no-op | равны по определению — схлопывание корректно. v0.4 · N-21 · 10-kernel §7 |
| GR-02 | Уникальность ключа зерна среди живых сущностей — правило `hard` в области зерна: пространство автора, индекс `(namespace, тип, hash)`; `grain_scope: store` — справочники `std`; `ensure` = найди или создай | нет тихих дублей; чужое пространство не занимает ключ владельца. v0.4 · ADR-27 · Q-15 C-3 |
| GR-03 | Смена `grain` у типа (состав или порядок) = новая версия типа + перезерновка + обязательный план в том же коммите | нет тихого схлопывания при смене гранулярности. v0.4 · Q-16 C-2 |
| GR-04 | Правка тела, дающая существующий ключ, отклоняется; выход — слить, различить или отменить; нарушение — `{rule: "grain-unique", with, diff}` во всех случаях | тот же механизм для одной сущности; одна форма ответа. v0.4 · Q-17 C-3 |
| GR-05 | Слияние — факты `core/alias` владельца, обратимо (`value: false`), история не переписывается; `merge` и `split` проходят те же hard-проверки, что и любой писатель | ссылки и доверие сохраняются, ошибку можно откатить. v0.4 · ADR-6 · T-16 · Q-18 C-2, C-3 · N-16 |
| GR-06 | Семантические дубли — только кандидаты `std/alias-candidate` через LENS (операция `aliasCandidates`, её вызывает хост после коммита); в силу — после подтверждения владельцем (`core/alias`) | похожесть — не основание для слияния (P5); кандидат не снимает действующий алиас. v0.4 · ADR-8 · Q-19 C-3 · Q-11-3 |
| GR-07 | Канонический при слиянии — по плану; по умолчанию старейший — меньший `seq` первой ревизии | предсказуемо; ULID — время машины. v0.4 · T-6 · Q-20 C-1 |
| GR-08 | Ключ зерна — по текущему определению зерна у типа, не по версии, закреплённой в ревизии | иначе уникальность нельзя проверить после смены зерна. v0.4 · Q-11-1 |
| GR-09 | Измерения `grain` — `required`; необязательное измерение — находка lint soft, отсутствующее входит в ключ как `null` | «равно любому» делает ключ неоднозначным. v0.4 · Q-15 C-4 · Q-11-2 |
| GR-10 | Слияние — только в одном пространстве, с правом на обе сущности; канонический — живой и не алиас, набор — звезда; связь между проектами — `core/deprecate` ([15](15-catalog.md)) | алиас — управляющий факт владельца пространства. v0.4 · T-1 · Q-17 C-2 · Q-20 C-2 · Q-11-4 |
| GR-11 | `ensure` не меняет найденную сущность: ответ `{id, created, differs}`; гонка — CAS по хвосту журнала ([12](12-ledger.md) §2) | без тихой правки тела (P8). v0.4 · T-9 · ADR-31 · Q-15 C-2 |
| GR-12 | Отказ по кандидату — факт `std/distinct` `{of: {a, b}}`, `a < b`, ключ `[a, b]`; политика кандидатов — `core/trust-policy.candidates` | память отказов: пара не предлагается повторно. v0.4 · T-8 · ADR-13 · Q-19 C-2 |
| GR-13 | Домен (`std/domain`) — в пространстве проекта, область зерна — пространство; поля `project` нет | пространство уже задаёт проект; два источника одной правды. v0.4 · ADR-27 · N-11 |
| GR-14 | Смена зерна `std`-типа — по пространствам, план — у владельца каждого; без плана версия не публикуется в хранилище | чужие сущности меняет только их владелец. v0.4 · ADR-7 · Q-16 C-3 |
| GR-15 | `split` помечает `stale` snapshot'ы через отменённый алиас; lint — «ссылка на бывший алиас» | разделение видно тем, кто на него опирался. v0.4 · Q-18 C-4 |
