# 11. identity & grain — идентичность, зерно, дубли, слияние

**Назначение.** Гарантировать P8: ни одного тихого схлопывания и ни одного тихого дубля. Определить, что значит
«та же самая сущность», и что происходит, когда это определение или тело объекта меняется.

**Зависит от:** [10-kernel](10-kernel.md). **Используют:** catalog, compose (потребности, решения), adapters (импорт).

## Главная идея

Identity и «одинаковость» — **разные вещи** (как `id()` и `==` в Python):

| | Identity (`id`) | Зерно (ключ зерна) |
|---|---|---|
| что | «это тот же объект во времени» | «это то же самое по смыслу владельца» |
| откуда | выдаётся один раз (ULID / внешнее имя) | вычисляется из тела по списку измерений типа |
| меняется | никогда | когда меняется тело или определение зерна |
| роль | ссылки, история, доверие | запрет дублей, «найди или создай» |

Поэтому изменение зерна **никогда не меняет identity**. Оно может только обнаружить, что две разные сущности теперь
выглядят одинаково. Что с ними делать, решает владелец явно.

## Модель

### 1. Зерно

```json
// тип
{ "id": "std/domain", "type": "core/type@1", "version": 2,
  "body": { "identity": "assigned", "mutable": true, "grain": ["project", "name", "language"] } }

// сущность
{ "id": "warrant/01J8…A", "type": "std/domain@2", "version": 1,
  "body": { "project": "warrant", "name": "lifecycle", "language": "ru", "code": "LCY" } }
```

- `grain` — пути в теле. Ключ зерна = `hash(id типа, [значения измерений по порядку grain])`.
- Нет `grain` — тип не проверяет дубли по содержимому (только семантически, п. 6).
- Ключ считается по **текущей** версии определения зерна у типа и хранится в индексе.

### 2. Значения — схлопываются автоматически и это правильно

Значение (`identity: content`) равно своему содержимому. Две записи с одинаковым содержимым — **один объект**
(интернирование, T29). Это не потеря данных: они одинаковы по определению. Новая запись значения, которое уже есть, —
no-op, и ссылки обеих сторон указывают на один `#hash`.

### 3. Сущности — никогда не схлопываются сами

**Правило `grain-unique` (hard):** среди живых сущностей типа ключ зерна уникален. Три случая, один механизм.

**Случай A — создание.** Новая сущность получает ключ, который уже есть → коммит отклонён с ответом
`duplicate_of: <id>`. Операция `ensure(type, body)` = «найди или создай»: возвращает существующую сущность вместо
ошибки (как `sys.intern`).

**Случай B — владелец меняет тело одной сущности** (твой пример: убрал измерение у объекта):

```text
было:   D1 {name: lifecycle, language: ru}      D2 {name: lifecycle}      (language у D2 не задан)
правка: D1 → {name: lifecycle}                  ключ D1 == ключ D2
```

Новая версия D1 отклоняется (`collides_with: D2`). Владелец выбирает одно:

| Выбор | Что происходит |
|---|---|
| **слить** | коммит: версия D1 не пишется; факт `core/alias` {alias: D1, canonical: D2} — всё, что ссылалось на D1, разрешается в D2 |
| **различить** | оставить или добавить измерение, которое их различает |
| **отменить** | правка не делается |

**Случай C — владелец меняет определение зерна у типа** (убрал измерение `language` из `grain`):

1. Новая версия типа — это публикация. Перед коммитом ядро делает **перезерновку** (T33): пересчитывает ключи всех
   живых сущностей типа по новому `grain`.
2. **Отчёт о коллизиях:** наборы сущностей с одинаковым новым ключом, например `{lifecycle/ru, lifecycle/en}`.
3. Коммит новой версии типа проходит **только с планом**: для каждого набора — `merge` (канонический + алиасы),
   `distinguish` (вернуть измерение или задать другое) или отказ от изменения зерна. Правило `regrain-plan` (hard).
4. План исполняется в том же коммите: версия типа + факты `core/alias` — всё или ничего.

Расширение зерна (добавили измерение) коллизий не создаёт; сужение (убрали) — может.

### 4. Слияние — алиасы, а не переписывание

- Слияние = факт `core/alias` `{of: {alias: A, canonical: B}, value: true}`, ключ факта — `[alias]`.
- История A не переписывается. Ревизии A остаются; закреплённые ссылки `A@n` разрешаются в ревизии A.
- Следующие ссылки на A (`A` без версии) разрешаются в B. Индекс хранит карту алиасов (цепочки сжимаются, циклы
  запрещены правилом `acyclic`).
- Факты о A (членства, утверждения, подсказки) при вычислении доверия и состава учитываются как факты о B.
- **Обратимо:** разделение (T32) — утверждение `−1` на факт алиаса или новый факт с `value: false`; A снова живая,
  её факты снова её.
- Канонический — по плану; по умолчанию — старейшая (меньший ULID) или та, у которой больше потребителей.

### 5. Что с ревизиями, закреплёнными на старой версии типа

Ревизия сущности закрепляет `type@n`, по которому её проверяли. После новой версии типа старые ревизии **остаются
валидными по своей версии**. Для уникальности зерна используется ключ по текущему определению (п. 1) — поэтому
перезерновка проверяет все живые сущности сразу. Перевод ревизий на новую версию типа — новые версии сущностей
(по мере правки или пакетом), не условие публикации.

### 6. Семантические дубли

Разные ключи, один смысл («archive» и «архивация»). Ядро их не видит. Их ищет LENS:

- при `ensure` и импорте: `judge.verify("A и B — одно и то же?")` по карточкам кандидатов той же области;
- выше порога → **кандидат в алиас**: факт `core/alias` с основанием `inferred` (автор — LLM или машина), в силу не
  входит, пока доверие не достигнет `declared` (владелец) — правило типа `core/alias`;
- никакого автоматического слияния.

## Операции

| Операция | Вход → выход |
|---|---|
| `grainKey(type, body)` | → hex или `null` (нет `grain`) |
| `ensure(type, body, by)` | → `{id, created: bool}` |
| `regrain(typeRevision)` | → `{collisions: [[id…]], unaffected: n}` |
| `merge(plan, by)` | → факты `core/alias` (в коммите) |
| `split(aliasFact, by)` | → утверждение `−1` |
| `resolve(ref)` | → ревизия (через алиасы и последнюю версию) или `broken` |

## Инварианты

1. Среди живых сущностей типа ключи зерна уникальны.
2. Ни одна операция не меняет `id` и не переписывает ревизии.
3. Граф алиасов ацикличен; у алиаса ровно один канонический.
4. Публикация сужающего зерна без полного плана невозможна.

## Решения

| ID | Решение | Почему |
|---|---|---|
| GR-01 | Значения интернируются автоматически | равны по определению — схлопывание корректно |
| GR-02 | Уникальность ключа зерна среди живых сущностей — правило `hard`; `ensure` = найди или создай | нет тихих дублей |
| GR-03 | Смена `grain` у типа = новая версия типа + перезерновка + обязательный план в том же коммите | нет тихого схлопывания при смене гранулярности |
| GR-04 | Правка тела, дающая существующий ключ, отклоняется; выход — слить, различить или отменить | тот же механизм для одной сущности |
| GR-05 | Слияние — факты `core/alias`, обратимо, история не переписывается | ссылки и доверие сохраняются, ошибку можно откатить |
| GR-06 | Семантические дубли — только кандидаты в алиас через LENS; в силу — после `declared` | похожесть — не основание для слияния (P5) |
| GR-07 | Канонический при слиянии — по плану; по умолчанию старейший | предсказуемо |

## Вопросы для grilling

1. **Ключ по текущему определению зерна** (п. 5) или по версии типа, закреплённой в каждой ревизии? Рекомендация: по
   текущему — иначе уникальность нельзя проверить после смены зерна.
2. **Пустое измерение** (`language` не задан) — равно любому значению или отдельное значение `null`? Рекомендация:
   отдельное значение `null`; «равно любому» делает ключ неоднозначным.
3. **Кандидат в алиас от LENS** — факт в журнале сразу (с основанием `inferred`) или только находка lint?
   Рекомендация: факт — так его увидят и подтвердят другие сессии.
4. **Слияние через границу пространств имён** (A в `warrant`, B в `std`)? Рекомендация: запрещено в первой версии;
   связь между проектами — `core/deprecate` с `replaced_by`.
