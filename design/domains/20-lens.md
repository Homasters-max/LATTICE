# 20. lens — поиск кандидатов

**Назначение.** По потребности вернуть 5–20 кандидатов из LATTICE с баллами, причинами и доверием — дёшево и
быстро. LENS **не выбирает** и **не разрешает действие** (P5): выбирает Composer.

**Зависит от:** kernel, ledger, trust; порт `judge` ([30](30-adapters.md)). **Используют:** compose, run.

## Модель

### 1. Карточка — то, что видит judge

Judge видит малую часть блока (замер черновиков: заголовок и первый абзац — 2,5 % текста документа). Поэтому поиск
идёт не по блокам, а по **карточкам** (T71):

```json
{ "id": "#9b1e02c4d7aa…", "type": "std/card@1",
  "body": { "of": {"$ref": "warrant/REQ-VER-007@4"},
            "title": "Waiver спасает только FAIL",
            "summary": "Waiver применяется к проверке со статусом FAIL; BLOCKED не снимает…",
            "cues": ["waiver", "исключение из проверки", "override check"] } }
```

- Карточка — **значение**: вычисляется шаблоном типа блока (`type.card`: какие поля тела → `title`, `summary`) +
  подсказки (`std/cue`) с основанием ≥ `observed`. Одинаковое содержимое — одна карточка; изменился блок или
  подсказки → новая карточка, старая оценка не переиспользуется.
- Текст карточки — из тела блока. Если `summary` написала LLM, это основание ревизии блока (`inferred`), а не
  свойство карточки.

### 2. Пул — что оценивается

- **Пул** (T77) = snapshot карточек живых блоков области: члены домена (`core/member`), не выведенные из
  обращения.
- Размер ≤ `pool_max` (по умолчанию 200) — оценивается весь; больше — предварительный отбор top-N по BM25.
- Snapshot пула пишется в оценку: на каком составе получены баллы.

### 3. Стадии LENS

Каждая стадия — способность `std/stage.*` с контрактом `ctx → ctx` ([22](22-run.md)); порядок и параметры задаёт
конвейер (объект в LATTICE).

| Стадия | Что делает | Результат в `ctx` |
|---|---|---|
| `normalize` | регистр, ё/е, пробелы, концевая пунктуация — только обратимые для смысла правила | `need.norm` |
| `route` | область не задана → `judge.choose` по описаниям доменов (+ словарь в `state`); два домена выше порога → сигнал составной задачи | `need.scope` |
| `id-lookup` | явные ID блоков в тексте (`REQ-…`, `ADR-…`) → прямые кандидаты | `candidates[]` с причиной `id` |
| `lexicon` | подсказки терминов → id терминов (для ключа потребности) и буст блокам, связанным с термином | `need.terms`, `boosts` |
| `pool` | собрать пул области, отрисовать карточки | `pool` (snapshot) |
| `score.bm25` | лексический балл по карточкам | `scores.bm25` |
| `score.judge` | `judge.score(state = словарь + описание области, query = потребность, items = карточки)` | `scores.judge`, событие оценки |
| `fuse` | слияние: `linear` (judge + 0,3 · bm25/max, по умолчанию) или `rrf` | `scores.fused` |
| `trust` | выведенные — убрать; устаревшие — понизить; пометки `inferred` / `contested` | `candidates[].trust` |
| `threshold` | max(fused) < `no_match` (предварительно 0,6) → кандидатов нет | `need.outcome = no-match` |
| `cut` | top-K (по умолчанию 20) с причинами (`trace`: какая стадия дала вклад) | `candidates[]` |

Стадии `recall` (повтор решения) и `select` (выбор) — в [21-compose](21-compose.md): они про потребности и решения.

### 4. Judge — три вопроса

| Вызов | Где используется | Выход |
|---|---|---|
| `score(state, query, items)` | релевантность карточек потребности | `{id: p}` |
| `verify(state, statement)` | «потребность A — та же, что B?»; «блок A и блок B — одно?» (GR-06) | `p` |
| `choose(state, query, options)` | маршрутизация по доменам | распределение, уверенность |

- `state` — один раз на запрос (словарь области, описание): токены не растут с числом вопросов.
- Вопросы атомарные; композиция — в коде стадий (принцип технологии оценки).
- Балл и уверенность — вход для порогов и порядка, не доверие (TR-06).

### 5. Кэш оценок

Ключ: `(адаптер, модель, prompt_hash, state_hash, need.norm, card id)` → балл. Смена пула дооценивает только новые
карточки. Кэш — часть адаптера judge; источник истины — события `std/measurement` в журнале.

### 6. Выход LENS (контракт для compose)

```json
{ "need": "…", "scope": "warrant/domain.lifecycle",
  "candidates": [
    { "ref": "warrant/REQ-VER-007@4", "card": "#9b1e…", "scores": {"judge": 0.91, "bm25": 0.40, "fused": 1.03},
      "trust": {"basis": "derived", "epistemic": "settled"}, "why": ["judge", "lexicon:waiver"] } ],
  "outcome": "candidates | no-match", "measurement": "warrant/MEA-01J8…" }
```

## Решения

| ID | Решение | Почему |
|---|---|---|
| LN-01 | Поиск по карточкам (значениям), а не по сырым блокам | judge видит мало; карточка — то, что он видит, и она кэшируется по хэшу |
| LN-02 | Подсказки ≥ `observed` входят в карточку; обучение поиска — через подсказки | один механизм алиасов, защищён доверием |
| LN-03 | Стадии — способности, конвейер — объект LATTICE | самоописание (P9), замена стадии — новая версия конвейера со стендом |
| LN-04 | Judge — порт с тремя вызовами; `state` — один раз на запрос | заменяемая технология; −42 % токенов (замер черновиков) |
| LN-05 | Гибрид judge + BM25, слияние `linear` по умолчанию | BM25 бесплатен и помогает на терминах; linear даёт понятный балл |
| LN-06 | Доверие — пометка и фильтр, не множитель | порядок решает стенд, политика явная |
| LN-07 | Порог «нет ответа» — параметр стадии, калибруется стендом | пустышки должны давать отказ |
| LN-08 | Каждая оценка — событие с snapshot'ом пула | аудит: на каком составе получены баллы |

## Вопросы для grilling

1. **Маршрутизация `route`** через `judge.choose` или по терминам словаря? Рекомендация: область обычно задаёт
   вызывающий (Change, домен задачи); `route` — запасной путь: сначала термины, при неоднозначности — `choose`.
2. **K для Composer** — 20 или меньше? Рекомендация: 20 для первого прогона, по стенду — сколько нужно для
   «эталон в выдаче» ≥ 0,95.
3. **Карточка для способностей** — те же поля? Рекомендация: да + строка контракта (`вход → выход`) в `summary`.

## Вне объёма

- Эмбеддинги и векторные индексы — не сравнивались; добавляются как ещё одна стадия `score.*`, если стенд покажет
  пользу.
