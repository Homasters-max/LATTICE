# 20. lens — поиск кандидатов

**Назначение.** По потребности вернуть 5–20 кандидатов из LATTICE с баллами, причинами и доверием — дёшево и быстро. LENS **не выбирает** и **не разрешает действие** (P5): выбирает Composer.

**Зависит от:** [10-kernel](10-kernel.md) (виды объектов, поле типа `card`), [12-ledger](12-ledger.md) (журнал, сегменты), [13-rules](13-rules.md) (способности, `reads`/`writes`, `impl.pins`), [14-trust](14-trust.md) (`trust()`, `policy.lens`), [15-catalog](15-catalog.md) (живость, устаревание, индекс ссылающихся); контракт стадий и `Ctx` — [22](22-run.md). Порт `judge` определяет этот домен (ADR-24); реализации — [30](30-adapters.md).

**Используют:** adapters (реализации `judge`), compose (кандидаты, `judge.verify`), хост (`aliasCandidates` после `ensure` и импорта, [11](11-identity-grain.md) §6), run (стадии), bench (метрики поиска).

## Модель

### 1. Карточка — то, что оценивается

Поиск идёт не по блокам, а по **карточкам** (`std/card`, T71): карточка — стабильная проекция `блока@n`, значение, адресуемое по содержимому; оценка кэшируется по её хэшу (LN-01). Сколько текста видит оценщик — параметр адаптера: у `judge-jev` в замере черновиков — заголовок и первый абзац, 2,5 % текста документа.

```json
{ "id": "#9b1e02c4d7aa…", "type": "std/card@1",
  "body": { "of": {"$ref": "warrant/REQ-VER-007@4"},
            "title": "Waiver спасает только FAIL",
            "summary": "Waiver применяется к проверке со статусом FAIL; BLOCKED не снимает…",
            "cues": ["waiver", "исключение из проверки", "override check"] } }
```

- Тело: `of` — закреплённая ссылка на ревизию блока; `title`, `summary` — отрисовка шаблона типа; `cues` — тексты подсказок. Одинаковое содержимое — одна карточка; изменился блок или подсказки → новая карточка, старая оценка не переиспользуется.
- **Шаблон** — поле типа `card` ([10](10-kernel.md) §6): `{title: "<путь тела>", summary: ["<пути>"]}` или закреплённая ссылка на тип, чей шаблон взять (`{"$ref": "std/knowledge@1"}`). Отрисовка: строка — как есть, список — через запятую, ссылка — `id@n`, отсутствующий путь пропускается. Наследник по `extends` шаблон не наследует — заимствует ссылкой (ADR-12). Блок — объект, у типа которого есть `card` (T66).
- **Способности** — те же поля: стандартный шаблон `std/capability` — `{title: "title", summary: ["input", "output", "reads", "writes"]}`, строка контракта без особого случая (LN-09).
- **Подсказки в карточке** — `std/cue` ([21](21-compose.md)) на **эту ревизию** блока, в силе — `inForce(cue)` ([14](14-trust.md) «Операции», ADR-47; у `std/cue` — `inForce: {basis: observed}`): порог LENS не выводит сам; не больше `cues_max` — по убыванию `support.plus`, при равенстве — по тексту. Подсказки прежней ревизии в карточку новой не переходят: они уходят в `recheck` ([22](22-run.md)) и входят снова после подтверждения (LN-10). Подтверждение считает доверие по группам независимости (ADR-26) и свойствам сессий `classify` ([14](14-trust.md) §1, ADR-40): сессии одной группы — один голос, сессии стенда не подтверждают — своего списка `purpose` у LENS нет.
- Текст карточки — из тела блока. Поля, написанные LLM, в тело ревизии другого автора не входят ([14](14-trust.md) TR-09: `summary` — отдельный факт автора `agent`); блок, написанный LLM целиком, — ревизия с основанием `inferred`. Достаточность карточки меряет стенд: базовая линия «по полному тексту блока» и `hit@3` по виду блока — [23](23-bench.md), [01](../01-first-run.md).

### 2. Типы знаний и словаря

| Тип | Вид | Тело | Зерно | Карточка |
|---|---|---|---|---|
| `std/knowledge` (T67) | сущность | `{title, summary, refs?, text_hash?}` — `refs`: документ, код, тесты; `text_hash` — хэш полного текста блока от `load()` (T181, ADR-36), в карточку не входит | — | `{title: "title", summary: ["summary"]}` |
| `std/term` (T73) | сущность | `{scope: ref std/domain, label, doc?}` | `[scope, label]` | нет — термин не блок |

- Типы проектов расширяют `std/knowledge` (`warrant/norm`, [30](30-adapters.md)); шаблон — ссылкой.
- Синонимы термина — подсказки `std/cue` с целью `term` ([21](21-compose.md)). Термины области — словарь (lexicon, T74): один раз на запрос уходит в judge как `state`.

### 3. Пул — что оценивается

**Пул** (T77) — значение `std/pool@1` `{scope, cards: [{"$ref": "#…"}]}`: карточки блоков области — членов домена (`core/member`), у которых правило выдачи `standing(target)` не `excluded` (жив, не выведен из обращения, не в `policy.lens.exclude` — [14](14-trust.md) «Операции», TR-15), — до judge, чтобы не платить за оценку того, что всё равно не выдаётся.

- Размер ≤ `pool_max` (по умолчанию 200) — оценивается весь; больше — предварительный отбор top-N по BM25. Блоки из буста (§4, `lexicon`) и кандидаты по `id` входят в пул в обход отбора. Полноту отбора меряет стенд (`pool-recall`, [23](23-bench.md)).
- Пул и карточки — значения в основном журнале: пишутся один раз, повторные оценки ссылаются на хэш ([12](12-ledger.md) §1 — то, на что ссылается трасса, не истекает).

### 4. Стадии LENS

Каждая стадия — способность `std/stage.<имя>` ([13](13-rules.md) §3): сигнатура `Stage` — [22](22-run.md) §2, `reads`/`writes` — пути `Ctx`, код закреплён `impl.pins`. Порядок и параметры задаёт конвейер (объект в LATTICE); конвейер v1 — линейный, без условий (Ф-5): стадия, которой нечего делать, пропускает потребность. Пути ниже — внутри `needs[]`.

| Стадия | Что делает | `reads` | `writes` |
|---|---|---|---|
| `normalize` | регистр, ё/е, пробелы, концевая пунктуация — только обратимые для смысла правила | `text` | `norm` |
| `route` | область не задана вызывающим → сначала термины словаря, при неоднозначности `judge.choose` по описаниям доменов; два домена выше порога → находка «составная задача» (сигнал, не ветвление) | `norm`, `scope` | `scope`, `findings` |
| `id-lookup` | явные ID блоков в тексте (`REQ-…`, `ADR-…`) → прямые кандидаты с причиной `id` | `text` | `candidates` |
| `lexicon` | подсказки терминов → id терминов (ключ потребности, [21](21-compose.md)); **буст** — блоки, ссылающиеся на термин (индекс ссылающихся, [15](15-catalog.md) §4) | `norm`, `scope` | `terms`, `boosts` |
| `pool` | собрать пул (§3), отрисовать карточки; параметры `pool_max`, `cues_max` | `scope`, `norm`, `boosts`, `candidates` | `pool`, `rows` (значения `std/pool`, `std/card`) |
| `bm25` | лексический балл по карточкам — адаптер шва `Scorer` (ниже) | `norm`, `pool` | `scores.bm25` |
| `bm25.doc` | базовая линия стенда: BM25 по документам целиком через `source`, кандидаты — блоки документа в порядке ранга документа; без `judge` ([23](23-bench.md) BN-15, LN-16) | `norm`, `scope` | `candidates`, `outcome` |
| `judge` | `judge.score(state = словарь + описание области, query = потребность, items = карточки)` → событие `std/measurement` (§6) — адаптер шва `Scorer` | `norm`, `terms`, `pool` | `scores.judge`, `measurement` (ссылка), `rows` (`std/measurement`) |
| `fuse` | **превращает баллы пула в `candidates`** — единственная стадия, которая это делает: порядок `linear` (judge + 0,3 · bm25/max, ADR-16) или `rrf`; кандидаты по `id` — впереди | `scores`, `candidates` | `scores.fused`, `candidates` |
| `trust` | `trust()` каждого кандидата; пометки `marks` по `policy.lens.mark` и устаревание `deprecated {replaced_by}`; балл не меняет | `candidates` | `candidates` |
| `threshold` | `max(scores.judge)` < `no_match` и нет кандидатов по `id` → кандидатов нет | `scores.judge`, `candidates` | `outcome` |
| `cut` | top-K (по умолчанию 20) с причинами `why` (какая стадия дала вклад) | `candidates` | `candidates` |

- **Буст балл не меняет** (LN-11): он гарантирует блоку место в пуле и даёт причину `lexicon:<термин>`; вес буста в `fuse` — кандидат сравнения на стенде, как `rrf`.
- **Шов `Scorer`** (T199, ADR-45) — оценщик пула: `score(pool, norm, deps) → Record<Id, number>` в `scores.<имя>`; адаптеры — стадии `bm25` и `judge`, эмбеддинги — ещё один адаптер («Вне объёма»). Слияние баллов в кандидатов — только `fuse`: новый оценщик не трогает порядок и порог.
- **Порог «нет ответа»** (T91) читает балл judge, не `fused`: `fused` — только порядок, не [0,1] (ADR-13, ADR-16). Параметр стадии `no_match` — калиброванный порог `CalibratedThreshold {value, calibrated_for, call: score, onMismatch: refuse}` (T198, [13](13-rules.md) §3, ADR-45): `calibrated_for {adapter, model, prompt_hash, bench}` (T136) — под какую версию judge и каким прогоном (его `state`) подобран порог; подбор — сеткой на `dev` по обеим ошибкам (ложный отказ, ложный ответ), проверка — один раз на `test` ([23](23-bench.md) §4 п. 8). Способность `threshold` объявляет `no_match` в `calibrated`. Порог — параметр конвейера проекта (`<пространство>/pipeline.solve`, [22](22-run.md) §1): калибровка пишет его ревизию. Рантайм отказывает, если `calibrated_for` расходится с judge из `setup` — обобщённая сверка по `call`, не по имени стадии ([22](22-run.md) §3, ADR-28). Без `calibrated_for` стадия `no-match` не выносит: кандидаты идут дальше, в трассе — `threshold: uncalibrated`; отказать может `select` (LN-07).
- Стадии `recall` (повтор решения) и `select` (выбор) — в [21-compose](21-compose.md): они про потребности и решения.

### 5. Порт `judge` — три вопроса

```ts
interface Judge {
  score(r: { state: Json; query: string; items: { id: Id; text: string }[] }): Promise<Scored>
  verify(r: { state: Json; pairs: { a: string; b: string }[] }): Promise<{ p: number[]; meta: Meta }>   // «то же ли» на пару
  choose(r: { state: Json; query: string; options: { id: Id; text: string }[] }): Promise<Chosen>
  describe(): Ident                    // adapter, model, prompts: {score, verify, choose} — [22](22-run.md) §3
}
type Scored = { scores: Record<Id, number>; meta: Meta }
type Chosen = { p: Record<Id, number>; meta: Meta }
```

| Вызов | Где используется | Выход |
|---|---|---|
| `score` | релевантность карточек потребности | балл на карточку |
| `verify` | «то же ли»: «потребность A — та же, что B?» ([21](21-compose.md)); «блок A и блок B — одно?» ([11](11-identity-grain.md) GR-06) | `p` на пару |
| `choose` | маршрутизация по доменам (`route`) | распределение по вариантам |

- **Балл на каждую карточку** (LN-18): ключи `scores` — ровно `items.id` запроса; недостающий или лишний ключ — ошибка стадии, а не «балла нет»: иначе таймаут части вопросов молча убирал карточку из `max` и сбой адаптера был неотличим от «нужного нет». Проверяет обёртка `Recording` над портом ([22](22-run.md) §3, ADR-44) — у живого, фиктивного и записанного адаптера (что обёртка делает над записанным — там же); пункт контрактного набора `judge` ([30](30-adapters.md) инв. 2).
- `Meta` — сводка ответа порта, общая с `composer` ([22](22-run.md), T135): адаптер, модель, цена, время, токены.
- `state` — один раз на запрос (словарь области, описание): стабильный префикс для кэша префикса поставщика и пакетной обработки ([30](30-adapters.md) §5); токены не растут с числом вопросов (LN-04).
- Вопросы атомарные; композиция — в коде стадий. Текст вопроса — шаблон адаптера, не данные `std`: его идентичность — `prompt_hash` в `describe()` и кортеже исполнения ([22](22-run.md) §1); данные `std` — промпты стадий Composer в `params` конвейера ([04](../04-architecture.md) §1).
- **Граница judge** (LN-17, P13, ADR-37): judge отвечает только о выданном пуле — насколько подходит (`score`), то же ли (`verify`: две формулировки или два блока), какой из (`choose`). Об истинности или применимости утверждений о предмете его не спрашивают. Ответ judge — событие (`std/measurement`, `calls` трассы) или факт с основанием `inferred`: кандидат в алиас (в силу не входит) или подсказка со следом `match` ([21](21-compose.md) CP-25), чьё доверие поднимают только вердикты; утверждением он не пишется.
- Балл и уверенность — вход для порогов и порядка, не доверие (TR-06); действие по баллу — только обратимое, ошибку которого ловит вердикт (ADR-13).
- Какой judge исполняет — адаптер и точная версия модели в `std/setup` ([22](22-run.md), ADR-28), не в теле конвейера; `prompt_hash` — от шаблона вопроса адаптера.

### 6. Оценка и кэш

Оценка — событие `std/measurement@1` (T90), наследник маркера `std/segment-event` — сегмент исполнения ([12](12-ledger.md) §1):

```json
{ "type": "std/measurement@1",
  "body": { "need": {"$ref": "warrant/01J8…N"}, "pool": {"$ref": "#4c0e…"},
            "judge": { "adapter": "judge-jev", "model": "<точная версия>", "prompt_hash": "sha256:…" },
            "scores": [ { "card": {"$ref": "#9b1e…"}, "score": 0.91 }, { "card": {"$ref": "#77a0…"}, "score": 0.12 } ],
            "execution": {"$ref": "warrant/01J8…X"} } }
```

- Тело тонкое: ссылки и числа; пул — ссылкой на значение, не копией (LN-08). Все ссылки тела — `{"$ref"}` (P12, [10](10-kernel.md) §5): ядро видит их обходом — проверка существования и индекс ссылающихся.
- **Кэш** — ускорение, не истина (T-4): ключ `(адаптер, модель@версия, prompt_hash, state_hash, norm, card id)` → балл — определён здесь (потребитель), живёт в обёртке `Recording` ([22](22-run.md) §3, ADR-44), не в каждом адаптере: фиктивный адаптер получает тот же кэш, «повтор из кэша» S5 проверяем без сети. Попадание в кэш экономит оплату, но не запись: стадия `judge` получает баллы от обёртки (живые или из кэша) и сама готовит строку `std/measurement` с баллами, которые использовала, в свои `rows` — и при попадании в кэш; `execution` — этот вызов (ADR-44 п. 3: один механизм записи, обёртка `std/measurement` не пишет). Ответы `verify` и `choose` — в `calls` стадии ([22](22-run.md) §3). Воспроизведение читает записи своего вызова, а не кэш. Смена пула дооценивает только новые карточки.

### 7. Выход LENS (контракт для compose)

```json
{ "need": "…", "scope": "warrant/domain.lifecycle",
  "candidates": [
    { "ref": "warrant/REQ-VER-007@4", "card": "#9b1e…", "scores": {"judge": 0.91, "bm25": 0.40, "fused": 1.03},
      "trust": { "basis": "derived", "epistemic": "unresolved", "support": {"plus": 0, "minus": 0}, "groups": 0,
                 "policy": "std/trust-policy@1" },
      "marks": [], "why": ["judge", "lexicon:waiver"] } ],
  "outcome": "candidates | no-match", "measurement": "warrant/MEA-01J8…" }
```

- **Кандидат** (T87): `ref`, `card`, `scores`, `trust` — выход `trust()` как есть ([14](14-trust.md), без `overruled`: перекрытое в пул не входит), `marks` — пометки `[{kind, replaced_by?}]` (T150), `why` — причины.
- **Значения `policy.lens`** в `std/trust-policy`: `{exclude: ["overruled"], mark: ["inferred", "contested", "rejected"]}`; словарь состояний — значения `basis`, `epistemic` (с `rejected`, [14](14-trust.md) TR-14) и `overruled`. То же правило выдачи применяют `recall`, `add[]` и `materialize` ([14](14-trust.md) §7, TR-15). Проект переопределяет ([14](14-trust.md) §4). `deprecated` — статус каталога, помечается всегда, вне политики; выведенное из обращения в пул не входит.

## Операции

| Операция | Вход → выход |
|---|---|
| `aliasCandidates(ids, by)` | → факты `std/alias-candidate` отдельным коммитом: `judge.verify` по карточкам кандидатов той же области, в значении — `{p, judge: {adapter, model, prompt_hash}}` (`describe()`) ([11](11-identity-grain.md) §6, T142); вызывает хост после `ensure` и импорта, коммит пишет сессия той же команды |
| `lens(need, scope?)` | → выход §7; пишет `std/measurement` и значения пула и карточек в коммит вызова ([22](22-run.md)) |
| `card(block@n)` | → карточка (§1): шаблон типа + подсказки ревизии в силе; чистая функция журнала |
| `judge.score / verify / choose` | порт §5 |

## Инварианты

1. Карточка — функция `блока@n`, шаблона его типа и подсказок этой ревизии в силе: одинаковый вход — одна карточка.
2. Доверие не меняет балл: исключение — до judge по политике, остальное — пометки.
3. `threshold` читает только балл judge закреплённой версии; `calibrated_for` порога `no_match` расходится с `setup` → рантайм отказывает (`onMismatch: refuse`).
4. Кандидаты с причиной `id` порогом не отбрасываются.
5. Каждая оценка, которую использовал вызов (оплаченная или из кэша), — событие `std/measurement` этого вызова со ссылкой на пул.
6. Сессии стенда (`purpose: bench`) подсказки не подтверждают (T-5, [14](14-trust.md) TR-12) — решает `classify`, не список LENS.
7. Ответ `score` несёт балл на каждую карточку запроса; ответ judge утверждением не пишется (P13).
8. Кандидатов из баллов пула делает только `fuse`; оценщики — адаптеры шва `Scorer` (ADR-45).

## Решения

| ID | Решение | Почему |
|---|---|---|

## Вопросы для grilling

v0.3 вопросы 1–3 закрыты в v0.4 — LN-12, LN-13, LN-09.

1. **LENS одной стадией `retrieve`** (ADR-45, отложено): `lens.retrieve(need, scope, deps) → LensOutput` с параметрами `pool_max`, `cues_max`, `fuse`, `k`, `no_match`, `calibrated_for`; внутренний шов — `Scorer`; `bm25.doc` — отдельная стадия базовой линии. Мелкие по тесту удаления стадии (`normalize` как стадия, `id-lookup`, `fuse`, `trust`, `threshold`, `cut`) уходят внутрь, инвариант 4 («ID-попадание переживает порог») держит модуль, а не порядок стадий. Против — огрубляет LN-03 («стадия = единица способности»): самоописание конвейера данными теряет гранулярность. Рекомендация: решить на коде S5, если тесты стадий требуют ручной сборки большого частичного `Ctx`. Триггер — начало среза S5.

## Вне объёма

- Эмбеддинги и векторные индексы — не сравнивались; добавляются как ещё один адаптер шва `Scorer` — стадия `std/stage.<имя>` с баллом в `scores` (LN-19). Триггер — доля промахов LENS (член `found_by: self-search` с `used`) на живых вердиктах или `hit@3` на ловушках (`kind: trap`) ниже порога, который владелец пишет в регрессионный план; тогда — план `explore` со стадией эмбеддингов как базовой линией. В v1 уже сейчас: обе метрики ([23](23-bench.md) §2).
- Вес буста и `rrf` в `fuse` — кандидаты регрессионного сравнения на стенде (S9), не значения по умолчанию.
- Ветвление конвейера по условиям — граф новой версией интерпретатора по триггеру [22](22-run.md) «Вне объёма» (Ф-5).
