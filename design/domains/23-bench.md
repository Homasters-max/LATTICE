# 23. bench — стенд

**Назначение.** Доказывать по данным, что поиск и решения работают и что новая настройка исполнения не хуже прежней (P11). Стенд — часть системы: элементы, наборы, планы и прогоны — объекты LATTICE.

**Зависит от:** run — конвейер, `std/setup`, вызов, вердикт, режим `simulate-consumer` ([22](22-run.md)); trust — свойства сессии `classify` (`purpose`, группа независимости, [14](14-trust.md) §1, ADR-40); rules — гейт обучения `learning-gate` и засчитанный прогон `countedRun` ([13](13-rules.md) §2, ADR-42); ledger — `scan`, сегменты ([12](12-ledger.md)); lens и compose — стадии, которые стенд меряет и калибрует ([20](20-lens.md), [21](21-compose.md)). **Используют:** первый запуск ([01](../01-first-run.md)), гейт обучения (регрессия ревизий `std/setup`), калибровки порогов.

## Модель

### 1. Объекты

| Объект | Тип | Вид | Тело |
|---|---|---|---|
| элемент | `std/bench-item` | сущность | `{q, scope, gold: [ref@n], kind: normal \| trap \| blank, paraphrase_of?: ref, subset: dev \| test, origin: {kind: authored \| observed \| trap-from-miss, from?: ref, note?}}` |
| набор | `std/bench-set` | сущность | `{scope, items: [ref@n]}` — ревизия набора закрепляет элементы вместе с их ревизиями |
| план | `std/bench-plan` | событие | `{kind: regression \| candidate \| explore, set: ref@n, subset, setup: ref@n, base?: ref, baselines: [{name, setup: ref@n}], mode: normal \| simulate-consumer, noise?: number, budget: {usd?, ms?}, state: seq, criteria: [{metric, by?, threshold, ci_lower?, role: primary \| guardrail}], n, seed, supersedes?: {plan: ref, reason}, recheck_every?: n}` — пишется **до** прогона |
| прогон | `std/bench-run` | событие | `{plan: ref, tuple: {setup: ref@n, code, prompts, policy: ref@n, kernel}, results: #value, metrics, verdict: pass \| fail \| invalid, copy: sha256}` |
| метка копии | `std/bench-copy` | событие | `{plan: ref}` — первый коммит копии кампании (T180, §3); `writers: {purpose: bench}` — право проверяет `authority.mayWrite` ([10](10-kernel.md) §7), `purpose` читает ядро (перечень [04](../04-architecture.md) §1) |

- **Элемент — объект** (BN-06): основание ставится на ревизию целиком ([14](14-trust.md) §2). Второй разметчик пишет `core/assert` на `bench-item@n`, владелец решает новой ревизией элемента (`declared`). `origin` — откуда элемент: написан, взят из решения рабочей сессии (§5), из промаха LENS.
- **План — событие** (ADR-21): правка — новый план с `supersedes` и причиной; `test` повторяется только новым планом. `kind` задаёт форму тела — правила типа с условием `when: {path: kind, eq: …}` ([13](13-rules.md) §1):
  - `regression` — регрессионный план (T143): `subset: test`, набор, `n`, критерии, δ (`role: guardrail` и `primary` с направлением, §4; среди guardrail — `{metric: hit@3, by: block_kind}`: каждый вид блока не ниже базы, BN-19), базовые линии; пишет владелец. Действующий — последний по `seq` среди записей владельца (как текущий управляющий факт, ADR-6). `recheck_every` — через сколько строк обучения после `state` засчитанного прогона владелец получает находку «перемерить той же настройкой» (§5, BN-18);
  - `candidate` — только `base`, `setup`, `state`: набор, часть (`subset`, T176), режим, `noise`, `n`, `seed`, критерии, бюджет и базовые линии `lattice bench` берёт из `base`, поэтому предлагающий настройку не выбирает ни порог, ни вопросы, ни `seed` (BN-07);
  - `explore` — всё сам, пишет любой участник; гейт его не засчитывает. `explore` со `subset: test` не от владельца — находка владельцу (отчёт, ADR-10).
- **Кортеж плана** — `set@n`, `subset`, `setup@n`, `state`, `seed`, `noise`, базовые линии; режим — поле `mode`, не флаг CLI; `noise` действует только при `mode: simulate-consumer`.
- **Базовая линия** — отдельный объект `std/setup` пространства, не действующая `<пространство>/setup` ([22](22-run.md) RN-29): ревизия базовой линии рабочий конвейер не меняет. Её кортеж закреплён так же. Базовые линии без LLM — конвейеры из детерминированных стадий без портов `judge` и `composer` (RN-27): (a) `frame.single` (задача → одна потребность в `request.scope`, [21](21-compose.md) §4) → `normalize` → `bm25.doc` (BM25 по документам целиком, [20](20-lens.md) §4); (b) `frame.single` → `normalize` → `lexicon` → `id-lookup` → `pool` → `bm25` → `fuse` → `cut` (BM25 в домене). Цепочку проверяет `contract` при публикации; порядок `fuse` без `scores.judge` — при реализации S9. У всех исполнителей E1 — одна и та же базовая линия (BN-15).
- **Кортеж прогона** — `tuple` в `std/bench-run`: кортеж исполнения (T131) вызовов кампании целиком — `setup@n`, `code` (хэши модулей, ADR-42), `prompts`, `policy`, `kernel` ([22](22-run.md) §1). Сверку кортежей стенд не пишет сам — зовёт `run/tuple.matches` ([22](22-run.md) §1): вызовы кампании с разным кортежем — прогон `invalid`; с разной ревизией источника (`execution.source`) или средой (`execution.env`) — тоже `invalid` (BN-16, ADR-36): копия журнала не защищает от правки живого источника, её ловит сверка. Гейт сравнивает с кортежем вызова `setup@n`, `code`, `prompts` и `policy` ([22](22-run.md) §1).
- **Прогон** `verdict: invalid` — `Meta` хотя бы одной оценки расходится с моделью порта в `setup@n` плана ([22](22-run.md) §3): прогон не засчитывается ни в `pass`, ни в `fail`. `results` — значение: по вопросу `{key, execution, метрики}`, где `execution` — id вызова в копии кампании (§3).

```json
{ "id": "warrant/01J9…C", "type": "std/bench-plan@1",
  "body": { "kind": "candidate", "base": {"$ref": "warrant/01J9…R"},
            "setup": {"$ref": "warrant/setup@4"}, "state": 18400 } }
```

### 2. Метрики

| Метрика | Определение | Уровень |
|---|---|---|
| `hit@3` | доля вопросов, где хотя бы один эталон — в топ-3 кандидатов; разрез по виду блока (таблица, код, короткий, длинный) — достаточность карточки ([20](20-lens.md) §1); вид блока `block_kind` — функция текста эталона в коде стенда: таблица markdown → `table`, блок кода → `code`, иначе `short` / `long` по длине (порог — параметр метрики, 400 символов); по виду — guardrail регрессионного плана (BN-19) | блок |
| `MRR` | средний обратный ранг первого эталона | блок |
| `in-K` | хотя бы один эталон среди K кандидатов, отданных Composer | блок |
| `pool-recall` | доля эталонных карточек, оставшихся в пуле после предотбора BM25, для областей больше `pool_max` ([20](20-lens.md) §3) | блок |
| `select-F1` | точность и полнота выбора Composer против всего списка эталона | решение |
| `no-match P/R` | отказ на пустышках, не отказ на вопросах с ответом — отдельно по `kind` (`normal`, `trap`, `blank`); у ловушек — свой критерий | вопрос |
| `recall-rate` | доля потребностей, обслуженных повтором без judge; доля серой зоны — повторов с `recall.by: composer` (ADR-13, [21](21-compose.md) §3) | потребность |
| доля принятых кандидатов | принятые владельцем `std/alias-candidate` к предложенным (T142, [11](11-identity-grain.md) §6) | кандидат |
| `cost`, `ms` | цена и задержка на вопрос; `cost` сравнивается при заданном `hit@3` | вопрос |
| `calibration-Δ` | `select-F1` после вердиктов минус до; ревизию политики доверия проверяют так же ([22](22-run.md) §6) | решение |
| группы с вердиктами | число групп независимости, кроме группы автора и `(agent, unknown)`, с вердиктом на решение за окно удаления `removal_window.m`; группа и счёт в окне — `classify` ([14](14-trust.md) §1) | решение |
| замыкаемость окна | доля решений, где вердиктов ≥ `removal_window.n` групп не из группы автора — окно удаления может сработать; на живых вердиктах — сигнал F10 ([22](22-run.md) «Вне объёма») | решение |

- **Эталон из нескольких блоков:** `hit@k`, `in-K` — хотя бы один, `MRR` — первый, `select-F1` — весь список.
- **Смена зерна** (новая версия типа, слияние, [11](11-identity-grain.md)) меняет то, что считается попаданием: прежние прогоны с новыми несравнимы, базис меряется заново на новом `state`. Эталон ссылается на алиас или выведенный из обращения блок — находка lint (`soft`) владельцу набора, исправление — новая ревизия элемента.
- **Документная базовая линия** («BM25 по документам целиком», стадия `bm25.doc`, BN-15): ранг вопроса = ранг первого документа, содержащего эталонный блок (ссылка блока на источник, порт `source`). В отчёте у всех систем — колонки `doc-hit` и `block-hit`.

### 3. Кампания и копия журнала

**Кампания** (T162) — прогоны планов на одной копии журнала: текущая и новая настройка, базовые линии, проходы первого запуска.

- Ревизии `std/setup` и планы кампании пишутся в основной журнал **до** неё; кампания идёт на копии `.lattice/bench/<run>` журнала до `plan.state` (T138, T-5). У `candidate` `state` ≥ `seq` его плана и ревизии кандидата: на одной копии идут текущая ревизия и кандидат («тот же `state`», §5). Все записи кампании — потребности, решения, вызовы, оценки, вердикты — остаются в копии. Внутри копии `recall` работает как обычно: его и меряет повтор (E2 первого запуска).
- **Метка копии** (T180, BN-14): первый коммит копии — событие `std/bench-copy {plan}`, его пишет хост `lattice bench` сессией `purpose: bench`. Метка видна ядру: гейт принимает вердикты `purpose: simulate` только в хранилище с ней ([13](13-rules.md) §2); хост отказывает в `open()` основного хранилища, где она есть ([30](30-adapters.md) §4) — копия, скопированная поверх основного журнала, и метка, записанная в основной журнал, не проходят тихо.
- Из кампании в основной журнал пишется только `std/bench-run` (значение `results` — по хэшу) с хэшем копии `copy` (BN-08). На него ссылается вызов рабочего пространства (`execution.bench`, [22](22-run.md) §3) и гейт обучения.
- `replay` вызова кампании — на её копии ([22](22-run.md) §7); копию хранят, пока её не удалит владелец, хэш в `bench-run` проверяет сохранённую копию. Копии нет — `replay` отвечает `expired`. Сроки сегментов ADR-3 копию не касаются ([12](12-ledger.md) §1).
- **Сессии кампании.** Хост `lattice bench` открывает их с `purpose: bench` — их утверждения и вердикты не питают доверие и обучение: так отвечает `classify` по таблице `purpose` ([14](14-trust.md) §1, TR-12), гейт — [13](13-rules.md) §2; своего списка `purpose` у стенда нет. Режим `simulate-consumer` — сессии `purpose: simulate` (T163): вердикты выводятся из эталона, в копии считаются как вердикты рабочих потребителей и проходят гейт при метке копии; вне копии хост их не открывает, гейт без метки их отклоняет, такая сессия в основном журнале — находка владельцу. Каждый потребитель-симулятор — свой участник `machine` из реестра владельца, то есть своя группа независимости (ADR-26): окно удаления замыкается только вердиктами ≥ `removal_window.n` групп.
- **Совершенный и зашумлённый симулятор** (BN-20). При `noise` 0 (по умолчанию) симулятор — совершенный потребитель: эталонному члену `unused` не ставит и недостающее добавляет всегда, поэтому критерий «ни один верный член не удалён» на нём провалиться не может. Такой прогон меряет механику обучения — E3 «при совершенном потребителе» ([01](../01-first-run.md)). Устойчивость к ошибкам потребителя меряет прогон с `noise` > 0: в этой доле вердиктов, выбранных по `seed`, симулятор ставит `unused` эталонному члену или `add` лишнего блока.

### 4. Протокол

1. Вопросы пишет агент **без доступа к документам**; эталон размечается чтением **до** прогона.
2. Ловушки: доля слов вопроса в тексте эталона ≤ 0,15. Пустышки — «почти по теме», ≥ 10 на контроль.
3. Критерии, `subset` и `n` — в плане до прогона; число прогонов `test` на одном `set@n` — в отчёте кампании (видно подглядывание).
4. Решение по плану — один прогон `test`; интервалы — бутстрэп 95 %. Шум мерят отдельно — повторными прогонами без кэша на `dev`; устойчивость моделей — тоже повторными прогонами, не `replay` ([22](22-run.md) §7).
5. `dev` — для подбора параметров, `test` — только для решения; во время подбора `test` не выводится.
6. Второй разметчик — на 20 % выборки: `core/assert` на элемент; расхождение решает владелец ревизией элемента.
7. Размер: `n` — в плане; ориентир — ≥ 40 вопросов на решение (малые эффекты требуют больше), домены можно объединять.
8. **Калибровки** — на `dev`, по обеим ошибкам, с записью `calibrated_for` (T136); вызовы калибровки — кампания плана `explore` (`subset: dev`) на копии (§3): её потребности и подсказки не попадают в память `recall` основного журнала (BN-04); в основной журнал — её `std/bench-run` и ревизии владельца: конвейер проекта `<пространство>/pipeline.solve` с порогами и `calibrated_for {adapter, model, prompt_hash, bench}` (`bench` — этот прогон, по нему виден `state` калибровки) и `std/setup`, которая на него ссылается ([22](22-run.md) §1, RN-35, BN-17). Порог `no_match` — сеткой, проверка один раз на `test` ([20](20-lens.md) LN-07); пороги `same_hi`/`same_lo` — на парах перефразов «та же / другая» с трудными отрицательными примерами проекта ([21](21-compose.md) §3); `min_p` кандидатов — так же (T142), его ревизия — политика пространства с `candidates.calibrated_for` ([14](14-trust.md) §4).
9. Эффект обучения подсказок меряют на **отложенных перефразах**, не участвовавших в обучении; абляция «LENS без выученных подсказок» — на `test`.

### 5. Регрессия и замкнутый цикл

- **Регрессия.** Новая ревизия `std/setup` (конвейер, модель, параметр стадии — одна политика, ADR-22) проверяется планом `candidate` с `base` на действующий регрессионный план в одной кампании с текущей ревизией: тот же `set@n`, `subset`, `state`. `pass` — если по каждой метрике δ-вектора нижняя граница парного бутстрэпа разности ≥ −δ с учётом направления (`hit@3`, `MRR`, `select-F1` — не ниже; `cost`, `ms` — guardrail), и δ не меньше измеренного шума. В плане — прогноз «что улучшится», в отчёте — прогноз против факта.
- **Первая ревизия и откат.** Ревизия, которой не с чем сравнить (первая рабочая, откат — новая ревизия с прежним содержимым, другой `setup@n`), проверяется тем же планом `candidate` с `setup` = ревизии регрессионного плана: сравнение с собой выполняет δ тривиально, решают абсолютные критерии `primary`.
- **Гейт.** Закрепление настройки — её ревизия, обратима и свободна. Барьер стоит на необратимом шаге — фактах обучения: вердикт учит, только если у его кортежа есть **засчитанный прогон** (T139) — значение одной функции ядра `countedRun(view, tuple)` ([13](13-rules.md) §2, ADR-42): последний по `seq` прогон этого кортежа по плану `candidate` с `base` на регрессионный план, действующий на `seq` этого плана (последний среди планов того, кто был владельцем на `seq` их записи), и он `pass`. Более поздний `fail` того же кортежа гейт закрывает: ошибочный эталон, исправленный новой ревизией набора, и повторный прогон отзывают прежний `pass`. Строка обучения несёт этот прогон в `bench` (ADR-29, BN-13); без засчитанного `pass` пакет помечен «не проверено стендом» ([22](22-run.md) §3). Та же функция у гейта, `learn`, пакета и стенда: `bench ≠ null` в пакете ⇔ гейт принимает строку обучения вердикта этого вызова. Число прогонов кандидата на одном кортеже — в отчёте кампании: подбор `state` виден.
- **Калибровка устарела** (BN-18) — находка `lint` (`soft`, отчёт, ADR-10) владельцу, когда после `state` прогона калибровки (`calibrated_for.bench`) в журнале есть: новая ревизия типа с `card`, чьи карточки оценивает порог; рост словаря области или доли карточек с подсказками в силе больше порога находки (10 % по умолчанию — допущение, число уточняет замер первого запуска). Распределение баллов judge сместилось, а RN-10 и гейт этого не видят.
- **Повторная регрессия** (BN-18): строк обучения после `state` засчитанного прогона действующей настройки больше `recheck_every` действующего регрессионного плана — находка владельцу «перемерить той же настройкой»: план `candidate` с тем же `setup` на свежем `state`, решают абсолютные критерии `primary` (как BN-12); более поздний `fail` закрывает гейт (BN-13). Базовая линия «LENS без `recall`» — конвейер без стадии `recall` — в том же прогоне отделяет вклад памяти от поиска: выученное проверяется внешним замером, а не только собственными вердиктами.
- **Кандидаты в эталоны** — решения `observed` / `declared` только из рабочих сессий; эталон из них — после подтверждения владельцем (ревизия элемента, `declared`), `origin: observed`, только в `subset: dev` ([22](22-run.md) §6).
- **Промахи LENS** (член `found_by: self-search`) → кандидаты в ловушки, `origin: trap-from-miss`.
- Новые эталоны и ловушки идут в следующую ревизию набора, текущий `test` не дописывается. Новый набор — новый базис: текущую настройку меряют на нём до сравнения. Изношенный `test` (много регрессий на одном `set@n`) — ротация: часть в `dev`, свежий `test` — новая ревизия набора и новый регрессионный план.

|---|---|
| `bench(plan)` | копия журнала до `plan.state` → прогоны плана и базовых линий → коммит `std/bench-run` в основной журнал (§3); команда `lattice bench <план>` — [30](30-adapters.md) |
| `replay(execution)` вызова кампании | на копии кампании ([22](22-run.md) §7); копии нет — `expired` |

## Инварианты

1. План — событие и пишется до прогона; `test` повторяется только новым планом (BN-02).
2. Кампания идёт на копии до `plan.state`; основной журнал получает от неё только `std/bench-run` (BN-08).
3. Сессии `purpose: bench` не питают доверие и обучение; сессии `purpose: simulate` существуют только в копии, гейт принимает их вердикты только при метке `std/bench-copy` (BN-04, BN-14).
4. Гейт засчитывает только последний по `seq` прогон кортежа по плану `candidate` с `base` на регрессионный план, действующий на `seq` плана, с тем же кортежем исполнения — `setup@n`, `code`, `prompts`, `policy` ([22](22-run.md) §1); более поздний `fail` закрывает гейт (BN-05, BN-07, BN-13). Это определение — одна функция `countedRun` ([13](13-rules.md) §2); стенд её зовёт, а не повторяет.
5. Сравнимы только прогоны с равным кортежем плана; `Meta` расходится с `setup@n`, вызовы кампании с разной `source` или `env` — прогон `invalid` (BN-01, BN-16).
6. Эталон `test` не дописывается: новые эталоны — в следующую ревизию набора и только в `dev` из рабочих сессий (BN-10).

## Решения

| ID | Решение | Почему |
|---|---|---|
| BN-01 | Элементы, наборы, планы, прогоны — объекты LATTICE; план закрепляет весь кортеж | стенд воспроизводим и связан с настройкой исполнения; прогоны сравнимы только при равном кортеже плана. v0.4 · T-2 · И-1 · И-16 |
| BN-02 | Критерии, часть набора (`subset`) и размер — в плане до прогона; план — событие, правка — новый план с `supersedes` | без подгонки под результат; вид объекта — флаг типа, без нового правила. v0.4 · ADR-21 · И-4 · И-5 |
| BN-03 | Уровень метрики — блок, зерно пространства (в WARRANT — норма), не документ | пакет агента состоит из блоков — метрика мерит то, что выдаётся; уровень документа тривиален для крупных документов. v0.4 · И-9 |
| BN-04 | Сессии стенда не учат систему; режим `simulate-consumer` — только в копии кампании, сессиями `purpose: simulate` | главный канал утечки — память (`recall`), поэтому изоляция — копия, а не только пометка; пометку ставит хост, не пишущий. v0.4 · T-5 · И-10 · И-11 · D11 Q5 |
| BN-05 | Барьер стенда — гейт на фактах обучения, не на смене настройки; одна политика проверки для любой смены | необратимо обучение, а не ревизия `setup`; до живого трафика риск смены не измерить. v0.4 · ADR-29 · ADR-22 · И-13 · N-4 · PF-05 |
| BN-06 | Элемент набора — объект `std/bench-item`; расхождение разметчиков — `core/assert` на него | основание ставится на ревизию целиком; происхождение и доверие — у каждого вопроса. v0.4 · И-2 · D11 Q1 |
| BN-07 | Регрессионный план и δ — владельца; кандидат подставляет только `setup`, `state`; `seed` — из `base` | предлагающий настройку не выбирает порог, вопросы и `seed`; без нового примитива «автор по полю». v0.4 · T-1 · И-6 · И-15 · D11 Q2 · v0.5 · CA-F04 |
| BN-08 | Из кампании в основной журнал — только `std/bench-run` с хэшем копии; `replay` кампании — на копии | вызовы кампании ссылаются на её `seq` и объекты, в основном журнале это висячие ссылки. v0.4 · T-4 · И-3 · И-11 · D11 Q3 |
| BN-09 | δ — вектор с направлением; решение — нижняя граница парного бутстрэпа; δ не меньше шума; сравнение в одной кампании | кэши делают повтор побайтным и прячут разброс; разные `set@n` и `state` несравнимы. v0.4 · И-14 |
| BN-10 | Кандидаты в эталон — только из рабочих сессий, в `dev`, после подтверждения владельцем | эталон не подтверждает сам себя. v0.4 · T-5 · И-12 · 22-run/И-16 · v0.3 вопрос 2 |
| BN-11 | Калибровка — кампания плана `explore` (`subset: dev`) на копии; в основной журнал — `std/bench-run` и ревизии конвейера проекта (пороги, `calibrated_for`) и `std/setup` на него (BN-17) | вызовы калибровки в основном журнале оставили бы потребности и подсказки, которые `recall` отдал бы на `test` (BN-04). v0.4 · F Q4 (N-134) · v0.5 · CA-F40 |
| BN-12 | Первая ревизия `std/setup` и откат — план `candidate` с `setup` = ревизии регрессионного плана; решают абсолютные критерии `primary` | совпадение гейта — по `setup@n`: без этого первая рабочая ревизия и откат не получают `pass`, и вердикты не учат; ADR-29 не меняется. v0.4 · F Q5 (N-135) |
| BN-13 | Гейт засчитывает последний по `seq` прогон кортежа по плану `candidate` на регрессионный план, действующий на `seq` плана; более поздний `fail` закрывает; строка обучения несёт этот прогон (`bench`) | засчитывался любой существующий `pass`: повтор с другим `seed`, `base` на старый мягкий план, `pass` до исправления эталона — «хотя бы раз повезло»; после `transfer` «владелец» плана не был определён. v0.5 · ADR-29 · CA-F04, CA-F31 |

| BN-15 | Базовая линия — отдельный объект `std/setup`; базовые линии без LLM — детерминированные стадии (`frame.single`, `normalize`, `bm25.doc` или цепочка LENS до `bm25`) | «BM25 по документам» как настройка не публиковался (`contract`, обязательный `judge`) или включал LLM `frame` — E1 сравнивал LENS с разными «BM25». v0.5 · CA-F34, CA-F47 |
| BN-16 | Вызовы одной кампании с разной `execution.source` или `execution.env` — прогон `invalid` | кампания копирует журнал, но `grep`, `find`, `text` ходят в живой источник, а `normalize` зависит от ICU: правка спеки во время прогона искажала δ молча. v0.5 · ADR-36 · CA-F41 |
| BN-17 | Калибровка пишет ревизию конвейера проекта `<пространство>/pipeline.solve` с порогами и `calibrated_for {…, bench}` и ревизию `setup` на него; `min_p` — ревизия политики пространства | пороги были `params` `std/pipeline.solve@1`, который проект не пишет, — «ревизия `setup` с `calibrated_for`» не выражалась; без `bench` не узнать, на каком `state` подобран порог. v0.5 · CA-F40, CA-F18 |
| BN-18 | Находка `lint` «калибровка устарела» по наблюдаемым событиям после `state` калибровки; `recheck_every` регрессионного плана — находка «перемерить той же настройкой»; базовая линия «LENS без `recall`» | пороги и `pass` привязаны к кортежу, а не к состоянию данных: обучение, словарь и шаблон карточки сдвигали баллы, RN-10 и гейт проходили, ни одна метрика не срабатывала. v0.5 · CA-F18 |

## Вне объёма

- **После первого запуска, по замеру:** базовая линия «карточка с `summary` units» против первого абзаца ([30](30-adapters.md) AD-12, D12 Q6); перенос `summary` в карточку — только если она выиграет (N-62).

- Сравнение с внешними поисковыми системами.
- Поэтапная раскатка настройки на долю запросов и автооткат — после живых вердиктов (ADR-22).
- Полосы по риску (быстрый `dev` для параметра, полный `test` для стадии) — нет: граница «параметр / конвейер» не определена, смена порога меняет вердикты так же, как смена стадии (ADR-22).
- `writers` с условием по полю тела — нет: ядро росло бы ради одного типа; право держат `base` и гейт (D11 Q2 (б)).
- Вызовы и оценки кампании в основном журнале — нет (D11 Q3 (б)).
