# 23. bench — стенд

**Назначение.** Доказывать по данным, что поиск и решения работают и что новая версия не хуже старой (P11). Стенд —
часть системы: наборы и прогоны — объекты LATTICE.

**Зависит от:** run. **Используют:** первый запуск, регрессия версий конвейера.

## Модель

### 1. Объекты

| Объект | Тип | Вид | Тело |
|---|---|---|---|
| набор | `std/bench-set` | сущность | `{scope, items: [{key, q, scope, gold: [ref], kind: normal \| trap \| blank, paraphrase_of?, split: dev \| test}]}` |
| план | `std/bench-plan` | сущность | `{set: ref@n, pipeline: ref@n, baselines: [...], criteria: [...], seed}` — пишется **до** прогона |
| прогон | `std/bench-run` | событие | `{plan: ref@n, results: #value, metrics: {...}, verdict: pass \| fail}` |

### 2. Метрики

| Метрика | Определение | Уровень |
|---|---|---|
| `hit@3` | доля вопросов, где эталонный блок в топ-3 кандидатов | блок (норма) |
| `MRR` | средний обратный ранг первого эталонного | блок |
| `in-K` | эталон среди K кандидатов, отданных Composer | блок |
| `select-F1` | точность и полнота выбора Composer против эталона | решение |
| `no-match P/R` | пустышки → отказ; вопросы с ответом → не отказ | вопрос |
| `recall-rate` | доля потребностей, обслуженных повтором без judge | потребность |
| `cost`, `ms` | цена и задержка на вопрос | вопрос |
| `calibration-Δ` | `select-F1` после вердиктов минус до | решение |

### 3. Протокол (уроки черновиков)

1. Вопросы пишет агент **без доступа к документам**; эталон размечается чтением **до** прогона.
2. Ловушки: доля слов вопроса в тексте эталона ≤ 0,15. Пустышки: ≥ 10 на контроль.
3. Критерии записываются в план до прогона (`criteria`: метрика, порог, нижняя граница 95 % CI).
4. Контроль — один прогон; интервалы — бутстрэп 95 %.
5. `dev` — для подбора параметров, `test` — только для решения; во время подбора `test` не выводится.
6. Второй разметчик на 20 % выборки; расхождения — maintainer.
7. **Без утечки:** сессии стенда помечены `purpose: bench`; обучение подсказок и калибровка на них не учатся, кроме
   явного режима `simulate-consumer` (первый запуск, [01](../01-first-run.md)).

### 4. Замкнутый цикл

- Решения с основанием `observed` / `declared` → кандидаты в эталоны (`gold` с пометкой происхождения).
- Промахи LENS (B) → кандидаты в ловушки.
- Регрессия: новая версия конвейера закрепляется проектом, только если на регрессионном наборе метрики не хуже
  текущей больше чем на δ (параметр плана).

## Решения

| ID | Решение | Почему |
|---|---|---|
| BN-01 | Наборы, планы, прогоны — объекты LATTICE | стенд воспроизводим и связан с версиями конвейера |
| BN-02 | Критерии — в плане до прогона | без подгонки под результат |
| BN-03 | Уровень метрики — блок (норма), не документ | уровень документа тривиален для крупных документов |
| BN-04 | Сессии стенда не обучают систему (кроме явного режима) | без утечки |
| BN-05 | Регрессионный барьер для новых версий конвейера | замена стадии — по данным |

## Вопросы для grilling

1. **Размер контроля** — 40 вопросов на решение (малые эффекты требуют больше)? Рекомендация: 40, домены можно
   объединять.
2. **Эталон из `observed`** — автоматически или с подтверждением maintainer'а? Рекомендация: с подтверждением
   (становится `declared`).
