# 10. kernel — объект, версия, ссылка, тип

**Назначение.** Определить, что такое объект и как он записан. Всё остальное в системе — объекты этой формы
и правила над ними.

**Зависит от:** ничего. **Используют:** все домены.

## Модель

### 1. Одна форма записи — ревизия

```json
{
  "id": "warrant/01J8ZQ4N7X5K2M9R3T6V8W0Y1A",
  "type": "std/domain@1",
  "version": 3,
  "at": "2026-09-26T19:40:12.345Z",
  "by": "warrant/SES-01J8ZQ3…",
  "body": { "name": "lifecycle", "code": "LCY", "language": "ru" }
}
```

| Поле | Что | Правило |
|---|---|---|
| `id` | identity (T04) | не меняется никогда; грамматика — п. 4 |
| `type` | **закреплённая** ссылка на ревизию типа (T19) | ревизия проверялась правилами именно этой версии типа |
| `version` | номер ревизии (T07) | 1, 2, 3 …; только следующий за текущим (LG-06) |
| `at` | время записи, UTC, мс | порядок при равенстве — `seq` журнала (T40) |
| `by` | сессия, которая записала (T53) | через сессию — участник (T52); основа доверия и прав |
| `body` | тело (T03) | любой JSON; ядро не ограничивает |

**Версия — в заголовке, не в теле.** Тело — «что есть объект», версия — «какая это по счёту ревизия». Если бы версия
была в теле, хэш содержимого менялся бы с каждой версией, и одинаковое содержимое нельзя было бы узнать. Запись того
же тела, что у текущей ревизии, — no-op: новая версия не создаётся (KR-03).

### 2. Три вида объектов — два флага типа

| Вид | `identity` | `mutable` | `id` | Версии | Примеры |
|---|---|---|---|---|---|
| **сущность** | `assigned` | `true` | ULID или внешнее имя | 1…n | норма, домен, потребность, решение, тип, правило |
| **событие** | `assigned` | `false` | ULID | только 1 | факт, утверждение, вызов, оценка, вердикт |
| **значение** | `content` | `false` | `#<hash>` | только 1 | snapshot, карточка |

Четвёртая комбинация (`content` + `mutable`) запрещена: содержимое, которое меняется, не может быть своей identity.

### 3. Хэш и каноническая форма

- `hash = sha256(canonical({"type": <id типа без версии>, "body": body}))`.
- Каноническая форма (T13): ключи объектов отсортированы по кодовым точкам, без пробелов, строки в NFC, числа — как
  `Number.prototype.toString` в ES, без `undefined`. Одинаковые данные дают одинаковые байты на любой машине.
- Тип без версии: одинаковое содержимое под новой версией того же типа — то же значение.
- Хэш хранится в индексе для каждой ревизии; для значений он и есть `id`.

### 4. Идентификаторы

```text
id        = namespace "/" local | "#" hex32
namespace = [a-z][a-z0-9-]* ("." [a-z0-9-]+)*        core, std, warrant, warrant.bench
local     = ULID | external | name
            ULID      01J8ZQ4N7X5K2M9R3T6V8W0Y1A     выдаётся машиной, несёт время
            external  REQ-KRN-011, ADR-0012          стабильное внешнее имя (из источника)
            name      type, rule, domain             для типов и объектов ядра/библиотек
value id  = "#" + первые 32 hex хэша                 #3fa29c0d71be44a2…  (без пространства имён)
ref       = id | id "@" version                      std/need@2, warrant/REQ-KRN-011
```

- Значения **вне пространств имён**: одинаковое содержимое в двух проектах — один объект (как объекты git).
- Префиксы в локальном имени (`REQ-`, `SES-`) — только для чтения человеком; тип из `id` **не выводится** никогда.

### 5. Ссылки

- **Закреплённая** `id@n` — всегда одна ревизия; разрешается всегда, даже если объект выведен из обращения.
- **Следующая** `id` — последняя живая ревизия; через алиасы (GR-05); у выведенного объекта не разрешается (`broken`).
- В теле ссылка — объект `{"$ref": "std/need@2"}`. Ядро находит ссылки обходом тела: так строятся проверка
  существования, индекс потребителей и snapshot'ы — без знания схемы типа.
- В заголовке `type` — всегда закреплённая ссылка; `by` — следующая ссылка на сессию.

### 6. Тип — тоже объект

```json
{ "id": "core/type", "type": "core/type@1", "version": 1, "at": "…", "by": "core/genesis",
  "body": {
    "identity": "assigned", "mutable": true,
    "extends": null,
    "grain": ["name"],
    "rules": [{"$ref": "core/rule.type-shape@1"}],
    "refs": "pin",
    "doc": "Тип объектов. Тип этого объекта — он сам."
  } }
```

Поля тела типа (все, кроме `identity` и `mutable`, необязательны):

| Поле | Что задаёт | Домен |
|---|---|---|
| `identity`, `mutable` | вид объекта (п. 2) | kernel |
| `extends` | один родитель: правила, роли, поля карточки наследуются | kernel |
| `grain` | измерения зерна — пути в теле | [11](11-identity-grain.md) |
| `rules` | закреплённые ссылки на правила | [13](13-rules.md) |
| `schema` | добровольная форма тела (подмножество JSON Schema) — это тоже правило | [13](13-rules.md) |
| `roles`, `key` | для типов фактов: допустимые роли и ключ факта | п. 7 |
| `refs` | политика ссылок на объекты этого типа: `pin` / `follow` | [15](15-catalog.md) |
| `card` | шаблон карточки для поиска | [20](20-lens.md) |
| `doc` | описание для людей и для поиска типов | — |

`core/type` имеет тип `core/type@1` — цепочка замыкается, как `type(type) is type` в Python. Генезис записывает
его первым; проверка «тип существует» для него выполняется по самому себе.

### 7. Факт — событие особой формы

Факт (T47) — объект-событие, тип которого расширяет `core/fact`. Его тело:

```json
{ "of": { "group": {"$ref": "warrant/SOL-…"}, "member": {"$ref": "warrant/REQ-VER-007@4"} },
  "value": true }
```

- `of` — роли → ссылки; допустимые роли и их типы объявляет тип факта (`roles`).
- `key` типа — роли, которые определяют «тот же факт»: текущий факт — последний по ключу (по `at`, затем `seq`).
  Пустой `key` — факты накапливаются (утверждения, подсказки).
- `value` — любой JSON; `false` / `null` у историзуемых фактов означает «закончился».

Так выражаются членство, алиас, вывод из обращения, утверждение, подсказка, допуск — один механизм.

### 8. Генезис и слои

| Слой | Пространство | Что | Как меняется |
|---|---|---|---|
| ядро | `core` | `type`, `rule`, `fact`, `assert`, `member`, `alias`, `retire`, `deprecate`, `grant`, `proposal`, `snapshot`, `namespace`, `actor`, `session`, `trust-policy`, правила-основы | только новой версией кода (генезис зашит в код) |
| библиотека | `std` | `block`, `knowledge`, `capability`, `card`, `cue`, `term`, `domain`, `need`, `distinct`, `solution`, `link`, `pipeline`, `ctx`, стадии, `measurement`, `execution`, `verdict`, `gap`, `bench-set`, `bench-plan`, `bench-run`, политика доверия по умолчанию | как любые данные: версии, владелец — сопровождающий LATTICE |
| проект | `warrant`, … | типы проекта (расширяют `std`), объекты, факты | владелец проекта |

Код ядра знает только: форму ревизии, хэш, каноническую форму, ссылки, режимы идентичности, факты с ролями и
примитивы проверок. Что такое «потребность» или «решение» — знают данные `std`.

## Операции (контракт ядра, чистые функции)

| Операция | Вход → выход |
|---|---|
| `canonical(json)` | → строка |
| `hash(typeId, body)` | → hex64 |
| `parseRef(s)` / `formatRef(id, v?)` | ↔ `{id, version?}` |
| `refsOf(body)` | → все `$ref` тела (обход) |
| `newId(namespace)` | → ULID-id |
| `valueId(typeId, body)` | → `#hex32` |
| `revision(input)` | → заполненная ревизия (без проверки правил) |

## Инварианты

1. `id` ревизии не меняется; пара `(id, version)` уникальна в журнале.
2. У объекта с `mutable: false` есть только `version: 1`.
3. У значения `id == "#" + hash[0:32]`.
4. `type` в заголовке — закреплённая ссылка на существующую ревизию типа (для `core/type@1` — на саму себя).
5. Каждая ссылка в теле разрешается (правило `ref-exists`, уровень задаёт тип).

## Решения

| ID | Решение | Почему |
|---|---|---|
| KR-01 | Одна форма записи для всего: ревизия `{id, type, version, at, by, body}` | один механизм хранения, проверки, истории (P1, P12) |
| KR-02 | Заголовок фиксирован и минимален; тело открыто | «ограничений нет — ограничивают правила» (P2) |
| KR-03 | Версия в заголовке, целое ≥ 1; ревизия неизменна; запись того же тела — no-op | версия ≠ содержимое; повтор не плодит версий |
| KR-04 | Два флага типа дают три вида: сущность, событие, значение; значения интернируются | как mutable / immutable / hashable в Python |
| KR-05 | Хэш = sha256 канонической формы `{id типа без версии, body}` | содержимое узнаётся независимо от версии типа |
| KR-06 | Каноническая форма JSON — своя функция ядра | одинаковые байты на любой машине |
| KR-07 | Ссылка — `id` или `id@n`; в теле — `{"$ref"}`; ядро находит ссылки обходом | ссылки видны без схемы: потребители, snapshot, проверки |
| KR-08 | Тип — объект; `core/type` типизирован самим собой | самоописание (P9) |
| KR-09 | `extends` — ровно один родитель | без MRO и конфликтов; композиция вместо иерархий |
| KR-10 | Смена типа сущности — новая версия с другим `type`; `id` не меняется | классификация не меняет identity |
| KR-11 | Слои `core` (код) → `std` (данные) → проект | малое замороженное ядро, остальное — данные |
| KR-12 | Грамматика `id` (п. 4); значения — без пространства имён | переносимость, дедупликация между проектами |
| KR-13 | Факт — событие с `{of: {роль: ref}, value}`; ключ факта — в типе | один механизм для членства, алиасов, утверждений, подсказок |
| KR-14 | Удаления нет | закреплённые ссылки разрешаются всегда |

## Вопросы для grilling

1. **`by` — сессия или участник?** Рекомендация: сессия; независимость подтверждений считается по сессиям, участник
   выводится из сессии.
2. **Хэш — от типа без версии** (KR-05)? Альтернатива — с версией: смена версии типа меняет identity всех значений.
   Рекомендация: без версии.
3. **Длина `id` значения** — 32 hex (128 бит)? Рекомендация: да; коллизия практически невозможна, строка читаема.
4. **Время `at`** — только время записи или ещё «время действия» у фактов (битемпоральность)? Рекомендация: только
   время записи; «действует с» — поле `value`, если понадобится типу.
5. **Факт как объект**: факты — полноценные события в журнале (много строк), а не отдельный вид записи.
   Рекомендация: да — одна форма записи важнее экономии; индекс отделяет факты от узлов графа.
