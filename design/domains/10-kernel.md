# 10. kernel — объект, версия, ссылка, тип

**Назначение.** Определить, что такое объект и как он записан. Всё остальное в системе — объекты этой формы
и правила над ними.

**Зависит от:** ничего. **Используют:** все домены.

## Модель

### 1. Одна форма записи — ревизия

```json
{
  "id": "warrant/01J8ZQ4N7X5K2M9R3T6V8W0Y1A",
  "type": "std/domain@1",
  "version": 3,
  "at": "2026-09-26T19:40:12.345Z",
  "by": "warrant/SES-01J8ZQ3…",
  "body": { "name": "lifecycle", "code": "LCY", "language": "ru" }
}
```

Тело в примере — иллюстрация формы; поля `std/domain` определяет [11](11-identity-grain.md).

| Поле | Что | Правило |
|---|---|---|
| `id` | identity (T04) | не меняется никогда; грамматика — п. 4 |
| `type` | **закреплённая** ссылка на ревизию типа (T19) | ревизия проверялась правилами именно этой версии типа |
| `version` | номер ревизии (T07) | 1, 2, 3 …; только следующий за текущим (LG-06) |
| `at` | время записи, UTC, мс | только для людей; порядок — `seq` журнала и ничего больше (T40, T-6) |
| `by` | сессия, которая записала (T53) | сессию открывает хост (ADR-25); через сессию — участник (T52); основа доверия и прав. У объектов генезиса — сессия `core/genesis` (п. 8) |
| `body` | тело (T03) | любой JSON в пределах входной проверки (п. 3); ядро не ограничивает |

Заголовок объекта меняется только новой версией формата ядра. Поля строки журнала (`seq`, `commit`, `kernel`, `key`)
— не заголовок объекта: их определяет [12](12-ledger.md).

**Версия — в заголовке, не в теле.** Тело — «что есть объект», версия — «какая это по счёту ревизия». Если бы версия
была в теле, хэш содержимого менялся бы с каждой версией, и одинаковое содержимое нельзя было бы узнать.

**Когда запись — no-op** (новая строка не пишется):
- сущность — то же тело под тем же `type@n`, что у текущей ревизии; то же тело под `type@n+1` — новая ревизия
  (ADR-2);
- факт — тот же ключ и то же `value`, что у текущего факта, независимо от `by`; у факта с пустым `key` no-op нет —
  такие факты накапливаются (п. 7);
- повтор коммита с тем же ключом идемпотентности — прежний результат ([12](12-ledger.md)).

Значение, которое уже лежит в хранилище, но пространство пишущей сессии его ещё не держит, — не no-op: шаг коммита
пишет `core/holds` (п. 7).

### 2. Три вида объектов — два флага типа

| Вид | `identity` | `mutable` | `id` | Версии | Примеры |
|---|---|---|---|---|---|
| **сущность** | `assigned` | `true` | ULID или внешнее имя | 1…n | норма, домен, потребность, решение, тип, правило |
| **событие** | `assigned` | `false` | ULID | только 1 | факт, утверждение, вызов, оценка, вердикт |
| **значение** | `content` | `false` | `#`+hex32 | только 1 | snapshot, карточка |

Как выбрать вид: **различать ли два объекта с одинаковым содержимым?** Да — сущность (если меняется) или событие
(если нет); нет — значение: его identity и есть содержимое (адресация по содержимому).

- Четвёртая комбинация (`content` + `mutable`) запрещена: содержимое, которое меняется, не может быть своей identity.
- У `content`-типов все ссылки тела закреплены (`id@n`, hard): следующая ссылка поменяла бы смысл значения, не меняя
  его identity (T-13).
- Новая ревизия сохраняет вид объекта — `identity` и `mutable` своего типа (hard, T-16).

### 3. Хэш и каноническая форма

- `hash = sha256(canonical({"type": <id типа без версии>, "body": body}))`.
- Тип без версии: одинаковое содержимое под новой версией того же типа — то же значение.
- Каноническая форма (T13) — JCS (RFC 8785) целиком; единственное отступление — строки приводятся к NFC на входе
  коммита (ADR-1). Одинаковые данные дают одинаковые байты на любой машине. Каноническая форма — межверсионный
  контракт: тестовые векторы входят в формат v1, следующая версия ядра обязана их воспроизводить.
- **Входная проверка коммита** (I-JSON): дубли ключей, неконечные числа, `-0`, целые вне ±2^53 — отказ; большие
  целые передаются строкой. Проверяется вход, каноническая форма не меняется: иначе тело (`-0`) и хэш (`0`)
  разошлись бы.
- Хэш хранится в индексе для каждой ревизии; для значений он и есть `id`. Запись и импорт уже существующего `#id`
  сверяют полный sha256 — расхождение — отказ (T-7).

### 4. Идентификаторы

```text
id        = namespace "/" local | value-id
namespace = [a-z][a-z0-9-]* ("." [a-z0-9-]+)*        core, std, warrant, warrant.bench
local     = ULID | external | name
            ULID      01J8ZQ4N7X5K2M9R3T6V8W0Y1A     выдаётся машиной, несёт время
            external  REQ-KRN-011, ADR-0012          стабильное внешнее имя (из источника)
            name      type, rule, domain             для типов и объектов ядра/библиотек
value-id  = "#" hex32                                схема 1: первые 32 hex хэша   #3fa29c0d71be44a2…
          | "#" label ":" hex                        резерв следующих схем; label = [g-z][a-z0-9]*
ref       = id | id "@" version                      std/need@2, warrant/REQ-KRN-011
```

- Значения **вне пространств имён**. Дедупликация между проектами — только для значений `core`/`std`: id типа входит
  в хэш, а у типов проекта пространство своё, поэтому одинаковое тело под типами двух проектов — разные значения
  (T-7).
- Схема `value-id` — формат v1: `#`+hex32 — схема 1; `#<label>:…` — зарезервировано, ядро v1 такой `id` отклоняет.
  Метка начинается с буквы вне hex, поэтому схемы не пересекаются.
- Точка в имени пространства — часть имени, без иерархии: `warrant.bench` — отдельное пространство, не дочернее
  `warrant`.
- **Происхождение пространства** (`origin`, T144) — неизменное поле `core/namespace`: ULID при `init` у проекта,
  константа генезиса у `core`, константа пакета LATTICE у `std`. Импорт отклоняет пространство с тем же именем и
  другим `origin` (T-7). Остальное тело `core/namespace` — [15](15-catalog.md).
- Префиксы в локальном имени (`REQ-`, `SES-`) — только для чтения человеком; тип из `id` **не выводится** никогда.

### 5. Ссылки

- **Закреплённая** `id@n` — всегда одна ревизия; для чтения разрешается всегда, даже если объект выведен из обращения.
  Для исполнения — нет, если версия отозвана или `impl.pins` расходится с кодом (T-1, T-2).
- **Следующая** `id` — последняя живая ревизия; через алиасы в силе — только `core/alias` (GR-05; кандидат
  `std/alias-candidate` не разрешает, ADR-8); у выведенного объекта не разрешается (`broken`).
- В теле ссылка — объект ровно с одним ключом `{"$ref": "std/need@2"}`; объект с `$ref` и другими ключами — отказ. В
  подмножестве `schema` `$ref` запрещён. Ядро находит ссылки обходом тела: так строятся проверка существования,
  индекс потребителей, snapshot'ы и пакет импорта — без знания схемы типа.
- В заголовке `type` — всегда закреплённая ссылка; `by` — следующая ссылка на сессию.
- Импорт — пакет неизменных строк с замыканием по ссылкам тела и заголовка; копия неизменна (ADR-4).

### 6. Тип — тоже объект

```json
{ "id": "core/type", "type": "core/type@1", "version": 1, "at": "…", "by": "core/genesis",
  "body": {
    "identity": "assigned", "mutable": true,
    "extends": null,
    "grain": ["name"],
    "schema": { "level": "hard", "type": "object", "required": ["identity", "mutable"], "additionalProperties": false, "…": "…" },
    "rules": [{"$ref": "core/rule.type-shape@1"}],
    "refs": "pin",
    "doc": "Тип объектов. Тип этого объекта — он сам."
  } }
```

Поля тела типа (все, кроме `identity` и `mutable`, необязательны; `schema` обязательна у `core`, `std` и
импортируемых типов):

| Поле | Что задаёт | Где описано |
|---|---|---|
| `identity`, `mutable` | вид объекта (п. 2) | kernel |
| `extends` | один родитель; наследуется контракт — правила, роли, `writers`/`inForce` — только с сужением; вид предка сохраняется; карточка не наследуется, заимствуется ссылкой (ADR-12). Цепочка ацикличная с учётом строк коммита, глубина ≤ 4; `migrate` — по цепочке | kernel |
| `grain`, `grain_scope` | измерения зерна — пути в теле; область уникальности (ADR-27) | [11](11-identity-grain.md) |
| `rules` | закреплённые ссылки на правила | [13](13-rules.md) |
| `schema` | форма тела (подмножество JSON Schema) — правило с уровнем (ADR-9); у `core`, `std`, импортируемых — обязательна и закрыта. Новая версия общего или `content`-типа принимает всё, что принимала прежняя; иначе — план миграции или новый `id` | [13](13-rules.md) |
| `roles`, `key` | для типов фактов: допустимые роли и ключ факта | п. 7 |
| `writers`, `inForce` | для типов фактов: кто вправе писать и когда факт действует (ADR-6) | п. 7 |
| `refs` | политика ссылок на объекты этого типа: `pin` / `follow` | [15](15-catalog.md) |
| `card` | шаблон карточки для поиска | [20](20-lens.md) |
| `doc` | описание для людей и для поиска типов | — |

Правило `core/rule.type-shape` проверяет только поля, которые читает код ядра: `identity`, `mutable`, `extends`,
`rules`, `schema`, `roles`, `key`, `writers`, `inForce`, `refs`, `grain`, `grain_scope`. `card` и `doc` проверяет
домен-потребитель; столбец «Где описано» — владелец описания поля, не граница проверки.

`core/type` имеет тип `core/type@1` — цепочка замыкается, как `type(type) is type` в Python. Это единственная
самоссылка по `type`; мета-тип один. Генезис записывает его первым; проверка «тип существует» для него выполняется
по самому себе.

### 7. Факт — событие особой формы

Факт (T47) — объект-событие, тип которого расширяет `core/fact`. Его тело:

```json
{ "of": { "group": {"$ref": "warrant/SOL-…"}, "member": {"$ref": "warrant/REQ-VER-007@4"} },
  "value": true }
```

- `of` — роли → ссылки; допустимые роли и их типы объявляет тип факта (`roles`).
- `writers` типа — кто вправе писать факт: владелец пространства цели, допущенные через `core/grant` или «любой»
  (по умолчанию — для накопительных фактов); `inForce` — когда факт действует. Проверяет примитив `owner`
  ([13](13-rules.md)) при коммите по цепочке `by` → сессия → участник (ADR-6).
- `key` типа — роли, которые определяют «тот же факт»: **текущий факт — последний по `seq` с этим ключом среди
  записей допущенных `writers`** (T-6, ADR-6). Пустой `key` — факты накапливаются (утверждения, подсказки); какое
  утверждение сессии текущее, выбирает [14](14-trust.md) (ADR-5).
- `value` — любой JSON; у историзуемых фактов единственный способ окончания — `value: false`. Голос «−1» влияет на
  доверие и `inForce`, но факт не заканчивает.

Так выражаются членство, алиас, вывод из обращения, утверждение, подсказка, допуск, держание — один механизм.

**Держание** (`core/holds`, T130) — тип генезиса. Шаг коммита пишет его вместо no-op, когда сессия записывает
значение, которое уже есть в хранилище, а пространство сессии (из `id` в `by`) его ещё не держит; тело значения
остаётся одно.

```json
{ "of": { "namespace": {"$ref": "warrant/namespace"}, "value": {"$ref": "#3fa29c0d71be44a2…"} }, "value": true }
```

Роли: `namespace` → `core/namespace`, `value` → `content`-тип; `key` — `[namespace, value]`; `writers` — любой.
Держание — провенанс, не голос: в доверие не входит; голос автора — через `core/assert` ([14](14-trust.md)).

### 8. Генезис и слои

| Слой | Пространство | Что | Как меняется |
|---|---|---|---|
| ядро | `core` | `type`, `rule`, `fact`, `assert`, `holds`, `member`, `alias`, `retire`, `deprecate`, `grant`, `proposal`, `snapshot`, `namespace`, `actor`, `session`, `commit`, `trust-policy`, правила-основы; сессия `core/genesis` | только новой версией кода ядра |
| библиотека | `std` | `knowledge`, `capability`, `card`, `cue`, `term`, `domain`, `need`, `distinct`, `alias-candidate`, `solution`, `link`, `pipeline`, `setup`, `ctx`, стадии, `measurement`, `execution`, `verdict`, `gap`, `bench-set`, `bench-plan`, `bench-run`, политика доверия по умолчанию | как любые данные: версии, владелец — сопровождающий LATTICE |
| проект | `warrant`, … | типы проекта (расширяют `std`), объекты, факты | владелец проекта |

- **Генезис порождается кодом ядра**, не читается из файла; хэш генезиса — константа версии ядра, сверяется при
  открытии хранилища (T23). Объекты генезиса пишет сессия `core/genesis` — объект `core/session` в самом генезисе;
  её `by` — она сама.
- `std` — типы механизма (потребность, решение, конвейер …); предметные типы — в проектах через `extends`. Блок —
  не тип, а признак: объект, у типа которого есть `card` (T66).

Код ядра знает только: форму ревизии, хэш, каноническую форму, ссылки, режимы идентичности, факты с ролями и
примитивы проверок. Что такое «потребность» или «решение» — знают данные `std`. Ядро — не весь код системы:
журнал, доверие, каталог, интерпретатор выходят обычными релизами (T21).

## Операции (контракт ядра, чистые функции)

| Операция | Вход → выход |
|---|---|
| `canonical(json)` | → строка |
| `hash(typeId, body)` | → hex64 |
| `parseRef(s)` / `formatRef(id, v?)` | ↔ `{id, version?}` |
| `refsOf(body)` | → все `$ref` тела (обход) |
| `newId(namespace)` | → ULID-id |
| `valueId(typeId, body)` | → `#hex32` |
| `revision(input)` | → заполненная ревизия (без проверки правил) |

## Инварианты

1. `id` ревизии не меняется; пара `(id, version)` уникальна в журнале.
2. У объекта с `mutable: false` есть только `version: 1`.
3. У значения `id == "#" + hash[0:32]`.
4. `type` в заголовке — закреплённая ссылка на существующую ревизию типа (для `core/type@1` — на саму себя).
5. Каждая ссылка в теле разрешается (правило `ref-exists`, уровень задаёт тип).

## Решения

| ID | Решение | Почему |
|---|---|---|
| KR-01 | Одна форма записи для всего: ревизия `{id, type, version, at, by, body}` | один механизм хранения, проверки, истории (P1, P12) |
| KR-02 | Заголовок фиксирован и минимален; тело открыто | «ограничений нет — ограничивают правила» (P2) |
| KR-03 | Версия в заголовке, целое ≥ 1; ревизия неизменна; запись того же тела — no-op | версия ≠ содержимое; повтор не плодит версий |
| KR-04 | Два флага типа дают три вида: сущность, событие, значение; значения интернируются | как mutable / immutable / hashable в Python |
| KR-05 | Хэш = sha256 канонической формы `{id типа без версии, body}` | содержимое узнаётся независимо от версии типа |
| KR-06 | Каноническая форма JSON — своя функция ядра | одинаковые байты на любой машине |
| KR-07 | Ссылка — `id` или `id@n`; в теле — `{"$ref"}`; ядро находит ссылки обходом | ссылки видны без схемы: потребители, snapshot, проверки |
| KR-08 | Тип — объект; `core/type` типизирован самим собой | самоописание (P9) |
| KR-09 | `extends` — ровно один родитель | без MRO и конфликтов; композиция вместо иерархий |
| KR-10 | Смена типа сущности — новая версия с другим `type`; `id` не меняется | классификация не меняет identity |
| KR-11 | Слои `core` (код) → `std` (данные) → проект | малое замороженное ядро, остальное — данные |
| KR-12 | Грамматика `id` (п. 4); значения — без пространства имён | переносимость, дедупликация между проектами |
| KR-13 | Факт — событие с `{of: {роль: ref}, value}`; ключ факта — в типе | один механизм для членства, алиасов, утверждений, подсказок |
| KR-14 | Удаления нет | закреплённые ссылки разрешаются всегда |

## Вопросы для grilling

1. **`by` — сессия или участник?** Рекомендация: сессия; независимость подтверждений считается по сессиям, участник
   выводится из сессии.
2. **Хэш — от типа без версии** (KR-05)? Альтернатива — с версией: смена версии типа меняет identity всех значений.
   Рекомендация: без версии.
3. **Длина `id` значения** — 32 hex (128 бит)? Рекомендация: да; коллизия практически невозможна, строка читаема.
4. **Время `at`** — только время записи или ещё «время действия» у фактов (битемпоральность)? Рекомендация: только
   время записи; «действует с» — поле `value`, если понадобится типу.
5. **Факт как объект**: факты — полноценные события в журнале (много строк), а не отдельный вид записи.
   Рекомендация: да — одна форма записи важнее экономии; индекс отделяет факты от узлов графа.
