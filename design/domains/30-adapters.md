# 30. adapters — реализации портов, корень сборки, хост и CLI

**Назначение.** Подключить внешнее — хранилище, технологию оценки, LLM, источник проекта — так, чтобы домены о нём не знали. Контракт порта определяет домен-потребитель (ADR-24); этот домен — реализации портов, корень сборки, проводка, хост, который открывает сессии, и CLI.

**Зависит от:** контракты портов — `store`, `clock`, `ids` ([12](12-ledger.md) §5), `judge` ([20](20-lens.md) §5), `composer`, `source` ([21](21-compose.md) §8), `Progress`, `Meta`, `describe()`, обёртка `Recording` ([22](22-run.md) §3); `std/setup` и операции `solve`, `answer`, `verdict`, `learn`, `replay` ([22](22-run.md)); коммит и `open()` ([12](12-ledger.md) §2); реестр участников, сессия, `purpose`, `software` ([14](14-trust.md) §1); обновление `std` ([15](15-catalog.md) §1); кампания стенда ([23](23-bench.md) §3); типы `std/knowledge`, `std/term` ([20](20-lens.md) §2), `std/domain`, `std/alias-candidate` ([11](11-identity-grain.md)), `std/bench-item`, `std/bench-set` ([23](23-bench.md) §1). Что кому можно импортировать — матрица [04](../04-architecture.md) §2. **Используют:** никто — корень сборки единственный импортирует `adapters/*`.

## Модель

### 1. Порты и адаптеры

| Порт | Контракт | Адаптеры | Фиктивный (тесты, срез S0) | Позже |
|---|---|---|---|---|
| `store` | `Store` — [12](12-ledger.md) §5 | `store-jsonl` | `store-memory` — журнал в памяти | SQLite, PostgreSQL (LG-09) |
| `clock`, `ids` | `Clock`, `Ids` — [12](12-ledger.md) §5 | системные | фиксированное время и счётчик ULID | — |
| `judge` | `Judge`, `Scored`, `Chosen` — [20](20-lens.md) §5 | `judge-jev` (TypeSafe) | `judge-fixture` — баллы по пересечению слов + переопределения из фикстуры | любая модель оценки, локальный классификатор |
| `composer` | `Composer` — [21](21-compose.md) §8 | `composer-claude` (API), `composer-caller` (агент) | `composer-fixture` — ответы из фикстуры по `(kind, смысловой ключ задания)`: потребность и id кандидатов, не хэш промпта (ADR-41) | другие LLM |
| `source` | `Source`, `Place` — [21](21-compose.md) §8 (чтения стадий) | `source-warrant`, `source-files` | `source-fixture` — каталог с 10–20 маленькими нормами | адаптеры других проектов |
| `loader` | `Loader` — здесь, §5 (загрузка, потребитель — хост `lattice load`) | `source-warrant`, `source-files` (тот же адаптер, что `source`) | `source-fixture` | адаптеры других проектов |
| `progress` | `Progress` — [22](22-run.md) §3 | `progress-fs` — файл хода `.lattice/runs/<id>.log` (T155) | `progress-memory` | — |

- Порта `exec` нет: способностей проектов вне пакета в v1 нет, шов без адаптера и потребителя не заводится ([22](22-run.md) RN-42).
- **Обёртка `Recording`** ([22](22-run.md) §3, T197, ADR-44): над портами `Deps` — кэш по ключу потребителя, проверка ключей ответа (LN-18), сверка `Meta.model` (у портов LLM), запись вызова в `calls`; что она делает над записанным адаптером — [22](22-run.md) §3. Адаптеры портов LLM сжимаются до транспорта: запрос поставщику, `Meta`, `describe()`; своего кэша и проверок у них нет.
- `Meta` и `describe(): Ident` портов LLM — [22](22-run.md) §3. Адаптер отдаёт в `Meta` цену, время, токены, своё — в `detail`: для рантайма он непрозрачен — не идентичность и не ключ кэша ([22](22-run.md) §3).
- **Контрактные тесты:** у каждого порта — общий набор; живой и фиктивный адаптер проходят один и тот же (контракт `Store` — [12](12-ledger.md) §5).
- **Ошибка адаптера** — `{adapter, code, status?, retryable}`, без тела и заголовков ответа поставщика: в них бывают ключи и данные запроса. Рантайм кладёт её в `error` стадии ([22](22-run.md) §3).
- **Код адаптера** (проверяет тест структуры; матрица — [04](../04-architecture.md) §2): адаптер импортирует интерфейс своего порта и ядро, но не другие адаптеры и не реализации доменов (AR-06). Пакеты из `dependencies` (SDK поставщика) и встроенные модули ввода-вывода (`node:fs`, `fetch`, `process.env`) — только в `adapters/` и `cli/`.
- Версия контракта — в экспорте адаптера (`contract: "source@1"`); корень сборки сверяет её при сборке.

### 2. Корень сборки и проводка

**Корень сборки** (T166, ADR-41) — `assemble(config, vars, overrides?) → {runtime, refusals}` в `src/cli/wire.ts`, единственном модуле, который импортирует `adapters/*`: `vars` — переменные окружения процесса (для `{"$env"}`), `overrides` — адаптеры тестов вместо системных (`store-memory`, `progress-memory`, фиксированные `clock` и `ids`). Проверки идут **названными фазами**; отказ несёт фазу и путь поля, следующая фаза после отказа не идёт:

| Фаза | Что делает и проверяет | Отказы |
|---|---|---|
| 1. схема | проводка `lattice.config.json` по `config/2`; `$env` — из `vars` | неизвестный ключ; секрет литералом, а не `{"$env"}` (T127); переменной окружения нет |
| 2. открытие | создаёт хранилище по `data` проводки (`store-jsonl`; в тестах — `overrides.store`) и зовёт `open()` со списком проекций ([12](12-ledger.md) §2, 04 §4) | генезис вне цепочки, расхождение маркеров, метка копии в основном хранилище (AD-15), `namespace.policy` не `std/policy` (LG-27) |
| 3. `setup` | `<пространство>/setup` из журнала ([22](22-run.md) §1) | нет `setup` |
| 4. привязки | адаптер на каждый порт `setup.ports` — живой или фиктивный, **тем же путём** (ADR-28) | у адаптера из `setup.ports` нет привязки; версия контракта адаптера ≠ порту |

Выход — `runtime: Runtime = {store, deps, progress, clock, ids, manifest, env}` ([22](22-run.md) §3): `deps` (T133) в обёртке `Recording`, `progress` — `progress-fs` (в тестах `progress-memory`), `manifest` — манифест кода, `env` — версии среды (T182). Рантайм не читает ни процесс, ни файловую систему. Модель порта против `setup` (алиас провайдера) сверяет не корень сборки, а таблица отказов старта рантайма ([22](22-run.md) §3) — по `describe()`. Таблицу отказов S0 проверяют тесты `assemble` ([05](../05-slices.md)).

- **Фиктивные адаптеры портов `setup.ports` (`judge`, `composer`, `source`) подключаются тем же путём, что живые** — через `setup.ports` в журнале: `judge-fixture`, `composer-fixture`, `source-fixture` — такие же адаптеры в ревизии `std/setup`. Фиктивную `setup` для `init` даёт семя тестов или `lattice init --setup <файл>` — `init` пишет `<пространство>/setup@1` из файла вместо умолчания. Порты вне `setup.ports` — `store`, `clock`, `ids`, `progress` — выбирает корень сборки: по проводке, в тестах — `overrides`.
- **Манифест кода** (T193, ADR-42) — сборка пакета генерирует `{модуль → {package@version, sha256}}` для модулей стадий `builtin` и адаптеров; тесты фиксируют его. Из него — `code` кортежа исполнения (зерно — модуль, [22](22-run.md) §1) и `impl.pins` в `std`-JSON: правка модуля меняет только его хэш, релиз, не тронувший модуль, не меняет ни `std`, ни кортеж.

**Проводка** (`bindings`, T128) — файл `lattice.config.json`, «где лежит». «Что лежит» (конвейер, адаптеры портов, модели) — `std/setup` в журнале (ADR-28, [22](22-run.md) §1):

```json
{ "$schema": "lattice://config/2",
  "namespace": "warrant",
  "data": ".lattice",
  "bindings": {
    "judge-jev":       { "endpoint": "https://…", "key": { "$env": "JEV_API_KEY" } },
    "composer-claude": { "key": { "$env": "ANTHROPIC_API_KEY" } },
    "source-warrant":  { "root": "D:/project/WARRANT" } } }
```

- Строгая схема. Запуск отменяется до первого вызова с фазой и путём поля — таблица фаз `assemble` выше; `model` в `setup` — алиас провайдера — отказ старта рантайма (сверка `describe()`, [22](22-run.md) §3).
- **Запасного адаптера нет** (PF-03): нет ключа или привязки — отказ, а не тихая подмена (judge → только BM25). Запасной режим — отдельная ревизия `std/setup`; она проходит стенд как любая другая.
- Моделей в проводке нет: они только в `std/setup`, точной версией (ADR-28).
- Значения, разрешённые из `$env`, хост регистрирует в проверке «нет зарегистрированных значений». Её проходят коммит ([12](12-ledger.md) §2, шаг 3) и каждый писатель `.lattice/` (§4).

### 3. Хост — кто открывает сессии

**Хост** (T164) — процесс команды CLI. Он открывает сессии (ADR-25), ставит `purpose` и `software` ([14](14-trust.md) §1) и вызывает операции доменов; пишущий участник сессию сам не открывает.

- **Кто действует:** `--as <участник>`, по умолчанию — переменная `LATTICE_ACTOR`. Нет ни того ни другого — пишущая команда отказывает с подсказкой. Читающие команды (`explain`, `lint`, `replay`, `rebuild --check`) сессий не открывают. Вид и модель участника — из реестра владельца; вне реестра — `agent` с неизвестной моделью, все такие — одна группа `(agent, unknown)` (ADR-26); сессия несёт `actor: null` и `claimed` — имя из `--as` ([14](14-trust.md) §1).
- **Личность — заявление вызывающего:** хост её не проверяет (допущение модели угроз, [14](14-trust.md) «Вне объёма»), но держит границу и пишет наблюдённое. Участника `kind: human` называет только `--as` в интерактивном терминале с подтверждением — `claimed_via: tty`; `LATTICE_ACTOR` или `--as` без терминала с человеком — отказ. В сессию хост пишет `claimed_via` (`flag` \| `env` \| `tty`) и `os_user` — хэш имени пользователя ОС с солью `origin` пространства. Участника `kind: machine` не называет никто: `--as` и `LATTICE_ACTOR` с ним — отказ; сессии `machine` (`learner`, парсер, симуляторы) хост открывает сам своими командами ([14](14-trust.md) TR-16). `LATTICE_ACTOR` агенту задаёт оркестратор на его процесс — имя агента из реестра; в профиле оболочки человека переменной нет. Решающие акты (`declared`, решающее «−», ревизии владельца-человека) — только человек; агент предлагает (`core/proposal`, вердикт с весом своей группы).
- **Одна сессия на участника команды;** ревизию сессии пишет хост (`by` — она сама, [14](14-trust.md) §1); `purpose` — имя команды, кроме сессий `learn` и `simulate` (таблица ниже) (`init`, `update`, `load`, `solve`, `answer`, `verdict`, `regrain`, `bench`). Эти значения, кроме `bench`, резервирует этот домен; `bench`, `simulate`, `learn` — их владельцы ([14](14-trust.md), [23](23-bench.md), [22](22-run.md)). **Перечень закрыт**: значения и их свойства (питает ли доверие, учит ли, считается ли в окне) — одна таблица [14](14-trust.md) §1 (ADR-40); здесь — только какая команда открывает сессию с каким `purpose` (таблица ниже); других значений хост не пишет. Новое значение — строка таблицы 14 и, если его читает гейт, новая версия ядра (AD-15).
- **Участников `machine`** хост берёт из реестра сам: `init` регистрирует `<пространство>/learner` (сессии `learn`, [22](22-run.md) §6); первый `load` регистрирует участников адаптера `source` сессией владельца. `software` парсера — `имя@версия`; смена версии — новая сессия того же участника (T148).

| Команда | Сессии: участник · `purpose` |
|---|---|
| `init`, `update` | владелец проекта · `init` / `update`; копии `std` сохраняют сессию пакета `std/release-<версия>` ([15](15-catalog.md) §1) |
| `load` | владелец · `load` — реестр и допуски участников адаптера; парсер (`machine`, `software`) · `load`; автор обогащения (`agent`) · `load` |
| `solve`, `answer` | вызывающий (`--as`) · `solve` / `answer` |
| `verdict` | потребитель (`--as`) · `verdict`; затем `<пространство>/learner` · `learn` |
| `learn` | `<пространство>/learner` · `learn` |
| `bench` | `--as` · `bench`; симуляторы · `simulate` — только в копии кампании ([23](23-bench.md) §3) |
| `regrain` | владелец · `regrain` |

| `runs/<id>.log` | файл хода вызова (T155, [22](22-run.md) §3) | адаптер `progress-fs` порта `Progress` | нет; удаляется после коммита |

| `reports/` | отчёты для человека (первый запуск — `first-run.md`) | хост | нет |

Каждый писатель проходит проверку «нет зарегистрированных значений» (AD-06, T-12). Хранилище — только локальный диск; сетевые файловые системы не поддерживаются ([12](12-ledger.md) LG-06).

**Допущение модели угроз** ([12](12-ledger.md) LG-19): `.lattice/` лежит в каталоге проекта, пишет его только хост, каталог — в `.gitignore` и вне облачной синхронизации. `init` и `open` предупреждают, если `.lattice/` под git (не в `.gitignore`) или в синхронизируемой папке (OneDrive и подобные). Что всё же склеилось, ловит `open()`: `hash` маркера каждого коммита против его строк и строгий рост `seq` — отказ с адресом. Основное хранилище (`.lattice/`, не `bench/<run>/`) с меткой копии `std/bench-copy` `open()` не открывает — отказ с адресом метки: копия кампании, скопированная поверх основного журнала, или метка, записанная в него в обход `lattice bench`, не учат тихо (AD-15).

### 5. Адаптеры

#### `store-jsonl`

- Реализует `Store` ([12](12-ledger.md) §5): `append` — под замком `lock` проверка `tail` и `expect`, дописывание строк и маркера `core/commit` с `fsync`; `scan` отдаёт только целые коммиты; `history` не реализует (есть `scan`); `saveIndex` / `loadIndex` — `index.json`.
- Один писатель: замок с владельцем и сроком; чужой непросроченный замок — ожидание со сроком, затем отказ `locked` (ADR-31); просроченный снимается; перед дописыванием `append` перечитывает `lock` — замок свой и не просрочен, иначе `locked` (ограждение, [12](12-ledger.md) §5).
- Переход на SQLite (порт не меняется) — по триггеру LG-09: p95 пересборки индекса выше порога; порог — замером первого запуска, объём файла — справочно (ADR-23). `store-memory` — тот же контракт в памяти, для тестов.

#### `judge-jev` — технология оценки TypeSafe

- `score` → оценка релевантности каждой карточки по шкале, балл на каждую (`scores` = `items.id`, [20](20-lens.md) LN-18); `verify` → вопрос «то же ли» — совпадение двух формулировок или блоков, не истинность (P13, ADR-37); `choose` → выбор из вариантов. Вопросы одного запроса независимы и идут параллельно; композиция — в стадиях ([20](20-lens.md) §5).
- `state` (словарь области и описание) — один раз на запрос; у `judge-jev` в замере черновиков это дало −42 % токенов. Это свойство адаптера, не порта: у обычной LLM тот же эффект — только кэшем префикса или пакетным вызовом; цену на принятый результат меряет стенд.
- `describe()` → `{adapter: "judge-jev", model, prompts: {score, verify, choose}}` — `prompt_hash` шаблонов вопросов; рантайм сверяет его с `std/setup` и `calibrated_for` ([22](22-run.md) §3). `Meta.model` — модель из ответа сервиса; если сервис её не возвращает — модель запроса, и эндпоинт остаётся допущением AR-09 (RN-32).
- Кэш `cache/judge/` по ключу `(адаптер, модель@версия, prompt_hash, state_hash, norm, card id)` ([20](20-lens.md) §6) ведёт обёртка `Recording`, не адаптер (ADR-44). Ключ API — ссылкой `{"$env"}` из проводки.
- Исходные замеры (черновики): ~$0,002 и ~1 с на вопрос при пуле ~200 карточек; оценщик видит заголовок и первый абзац — 2,5 % текста документа ([20](20-lens.md) §1).

#### `composer-claude`

- Вызов модели Claude с JSON-схемой выхода; модель — из `std/setup`, точной версией (ADR-28); промпт стадии — из её `params`, `prompt_hash` считает рантайм ([21](21-compose.md) §8). `describe()` → `{adapter: "composer-claude", model}`.
- Кэш `cache/composer/` — по ключу потребителя ([21](21-compose.md) §8), ведёт обёртка `Recording` (ADR-44). Попадание экономит оплату, но ответ всё равно пишется в `calls` вызова ([22](22-run.md) §3, §7).
- Выход проверяется схемой задания; невалидный выход — ошибка стадии, не «лучшее, что получилось» (AD-05).

#### `composer-caller` — режим агента

- Модель не вызывает: задание уходит вызывающему агенту. Режим задаёт ревизия `std/setup` — `ports.composer = {adapter: "composer-caller", model: "<точная версия модели агента>"}`, а не флаг вызова (AD-03). `describe().model` — модель из `setup`: проверить её адаптер не может, это слово вызывающего, как личность у хоста. Поэтому рантайм сверяет его с моделью участника сессии из реестра: `model` участника ≠ `setup.ports.composer.model` — отказ на старте ([22](22-run.md) RN-32); остаток — допущение «агент назван верно» (личность, ADR-25).
- Протокол (ADR-19, [22](22-run.md) §3):

```text
lattice solve "<задача>"   → pending: stdout {status: "pending", execution, task: {kind, prompt_hash, input, schema}},
                             отдельный код выхода; в журнал — ничего; ход — park с кортежем вызова (Progress)
lattice answer <execution> <json|@файл>
                           → ответ по схеме task (AD-05) → дописать в .lattice/answers/<execution>.jsonl
                             с ключом (kind, prompt_hash, хэш input) → перезапуск вызова с тем же id
перезапуск                 → кортеж ≠ записанному при begin (ревизия setup, код, промпт) → ответы сброшены,
                             задание уходит заново (ADR-41); иначе composer-caller отдаёт записанные ответы
                             по ключу; первое новое задание — снова pending; judge — из кэша;
                             коммит вызова (ok или error) → ход и файл ответов удаляются (Progress.end)
```

- Истина — `calls` трассы `std/execution`, не файл ответов; кэша у адаптера нет (Ф-3).
- **Брошенный вызов:** ход `pending` старше `pending_ttl` (параметр хоста, по умолчанию 24 ч) закрывает следующая `lattice solve` или `lattice answer` — вызовом с ошибкой `abandoned` своей сессией ([22](22-run.md) RN-37): брошенные отдаёт `Progress.abandoned(now, ttl)`, стадии и время — из хода, ход и ответы удаляются; `lattice answer` на этот вызов — отказ. Читающие команды брошенные вызовы не закрывают.

#### Порт загрузки `Loader`

Контракт — здесь: потребитель — хост (`lattice load`), не стадии (ADR-24, разбор 2026-09-29, кандидат 11). Чтения стадий — порт `Source` ([21](21-compose.md) §8); один адаптер проекта реализует оба.

```ts
interface Loader {
  load(): AsyncIterable<RevisionInput>   // T129: полный перечень блоков источника, не только изменённые
}
```

- **Полный перечень** (CP-19): пишутся только изменённые (no-op), а живой объект пространства из прежних загрузок, которого в перечне нет, получает находку `std/load-finding {kind: missing}` (§6); вывести его из обращения (`core/retire`) решает владелец. Вернулся в источник — находка снимается (`value: false`).
- **`text_hash`** (T181, CP-23, ADR-36): `load()` пишет в тело блока `sha256` текста, который вернёт `Source.text(ref)` (переводы строк → LF). Правка текста блока — новая ревизия; без правки — no-op. Контрактный тест пересекает оба порта: хэш `text()` сразу после `load()` равен `text_hash`.
- **`id` блока — устойчивый якорь источника**: внешнее имя, которое не меняется от вставки соседей; порядковый номер пункта якорем не бывает — у пункта без своего якоря блок — документ целиком (CP-19).
- Replay записывает только сторону `Source`; фикстуре чтения `Loader` реализовывать не нужно.

#### `source-warrant` — первый проект

- `load()` (порт `Loader`, T129) отдаёт ревизии загрузки:
  - **Нормы** — парсер разбирает структуру документов WARRANT: `warrant/<внешний ID>` (`REQ-…`, `SCN-…`, `ADR-…#п`, `TERM-…`); `#п` — только собственный якорь пункта в тексте ADR, не его порядковый номер; без якоря блок — ADR целиком ([21](21-compose.md) CP-19), тип `warrant/norm` (расширяет `std/knowledge@1`, карточка — ссылкой на его шаблон, [20](20-lens.md) §2). Тело — только извлечённые поля: `title`, `summary` — первый абзац нормы, `refs` (документ, код, тесты) и `text_hash` — хэш полного текста нормы, который вернёт `text(ref)` (ADR-36): правка текста за первым абзацем — новая ревизия. Автор — сессия парсера (`machine`, `software: warrant-parser@<версия>`) → основание `derived`.
  - **Обогащение из units доменов** (370, написаны LLM) — автор `agent` `warrant/units` → `inferred`. `summary` units — факт `warrant/summary` (`of: {norm: ref@n}`, значение — текст; тип проекта, [14](14-trust.md) TR-09); в карточку не входит — служит `explain` и базовой линией стенда. Алиасы — `std/alias-candidate` (ADR-8): в силу входят только через `core/alias` владельца.
  - **Расхождения** парсера и units (нормы нет, другой заголовок, другой домен) — `std/load-finding` (§6).
  - **Домены:** `lifecycle` (`LCY`), `cli-core` (`CLI`) → `std/domain` + членство норм.
  - **Словарь:** `docs/02-vocabulary.md` → `std/term {scope, label, doc?}`; синонимы — подсказки `std/cue` с целью `term`.
  - **Набор стенда:** вопросы и эталоны → `std/bench-item` и `std/bench-set {scope, items: [ref@n]}`; данные — от владельца.
- Повторный `load` пишет только изменённое (no-op — [12](12-ledger.md) §2) и снимает исчезнувшие расхождения (`value: false`). Норма, которой в источнике больше нет, — находка `missing` (§6); норму не выводит из обращения загрузка, а владелец (`core/retire`).
- `text(ref)` → `{text, revision}` — полный текст блока и ревизия содержимого источника (коммит WARRANT); ревизия уходит в `execution.source` (PF-04). Текст читается из рабочего дерева: совпадение с `ref@n` сверяет `deliver` по `text_hash` ([22](22-run.md) §4).
- `locate(ref)` → `{places: [{kind, path, lines?}]}`; `grep(q, scope)` → `Ref[]` по тексту блоков области (self-search); `find(q, scope?)` → `{places}` по сырому репозиторию — места для дыры покрытия ([21](21-compose.md) §8). Путь и строки вычисляются при чтении и не входят в identity.

#### `source-files` — простой проект

- Каталог `root` (+ `glob`): файл — блок `std/knowledge`; заголовок файла (front matter) — `id`, `title`, `domain?`, `refs?`; `summary` — первый абзац; `text_hash` — хэш текста файла (ADR-36). Автор — участник `machine` адаптера → `derived`.
- Новый простой проект подключается без нового адаптера: `source-files` (порты `source` и `loader`) выбран в `setup.ports` его хранилища (`lattice init --setup <файл>`), корень — в проводке `bindings`; проверка — E7 первого запуска ([01](../01-first-run.md)).

### 6. Находка загрузки — `std/load-finding` (T165)

```json
{ "type": "std/load-finding@1", "by": "warrant/SES-…",
  "body": { "of": { "target": {"$ref": "warrant/REQ-VER-007"} },
            "value": { "kind": "title-mismatch", "note": "units: «…»; парсер: «…»" } } }
```

- Факт (`extends core/fact`, KR-13): ключ `(target, kind)`; `writers: {purpose: load}` — сессии загрузки ([10](10-kernel.md) §7); `value: false` — расхождение снято следующей загрузкой.
- `kind`: расхождения парсера и units (`title-mismatch`, нормы нет в units, другой домен) и `missing` — блока, записанного прежними загрузками, нет в полном перечне `load()` ([21](21-compose.md) §8, CP-19).
- По журналу не пересчитывается (наблюдение внешнего источника), поэтому это факт, а не отчёт (ADR-10, [13](13-rules.md) RL-06). В доверие не входит; владелец видит действующие находки запросом по типу.

## Инварианты

1. `adapters/*` импортирует только корень сборки; адаптеры не импортируют друг друга; пакеты и ввод-вывод — только в `adapters/` и `cli/` (AD-01).
2. Живой и фиктивный адаптер порта проходят один контрактный набор (AD-07).
3. Ни один файл `.lattice/` не содержит значения секрета: в проводке — только `{"$env"}`, писатели проверяют зарегистрированные значения (AD-06).
4. Проводка невалидна (фазы `assemble`) или модель — алиас (таблица отказов старта рантайма) → отказ до первого вызова; адаптер не подменяется (AD-08).
5. Выход Composer — любого адаптера — проходит схему задания до стадии (AD-05).
6. Каждая пишущая команда — сессии, открытые хостом; сессию `simulate` хост открывает только в копии кампании (AD-10, BN-04).
7. Кэши и `answers/` — ускорение и транспорт, не истина: их потеря не теряет данных журнала (AD-09, T-4).

## Вне объёма

- Флаг вызова `--composer caller` — нет: подмена мимо `setup@n` ломает гейт обучения (D12 Q1 (б)).
- Запасной адаптер при отсутствии ключа — нет (PF-03).
