# 14. trust — факты, утверждения, доверие

**Назначение.** Ответить «насколько этому верить» для любой ревизии и любого факта — вычислением из утверждений, а не присвоенным статусом (P5).

**Зависит от:** [10-kernel](10-kernel.md) (проекция полномочий `authority` — участник, вид, группа на `seq`), [12-ledger](12-ledger.md) (журнал, индекс фактов), [15-catalog](15-catalog.md) (владелец, допуски). Раздел индекса `trust` — проекция, которую подключает этот домен: 12 перечисляет раздел, но от 14 не зависит (механизм подключаемых проекций — [04](../04-architecture.md) §4, N-32).

**Используют:** lens (ранжирование и пометки), compose (повтор решений), run (обучение), bench (эталоны), adapters (хост открывает сессию).

## Модель

### 1. Участники, сессии, реестр

| Объект | Тело | Зачем |
|---|---|---|
| `core/actor` (сущность) | `{kind: human \| agent \| machine, name, model?}`; `model` обязателен при `kind: agent` | кто пишет; вид задаёт вес и группу независимости |
| `core/session` (сущность) | `{actor: ref@n \| null, claimed?, claimed_via?, os_user?, started, ended?, purpose, software?}` | сеанс участника; единица «последнего утверждения» |

- Каждая ревизия несёт `by` = сессия ([10](10-kernel.md) §1).
- **Реестр участников** (ADR-25). Вид участника и право декларанта берутся из реестра владельца пространства, а не из тела записи самого участника: `core/actor` — ревизии пространства проекта, их пишет владелец или допущенный ([15](15-catalog.md) «Кто что пишет»); детализацию `model` задаёт владелец. Декларант — допуск `core/grant {declare: true}` ([15](15-catalog.md) CT-13) — только участнику `kind: human`: допуск не-человеку отклоняет проверка `owner` при записи (`authority.mayWrite`, [10](10-kernel.md) §7, ADR-40), решающее «−» даёт только человек (T-1). Участник вне реестра получает вес и основание уровня `agent`.
- Сессию открывает хост-процесс, а не пишущий участник ([22](22-run.md), [30](30-adapters.md)); он же ставит `purpose` и `software`. **Ревизию `core/session` пишет хост**, её `by` — она сама (самоссылка, как у `core/genesis`); проверка `owner` пропускает `core/session` только с таким `by` ([13](13-rules.md) §2). Участник вне реестра — `actor: null` и `claimed` — имя из `--as` ([30](30-adapters.md) §3); группа — `(agent, unknown)`.
- **Личность — заявление вызывающего**; хост её не проверяет, но пишет в сессию наблюдённое им самим: `claimed_via` (T178) — как участник назван (`flag` — `--as` без терминала, `env` — `LATTICE_ACTOR`, `tty` — `--as` в интерактивном терминале с подтверждением) и `os_user` — хэш имени пользователя ОС процесса с солью — `origin` пространства (T144): совпадение пользователя видно, имени в журнале нет (KR-14). Участника `kind: human` называет только `tty`: `env` и `flag` с человеком — отказ ([30](30-adapters.md) §3). Так агент, запущенный из оболочки владельца, не пишет от имени владельца, а подмену видно по журналу постфактум («Вне объёма»). Хост пишет оба поля у каждой своей сессии; их нет только у сессий, которые хост не открывал, — `core/genesis` и сессий пакета `std`.
- `purpose` — строка, обязательна; значения — **закрытый перечень — таблица ниже** (ADR-40): новое значение — строка таблицы со всеми свойствами и решение гейта обучения, если он его читает (новая версия ядра, ADR-34). Какая команда хоста открывает сессию с каким `purpose` — [30](30-adapters.md) §3. Вне ядра `purpose` читает **только `classify`** («Операции», T192): доверие, окно удаления членства ([22](22-run.md) §6), подсказки LENS ([20](20-lens.md)) и стенд ([23](23-bench.md)) берут свойства сессии из неё, своих списков разрешённых не держат. В ядре `purpose` читают `authority` (`writers {purpose}`, [10](10-kernel.md) §7) и `learning-gate` — перечень [04](../04-architecture.md) §1. Значение вне таблицы — ни одного свойства: не питает, не учит, не считается (TR-12).

| `purpose` | Резервирует | `feedsTrust` — голоса входят в доверие | `teaches` — вердикты сессии учат | `countsInWindow` — голос в окне удаления |
|---|---|---|---|---|
| `init`, `update`, `load`, `solve`, `answer`, `regrain` | [30](30-adapters.md) | да | нет | нет |
| `verdict` | [30](30-adapters.md) | да | да — если гейт примет (засчитанный прогон, [13](13-rules.md) §2) | да |
| `learn` | [22](22-run.md) | голос посредника — автора `via` (§2) | нет | нет |
| `bench` | этот домен | нет — стенд меряет, а не голосует | нет | нет |
| `simulate` | [23](23-bench.md) | да — только в копии кампании, как рабочая сессия ([23](23-bench.md) §3) | да — только при метке копии `std/bench-copy` | да — в копии |
- `software` (`core/session.software`) — `имя@версия` программы, которой действует участник `machine` (парсер). Смена версии — новая сессия того же участника, не новый участник: иначе две группы независимости при коррелированных ошибках одного парсера.
- **Группа независимости** (ADR-26) — единица независимых подтверждений: `human` и `machine` — участник, `agent` — пара `(kind, model)`. Разные сессии одной группы поддержку не увеличивают. Группа `(agent, unknown)` — участники вне реестра — никому не «другая»: её голоса не дают `observed` и не входят в окно удаления членства (TR-16).
- **Реестр читается на `seq` голоса.** Вид и модель участника, владелец пространства цели и декларант для утверждения (и для голоса автора) — какими они были на `seq` этого утверждения, как допуск при записи (ADR-6): `core/session.actor` — закреплённая `actor@n`. Цепочку реестра этот домен не строит сам — берёт участника, вид и группу из проекции полномочий `authority.principal(session, seq)` ([10](10-kernel.md) §7, ADR-40), той же, по которой проверка `owner` решает право записи. `transfer`, отзыв `declare`, уточнение `model` действуют на следующие голоса и не переписывают прошлое доверие (TR-13).
- Владелец пространства (`owner`) — участник или список участников ([15](15-catalog.md) §1); владелец — любой член списка.

### 2. Утверждение

```json
{ "id": "warrant/01J8…", "type": "core/assert@1", "version": 1, "by": "warrant/SES-…",
  "body": { "of": { "target": {"$ref": "warrant/01J8…member-fact"} }, "value": 0.5, "reason": "used in answer" } }
```

- `target` — любой факт или ревизия. Следующая ссылка на ревизию разрешается при коммите: индекс относит утверждение к `id@n` на `seq` утверждения — правка объекта не переносит голос на новую ревизию (TR-13). **Основание — на одну ревизию или факт**, не на часть тела: составное тело, поля которого пришли из источников разной надёжности, делится на факты своих авторов. Норма WARRANT: ревизия парсера — только извлечённые поля; `summary` — отдельный факт автора `agent` о ревизии (тип проекта, определяет адаптер, [30](30-adapters.md)); алиасы — `std/alias-candidate` (ADR-8).
- `value` — надёжность −1…1. `reason` необязателен; при принятии предложения — обязателен ([15](15-catalog.md) CT-11).
- `via` — исходная сессия, когда запись пишет посредник (сессия `learn`, [22](22-run.md)). **Автор голоса — `via ?? by`** (ADR-5, ADR-47) — у утверждения и у любой записи с `via`. Запись с `via` — голос группы автора, но не решающий: `declared` и решающее «−» даёт только явное `core/assert` **без `via`** (TR-17). Этот домен не знает имён типов run: что у каждой строки, выведенной из вердикта, есть `via` — контракт run ([22](22-run.md) §6); «утверждения» здесь — `core/assert` и его наследники.
- **Голос хранит свои признаки на своём `seq`:** проекция `trust` держит у каждого голоса группу и вид (`authority.principal`) и свойства сессии (`classify`) на `seq` голоса. Смена политики перевзвешивает сохранённые голоса новыми весами и порогами — журнал не прогоняется; проекция не читает разделы, обновлённые той же строкой, поэтому её результат не зависит от порядка списка проекций ([12](12-ledger.md) §3, ADR-47).
- **Автор факта или ревизии неявно утверждает её с надёжностью +1.** Отдельного утверждения автора не пишется; голос автора идёт в основание, не в сумму спора (§3).
- Утверждения копятся ([10](10-kernel.md) §7, исключение); текущее выбирает этот домен:
  - **голос сессии** — её последнее утверждение по цели (переобуться можно, накрутить повтором нельзя);
  - **голос группы**: `human`, `machine` — последнее утверждение участника; `agent` — среднее голосов сессий группы (одна свежая сессия модели не переворачивает её прежние);
  - владелец пространства цели и декларант — последнее утверждение **участника** (ADR-5).
- Держание `core/holds` — провенанс, не голос ([10](10-kernel.md) §7).

### 3. Доверие — две оси

**Основание (`basis`)** — откуда известно: кем и как создана запись и сколько независимых групп её подтвердило. Выбирается высшее выполненное:

| Значение | Условие (пороги — политика, §4) |
|---|---|
| `declared` | действующее «+» (последнее явное `core/assert` участника без `via`) человека-владельца пространства цели или допущенного декларанта |
| `derived` | автор — `machine`, запись получена детерминированным разбором внешнего источника (документ, правило); сессия несёт `software` |
| `observed` | «+» от ≥ `observe_groups` разных групп независимости, из них ≥ 1 не из группы автора |
| `inferred` | иначе: поддержка только от LLM-агентов или одной группы |

- **Порядок** `declared > derived > observed > inferred` — единственное определение порядка оснований (его читают `inForce` типов фактов, [10](10-kernel.md) §7, и операция `inForce`): за `declared` отвечает владелец; ошибка `derived` воспроизводима и ловится проверкой разборщика; `observed` — независимые группы, но без ответственного; `inferred` — одиночный голос. Довод дизайна, опоры в базе знаний нет — пересмотр по данным стенда.
- **Вывод не отмывает основание.** Запись, выведенная из вердиктов (обучение, [22](22-run.md)), несёт `via` — сессию вердикта; её основание считается по этой таблице, как у любой записи: автор — `via ?? by`, то есть сессия вердикта ([22](22-run.md) §6), подтверждения — утверждения и вердикты других групп. `derived` ей недоступно: автор — сессия вердикта, не разбор источника; вид сессии-посредника `learn` записи не передаётся. `declared` — только «+» человека-владельца или декларанта явным `core/assert` без `via`: утверждение из вердикта владельца — обычный голос его группы (TR-17).
- «Сколько подтвердило» читается из поля `groups` выхода `trust()`, а не через `basis` (эталоны стенда, `std/cue`, §7).

**Состояние спора (`epistemic`)** — есть ли спор:

| Значение | Условие |
|---|---|
| `contested` | суммы «+» и «−» обе ≥ `contest_min`; или раскачка — историзуемый факт переключался ≥ `oscillation_cycles` раз |
| `rejected` | «−» ≥ `resolve_min`, «+» < `contest_min` — независимые группы отвергли (TR-14) |
| `unresolved` | модуль суммы < `resolve_min` |
| `settled` | иначе — итог «+» |

Условия проверяются сверху вниз; первое выполненное — значение.

Сумма = Σ голос группы × вес (ключ весов, §4) по группам, **кроме группы автора**. Голос автора в сумму не входит: свежая запись одного автора — `unresolved`, пока её не подтвердит другая группа.

**Перекрытие владельцем.** «−» человека-владельца пространства цели или декларанта явным `core/assert` без `via` решающее: `trust()` отдаёт `overruled: {by, at}`, какой бы ни была остальная поддержка. «−» агента-владельца и «−» с `via` (из вердикта владельца, например `wrong`) — обычные голоса в сумме (TR-17).

### 4. Политика доверия — объект типа `std/policy`

```json
{ "id": "std/trust-policy", "type": "std/policy@1",
  "body": { "weights": {"human": 1.0, "machine": 1.0, "agent": 0.5},
            "observe_groups": 2, "contest_min": 0.5, "resolve_min": 0.5, "oscillation_cycles": 2,
            "lens": {…}, "candidates": {…},
            "calibration": { "add_min_verdicts": 1, "verdict_weights": {…}, "removal_window": {"n": 3, "m": 5} } } }
```

| Поле | Что | Переопределяет проект |
|---|---|---|
| `weights` | вес голоса по ключу `kind` → `kind/model` → `kind/model@namespace` (берётся самый точный заданный); числа — допущение, калибрует стенд | да |
| `observe_groups` | порог `observed` | да |
| `contest_min`, `resolve_min`, `oscillation_cycles` | пороги спора | да |
| `lens` | `{exclude, mark}` — какие состояния доверия LENS исключает до judge и какие помечает ([20](20-lens.md)) | да |
| `candidates` | политика кандидатов в алиас: порог (ADR-13) — калиброванный порог `CalibratedThreshold` (T198, ADR-45): `calibrated_for` — под какую версию judge и каким прогоном он подобран (T136), `call: verify`, `onMismatch: mark` — расходится с judge из `setup` — кандидаты как без калибровки ([22](22-run.md) RN-35), бюджет — размер очереди владельца, не предел записи ([11](11-identity-grain.md) GR-17), кластер — одно решение, память отказов `std/distinct` (GR-12) | да |
| `calibration` | правила обучения ([22](22-run.md) RN-05): `add_min_verdicts`, `verdict_weights`, окно удаления членства `removal_window` (ADR-20) | только `std` |

- Значения `lens`, `candidates`, `verdict_weights` задают их потребители — [20](20-lens.md), [21](21-compose.md), [22](22-run.md); здесь — форма.
- Своя политика у каждого пространства имён (`namespace.policy`, [15](15-catalog.md)); по умолчанию — `std/trust-policy`. До второго проекта WARRANT ссылается на `std/trust-policy`. Ссылка **закреплена** `id@n` (`refs: pin`, [15](15-catalog.md) CT-16): `lattice update` с новой ревизией политики её не меняет; смена — ревизия пространства владельцем, `policy@n` входит в кортеж исполнения, и прежний `pass` стенда её не покрывает ([22](22-run.md) §1, RN-24).
- Тип политики — `std/policy`, не тип генезиса: ядро политику не читает (ADR-35); новый ключ — новая версия `std/policy` по совместимости схемы общего типа. Ядро проверяет только, что ссылка `namespace.policy` разрешается; цель не `std/policy` (или наследник) — такую ревизию `core/namespace` не собирает каталог (`setPolicy`, [15](15-catalog.md) «Операции»), а записанную в обход хоста ловит `open()` — отказ с адресом коммита ([12](12-ledger.md) §2, LG-27, ADR-47): один раз при открытии, не каждое чтение `trust()`; политика не подменяется.
- **Чья политика считает.** Доверие в хранилище считает политика проекта-владельца хранилища — `policy` его единственного пространства ([15](15-catalog.md) §1) — для всех целей, включая копии `core`, `std` и импортированных пространств; доверие, посчитанное поставщиком, — справочное (T-7). Выход `trust()` несёт `policy: id@version`; смена политики — ревизия и перевзвешивание сохранённых голосов (§2), журнал не меняется и не прогоняется.

### 5. Доверие составных вещей

- **Решение** (T82): доверие каждого членства отдельно; сводка решения — наименьшее основание среди членств; из состояний — худшее: `overruled` > `contested` > `rejected` > `unresolved` > `settled` (перекрытое членство поднимается в сводку).
- **Блок:** основание ревизии (кто и как написал) + утверждения на ревизию. Вердикты пишут утверждения на членства, не на блок: вердикты решений, где блок участвовал, — справка `explain`, в доверие блока не входят (иначе петля: доверие блока → выдача → вердикты → доверие блока).
- **Способность:** то же; вердикты исполнения — справка `explain`.

### 6. Чем доверие не является

- **Балл judge не превращается в утверждение.** Оценка — событие `std/measurement`, влияет на выдачу, но не на доверие.
- Число вызовов не является доверием: «18 000 оценок» ничего не говорит без вердиктов.
- Держание значения (`core/holds`) — не голос.
- Доверие не затухает со временем: устаревание решает статус snapshot'а (изменились версии членов или состав решения), а не возраст.
- Доверие не хранится — пересчитывается в индексе при каждом новом утверждении по затронутой цели.

### 7. Как доверие используется

**Балл решает только обратимое действие** (ADR-13). Действие по баллу judge без участника допустимо, только если оно обратимо и дёшево и его ошибку ловит последующий вердикт (потребителя или стенда); остальное решает правило, владелец или вердикт. Названное исключение — повтор решения (`recall`): выдача без поиска с полями `by: exact / judge / composer` и баллом `p`, доля серой зоны — в отчёте стенда ([23](23-bench.md)). Порог — по `max(scores.judge)` закреплённой версии judge, не по `fused` ([20](20-lens.md)). Для сущностей тот же приём запрещён: похожесть даёт только кандидата в алиас (`std/alias-candidate`, ADR-8, [11](11-identity-grain.md) GR-06).

| Где | Правило |
|---|---|
| повтор решения (`recall`) | по сводке решения (§5): `overruled`, `contested` или `rejected` → заново через LENS и Composer; иначе (`settled`, `unresolved`) — по основанию: ≥ `observed` → выдать без поиска (`by`, `p`), `inferred` → выдать с пометкой «не подтверждено». Пустое решение `recall` не выдаёт — всегда через LENS (TR-14) |
| правило выдачи — все пути | блок выдаётся, только если жив (не выведен из обращения) и его доверие не в `policy.lens.exclude`; пометки — `policy.lens.mark` и `deprecated`. Одна операция — `standing(target)` («Операции», ADR-47); её читают LENS (пул), `recall` (член не проходит → как `broken`: LENS по сохранённой потребности), проверка `add[]` вердикта и `materialize` (TR-15) |
| выдача LENS | доверие — пометка и фильтр по `policy.lens` (правило выдачи), не множитель к баллу (порядок решает стенд); перекрытое — исключается до judge ([20](20-lens.md)). Перекрытое при `support.plus` ≥ `contest_min` от других групп — находка `lint` владельцу: иначе ошибка владельца самозапечатывается — нет выдач, нет вердиктов (TR-04) |
| эталоны стенда | решения `observed` / `declared` — кандидаты в эталоны; сессии стенда доверие не питают |
| алиасы, подсказки | `core/alias` — управляющий факт: `inForce: write` — в силе по праву записи (`writers`, ADR-6), кандидат в силу не входит (ADR-8); `std/cue` — `inForce: {basis: observed}`; «в силе ли» отвечает операция `inForce(fact)` — потребитель (LENS, [20](20-lens.md) LN-10) порог не выводит сам |

## Операции

| Операция | Вход → выход |
|---|---|
| `assert(target, value, reason?, via?, by)` | → событие `core/assert` |
| `trust(target)` | → `{basis, epistemic, support: {plus, minus}, groups, overruled?: {by, at}, policy}` — то же хранит раздел индекса `trust` ([12](12-ledger.md) §3) |
| `explain(target)` | → голоса групп, из каких утверждений они взяты, и веса — почему такое доверие |
| `classify(session@seq)` | → `{group, feedsTrust, teaches, countsInWindow}` — свойства сессии: группа — из `authority.principal` ([10](10-kernel.md) §7), остальное — строка `purpose` таблицы §1; единственный читатель `purpose` вне ядра (T192, ADR-40) |
| `inForce(fact)` | → `bool` — в силе ли факт по `inForce` его типа: `write` — допущенная запись текущая; `{basis: X}` — основание текущего факта ≥ X по порядку §3 (ADR-47) |
| `standing(target)` | → `{live, excluded, marks: [...], trust}` — правило выдачи (§7, TR-15) одной операцией для LENS, `recall`, `add[]` и `materialize` (ADR-47) |

`support.plus` / `support.minus` — взвешенные суммы «+» и «−» голосов групп без группы автора; `groups` — число групп независимости с «+», не считая группы автора; `policy` — `id@version` политики, которая считала.

## Инварианты

1. Доверие не пишется в журнал: `trust()` — функция журнала и политики; пересборка индекса даёт тот же результат.
2. Разные сессии одной группы независимости не увеличивают поддержку; голос автора не входит в сумму спора. Прошлое доверие меняется только новыми утверждениями или ревизией политики: реестр, владелец и декларант читаются на `seq` голоса (TR-13).
3. `derived` — только детерминированный разбор внешнего источника; запись, выведенная из вердиктов, — не `derived`, её основание — по таблице §3 с автором `via ?? by` — сессией вердикта.
4. `declared` и перекрытие (`overruled`) дают только явные `core/assert` без `via` человека-владельца пространства цели или допущенного декларанта (декларант — только `human`) (TR-17); домен не знает имён типов run (ADR-47).
5. Вид участника и право декларанта читаются из реестра владельца пространства через `authority.principal`; участник вне реестра — уровня `agent`.
6. В доверие входят голоса сессий, у которых `classify` даёт `feedsTrust` (таблица §1); значение `purpose` вне таблицы — не входит (TR-12).
7. Результат `trust()` не зависит от порядка проекций и пересчёта: голос хранит свои признаки на своём `seq`; смена политики перевзвешивает, не прогоняет журнал (ADR-47).

## Вне объёма

- Криптографическая подпись утверждений.
- **Снятие голосов подменённой сессии** (сессия, чья личность оказалась подменой, F01): голоса на `seq` голоса остаются (TR-13), отзыв `declare` их не снимает. Механизм — утверждение владельца «сессии X…Y недействительны» или пересчёт без них — когда понадобится. Триггер — первая обнаруженная подмена (видна по `claimed_via` и `os_user`). В v1 уже сейчас: сессия несёт `claimed_via`, `os_user` и `actor@n`.
- Аутентификация участника — порт окружения. Допущение модели угроз (ADR-25): личность в сессии — заявление вызывающего, хост её не проверяет. На нём стоят `owner`, `declared`, решающее «−» (`overruled`), декларант, группы независимости и гейт обучения (`purpose`). Граница хоста: `human` — только `--as` в терминале с подтверждением; `LATTICE_ACTOR` агенту задаёт оркестратор на процесс, в профиле человека его нет ([30](30-adapters.md) §3). Подмену видно постфактум — по `claimed_via` и `os_user` сессии; предотвращения нет. Восстановление владения при утрате — через хост или адаптер.
- Общий `std`-тип для полей LLM-обогащения (как `summary`) — когда он понадобится второму адаптеру (TR-09).
