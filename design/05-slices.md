# 05. Вертикальные срезы — порядок реализации

Срез (T171) — сценарий конец-в-конец, который проходит через несколько доменов и проверяется тестом. Каждый следующий
опирается на предыдущие. S0 — скелет: тонкий настоящий код всех слоёв; S1–S9 наполняют его. Первый запуск
([01](01-first-run.md)) требует S0–S9: E6 и R10–R11 первого запуска — содержимое S9.

| # | Срез | Домены | Готово, когда (тест) |
|---|---|---|---|
| **S0** | **Скелет** | все слои, адаптеры (фиктивные), CLI | тест структуры проходит ([04](04-architecture.md) §3); каждый фиктивный адаптер проходит контрактный набор своего порта; проводка `config/2`: неизвестный ключ, литерал секрета, нет переменной окружения, нет привязки у адаптера из `setup.ports` — отказ до первого вызова с путём поля; `lattice init` + `lattice solve "<задача>"` на пустом проекте → пакет, где каждая потребность — `gap absent`; вызов записан одним коммитом |
| **S1** | **Запись объекта** | kernel, ledger, rules, хост | `init` пишет генезис из кода; хэш генезиса — константа версии ядра, `open()` его сверяет; сущность v1 → v2; то же тело — no-op по `(type@n, hash)`, под `type@n+1` — новая ревизия; значение пишется дважды — один `#id`, тот же `#id` с другим полным хэшем — отказ; нарушение `hard` отклоняет весь коммит; хвост без маркера `core/commit` уходит в `recovered/`; `rebuild --check` побайтно совпадает; фиктивный секрет в окружении — `grep` по `.lattice/` пуст; пишущая команда без `--as` / `LATTICE_ACTOR` — отказ; участник `human` через `LATTICE_ACTOR` или `--as` без терминала — отказ, через `--as` в терминале с подтверждением — сессия с `claimed_via: tty`; каждая сессия несёт `claimed_via` и `os_user`; строка под `type@n`, не последней версией типа, — отказ (`type-latest`); перестановка строк коммита с разными `id` не меняет исход; `count` с `max` после ужесточения правила: окончание факта при превышении принято, установка — отказ; `open()` принимает генезис из цепочки ядра, хэш вне цепочки — отказ; подменённая строка коммита или убывающий `seq` — отказ `open()` с адресом; писатель с просроченным замком — `locked`, ничего не записано; каноническая форма проходит тестовые векторы JCS формата v1 (ADR-1); `#label:…` и `{"$enc"}` — отказ; повтор коммита с тем же `key` и содержимым — прежний результат, с другим содержимым или `by` — отказ `differs` с адресом прежнего коммита, ничего не записано; строка проектного типа-наследника `std/segment-event` — в сегменте исполнения, как `std/execution`; каждый `open()` — строка в `.lattice/metrics/open.jsonl`, `lint` сообщает p95 |
| **S2** | **Типы и зерно** | catalog, identity, rules | `init` копирует `std` замкнутым пакетом, копия совпадает с оригиналом по `id`, версии и хэшу; хэш пакета `std` ≠ хэшу релиза в коде — отказ, ключ коммита обновления несёт хэш релиза; тип с `grain`; дубль отклонён нарушением `{rule: grain-unique, with, diff}`; `ensure` возвращает существующую; правка тела в чужой ключ отклонена; любое изменение зерна или `grain_scope` без плана отклонено, с планом — версия типа + алиасы одним коммитом; тип с необязательным измерением `grain` публикуется, `lint` — находка «пустое измерение»; `split` возвращает сущность и её ключ в индекс `grain`; ссылки через алиас разрешаются; `extends` — только с сужением, цикл отклонён; версия с невыполненными `examples` не публикуется; ревизию пишет только владелец пространства или допущенный; первый коммит пространства с владельцем проходит (самоустановление, ADR-33), второй проектный — отказ |
| **S3** | **Факты и доверие** | trust, catalog | членство true/false по ключу; правка нормы-члена — тот же факт членства, доверие сохраняется, snapshot `stale`; `transfer` и уточнение `model` не меняют прошлое доверие (реестр — на `seq` голоса); голос участника вне реестра не даёт `observed`; `--as <machine>` — отказ; три «−» разных групп без «+» — `rejected`; перекрытое при «+» других групп — находка `lint`; утверждения разных групп независимости дают `observed`, сессии одной группы — нет; «+» и «−» дают `contested`; явное `core/assert` «−» человека-владельца или декларанта даёт `overruled`, «−» агента-владельца и «−» из вердикта владельца (`std/learned-assert`) — голос в сумме; управляющий факт пишет только допущенный `writers` типа; правка чужого объекта `refs: follow` — только `core/proposal`; допуск разрешает агенту создавать `std/need`; участник вне реестра — `agent`; пересборка даёт то же доверие |
| **S4** | **Импорт проекта** | adapters (`source-warrant`, `source-files`), catalog | пространство `warrant`, участники адаптера в реестре; типы проекта; нормы — ревизии из извлечённых полей (`derived`, `summary` — первый абзац, `text_hash` — хэш полного текста; правка текста за первым абзацем — новая ревизия), `summary` units — факт `warrant/summary` вне карточки; домены `lifecycle`, `cli-core`, словарь; алиасы — кандидаты `std/alias-candidate`, индекс их не видит; расхождения — `std/load-finding`; `lint` без нарушений `hard`; повторный импорт без изменений — ноль новых строк; блок, исчезнувший из источника, — находка `load-finding missing`, объект жив до `retire` владельца; второй проект через `source-files` во втором хранилище — без правки ядра (E7) |
| **S5** | **Поиск кандидатов** | lens, run, adapters (judge) | запрос → кандидаты с баллами и причинами; ID в тексте — прямое попадание, порогом не отбрасывается; пустышка → `no-match` (у `threshold` есть `calibrated_for`); модель берётся из ревизии `std/setup`, правка проводки её не меняет; модель порта ≠ `setup@n`, `calibrated_for` ≠ `describe()`, код ≠ `impl.pins`, порт стадии вне `setup.ports` — отказ на старте; оплаченная оценка — событие `std/measurement` со ссылкой на пул; ответ `score` без балла части карточек или с лишним ключом — ошибка стадии; повтор — из кэша judge без вызова; `Meta.model` из ответа ≠ модели в `setup` — ошибка стадии; калибровка пишет `<пространство>/pipeline.solve` с порогами и `calibrated_for {…, bench}` и ревизию `setup` на него |
| **S6** | **Решение потребности** | compose, run | задача → потребности (`frame`) → выбор 1…7 с цитатами из карточек → `check` → решение + членства + snapshot → пакет с шапкой (`header` стадии `deliver`); вызов — один коммит с кортежем исполнения; ссылка вне кандидатов и `found` отклонена; у `form: set` нет связей; промах → self-search → `found_by: self-search`; нет блока → `gap`, у `coverage` — место в источнике; место `source.find`, пересекающееся с местом живого блока, — блок в `found` (промах B), не `coverage`; строка типа вне `emits` стадии — ошибка стадии, конвейер со стадией, чьи `emits` содержат тип блока, не публикуется (`contract`); файл хода `pending` старше `pending_ttl` закрывает следующая `solve` — вызов с ошибкой `abandoned`, `answer` на него — отказ, `explain` его не закрывает; `composer-caller`: `pending` → `lattice answer` → перезапуск с тем же id, ответ проходит схему; участник сессии с моделью ≠ `setup.ports.composer.model` — отказ на старте; текст блока, изменённый в источнике после `load` (хэш ≠ `text_hash`), — в пакете карточка `ref@n` с пометкой «источник изменён», тексты блоков — в разметке цитаты |
| **S7** | **Повтор** | compose, trust | та же потребность другими словами → `recall` → выдача без LENS; judge без `calibrated_for` «ту же потребность» не выносит; `stale` после правки нормы → `recheck` → новый snapshot; `stale` после `add` или удаления члена обучением → новый snapshot с текущим составом; пустое решение → LENS; подсказка не в силе → judge, не `by: exact`; подсказка, записанная `recall` или `recheck`, несёт `match` (`by`, `p`, адаптер и модель оценщика); `contested`, `rejected` или перекрытый член → заново через LENS; выведенный или перекрытый блок не проходит `add[]` и `materialize`; слияние потребностей сверх `max` — находка «разбить», текущий факт — канонического; кандидаты в алиас сверх `budget` записаны и входят в очередь владельца по мере разбора |
| **S8** | **Вердикт и обучение** | run, trust, bench | вердикты меняют доверие по правилам ([22](domains/22-run.md) §6), один вердикт на пару `(execution, solution)`; `used: [X]` после правки X@4 → X@5 относится к ревизии из snapshot вердикта; `incomplete` + `add` чинит решение; член удаляется при `unused` в 3 из 5 последних выдач по группам; раскачка → `contested`; self-search → кандидат в ловушку; настройка (`setup@n`) без `bench-run pass` — пакет помечен, факт обучения `from: verdict` отклонён коммитом, с засчитанным `pass` — принят и несёт `bench`; более поздний `fail` того же кортежа закрывает гейт, `pass` по плану на старый регрессионный план не засчитан; смена `namespace.policy` без прогона — вердикт ждёт `pass`; `std/member {value: false}` без `from` — отказ; `unused` не меняет сумму спора; вердикт с `evidence` принят, обучение поле не читает; вердикт на пару от участника не из сессии вызова и не владельца — отказ, повтор вердикта с другим содержимым — `differs`; цитата `add[]` из полного текста блока принята, неверная — отклонён элемент, `used`/`unused` записаны; вердикт кортежа, который установленным кодом не прогнать, — находка владельцу; сессии `bench` и `purpose` вне перечня не питают доверие, подсказки и обучение; `simulate` — только в копии кампании: вердикт `simulate` без метки `std/bench-copy` — отказ гейта, основное хранилище с меткой — отказ `open()`; E3: k симуляторов `machine` — k групп, окно удаления замыкается при k ≥ `removal_window.n`, те же вердикты одной группы не удаляют (ADR-26, [23](domains/23-bench.md) §3); с `noise` > 0 верные члены не удаляются; `explain <пространство>` показывает вердикт, ждущий `pass`, со счётом и возрастом |
| **S9** | **Самоописание** | run, bench, catalog | конвейер читается из LATTICE (`std/setup` → `pipeline@n`); новая ревизия `std/setup` с конвейером, где стадия `fuse` — `mode: rrf`, проходит или не проходит регрессионный план (план `candidate` с `base` на регрессионный: тот же `set@n`, `subset`, `state`); сравнимы только прогоны с равным кортежем, `Meta` ≠ `setup@n` → `invalid`; эталон `test` не дописывается; базовые линии E1 — объекты `std/setup` без LLM (`frame.single`, `bm25.doc`), исполняются без портов `judge` и `composer`, действующая `<пространство>/setup` от них не меняется; закреплённый кортеж → `replay` по журналу побайтно совпадает, без кэшей, записи и живых вызовов; хэш кода стадий ≠ `code` — отказ `code-changed`, версии адаптеров не сверяются; релиз, не тронувший модуль стадии, `solve` не останавливает; вызовы кампании с разной `source` или `env` — прогон `invalid`; новая ревизия типа с `card` после калибровки — находка «калибровка устарела»; строк обучения больше `recheck_every` — находка «перемерить той же настройкой»; `hit@3` одного вида блока ниже базы при росте среднего — `fail` по guardrail (RN-34, BN-16, BN-18, BN-19) |

## Что срез обязан оставить после себя

- тесты из столбца «Готово, когда» и инвариантов своей строки — написаны до реализации; исполнитель среза критерии не
  меняет (уточнение — решением в домене);
- тесты на фикстурах: маленький синтетический проект, без сети — фиктивные адаптеры ([30](domains/30-adapters.md) §1);
- команду CLI, которой срез показывается владельцу проекта руками (приёмка);
- зелёные тест структуры и наборы всех прежних срезов;
- запись в журнале решений (ID из доменов), если при реализации что-то уточнилось.

Живые адаптеры (`judge-jev`, `composer-claude`, `source-warrant`) проходят те же контрактные наборы, а сценарии — только
в первом запуске и в ручных проверках.

## Решения

| ID | Решение | Почему |
|---|---|---|
| SL-01 | Первый срез — скелет S0: все слои тонким настоящим кодом, фиктивные адаптеры через корень сборки, тест структуры, сквозной `solve` с коммитом | ошибки стыков порт ↔ рантайм ↔ коммит видны с начала, а не в S6. v0.4 · 30-adapters/И-13 · И-17 · D13 Q3 |
| SL-02 | «Готово, когда» — спецификация приёмки: тесты до реализации, исполнитель критерии не меняет, приёмка — показ CLI владельцу | критерий, который правит исполнитель, ничего не проверяет. v0.4 · 30-adapters/И-14 |
| SL-03 | Инвариант домена входит в срез номером, текст — у домена; первым его проверяет срез из таблицы | у понятия один владелец; видно, что ни один инвариант не остался без теста. v0.4 · D13 Q6 · N-22…N-64 |
| SL-04 | Генезис v1 полон к первой записи реальных данных (первый запуск); до того смена генезиса — новая константа и пересчёт фикстур; в S1 — тест «хэш генезиса = константа версии» | до первого журнала проекта данных нет; требование полноты к S1 заставило бы S1 проектировать поля S3 и S8. v0.4 · N-18 · D13 Q4 · T-10 |
