# ADR-40. Полномочия на `seq` — проекция `authority` в ядре, свойства сессии — `classify` в trust

Статус: принято 2026-09-29 · сессия R1–R4 (архитектурный разбор 2026-09-29, кандидат 3)

Вопросы «может ли сессия писать эту строку» (проверка `owner`) и «чей это голос, какой он группы» (проекция `trust`) идут по одной цепочке `by` → сессия → `actor@n` → владелец пространства → допуск на `seq`, а раздела индекса для неё нет — оба модуля построили бы её сами. Часть правил жила прозой вдали от проверки: CT-14 (`edit` не действует на `refs: follow`) в строке `owner` 13 §2 не упомянут; `declare` у не-человека отсекался при чтении trust, а не при записи. Значения `purpose` — поле у 14 §1, закрытый перечень — таблица 30 §3 (AD-15), а читали их пять отдельных списков разрешённых (trust, окно удаления run, подсказки lens, стенд, гейт); проверка `owner` читает `purpose` (`writers: {purpose: bench}`, 23 §1), а перечень 04 §1 называл читателем `purpose` только гейт.

Решили:

1. **Проекция `authority` — слой замороженного ядра** (ADR-32, перечень ADR-35): `principal(session, seq) → {actor@n, kind, model, group}` и `mayWrite(row, view) → ok | нарушение` — одна модель прав: владелец и допуски пространства на `seq`, `writers` типа факта в пространстве роли `target`, `writers {purpose}`, CT-14, самоустановление (ADR-33), `declare` только `human` — отказ при записи. Проверка `owner` — вызов `mayWrite`.
2. **`classify(session@seq) → {group, feedsTrust, teaches, countsInWindow}`** — операция trust и единственный читатель `purpose` вне ядра: доверие, окно удаления членства (run), подсказки (lens), стенд читают её, а не свои списки. Внутри ядра `purpose` читают `authority` (`writers {purpose}`) и `learning-gate` — перечень 04 §1.
3. **Перечень значений `purpose` с их свойствами — одна таблица в 14-trust.** 30 §3 оставляет только «команда хоста → участник · `purpose`»; новое значение — строка таблицы 14 (питает ли доверие, учит ли, считается ли в окне) и решение гейта, если он его читает (новая версия ядра, ADR-34).
4. Группа независимости (ADR-26, TR-16) — поле выхода `classify` и `principal`: run и bench не повторяют ADR-26 у себя.

**Варианты:** (б) каждый читатель — свой список разрешённых `purpose`, `owner` строит цепочку сам — пять мест, где новое значение надо не забыть; (в) `authority` в catalog — исполнитель прав — замороженный код ядра (AR-12), catalog ему недоступен (AR-04).

**Последствия:** 10-kernel (§7 — `authority`), 13-rules (§2 — `owner` через `mayWrite`, CT-14, `declare`), 14-trust (§1 — таблица `purpose`, «Операции» — `classify`), 15-catalog (CT-03, CT-13, CT-14, CT-15 — исполнитель `authority`), 22-run (§6 — окно удаления), 20-lens (подсказки), 23-bench (§1, §3), 30-adapters (§3, AD-15), 04-architecture (§1 — перечень чтений ядра + `authority`; §8 — владелец `purpose`), 02-glossary. Проекция ядра меняется только версией ядра (ADR-34): до первых данных — дёшево.
