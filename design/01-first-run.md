# 01. Первый запуск — цель, эффект, протокол

## Цель

Показать на реальных данных WARRANT (подбор норм для агентов), что система:

1. **находит** нужные нормы лучше простого поиска;
2. **помнит**: повтор потребности обслуживается без поиска — дешевле и не хуже;
3. **учится**: вердикты чинят неполные и ошибочные решения;
4. **честно отказывает**: «нужного нет» отличает от промаха поиска;
5. **не дублирует и не схлопывает** объекты при смене гранулярности;
6. **описывает и воспроизводит себя**: конвейер и модели берутся из настройки в LATTICE (`std/setup`), вызов
   воспроизводится побайтно.

Один прогон проверяет обе половины концепции: блоки знаний — нормы WARRANT; блоки способностей — стадии конвейера,
который их ищет.

## Что мы увидим (эффекты и критерии)

Критерии предварительные: окончательные числа пишет владелец в регрессионном плане `std/bench-plan` **до** R4 (BN-02,
BN-07 [23](domains/23-bench.md)).

| # | Эффект | Как видно | Критерий (предварительно) |
|---|---|---|---|
| **E1** | Находит | `hit@3`, `MRR` на контроле против четырёх базовых линий (R4); колонки `doc-hit` и `block-hit` | `hit@3` ≥ 0,95; `MRR` выше «BM25 по документам целиком» на ≥ 0,3, нижняя граница 95 % CI > 0; guardrail — не ниже черновиков (`MRR` 0,90 / 1,00 в доменах) на подмножестве их контроля |
| **E2** | Помнит | проход B: перефразы и точные повторы | `recall-rate` ≥ 0,6 на перефразах и 1,0 на повторах; `select-F1` не ниже прохода A (Δ ≥ −0,02); цена на вопрос ниже ≥ 50 %; доля серой зоны (`recall.by: composer`) — в отчёте |
| **E3** | Учится — механика при совершенном потребителе | проход C: испорченные решения после вердиктов симуляторов (`noise: 0`), на отложенных перефразах; устойчивость — тот же проход с `noise` > 0 ([23](domains/23-bench.md) BN-20) | `calibration-Δ` (`select-F1`) ≥ +0,1; недостающее добавлено ≥ 80 %; лишнее удалено ≥ 80 % — вердиктами ≥ `removal_window.n` групп; отрицательный контроль: те же вердикты одной группы не удаляют ничего; ни один верный член не удалён — на прогоне с `noise` > 0 (при `noise: 0` выполняется по построению и в зачёт не идёт) |
| **E4** | Честно отказывает | матрица B / C / покрытие | ловушки → промах B (член `found_by: self-search`, пара — кандидат в ловушку); пустышки → C (`gap absent`): точность и полнота ≥ 0,8; блок, вырезанный из каталога, → `gap coverage`; перед `absent` — проверка дублей потребности |
| **E5** | Не дублирует | сценарий смены зерна домена | 0 тихих слияний, 0 дублей: кандидаты в алиас (`std/alias-candidate`) без `core/alias` владельца в силу не входят; публикация без плана отклонена; слияние и разделение обратимы; `rebuild --check` совпадает |
| **E6** | Самоописание и воспроизводимость | конвейер из `std/setup`; `replay`; новая ревизия настройки (стадия `fuse` с `mode: rrf`) | конвейер читается из журнала; `replay` и `rebuild` побайтно совпадают; новая ревизия получает `pass` или `fail` по регрессионному плану, при `fail` вердикт на её вызов не обучает, при `pass` — обучает (гейт, R10b в основном журнале) |
| **E7** | Универсальность корпусов | второй корпус (малый справочник) — второе хранилище (`init`) на том же `std`: в хранилище v1 одно проектное пространство (ADR-33) | ноль правок ядра и `std`; только адаптер `source` и конфигурация. Проверяет универсальность по корпусам блоков, выдаваемых по потребности, — не по видам работы (VI-05, [22](domains/22-run.md) «Вне объёма») |

Главная картинка для человека — **три реальные задачи WARRANT** (группы задач Change): пакет норм, который получил
бы агент, с причинами и доверием, рядом с тем, что агент читал без LATTICE.

## Протокол прогона

```text
R0  init                 .lattice/, core + std, пространство warrant, политика доверия (@n), warrant/setup@1;
                         базовые линии — отдельные объекты std/setup ([23] §1, BN-15);
                         в реестре владельца — участники-симуляторы sim-1…k (machine), k ≥ removal_window.n
R1  load                 нормы, домены, словарь, элементы и набор стенда                → S4
R2  lint + rebuild       ноль нарушений hard; rebuild --check побайтно                  → E6 (часть)
R2b калибровка           кампания explore (subset: dev) на копии ([23] §4 п. 8): пороги no_match,
                         same_hi/same_lo, min_p кандидатов →
                         warrant/pipeline.solve@1 с порогами и calibrated_for {…, bench},
                         warrant/setup@2 на него, min_p — ревизия политики пространства
                         (без calibrated_for no-match не выносится)                    → S5
R3  план                 регрессионный план владельца (kind: regression, subset: test,
                         mode: simulate-consumer — проходы A–C; кандидат R10 берёт его из base):
                         набор@n, setup@2, базовые линии, критерии, δ, n, seed          → записан до прогона
═══ кампания — копия журнала до plan.state ([23] §3) ══════════════════════════════════
─── проход A (холодный) ────────────────────────────────────────────────────────────────
R4  solve × контроль     все вопросы test через конвейер; базовые линии:
                         (a) BM25 по документам целиком (frame.single → normalize → bm25.doc),
                         (b) BM25 в домене (frame.single → … → bm25, без judge), (c) LENS без recall,
                         (d) по полному тексту блока в домене                           → E1, E4
R5  вердикты             режим simulate-consumer (сессии purpose: simulate): вердикт по эталону
                         (выбор = эталон → complete; не хватает → incomplete + add; лишнее → unused;
                          мимо → wrong); сессии — разные для групп перефразов           → S8
─── проход B (повтор) ──────────────────────────────────────────────────────────────────
R6  solve × перефразы    перефразы и точные повторы вопросов прохода A                  → E2
─── проход C (обучение) ────────────────────────────────────────────────────────────────
R7  порча                синтетическая: отдельная сессия убирает по одному эталонному члену у N решений
                         и добавляет по одному лишнему (факты членства); реальная: неполные решения
                         прохода A; в отчёте — раздельно
R8  solve + вердикты     те же потребности; вердикты k симуляторов (k групп); отрицательный
                         контроль — те же вердикты одной группы; ожидаемый режим эксплуатации —
                         потребители одной модели с автором (группа автора): в отчёте E3 отдельно,
                         с метриками «группы с вердиктами» и «замыкаемость окна»; мерить на
                         отложенных перефразах; повтор с зашумлённым симулятором
                         (noise 0,1 — unused эталону, add лишнего)                      → E3
─── сценарии ───────────────────────────────────────────────────────────────────────────
R9  зерно                фикстура: домены lifecycle/ru и lifecycle/en; новая версия std/domain
                         без language в grain → отчёт → без плана отклонено → merge → split   → E5
R11 replay               повтор вызовов R4 на копии кампании → побайтное сравнение пакетов → E6
═══ конец кампании: в основной журнал — std/bench-run с хэшем копии ═══════════════════
R10 новая настройка      в основном журнале: ревизия warrant/setup@3 (fuse mode: rrf), план candidate с base
                         на R3 → кампания кандидата на копии до его state: setup@2 и setup@3 →
                         std/bench-run pass или fail ([23] §3)                             → E6
R10b гейт                в основном журнале: solve на setup@3 → вердикт владельца (purpose: verdict) →
                         при fail факт обучения отклонён коммитом, при pass принят (как S8) → E6
R12 второе хранилище    малый справочник: init второго хранилища, адаптер source +
                         конфигурация, R1–R4 на нём                                      → E7
R13 демонстрация         3 задачи Change → пакеты                                        → картинка
R14 отчёт                .lattice/reports/first-run.md + std/bench-run в журнале
```

**Режим `simulate-consumer`** — единственное место, где стенд обучает систему, и только в копии кампании (BN-04):
вердикты выводятся из эталона, чтобы измерить механику обучения без живых агентов. Симуляторы — разные участники,
значит разные группы независимости (ADR-26); их независимость объявлена, а не проверена, — это явно помечено в
отчёте. Живые вердикты агентов — следующий этап.

## Отчёт (что будет в `first-run.md`)

1. Таблица E1–E7: метрика, критерий, результат, CI, PASS/FAIL; число прогонов `test` на `set@n`.
2. E1: `hit@3` / `MRR` по доменам, видам вопросов (обычные, ловушки) и видам блоков против четырёх базовых линий;
   `doc-hit` и `block-hit`.
3. E2: доля повторов без поиска, доля серой зоны, цена и задержка до/после, `select-F1` A против B.
4. E3: испорченные решения — было / стало, отдельно добавление и удаление, синтетические и реальные; отрицательный
   контроль одной группой; совершенный (`noise: 0`) и зашумлённый симулятор — раздельно, удалённые верные члены — по
   зашумлённому.
5. E4: матрица B / C / покрытие; промахи B — список ловушек-кандидатов.
6. E5: отчёт о коллизиях, план, журнал фактов алиасов, результат `rebuild --check`.
7. E6: ревизии настройки, `pass`/`fail` новой (`setup@3`), результат `replay`.
8. E7: что понадобилось для второго пространства.
9. Замеры (таблица выше).
10. Три пакета норм для реальных задач.
11. Что не сработало и какие решения доменов пересмотреть.

## Вне первого запуска

- Исполнение способностей проектов (`exec`) — только builtin-стадии.
- Живые вердикты агентов (вердикт владельца R10b — единственный), UI, несколько хранилищ.
