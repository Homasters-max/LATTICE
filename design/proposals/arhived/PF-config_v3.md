# Предложение PF — поведение в журнале, проводка в конфиге

> Статус: **прошло grilling 2026-09-27**, решения PF-01…PF-06 приняты; выводы проверки по базе знаний ([PF-config-kb](PF-config-kb.md) C-1…C-6) внесены, PF-05 пересмотрен по C-5. **Внесено в design v0.4** (ADR-28 `std/setup`, ADR-29 гейт, [04](../04-architecture.md) §5, [30](../domains/30-adapters.md) §2); этот файл — история, не норма: где расходится с доменами — действуют домены. Идея — из устройства конфигурации OpenClaw (п. 2). **Ядро не меняется:** ни новых типов, ни новых примитивов проверки. Концепция (P1–P12) сохраняется без изменений.

## 1. Проблема

```json
{ "pipeline": "std/pipeline.solve@1",
  "adapters": { "judge":    { "use": "judge-jev",       "model": "…" },
                "composer": { "use": "composer-claude", "model": "…" } } }
```

Этот фрагмент `lattice.config.json` ([04](../04-architecture.md)) — единственное место, где поведение задаётся мимо журнала: какой конвейер действует и какие модели оценивают и выбирают. Смену модели не видит ни версия, ни стенд, а прогон нельзя связать с поведением, которое его породило. Находки реестра: D-38, D-42, D-67, D-78, D-82.

## 2. Что взято из OpenClaw

OpenClaw разделяет **проводку** (`openclaw.json`: адреса, ключи; строгая схема, при ошибке не стартует) и **поведение** агента. У нас это признак:

> **Поле — в журнал, если при том же журнале и том же запросе его смена может изменить пакет или цену. Иначе — в проводку.** Уточнение: **«где лежит»** (путь, адрес, ключ) — проводка; **«что лежит»** (версия содержимого за этим адресом) — журнал (C-1).

Пример: путь к репозиторию источника — в проводке, но текст пакета зависит от того, какая ревизия лежит по этому пути, поэтому ревизию источника пишет вызов (п. 3.3).

Вторая мысль — политика исполняется кодом, а не текстом промпта (п. 3.5).

## 3. Решение

### 3.1. Настройка проекта — ревизия пространства имён

Тело `core/namespace` уже хранит владельца, импорты и политику доверия. Добавляются действующий конвейер и адаптеры портов с моделями:

```json
{ "id": "warrant/namespace", "type": "core/namespace@1",
  "body": { "name": "warrant", "owner": {"$ref": "warrant/ACT-maintainer"},
            "imports": ["core", "std"],
            "policy":   {"$ref": "warrant/trust-policy@1"},
            "pipeline": {"$ref": "std/pipeline.solve@1"},
            "ports": { "judge":    { "adapter": "judge-jev",       "model": "<точная версия>" },
                       "composer": { "adapter": "composer-claude", "model": "<точная версия с датой>" },
                       "source":   { "adapter": "source-warrant" } } } }
```

- Вся настройка проекта — **одна ревизия владельца** (правило `owner`, CT-03). Смена модели или конвейера — новая ревизия; откат — ещё одна. История — в журнале.
- `std/pipeline.solve` остаётся нейтральным к технологии: какой judge и какая модель — решает проект, а не библиотека (P10, AD-02).
- `imports` — только здесь (D-38).
- `model` — **точный идентификатор версии** модели. Алиас, за которым провайдер может тихо сменить модель (`latest`, имя без даты или номера), отклоняется при запуске (C-4).
- Конвейер и модели лежат в одной ревизии, потому что обязаны меняться атомарно: пороги стадий зависят от модели judge (PAT-129). Владелец и импорты рядом безвредны, пока `namespace@n` закрепляют только вызов и план стенда.

  **Условие пересмотра:** если `namespace@n` начнёт закреплять что-то ещё, пару «конвейер + порты» вынести в отдельный объект — иначе частые смены модели будут задевать это «что-то» (C-2).

### 3.2. Проводка

```json
{ "$schema": "lattice://config/2",
  "namespace": "warrant",
  "data": ".lattice",
  "bindings": {
    "judge-jev":       { "endpoint": "https://…", "key": { "$env": "JEV_API_KEY" } },
    "composer-claude": { "key": { "$env": "ANTHROPIC_API_KEY" } },
    "source-warrant":  { "root": "D:/project/WARRANT" } } }
```

Строгая схема. Запуск отменяется до первого вызова, с путём поля, если: неизвестный ключ; ключ API литералом вместо `{"$env": …}`; переменной окружения нет; у адаптера из `ports` нет привязки; `model` — алиас. Это код CLI, не модель данных.

**Запасного режима нет** (C-3): нет ключа или привязки — отказ, а не тихая подмена адаптера (например, judge → только BM25). Подмена дала бы пакет другого качества под видом обычного (ANT-036). Если запасной режим нужен, это отдельная ревизия пространства со своими `ports`, и она проходит стенд как любая другая.

### 3.3. Вызов помнит, чем он был порождён

Тело `std/execution` получает три поля:

- `namespace: ref@n` — ревизия пространства, то есть конвейер и модели;
- `code: {lattice: "0.3.0", "judge-jev": "0.4.1", …}` — фактические версии пакета и адаптеров;
- `source: "<ревизия>"` — версия содержимого источника, из которого взяты тексты пакета (для WARRANT — коммит репозитория; адаптер `source` отдаёт её вместе с текстом) (C-1).

`replay` сверяет все три и сообщает расхождение явно (D-42, E6). По `namespace@n` находятся все результаты, задетые моделью, если её позже признают плохой (TERM-133).

### 3.4. Стенд проверяет пару «конвейер + модели»

- План стенда закрепляет кортеж оценки: `std/bench-plan` `{set, pipeline: ref@n, ports: {…}, budget: {usd, ms}, …}` — пороги стадий, модель judge и бюджет проверяются вместе (D-67, D-78; PAT-106: версия оценки = модель + harness + бюджет, C-4).

**Барьер стоит на переходе, который нельзя откатить** (C-5, решает D-82). Находка `lint` — это ревью, а не барьер: её можно не заметить (TERM-206). Строгость барьера — по обратимости (PAT-049):

| Переход | Откат | Барьер |
|---|---|---|
| смена конвейера или модели | лёгкий: ещё одна ревизия пространства | не нужен |
| обучение по вердиктам (факты, утверждения, доверие) | нет: ревизия пространства выученное не отменяет | **нужен** |

- Интерпретатор `run` при старте ищет в журнале прогон стенда `pass`, план которого закрепляет ту же пару «конвейер + порты» (и тот же бюджет), что действующая ревизия пространства.
- Нашёл — обычный прогон. Не нашёл — прогон **разрешён**, но пакет помечен «конфигурация не проверена стендом», а вердикты по нему **не обучают** систему (как сессии стенда, BN-04). Нет доказательства — переход закрыт (fail closed).
- Это проверка в коде `run`, не правило коммита: нового примитива ядра нет.
- Находка `lint` «пара без прогона `pass`» остаётся — как подсказка владельцу, а не как барьер.
- Вердикты непроверенной пары нужны для обучения намеренно — только явным режимом, как `simulate-consumer`.

### 3.5. Шапка пакета и граница «текст — не охрана»

- Стадия `deliver` получает параметр `header` — короткую инструкцию агенту-потребителю: пакет — закрытый мир, как читать доверие, как вернуть вердикт (`lattice verdict`, формат). Без неё агент не знает, что вердикт нужен, а без вердиктов нет обучения (E3). Версия текста = версия конвейера.
- Принцип для всех промптов стадий и шапки: **граница, сказанная в тексте, дублируется проверкой кода**. Текст объясняет, код запрещает; текст — последний слой, а не единственный (PAT-102, ANT-004).
- Соответствие держится **явной таблицей** — граница без проверки становится долгом, проверка без текста — ловушкой (PAT-095, C-6):

| Сказано в тексте | Чем проверяется |
|---|---|
| ссылайся только на кандидатов | стадия `check`, закрытый мир (CP-06) |
| 1…7 членов решения | правило `max-members` |
| у каждого члена — причина-цитата | JSON-схема выхода Composer (AD-05) |
| верни вердикт на каждое решение | не принуждается кодом (потребитель внешний); проверка — метрика доли пропущенных вердиктов ([22](../domains/22-run.md), вопрос 1) |

Новая граница в промпте без строки в этой таблице — не публикуется в версии конвейера (ревью владельца).

## 4. Решения

| ID | Решение | Почему |
|---|---|---|
| PF-01 | Признак: меняет пакет или цену при том же журнале → журнал, иначе → проводка; «где лежит» — проводка, «что лежит» — журнал | граница по смыслу (TERM-077, PAT-195) |
| PF-02 | Действующий конвейер и адаптеры портов с моделями (точная версия, не алиас) — в теле `core/namespace`; `imports` — только там | пара меняется атомарно (PAT-129); `std` нейтральна к технологии |
| PF-03 | Проводка — строгая схема, секреты только `{"$env"}`, отказ до первого вызова; запасного адаптера нет | ошибки конфигурации — на старте, без правдоподобной подмены (AD-06, ANT-036) |
| PF-04 | Вызов пишет `namespace@n`, фактические версии кода и ревизию источника | воспроизведение и lineage (TERM-133) |
| PF-05 | План стенда закрепляет «конвейер + порты + бюджет»; без прогона `pass` вердикты не обучают, пакет помечен | барьер на необратимом переходе, без правки ядра (TERM-206, PAT-049) |
| PF-06 | Шапка пакета — параметр `deliver`; граница в тексте дублируется кодом по явной таблице | политика — кодом, текст — последний слой (PAT-095, ANT-004) |

## 7. Отложено

Пакет из карточек с полным текстом по запросу (вариант стадии `deliver`, выбор по стенду) — после первого запуска. Выгрузка шапки и команд в `SKILL.md` для harness'ов агентов — когда появится второй потребитель.

## 8. Не берём

`SOUL.md` (личность, тон), файлы памяти, приоритет навыков по имени, самосоздание навыков и ClawHub, горячая перезагрузка, JSON5 и `$include`: роли LATTICE не ведут беседу, память — журнал, молчаливое перекрытие противоречит P8 и CT-06, Composer не создаёт блоки (P6), формат один (KR-06). Лимит длины промптов и `requires` у способностей — уже покрыты: промпты пишет владелец и меряет стенд, отсутствие привязки ловит проверка проводки.
