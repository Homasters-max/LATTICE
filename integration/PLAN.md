# План внедрения итогов разбора: design v0.3 → v0.4

Составлен 2026-09-27. Навык — `/arch-integrate` (`~/.claude/skills/arch-integrate`: процедура `reference/phases.md`,
форматы `reference/formats.md`, инструменты `scripts/ledger.mjs`, `scripts/design-lint.mjs`). Точка входа сессии —

## 1. Цель и критерии готовности

Цель — **v0.4 как одна согласованная архитектура**: все обоснованные предложения разбора внесены, спорные — решены
пользователем, ни одно не потеряно, понятия определены по одному разу, решения прослеживаются до опоры.

v0.4 готова, когда:
1. Реестр внедрения закрыт: каждая строка `внесён` / `сверен` либо `отклонить` / `отложить` с причиной и местом
   (`ledger.mjs check --strict` — PASS).
2. `design-lint` без базовой линии — 0 ошибок: ID решений и ADR разрешаются, глоссарий без дублей, старых имён нет
   (все переименования `действует`), ссылки живые; у каждого типа есть домен-владелец; зависимости симметричны, без циклов.
3. Каждая сквозная тема T-1…T-16 решена одинаково во всех файлах (аудит C1 без находок «блокирует»).
4. Противоречия П-1…П-32 и Ф-1…Ф-12 закрыты, новых аудит не нашёл.
5. Каждый инвариант доменов проверяется каким-то срезом `05-slices`; первый срез — ходячий скелет (S0).
6. Каждое решение — строка «Решения» с «Почему» и опорой; каждая ADR — с опорой, выбор против рекомендации — с доводом.
7. Принципы `00-vision` P1–P12 не нарушены, либо изменены через ADR.
8. Свежее чтение (F) — без находок «блокирует»; `CHANGELOG-v0.4.md`; тег `design-v0.4`.

## 3. Почему так устроено (главные решения плана)

1. **Не «домен за доменом с нуля», а решения → домены.** 16 сквозных тем проходят через 3–9 файлов каждая; если
   решать их в доменных сессиях, домен 14 решит «права на управляющие факты» иначе, чем домен 10, — ровно та
   рассогласованность, которую итоги нашли в v0.3 (32 противоречия). Поэтому сначала 6 сессий R решают все ADR и темы
   (скелет), затем доменные проходы D вносят их вместе с местными пунктами, решая только местное.
2. **Доменные проходы — по графу зависимостей**, не по номерам: каждый файл пишется против окончательных
   определений выше по течению. Граф из шапок v0.3: 11←10; 13←10; 12←10,13; 15←10,11,13; 14←10,12,15;
   20←10,12,14; 21←10,11,14,20; 22←все; 23←22. Контракт порта — у домена-потребителя (рекомендация итогов T-10,
   30-adapters/И-2…И-4; вопрос S0), поэтому 30-adapters — после всех потребителей.
3. **Реестр вместо памяти.** 322 строки не удержать в голове и в `START.md`. Каждая сессия берёт свой срез
   (`ledger.mjs show --wave N` / `--file X`), закрывает его статусами, новое — `ledger add`.
4. **Бриф субагентом, решение — пользователем.** Сессию готовит субагент (факты, триаж A–F, черновик раундов) —
   главный контекст тратится на grilling и точную правку, а не на чтение 316 КБ фрагментов.
5. **Каждая сессия заканчивается целой** (lint, реестр, коммит) — обрыв не оставляет полупереписанный дизайн.
6. **v0.3 сохраняется** тегом: отчёты исследования ссылаются на строки v0.3 с отпечатками; после правки их
   `check-refs` покажет «текст изменился» — это ожидаемо, отчёты — доказательства по v0.3, их не «чинят».

## 5. Как не потерять важное (механизмы)

| Риск | Чем закрыт |
|---|---|
| пункт итогов забыт | реестр 322 строки + `check` (каждый ID источника обязан быть строкой); `--strict` в C2 |
| местное решение противоречит общему | фаза R до D; бриф D приносит ADR и решения прошлых сессий; «меняет ADR-n» — вопрос, не молчаливая правка |
| одно понятие определено по-разному | `ownership.md` (владелец-файл), `design-lint --index`, аудит C1 «ownership» |
| термины расползаются | глоссарий правится сразу в сессии; `renames.md` `план` → `действует`; lint ловит старые имена |
| правка домена ломает уже пройденный | «сквозные последствия» в каждой D: `grep -rn` имени, обратная правка или строка N |
| решение без основания | «Почему» у каждой строки «Решения» (`ADR-n`, `Q-NN C-n`), ADR с «Опорой»; выбор против рекомендации — в «Вариантах» |
| рассыпался формат доменов | шаблон домена v0.3 (Назначение → … → Вне объёма) сохраняется; D13–D14 сверяют обзорные файлы |
| обрыв сессии | коммит в конце каждой; реестр + журнал + `git diff` показывают, что успело попасть (`phases.md`, «Если оборвалась») |
| усталость и «на автомате» | пакетное согласие A/C одним вопросом; ≤ 8 вопросов в раунде; одна сессия — одна область |
| PF и итоги спорят | сверка в S0, конфликты — строки N в сессии R своей волны; PF не переоткрывается без конфликта |
| незаметные дефекты v0.3 | lint-базовая линия в S0 → строки N; к C2 базовая линия не нужна |
