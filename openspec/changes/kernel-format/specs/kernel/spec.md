# Spec Delta

## Purpose

Формат v1 замороженного ядра LATTICE: входная проверка тела, каноническая форма, хэш и идентификатор значения,
грамматика идентификаторов и ссылок, поиск ссылок в теле и форма ревизии — чистые функции, от которых зависят все
байты журнала и все сравнения по содержимому.

## ADDED Requirements

### Requirement: Отказ — значение, функции ядра чистые
<!-- id: REQ-KR-001 -->

Функции ядра этой возможности — `checkInput`, `canonical`, `hash`, `valueId`, `parseRef`, `formatRef`, `newId`,
`refsOf`, `revision` — SHALL экспортироваться модулем ядра проекта. Каждая функция SHALL возвращать либо успех
`{ ok: true, value }`, либо отказ `{ ok: false, errors }`, где `errors` — непустой список элементов `{ code, path }`:
`code` — строка из перечня кодов требования этой функции, `path` — JSON Pointer (RFC 6901) на место во входе, к
которому относится отказ. Вход функции с одним параметром — сам аргумент (`""` — аргумент целиком); вход функции с
несколькими параметрами — объект с именами параметров (`hash`, `valueId`: `/typeId`, `/body`; `formatRef`: `/id`,
`/version`; `newId`: `/namespace`, `/ulid`; `revision`: `/input`, `/at`). На недопустимом входе функция SHALL
возвращать отказ и SHALL NOT бросать исключение. Аргумент неверного типа JavaScript (не строка там, где ждут строку,
`null`, `undefined`, число, объект) SHALL давать тот же код, что недопустимое значение этого параметра, с тем же
`path`. Функция с несколькими параметрами SHALL возвращать отказы всех недопустимых параметров в порядке параметров.

Функции SHALL быть детерминированными: равные входы дают равные результаты на любой машине и при любом числе вызовов;
функция SHALL NOT менять свои аргументы и SHALL NOT выполнять ввод-вывод, читать часы, окружение процесса или
случайные числа. Время и ULID приходят аргументами.

#### Scenario: Недопустимый вход — отказ без исключения и без изменения аргументов
<!-- id: SCN-KR-001 -->
- **WHEN** каждая функция вызывается с каждым входом сценариев `SCN-KR-002`…`SCN-KR-023`, допустимым и недопустимым;
  перед вызовом с объектом-аргументом (`canonical`, `hash`, `valueId`, `refsOf`, `revision`) делается его снимок по
  содержимому; каждый вызов повторяется дважды
- **THEN** ни один вызов не бросает исключение; каждый недопустимый вход даёт `ok: false` с непустым `errors`; оба
  результата одного входа равны по содержимому; объекты-аргументы после вызова равны своим снимкам

#### Scenario: Аргументы неверного типа
<!-- id: SCN-KR-020 -->

- **THEN** отказы: `syntax` `""`; `bad-ref` `""`; `bad-id` `/id`; `bad-version` `/version`; `bad-version` `/version`;
  `bad-namespace` `/namespace`; `bad-type-id` `/typeId`; `bad-input` `/input`

#### Scenario: Отказы нескольких параметров — все, в порядке параметров
<!-- id: SCN-KR-021 -->
- **WHEN** вызываются `hash("domain", {"x": NaN})`, `formatRef("Warrant/x", 0)`, `newId("Warrant", "x")`
- **THEN** отказы по порядку: `bad-type-id` `/typeId`, `not-json` `/body/x`; `bad-id` `/id`, `bad-version` `/version`;
  `bad-namespace` `/namespace`, `bad-ulid` `/ulid`

### Requirement: Входная проверка тела
<!-- id: REQ-KR-002 -->

`checkInput(text)` SHALL принимать JSON-текст (RFC 8259) строкой и возвращать при успехе разобранное значение, в
котором каждая строка — значение строки и ключ объекта — приведена к форме нормализации Unicode NFC (`UNK-KR-001`).
Версия Unicode формата v1 — 16.0 (`UNK-KR-005`): NFC — по Unicode 16.0, строки из кодовых точек, назначенных в нём.
Ключ `"__proto__"` и любой другой ключ SHALL быть обычным членом объекта результата. Число SHALL представляться
ближайшим числом двойной точности IEEE 754. Все проверки, кроме `lone-surrogate`, и все ключи в `path` SHALL
относиться к строкам после NFC; `lone-surrogate` проверяется по кодовым единицам UTF-16 строки после декодирования
escape-последовательностей и до NFC: суррогаты, образующие пару по кодовым единицам, — не одиночные, как бы каждый из
них ни был записан.

Вход SHALL отклоняться с кодами; у каждого кода — `path` и позиция в тексте, по которой упорядочиваются отказы:
- `syntax` — текст не является JSON-текстом RFC 8259, включая метку порядка байтов в начале, лишние символы после
  значения, запятую после последнего элемента, и аргумент — не строка; `path` — `""`, позиция — место ошибки;
- `too-deep` — вложенность массивов и объектов больше 64 уровней (`UNK-KR-004`): контейнер верхнего уровня — уровень
  1, скаляр верхнего уровня — уровень 0; `path` — контейнер уровня 65, позиция — его открывающая скобка;
- `duplicate-key` — в одном объекте два члена с равными ключами после NFC; `path` — член, встреченный вторым,
  позиция — начало его ключа;
- `negative-zero`, `non-finite`, `unsafe-integer` — по ближайшему числу двойной точности; числу — не больше одного
  отказа, по первому подходящему в этом порядке: `negative-zero` — ближайшее число `-0` (`-0`, `-0.0`, `-0e3`,
  `-1e-400`); `non-finite` — ближайшее число бесконечно (`1e400`, `1.7976931348623159e308`); `unsafe-integer` —
  ближайшее число целое (независимо от записи: `2`, `2.0`, `2e0`) и вне диапазона от −(2^53−1) до 2^53−1 включительно
  (`UNK-KR-002`); `path` — число, позиция — начало его записи;
- `lone-surrogate` — строка значения с одиночным суррогатом: `path` — строка, позиция — её открывающая кавычка; ключ с
  одиночным суррогатом: `path` — объект, позиция — открывающая кавычка ключа, значение этого члена проверяется только на
  `syntax` и `too-deep`, в проверку дублей член не входит;
- `unassigned` — строка значения или ключ с кодовой точкой, не назначенной в Unicode 16.0 (общая категория `Cn` по
  UCD 16.0, включая нехарактеры `U+FDD0`…`U+FDEF` и `U+xxFFFE`, `U+xxFFFF`; точки частного использования назначены);
  `path` и позиция — как у `lone-surrogate`, с тем же правилом для ключа; строке или ключу — не больше одного отказа
  из `lone-surrogate` и `unassigned`, по первому в этом порядке;
- `reserved-enc` — объект с ключом `$enc` на любой глубине (резерв шифруемых полей); `path` — объект, позиция — начало
  первого ключа `$enc`;
- `bad-ref` — объект с ключом `$ref`, у которого есть другие ключи, или значение `$ref` не строка, или строка не
  является ссылкой по требованию `REQ-KR-005`; объекту — не больше одного отказа `bad-ref`; `path` — объект, позиция —
  начало первого ключа `$ref`.

Отказ `syntax` или `too-deep` SHALL прекращать разбор и быть единственным элементом `errors`: возвращается тот из них,
чья позиция в тексте раньше; прежде найденные отказы других кодов отбрасываются, текст дальше не проверяется.
`too-deep` SHALL возвращаться для входа любой глубины, не исчерпывая стек. Остальные отказы SHALL собираться все, в
порядке их позиций в тексте; проверка SHALL продолжаться внутри отклонённых объектов (`$enc`, `$ref`) и внутри значения
члена-дубля.

### Requirement: Каноническая форма — JCS
<!-- id: REQ-KR-003 -->

`canonical(value)` SHALL возвращать строку канонической формы значения по JCS (RFC 8785) без изменений: порядок
ключей — по кодовым единицам UTF-16, числа — по правилу сериализации ECMAScript, строки — с минимальным
экранированием RFC 8785, без пробелов. Байты канонической формы — её кодировка UTF-8. `canonical` SHALL NOT
нормализовать строки: NFC — дело входной проверки. Число `-0` SHALL сериализоваться как `0` (RFC 8785).

`canonical` определена на JSON-значениях, а не на телах, прошедших входную проверку: конечное число любой величины,
включая целые вне ±(2^53−1) (векторы RFC 8785 `1E30` и большие целые приложения B), сериализуется, хотя `checkInput`
отклонила бы его запись.

Обход SHALL идти в глубину: члены объекта — в порядке ключей канонической формы, элементы массива — по индексу. Член
объекта — собственное перечислимое свойство-данные со строковым ключом; элемент массива — собственное
свойство-данные с индексом. `canonical` SHALL NOT вызывать геттеры и прочий код значения.

`canonical` SHALL отклонять с кодом `not-json` значение, которое не является JSON-значением; отказ — единственный, с
`path` на первое такое место в порядке обхода: `undefined`, функция, символ, `bigint`, неконечное число, строка или
ключ с одиночным суррогатом, объект, чей прототип не `Object.prototype` и не `null` (кроме массива), массив с
пропусками, свойство-аксессор (`path` — свойство), неперечислимое собственное свойство со строковым ключом (`path` —
свойство), собственное свойство с ключом-символом (`path` — объект), у массива — собственное свойство, кроме индексов
и `length` (`path` — свойство), циклическая ссылка — объект, который уже есть на текущем пути обхода от корня (`path` —
место повторного появления). Объект, встреченный повторно не на текущем пути (общий подобъект), — не цикл.

#### Scenario: Тестовые векторы RFC 8785
<!-- id: SCN-KR-006 -->

- **THEN** выход каждого вектора побайтно равен ожидаемому выходу RFC; числа NaN и Infinity таблицы — отказ `not-json`

<!-- id: SCN-KR-007 -->

<!-- id: SCN-KR-019 -->

### Requirement: Хэш и идентификатор значения
<!-- id: REQ-KR-004 -->

`hash(typeId, body)` SHALL возвращать 64 строчные шестнадцатеричные цифры `sha256` от байтов канонической формы
объекта `{"type": typeId, "body": body}`. `typeId` SHALL быть идентификатором вида `namespace/local` по требованию
`REQ-KR-005` без версии; иначе — отказ `bad-type-id` с `path` `/typeId`. Тело, которое `canonical` отклоняет, —
отказ `not-json` с `path` на место внутри тела, с префиксом `/body`.

`valueId(typeId, body)` SHALL возвращать `"#"` и первые 32 цифры `hash(typeId, body)` (схема 1) с теми же отказами.

#### Scenario: Хэш равен sha256 канонической формы, порядок ключей не важен
<!-- id: SCN-KR-008 -->
- **WHEN** `hash("std/domain", {"name": "lifecycle", "code": "LCY"})` и `hash("std/domain", {"code": "LCY", "name":
  "lifecycle"})`, затем `valueId` с теми же аргументами
- **THEN** оба хэша равны `a4ab98af0a7f2bf7899d59506cd69fb5aab77c4e292679dc1f1a28ddcf251fe4` — `sha256` от UTF-8
  строки `{"body":{"code":"LCY","name":"lifecycle"},"type":"std/domain"}`; `valueId` равен
  `#a4ab98af0a7f2bf7899d59506cd69fb5`

#### Scenario: Отказы хэша
<!-- id: SCN-KR-009 -->
- **WHEN** `hash` получает `typeId` `"std/domain@1"`, `"#3fa29c0d71be44a2b6c1d0e9f8a7b6c5"`, `"domain"`, затем
  `typeId` `"std/domain"` с телом `{"x": NaN}`
- **THEN** первые три — отказ `bad-type-id` с `path` `/typeId`; последний — отказ `not-json` с `path` `/body/x`

### Requirement: Идентификаторы и ссылки
<!-- id: REQ-KR-005 -->

Идентификатор SHALL иметь вид `namespace "/" local` или `value-id`:
- `namespace` — `[a-z][a-z0-9-]*` и ноль или больше частей `"." [a-z0-9-]+`;
- `local` — `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`, регистр значим (`UNK-KR-003`);
- `value-id` — `"#"` и ровно 32 строчные шестнадцатеричные цифры (схема 1);
- `"#" label ":" hex` с `label` = `[g-z][a-z0-9]*` и `hex` = `[0-9a-f]+` — зарезервированная схема: ядро v1 её
  отклоняет кодом `reserved-scheme` везде, где ждёт идентификатор (`parseRef`, `formatRef`, `revision`); строка
  `"#" label ":"` с пустым или не шестнадцатеричным хвостом — не идентификатор.

Ссылка SHALL иметь вид `id` (следующая) или `id "@" version` (закреплённая), где `version` — десятичное целое без
ведущих нулей от 1 до 2^53−1.

`parseRef(s)` SHALL возвращать `{ id }` или `{ id, version }` (число) либо отказ `reserved-scheme` или `bad-ref` с
`path` `""`. `formatRef(id, version?)` SHALL возвращать строку ссылки, для которой `parseRef` даёт те же `id` и
`version`; недопустимый `id` — отказ `bad-id` с `path` `/id` (зарезервированная схема — `reserved-scheme` с `path`
`/id`), недопустимая версия — `bad-version` с `path` `/version`; `version`, равная `undefined`, — ссылка без версии.
Для любой допустимой строки ссылки `s` SHALL выполняться `formatRef` от результата `parseRef(s)` равно `s`.

`newId(namespace, ulid)` SHALL возвращать `namespace "/" ulid`, если `namespace` допустим, а `ulid` — 26 символов
алфавита Crockford Base32 в верхнем регистре (`0-9`, `A-H`, `J`, `K`, `M`, `N`, `P-T`, `V-Z`) с первым символом от `0`
до `7`; иначе — отказ `bad-namespace` с `path` `/namespace` или `bad-ulid` с `path` `/ulid`.

### Requirement: Ссылки в теле
<!-- id: REQ-KR-006 -->

`refsOf(body)` SHALL принимать тело — значение, которое вернула успешная `checkInput`, — и возвращать список ссылок
тела: результатов `parseRef` для каждого объекта `{"$ref": s}` на любой глубине, включая само тело. Обход SHALL идти
так же, как обход `canonical` (`REQ-KR-003`). Ссылка, строка которой уже встречалась, SHALL NOT повторяться: остаётся
первое появление. Строка `"$ref"` как значение ссылкой не является.

Значение, построенное в коде в обход `checkInput`, SHALL отклоняться:
- `not-json` — значение, которое отклоняет `canonical`; отказ единственный, с тем же `path`;
- `bad-ref` — объект с ключом `$ref`, который отклонила бы входная проверка (`REQ-KR-002`: другие ключи, значение не
  строка или не ссылка); `path` — объект; отказы собираются все, в порядке обхода.

#### Scenario: Обход тела
<!-- id: SCN-KR-013 -->
- **WHEN** `refsOf` получает значение `checkInput` для
  `{"b": [{"$ref": "std/need@2"}, {"x": {"$ref": "warrant/REQ-1"}}], "a": {"$ref": "warrant/REQ-1"}, "c": "$ref"}`,
  затем для `{"$ref": "core/type@1"}`, затем для `[1, "a", null]`
- **THEN** первый — `[{ id: "warrant/REQ-1" }, { id: "std/need", version: 2 }]` (ключ `a` раньше `b`); второй —
  `[{ id: "core/type", version: 1 }]`; третий — пустой список

#### Scenario: Отказы поиска ссылок
<!-- id: SCN-KR-022 -->
- **WHEN** `refsOf` получает построенные в коде `{"$ref": 5}`, `{"y": {"$ref": "x/y", "k": 1}, "x": {"$ref": "a"}}`
  и объект, ссылающийся сам на себя по ключу `s`
- **THEN** первый — отказ `bad-ref` `""`; второй — отказы по порядку `bad-ref` `/x`, `bad-ref` `/y`; третий — отказ
  `not-json` `/s`

### Requirement: Ревизия
<!-- id: REQ-KR-007 -->

`revision(input, at)` SHALL собирать ревизию — объект ровно с ключами `id`, `type`, `version`, `at`, `by`, `body` — из
`input` `{ id, type, version, by, body }` и `at`, без проверки правил, типа и вида объекта:
- `input` — объект с прототипом `Object.prototype` или `null`, иначе единственный отказ `bad-input` `/input`;
  собственный ключ `input`, кроме пяти названных, — отказ `bad-input` `/input/<ключ>`;
- `id` — идентификатор по `REQ-KR-005`, иначе отказ `bad-id` `/input/id` (зарезервированная схема —
  `reserved-scheme` `/input/id`);
- `type` — закреплённая ссылка `namespace/local@n`, иначе отказ `bad-type` `/input/type`;
- `version` — целое от 1 до 2^53−1, иначе отказ `bad-version` `/input/version`;
- `by` — идентификатор `namespace/local` без версии, иначе отказ `bad-by` `/input/by`;
- `body` — собственное свойство `input` со значением не `undefined`, иначе отказ `bad-body` `/input/body`; переносится
  той же ссылкой, без копии и заморозки; ядро его не проверяет (тело приходит из `checkInput`);
- `at` — целое число миллисекунд от 1970-01-01T00:00:00.000Z от 0 до 253402300799999 включительно; в ревизии —
  строка `YYYY-MM-DDTHH:mm:ss.sssZ` (UTC); иначе отказ `bad-at` `/at`.

Ревизия — новый обычный объект, не замороженный. Все отказы входа SHALL собираться в порядке: лишние ключи `input` в
порядке `Object.keys`, затем `id`, `type`, `version`, `by`, `body`, `at`.

#### Scenario: Ревизия собрана
<!-- id: SCN-KR-014 -->
- **WHEN** `revision({ id: "warrant/01J8ZQ4N7X5K2M9R3T6V8W0Y1A", type: "std/domain@1", version: 3, by:
  "warrant/SES-01J8ZQ3", body: { "name": "lifecycle" } }, 1790451612345)`
- **THEN** успех; ключи ревизии — ровно `id`, `type`, `version`, `at`, `by`, `body`; `at` —
  `"2026-09-26T19:40:12.345Z"`; остальные поля равны входу; `body` ревизии — тот же объект, что `body` входа

#### Scenario: Отказы ревизии
<!-- id: SCN-KR-015 -->
- **WHEN** `revision` получает `{ id: "warrant/x", type: "std/domain", version: 0, by: "warrant/SES-1@2", body: {} }`
  с `at` −1, затем верный вход с `at` 253402300800000 и с `at` 1.5, затем с `at` 0 — верный вход с лишним ключом
  `extra` и без ключа `body` и верный вход с `id` `#g1:ab`
- **THEN** первый — отказы по порядку `bad-type` `/input/type`, `bad-version` `/input/version`, `bad-by` `/input/by`,
  `bad-at` `/at`; второй и третий — отказ `bad-at` `/at`; четвёртый — отказы по порядку `bad-input` `/input/extra`,
  `bad-body` `/input/body`; пятый — отказ `reserved-scheme` `/input/id`
