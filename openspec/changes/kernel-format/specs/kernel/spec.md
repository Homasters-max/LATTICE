# Spec Delta

## Purpose

Формат v1 замороженного ядра LATTICE: входная проверка тела, каноническая форма, хэш и идентификатор значения,
грамматика идентификаторов и ссылок, поиск ссылок в теле и форма ревизии — чистые функции, от которых зависят все
байты журнала и все сравнения по содержимому.

## ADDED Requirements

### Requirement: Отказ — значение, функции ядра чистые
<!-- id: REQ-KR-001 -->

Функции ядра этой возможности — `checkInput`, `canonical`, `hash`, `valueId`, `parseRef`, `formatRef`, `newId`,
`refsOf`, `revision` — SHALL экспортироваться модулем ядра проекта. Каждая функция SHALL возвращать либо успех
`{ ok: true, value }`, либо отказ `{ ok: false, errors }`, где `errors` — непустой список элементов `{ code, path }`:
`code` — строка из перечня кодов требования этой функции, `path` — JSON Pointer (RFC 6901) на место во входе, к
которому относится отказ (`""` — вход целиком). На недопустимом входе функция SHALL возвращать отказ и SHALL NOT
бросать исключение.

Функции SHALL быть детерминированными: равные входы дают равные результаты на любой машине и при любом числе вызовов;
функция SHALL NOT менять свои аргументы и SHALL NOT выполнять ввод-вывод, читать часы, окружение процесса или
случайные числа. Время и ULID приходят аргументами.

#### Scenario: Недопустимый вход — отказ без исключения и без изменения аргументов
<!-- id: SCN-KR-001 -->
- **WHEN** каждая функция вызывается с недопустимым входом из сценариев этой возможности, а `canonical` и `revision`
  — с объектом, снимок которого сделан до вызова; каждый вызов повторяется дважды
- **THEN** ни один вызов не бросает исключение, каждый возвращает `ok: false` с непустым `errors`, оба результата
  одного входа равны по содержимому, объекты-аргументы после вызова равны своим снимкам

### Requirement: Входная проверка тела
<!-- id: REQ-KR-002 -->

`checkInput(text)` SHALL принимать JSON-текст (RFC 8259) строкой и возвращать при успехе разобранное значение, в
котором каждая строка — значение строки и ключ объекта — приведена к форме нормализации Unicode NFC (`UNK-KR-001`).
Ключ `"__proto__"` и любой другой ключ SHALL быть обычным членом объекта результата. Число SHALL представляться
ближайшим числом двойной точности IEEE 754.

Вход SHALL отклоняться с кодами:
- `syntax` — текст не является JSON-текстом RFC 8259, включая метку порядка байтов в начале, лишние символы после
  значения, запятую после последнего элемента; `path` — `""`;
- `duplicate-key` — в одном объекте два члена с равными ключами после NFC; `path` — член, встреченный вторым;
- `negative-zero` — число со значением `-0` в любой записи (`-0`, `-0.0`, `-0e3`);
- `non-finite` — число, запись которого вне диапазона двойной точности (например `1e400`);
- `unsafe-integer` — число с целым значением (независимо от записи: `2`, `2.0`, `2e0`) вне диапазона от −(2^53−1)
  до 2^53−1 включительно (`UNK-KR-002`); запись, которая округляется к такому значению, — тоже;
- `lone-surrogate` — строка или ключ с одиночным суррогатом UTF-16, заданным escape-последовательностью или
  непосредственно;
- `reserved-enc` — объект с ключом `$enc` на любой глубине (резерв шифруемых полей);
- `bad-ref` — объект с ключом `$ref`, у которого есть другие ключи, или значение `$ref` не строка, или строка не
  является ссылкой по требованию `REQ-KR-005`;
- `too-deep` — вложенность массивов и объектов больше 64 уровней (`UNK-KR-004`): контейнер верхнего уровня — уровень
  1, скаляр верхнего уровня — уровень 0; `path` — первый контейнер уровня 65.

Отказ `syntax` SHALL быть единственным элементом `errors`. Остальные отказы SHALL собираться все, в порядке появления
их места в тексте; `too-deep` SHALL возвращаться для входа любой глубины, не исчерпывая стек.

#### Scenario: NFC и обычный ключ `__proto__`
<!-- id: SCN-KR-002 -->
- **WHEN** `checkInput` получает текст `{"e\u0301": "cafe\u0301", "__proto__": {"a": 1}}` (escape-последовательности
  JSON: `e` и комбинирующий акут U+0301)
- **THEN** успех; у результата ключ из одной кодовой точки U+00E9 со значением из `caf` и U+00E9; член `__proto__` —
  собственное свойство со значением `{"a": 1}`, прототип результата не изменён

#### Scenario: Числа на границах
<!-- id: SCN-KR-003 -->
- **WHEN** `checkInput` получает по отдельности тексты `9007199254740991`, `-9007199254740991`, `1.0`, `0.5`,
  `1e-300`, `9007199254740992`, `9007199254740993`, `-9007199254740992`, `1e300`, `2e0`, `-0`, `-0.0`, `1e400`,
  `-1e400`
- **THEN** первые пять — успех со значениями 9007199254740991, −9007199254740991, 1, 0.5, 1e−300; `9007199254740992`,
  `9007199254740993`, `-9007199254740992` и `1e300` — отказ `unsafe-integer`; `2e0` — успех со значением 2; `-0` и
  `-0.0` — отказ `negative-zero`; `1e400` и `-1e400` — отказ `non-finite`; у каждого отказа `path` — `""`

#### Scenario: Структурные отказы с местом
<!-- id: SCN-KR-004 -->
- **WHEN** `checkInput` получает по отдельности: `{"a":1,"a":2}`; `{"\u00e9":1,"e\u0301":2}`; `{"s":"\ud800"}`;
  текст, где в строке `s` стоит непосредственный одиночный суррогат U+DC00; `{"x":[{"$enc":"q"}]}`;
  `{"r":{"$ref":"std/need@2","k":1}}`; `{"r":{"$ref":5}}`; `{"r":{"$ref":"#g1:ab"}}`; `[1,]`; текст `{}` с меткой
  порядка байтов U+FEFF в начале; `{} x`; `{"a":-0,"b":{"$enc":1},"a":2}`
- **THEN** отказы и места: `duplicate-key` `/a`; `duplicate-key` — путь `/` и U+00E9; `lone-surrogate` `/s`; `lone-surrogate` `/s`;
  `reserved-enc` `/x/0`; `bad-ref` `/r`; `bad-ref` `/r`; `bad-ref` `/r`; `syntax` `""`; `syntax` `""`; `syntax` `""`;
  для последнего текста — три отказа по порядку: `negative-zero` `/a`, `reserved-enc` `/b`, `duplicate-key` `/a`

#### Scenario: Предел вложенности
<!-- id: SCN-KR-005 -->
- **WHEN** `checkInput` получает массив из 64 вложенных массивов (`[[…[]…]]`, 64 открывающие скобки), затем из 65, затем
  текст из 100 000 открывающих скобок `[`
- **THEN** 64 уровня — успех; 65 уровней — отказ `too-deep` с `path` из 64 сегментов `/0`; 100 000 скобок — отказ
  `too-deep` (не `syntax`) без исключения

### Requirement: Каноническая форма — JCS
<!-- id: REQ-KR-003 -->

`canonical(value)` SHALL возвращать строку канонической формы значения по JCS (RFC 8785) без изменений: порядок
ключей — по кодовым единицам UTF-16, числа — по правилу сериализации ECMAScript, строки — с минимальным
экранированием RFC 8785, без пробелов. Байты канонической формы — её кодировка UTF-8. `canonical` SHALL NOT
нормализовать строки: NFC — дело входной проверки. Число `-0` SHALL сериализоваться как `0` (RFC 8785).

`canonical` SHALL отклонять с кодом `not-json` значение, которое не является JSON-значением, с `path` на первое такое
место в порядке обхода: `undefined`, функция, символ, `bigint`, неконечное число, строка или ключ с одиночным
суррогатом, объект, чей прототип не `Object.prototype` и не `null` (кроме массива), массив с пропусками, циклическая
ссылка.

#### Scenario: Тестовые векторы RFC 8785
<!-- id: SCN-KR-006 -->
- **WHEN** `canonical` получает входы векторов RFC 8785: пример раздела 3.2.2 (`numbers`, `string`, `literals`),
  пример сортировки раздела 3.2.3 и каждое число таблицы приложения B, заданное битами IEEE 754; векторы лежат
  фикстурой в `test/fixtures/` с указанием раздела RFC
- **THEN** выход каждого вектора побайтно равен ожидаемому выходу RFC; числа NaN и Infinity таблицы — отказ `not-json`

#### Scenario: Не JSON-значение
<!-- id: SCN-KR-007 -->
- **WHEN** `canonical` получает `{"a": [1, undefined]}`, `{"b": 1n}`, `{"c": new Date(0)}`, `[1, , 3]`, объект,
  ссылающийся сам на себя по ключу `s`, строку с одиночным суррогатом `"\ud800"` и значение `-0`
- **THEN** отказ `not-json` с местами `/a/1`, `/b`, `/c`, `/1`, `/s`, `""`; для `-0` — успех `"0"`

### Requirement: Хэш и идентификатор значения
<!-- id: REQ-KR-004 -->

`hash(typeId, body)` SHALL возвращать 64 строчные шестнадцатеричные цифры `sha256` от байтов канонической формы
объекта `{"type": typeId, "body": body}`. `typeId` SHALL быть идентификатором вида `namespace/local` по требованию
`REQ-KR-005` без версии; иначе — отказ `bad-type-id` с `path` `""`. Тело, которое `canonical` отклоняет, — отказ
`not-json` с `path` на место внутри тела, с префиксом `/body`.

`valueId(typeId, body)` SHALL возвращать `"#"` и первые 32 цифры `hash(typeId, body)` (схема 1) с теми же отказами.

#### Scenario: Хэш равен sha256 канонической формы, порядок ключей не важен
<!-- id: SCN-KR-008 -->
- **WHEN** `hash("std/domain", {"name": "lifecycle", "code": "LCY"})` и `hash("std/domain", {"code": "LCY", "name":
  "lifecycle"})`, затем `valueId` с теми же аргументами
- **THEN** оба хэша равны `sha256` от UTF-8 строки `{"body":{"code":"LCY","name":"lifecycle"},"type":"std/domain"}` в
  строчном hex; `valueId` равен `"#"` и первым 32 символам этого хэша

#### Scenario: Отказы хэша
<!-- id: SCN-KR-009 -->
- **WHEN** `hash` получает `typeId` `"std/domain@1"`, `"#3fa29c0d71be44a2b6c1d0e9f8a7b6c5"`, `"domain"`, затем
  `typeId` `"std/domain"` с телом `{"x": NaN}`
- **THEN** первые три — отказ `bad-type-id` с `path` `""`; последний — отказ `not-json` с `path` `/body/x`

### Requirement: Идентификаторы и ссылки
<!-- id: REQ-KR-005 -->

Идентификатор SHALL иметь вид `namespace "/" local` или `value-id`:
- `namespace` — `[a-z][a-z0-9-]*` и ноль или больше частей `"." [a-z0-9-]+`;
- `local` — `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`, регистр значим (`UNK-KR-003`);
- `value-id` — `"#"` и ровно 32 строчные шестнадцатеричные цифры (схема 1);
- `"#" label ":" …` с `label` = `[g-z][a-z0-9]*` — зарезервированная схема: ядро v1 её отклоняет кодом
  `reserved-scheme`.

Ссылка SHALL иметь вид `id` (следующая) или `id "@" version` (закреплённая), где `version` — десятичное целое без
ведущих нулей от 1 до 2^53−1.

`parseRef(s)` SHALL возвращать `{ id }` или `{ id, version }` (число) либо отказ `reserved-scheme` или `bad-ref` с
`path` `""`. `formatRef(id, version?)` SHALL возвращать строку ссылки, для которой `parseRef` даёт те же `id` и
`version`; недопустимый `id` — отказ `bad-id` с `path` `/id` (или `reserved-scheme`), недопустимая версия — `bad-version`
с `path` `/version`. Для любой допустимой строки ссылки `s` SHALL выполняться `formatRef` от результата `parseRef(s)`
равно `s`.

`newId(namespace, ulid)` SHALL возвращать `namespace "/" ulid`, если `namespace` допустим, а `ulid` — 26 символов
алфавита Crockford Base32 в верхнем регистре (`0-9`, `A-H`, `J`, `K`, `M`, `N`, `P-T`, `V-Z`) с первым символом от `0`
до `7`; иначе — отказ `bad-namespace` с `path` `/namespace` или `bad-ulid` с `path` `/ulid`.

#### Scenario: Допустимые ссылки и круговой разбор
<!-- id: SCN-KR-010 -->
- **WHEN** `parseRef` получает `std/need@2`, `warrant/REQ-KRN-011`, `core/rule.type-shape@1`, `acme.tools/x_1`,
  `warrant/01J8ZQ4N7X5K2M9R3T6V8W0Y1A`, `#3fa29c0d71be44a2b6c1d0e9f8a7b6c5`, `#3fa29c0d71be44a2b6c1d0e9f8a7b6c5@1`,
  `warrant/x@9007199254740991`, и для каждого результата вызывается `formatRef`
- **THEN** каждая строка разобрана: `std/need@2` → `{ id: "std/need", version: 2 }`, `warrant/REQ-KRN-011` →
  `{ id: "warrant/REQ-KRN-011" }`; `formatRef` каждого результата равен исходной строке

#### Scenario: Недопустимые ссылки
<!-- id: SCN-KR-011 -->
- **WHEN** `parseRef` получает `#g1:abcd`, `#z:1`, `#3FA29C0D71BE44A2B6C1D0E9F8A7B6C5`, `#3fa29c0d71be44a2b6c1d0e9f8a7b6c`,
  `warrant/`, `Warrant/x`, `warrant/a b`, `warrant/a/b`, `warrant/-x`, `warrant/x@0`, `warrant/x@01`,
  `warrant/x@9007199254740992`, `warrant/x@`, `std/need@2@3`, пустую строку и строку из `warrant/` и 129 символов `a`;
  `formatRef` получает `("warrant/x", 0)`, `("warrant/x", 1.5)`, `("Warrant/x")`
- **THEN** `#g1:abcd` и `#z:1` — отказ `reserved-scheme`; остальные строки — отказ `bad-ref`; `formatRef` — отказы
  `bad-version` `/version`, `bad-version` `/version`, `bad-id` `/id`

#### Scenario: Новый идентификатор из ULID
<!-- id: SCN-KR-012 -->
- **WHEN** `newId` получает `("warrant", "01J8ZQ4N7X5K2M9R3T6V8W0Y1A")`, `("Warrant", "01J8ZQ4N7X5K2M9R3T6V8W0Y1A")`,
  `("warrant", "01j8zq4n7x5k2m9r3t6v8w0y1a")`, `("warrant", "81J8ZQ4N7X5K2M9R3T6V8W0Y1A")`,
  `("warrant", "01J8ZQ4N7X5K2M9R3T6V8W0Y1")`, `("warrant", "01J8ZQ4N7X5K2M9R3T6V8W0YIL")`
- **THEN** первый — успех `warrant/01J8ZQ4N7X5K2M9R3T6V8W0Y1A`; второй — отказ `bad-namespace` `/namespace`;
  остальные — отказ `bad-ulid` `/ulid`

### Requirement: Ссылки в теле
<!-- id: REQ-KR-006 -->

`refsOf(body)` SHALL принимать значение, которое вернула успешная `checkInput`, и возвращать список ссылок тела —
результатов `parseRef` для каждого объекта `{"$ref": s}` на любой глубине, включая само тело. Обход SHALL идти в
глубину: члены объекта — в порядке ключей канонической формы, элементы массива — по индексу. Ссылка, строка которой
уже встречалась, SHALL NOT повторяться: остаётся первое появление. Строка `"$ref"` как значение ссылкой не является
(объект с ключом `$ref` и другими ключами входная проверка отклоняет).

#### Scenario: Обход тела
<!-- id: SCN-KR-013 -->
- **WHEN** `refsOf` получает значение `checkInput` для
  `{"b": [{"$ref": "std/need@2"}, {"x": {"$ref": "warrant/REQ-1"}}], "a": {"$ref": "warrant/REQ-1"}, "c": "$ref"}`,
  затем для `{"$ref": "core/type@1"}`, затем для `[1, "a", null]`
- **THEN** первый — `[{ id: "warrant/REQ-1" }, { id: "std/need", version: 2 }]` (ключ `a` раньше `b`); второй —
  `[{ id: "core/type", version: 1 }]`; третий — пустой список

### Requirement: Ревизия
<!-- id: REQ-KR-007 -->

`revision(input, at)` SHALL собирать ревизию — объект ровно с ключами `id`, `type`, `version`, `at`, `by`, `body` — из
`input` `{ id, type, version, by, body }` и `at`, без проверки правил, типа и вида объекта:
- `id` — идентификатор по `REQ-KR-005`, иначе отказ `bad-id` `/id`;
- `type` — закреплённая ссылка `namespace/local@n`, иначе отказ `bad-type` `/type`;
- `version` — целое от 1 до 2^53−1, иначе отказ `bad-version` `/version`;
- `by` — идентификатор `namespace/local` без версии, иначе отказ `bad-by` `/by`;
- `at` — целое число миллисекунд от 1970-01-01T00:00:00.000Z от 0 до 253402300799999 включительно; в ревизии —
  строка `YYYY-MM-DDTHH:mm:ss.sssZ` (UTC); иначе отказ `bad-at` `/at`;
- `body` — переносится без изменений; ядро его не проверяет (тело приходит из `checkInput`).

Все отказы входа SHALL собираться в порядке `id`, `type`, `version`, `by`, `at`.

#### Scenario: Ревизия собрана
<!-- id: SCN-KR-014 -->
- **WHEN** `revision({ id: "warrant/01J8ZQ4N7X5K2M9R3T6V8W0Y1A", type: "std/domain@1", version: 3, by:
  "warrant/SES-01J8ZQ3", body: { "name": "lifecycle" } }, 1790451612345)`
- **THEN** успех; ключи ревизии — ровно `id`, `type`, `version`, `at`, `by`, `body`; `at` —
  `"2026-09-26T19:40:12.345Z"`; остальные поля равны входу

#### Scenario: Отказы ревизии
<!-- id: SCN-KR-015 -->
- **WHEN** `revision` получает `{ id: "warrant/x", type: "std/domain", version: 0, by: "warrant/SES-1@2", body: {} }`
  с `at` −1, затем верный вход с `at` 253402300800000 и с `at` 1.5
- **THEN** первый — отказы по порядку `bad-type` `/type`, `bad-version` `/version`, `bad-by` `/by`, `bad-at` `/at`;
  второй и третий — отказ `bad-at` `/at`
