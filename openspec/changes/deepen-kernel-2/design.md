# Design

## Context

Мотивация — proposal.md, Why; поведение — `specs/architecture/spec.md` этого Change и действующая
`openspec/specs/kernel/spec.md` (не меняется). Сейчас:
- `test/architecture/structure.ts` — `checkKernel(dir)` (REQ-AR-001: обход каталога, `insideRoot` — граница ядра —
  корень каталога, правила чистоты в `checkKernelFile`) и `checkTests(files)` (REQ-AR-002) со своим разбором; фикстуры
  `test/fixtures/structure/{kernel,broken,tests}/` несут ожидания метками `// expect: <правило>` на строках.
- `src/kernel/` — десять файлов; все достижимы из `index.ts`; циклов импортов нет. Вне `index.ts` ядро импортирует
  только `test/kernel/environment.test.ts` (`assignedRanges`, `isAssigned16` из `unicode16.ts`).
- Стек — TypeScript / Node.js 22, `node:test`, разбор — `typescript` (devDependency, kernel-format D-5).

## Goals / Non-Goals

**Goals:**
- Тест структуры — одна форма, в которую правила 04 §3 п. 1, 4, 5 и перечень периметра S1 лягут данными политики и
  функцией над тем же графом, без нового обхода и разрешения импортов.
- Правки ядра — без смены поведения: те же коды, пути, порядок отказов, байты; `test/kernel/**` не правится.

**Non-Goals:**
- Правила матрицы, адаптеров и пакетов; точка входа `kernel-v1` (proposal.md, Non-goals).
- Производительность теста структуры сверх одного разбора файла за прогон.

## Decisions

### D-1. Тест структуры — один модуль: граф импортов и политика-данные

`test/architecture/structure.ts` отдаёт:
- `type Policy = { sources: readonly string[]; entry: string; perimeter: readonly string[] }` — глобы и путь
  относительно корня дерева;
- `checkStructure(root, policy): Violation[]` — REQ-AR-001, REQ-AR-003, REQ-AR-004; `Violation` — прежний
  `{ file, line, rule }`, `file` — путь относительно корня с `/` (у `no-kernel` — корень как передан или точка входа);
- `checkTests(files): Violation[]` — REQ-AR-002, поведение прежнее, разбор — та же внутренняя функция `parse`;
- `listFiles`, `projectTestFiles` — как сейчас.

Внутри: загрузка дерева — список файлов, подходящих под `sources` ∪ `perimeter` (обход начинается со статического
префикса каждого глоба — части до первого сегмента с `*`, так `node_modules` проекта не читается), каждый `.ts` файл
разбирается один раз в факты: диагностики разбора, рёбра импорта (D-2) со строкой, узел AST для правил чистоты. Правила
— внутренние функции над загруженным деревом: `purity` (правила REQ-AR-001 из нынешнего `checkKernelFile`, перенесены
без изменения логики, `insideRoot` заменён проверкой «путь `.ts` и подходит под перечень периметра»), `perimeter`
(REQ-AR-003, обход в ширину от точки входа по рёбрам файлов периметра), `cycles` (REQ-AR-004, обход в глубину с тремя
цветами в порядке путей). `no-kernel` проверяется до правил, по порядку условий REQ-AR-001 (корень, `.ts` периметра,
точка входа), и прекращает проверку. Результат — множество троек `file:line:rule` (REQ-AR-001), упорядоченное по
файлу, строке, правилу; тесты сравнивают список целиком.

Загрузка — `readdirSync(…, { withFileTypes: true })`: `Dirent.isDirectory()` символическую ссылку каталогом не
считает, ссылки не прослеживаются. Множество путей дерева — строки из обхода; существование пути ребра — точное
совпадение строки с одной из них, с учётом регистра, поэтому Windows и Linux CI дают один граф (`./Ref.ts` при файле
`ref.ts` — несуществующий путь). Роль `sources` — узлы правила циклов; разбираются файлы `sources` ∪ `perimeter`
(на них и `parse-error`); правило периметра идёт по рёбрам файлов периметра независимо от `sources` (SCN-AR-005,
третий прогон).

Глоб — свой разборщик: сегмент `**` — ноль и больше сегментов, `*` — `[^/]*` внутри сегмента, прочее — буквально
(REQ-AR-001). `path.matchesGlob` Node 22 — экспериментальный; пакет — лишняя зависимость ради двух символов.

Политика проекта — данные в `test/architecture/policy.ts`: `{ sources: ["src/**"], entry: "src/kernel/index.ts",
perimeter: ["src/kernel/**"] }`. S1: политика получает матрицу доменов, точку входа `src/ledger/kernel-v1.ts` и перечень
периметра 04 §3 п. 6 — строками данных; правило матрицы — ещё одна функция над тем же графом.

Отвергнуто:
- Оставить `checkKernel(dir)` и добавлять по функции на правило: каждое правило со своим обходом и разрешением
  спецификаторов, периметр каталогом не выражается (разбор архитектуры, кандидат 1).
- Пакеты графа зависимостей (`madge`, `dependency-cruiser`): разрешение импортов у них своё, а правила чистоты всё
  равно требуют AST TypeScript, который тест уже строит.

### D-2. Рёбра графа и разрешение спецификаторов

Ребро — узел `ImportDeclaration`, `ExportDeclaration` с `moduleSpecifier`, `ImportEqualsDeclaration` с
`ExternalModuleReference`, `ImportTypeNode` (`import("…")` в позиции типа) — с относительным спецификатором (`./`,
`../`). Не рёбра: не относительный спецификатор (`node:*`, пакет — в файлах периметра его решает
`import-outside-kernel`), вызов `import(…)` и `require(…)` (`dynamic-import`), `/// <reference …>`
(`import-outside-kernel`).

Путь — `resolve(dirname(file), spec)` относительно корня дерева, разделитель `/`; расширение не переписывается
(`./x.js` — путь `x.js`), индекс каталога не подставляется: импорты проекта — с явным `.ts` (kernel-format D-6). Путь вне
корня начинается с `..` и не подходит ни под один глоб. Существование файла по пути: для `import-outside-kernel` и
`outside-perimeter` не требуется (решение по пути, как сейчас); обход периметра продолжается только из существующих
файлов периметра; узлы графа циклов — только существующие файлы источников. Строка ребра — `getStart` узла
объявления (или узла `ImportTypeNode`), как сейчас: многострочный импорт получает строку своего первого токена.

Файл с `parse-error` — узел без исходящих рёбер и без правил чистоты: AST TypeScript после синтаксической ошибки
восстановлен эвристически, выводить из него рёбра и нарушения — угадывать (как нынешний `checkKernelFile`, который
после первой диагностики файл не проверяет). Входящие рёбра в него — обычные.

**`import type` — ребро.** ADR-43 и 04 §3 п. 6 включают в перечень периметра интерфейсы `src/*/types.ts`: это имеет
смысл, только если импорт типа приводит файл в периметр; 04 §2 требует «между файлами нет циклов» именно для
интерфейсов, которые импортируют друг друга типами; REQ-AR-001 уже считает `import type` импортом. Отвергнуто: только
импорты значений — тип стирается при исполнении, но правка интерфейса меняет контракт ядра так же, как правка кода.

### D-3. Отказы периметра: `outside-perimeter` и `no-kernel`

- Новый код `outside-perimeter` — у ребра из достижимого файла периметра в путь вне перечня, на строке импорта; у точки
  входа вне перечня — строка 0. Рёбра из файлов вне периметра не прослеживаются: отказ называет импорт, который вывел за
  перечень, а не хвост цепочки.
- При правиле `import-outside-kernel` над каждым файлом перечня тот же импорт даёт и его: два правила с одной строкой
  (REQ-AR-003). Своё у `outside-perimeter` — точка входа и достижимость: файл перечня, не достижимый из точки входа,
  получает только `import-outside-kernel` (SCN-AR-004, `orphan.ts`). На S1, когда правила импорта файлов `src/` задаст
  матрица, `outside-perimeter` останется единственной защитой периметра `kernel-v1`.
- Нет файла точки входа — `no-kernel`, как нет корня или `.ts` файлов периметра: проверять нечего, другой код не
  нужен; отказ называет точку входа. Условия проверяются по порядку «корень, `.ts` периметра, точка входа» — при
  отсутствии корня отказ называет корень, а не точку входа (REQ-AR-001).

Отвергнуто: подавлять `import-outside-kernel`, когда тот же импорт даёт `outside-perimeter`, — правило чистоты стало бы
зависеть от точки входа, а фикстура `kernel/**` потеряла бы вектор.

### D-4. `ref.ts` — владелец таблицы REQ-KR-005

Интерфейс `ref.ts` внутри ядра:
- `checkAt(position, value, path): Refusal | null` — строка таблицы позиции:

  | Позиция | Допустимо | Отказ | Вызывающие |
  |---|---|---|---|
  | `id` | `namespace/local` или `value-id` | зарезервированная схема — `reserved-scheme`, иначе `bad-id` | `formatRef`, `revision` |
  | `typeId` | `namespace/local` | `bad-type-id` | `hash`, `valueId` |
  | `type` | закреплённая ссылка `namespace/local@n` | `bad-type` | `revision` |
  | `by` | `namespace/local` | `bad-by` | `revision` |
  | `version` | целое 1…2^53−1 | `bad-version` | `formatRef`, `revision` |
  | `namespace` | `namespace` ≤ 64 символов | `bad-namespace` | `newId` |

- `refObject(others, value, rejected): Ref | null` — вердикт объекта `{"$ref"}`: `null` (отказ `bad-ref` — у
  вызывающего, со своими `path` и позицией), если есть другие ключи, значение не строка, строка отклонена или `parseRef`
  её отклоняет. Что считать «другим ключом» и «отклонённой строкой» — вход от вызывающего: `input.ts` считает по тексту
  (отклонённые ключи — другие, дубль `$ref` — нет, строка после NFC, `rejected` — `lone-surrogate` или `unassigned`),
  `refs.ts` — по значению (`Reflect.ownKeys` больше одного, свойство-аксессор — значение `undefined`, `rejected` —
  `false`); ссылку из результата `refs.ts` кладёт в список.
- `parseRef`, `formatRef` — как сейчас; `idKind`, `isNamespace`, `isVersion` — не экспортируются.

Порядок проверок вызывающих не меняется: `revision` — лишние ключи, `id`, `type`, `version`, `by`, `body`, `at`;
`formatRef` — `id`, затем `version`, если она не `undefined`. Векторы — SCN-KR-004, 009…015, 017, 020…022.

Отвергнуто: оставить предикаты и отображение в коды у вызывающих — таблица REQ-KR-005 снова у каждого вызывающего, а
`revision.ts` проверяет версию своим выражением.

### D-5. Каноническая форма — две операции, хэш канонизирует конверт

`canonical.ts` отдаёт `canonical(value): Result<string>` (публичная, без изменений) и `eachObject(value, fn):
Refusal | null` — обход с вызовом `fn(obj, path)` при входе в каждый объект после его проверок и до членов, отказ
`not-json` — первый, как у `canonical`. Обе — над одним внутренним обходом явным стеком (kernel-format D-2) с
посетителем; флага `emit` и префикса пути в интерфейсе нет. Векторы `canonical` — SCN-KR-006, 007, 019, 024.

`hash(typeId, body)`: сначала `checkAt("typeId", typeId, "/typeId")`; затем `canonical` конверта — `{body, type:
typeId}` при допустимом `typeId`, `{body}` при недопустимом (строка `typeId` из грамматики не бывает не JSON, поэтому
отказ обхода всегда внутри `/body`, а путь `/body/…` даёт сам конверт). Порядок отказов — `bad-type-id`, затем
`not-json` (SCN-KR-009, SCN-KR-021); байты — `{"body":…,"type":…}` в порядке JCS, как собирались руками (SCN-KR-008);
лишний уровень конверта обход без рекурсии не чувствует (SCN-KR-024). `refsOf` — `eachObject` с `refObject`
(SCN-KR-013, SCN-KR-022).

Отвергнуто: оставить сборку конверта строкой в `hash.ts` — правило JCS о порядке ключей вне `canonical.ts`.

### D-6. Допуск строки — `admit` в `unicode16.ts`

`unicode16.ts` отдаёт `admit(s)` → `{ ok: true, nfc }` или `{ ok: false, code }` с `code` `lone-surrogate` либо
`unassigned` — первый по этому порядку, NFC — только допущенной строке (REQ-KR-002); `hasLoneSurrogate` переезжает сюда
из `canonical.ts` (`canonical` отклоняет только одиночные суррогаты и не нормализует — REQ-KR-003, поэтому берёт
предикат, а не `admit`); `isAssigned16` и `assignedRanges` остаются экспортами для `test/kernel/environment.test.ts`.
`input.ts`: `readString` возвращает декодированную строку, одна ветка `admit` — для ключа и для значения;
`hasUnassigned` удаляется. Векторы — SCN-KR-002, 004, 007, 016…018, 023.

Место — `unicode16.ts`, а не новый файл: правило «строка допустима в Unicode 16.0» живёт рядом со своей таблицей, а
файл уже содержит функцию поиска по ней; сгенерированная часть — только массив диапазонов. Отвергнуто: новый
`src/kernel/text.ts` — ещё один модуль и ребро ради двух функций.

### D-7. Не новая версия ядра

Правка `src/kernel` здесь — не новая версия (ADR-32, ADR-43): точки входа `kernel-v1` нет, а публичный интерфейс и
векторы формата v1 не меняются. Критерий: `src/kernel/index.ts` (девять функций REQ-KR-001, типы), `test/kernel/**`,
`test/fixtures/jcs-vectors.json` — без правки в диффе Change; все тесты `SCN-KR-…` проходят; тест структуры с политикой
проекта (SCN-AR-001, SCN-AR-007) проходит на переделанном ядре. Внутренние экспорты между файлами ядра меняются
(`walk`, `idKind`, `isNamespace`, `isVersion`, `hasLoneSurrogate` из `canonical.ts`) — их вне ядра никто не импортирует.

Страж поведения — векторы `SCN-KR-…` и Non-goals proposal.md; spec этого Change смены отказов, путей, порядка и байтов
ядра не разрешает. Поведение, которое REQ-KR не закрепляет векторами, векторы не ловят: на review impl-PR порядок
отказов `revision` и `refsOf` сверяется с нынешним кодом, а не только с тестами (review 1, F-13).

### D-8. Фикстуры и метки

Метка — `// expect: <правило>[ <правило>…]`: несколько правил на одной строке через пробел (SCN-AR-004 — две на
импорте); прежние метки — одно правило, не правятся. Новые деревья — `test/fixtures/structure/perimeter/`
(`kernel/`, `outside/`, SCN-AR-004, SCN-AR-005) и `test/fixtures/structure/cycles/` (SCN-AR-006); имена файлов — как в
сценариях (`a.ts`, …): под `test/**/*.test.ts` не попадают, каталог `test/fixtures` исключён из `tsconfig.json`.
В прежних деревьях `kernel/` и `broken/` файлы названы `*.fixture.ts`: имя сценария `other.ts` — файл
`other.fixture.ts`, `broken.ts` — `broken.fixture.ts`. Отказы со строкой 0 (`no-kernel`, точка входа вне перечня) тест
проверяет явным значением, как сейчас `no-kernel`.

Политики фикстур — в `structure.test.ts`: `kernel/` — источники и периметр `**`, точка входа `clean.fixture.ts`;
`broken/` — источники и периметр `**`, точка входа `other.fixture.ts`. `broken/` дополняется (SCN-AR-002):
`other.fixture.ts` импортирует `./broken.fixture.ts`, `broken.fixture.ts` на строке 2 импортирует `../outside.ts` без
метки — у файла с `parse-error` нет ни рёбер, ни правил чистоты. `cycles/` покрывает все виды рёбер (SCN-AR-006):
`import`, `import type`, `export … from`, `import x = require(…)`, `import("…")` в позиции типа и импорт самого себя;
`perimeter/kernel/a.ts` выходит за перечень и через `export … from` (SCN-AR-004).

## Risks / Trade-offs

- [Два отказа на одном импорте] → оба правила названы в spec (REQ-AR-003), метка несёт оба; отказ читается как «импорт
  вне перечня» и «вывел достижимое за периметр».
- [Обход в глубину называет не каждый элементарный цикл: циклы с общим ребром могут дать один отказ] → spec обещает
  отказ хотя бы на каждый цикл; после правки следующий прогон назовёт оставшийся.
- [Правка ядра меняет порядок или пути отказов незаметно] → `test/kernel/**` не правится, векторы SCN-KR-… — норма;
  задача 2.4 сверяет дифф, review impl-PR сверяет порядок отказов с кодом (D-7).
- [Свой разборщик глобов уже привычного синтаксиса: нет `?`, `[…]`, `{…}`] → синтаксис задан REQ-AR-001; политика S1
  выражается `**` и путями файлов.
- [После S1 эти файлы ядра заморожены версией] → срок Change — до S1 (proposal.md, Why).

## Migration Plan

`structure.test.ts` вызывает `checkStructure` с политикой проекта и политиками фикстур; `checkKernel` удаляется — других
потребителей нет. Фикстуры `kernel/`, `tests/` не правятся; `broken/` дополняется импортами (D-8), прежние метки
остаются. Откат — revert merge commit impl-PR: данных и журнала нет.
