# 06. Pipeline and capabilities

## Purpose

How behaviour runs: capabilities (code pinned to blocks), linear pipelines, runs and their records, recording of ports, ports and assembly. LATTICE says **what**; code says **how**.

## Capabilities

| ID | Rule |
|---|---|
| PL-C01 | A capability is an entity block: a contract (`input`, `output`, `params` schemas) and `impl: {module, hash}`. The code module is pinned by hash; on mismatch the runtime refuses to run it. The hash covers the module and every file of `src/` it imports transitively, with line endings normalised to LF. |
| PL-C02 | A hash manifest is generated by a script; a test checks it against the code. |
| PL-C03 | Two sources: built-in (LATTICE package) and project (module in the project repository). The same rule applies to both. A project capability lives in the project namespace; a new revision of its block is an owner act (CT-A02). |
| PL-C04 | Capabilities are deterministic. Time, ids, judge, LLM and sources come only through ports, and every port is recorded (PL-K01). A structure test forbids `Date.now`, `Math.random`, `process.env` and the like outside adapters (ST-S03). |
| PL-C05 | A capability declares its effects from a closed list: `reads-source`, `calls-llm`, `writes-proposal`, `irreversible`. The runtime gives it only the declared ports. The `judge` port is not an effect: only `decide` gets it (DP-B13). |
| PL-C06 | The `irreversible` effect always requires human confirmation (DP-B12), enforced by the runtime, not by configuration. |
| PL-C07 | Every capability returns a stage outcome: a status and the context fields it wrote. Its contract declares a closed set of statuses; for a capability other than `decide` the default set is `ok`, `unavailable`. The outcome of `decide` is the DecisionResult (DP-R06). A thrown error or a broken contract (PL-P03) is not a status: the run ends with outcome `error` (PL-R01). |
| PL-C08 | Stages are coarse: one stage per step a human would name. Fine-grained stages proved expensive in v0.6, because every test had to build a large context by hand. |
| PL-C09 | A `judge` capability block pins the exact model id of the service behind it (a vendor model, or the version of Jev) as data of its revision; its prompt is code covered by the module hash (PL-C01). So `judge@n` fixes the model and the prompt, and changing either is a new revision (DP-L04). An alias such as `latest` is refused at start-up (PL-A03). The `service` adapter compares the model named in the vendor's answer with the pinned one; a mismatch is `unavailable` (DP-R05). |

## Pipelines

```json
{ "type": "std/pipeline", "id": "solve",
  "stages": [
    { "capability": "lens.candidates@2", "params": { "pool_max": 200 },
      "reads": ["need"], "writes": ["pool"] },
    { "capability": "decide@1", "params": { "point": "lens-rank@3" },
      "reads": ["need", "pool"], "writes": ["selection"],
      "on": { "insufficient": { "fallback": "lens.widen@1" }, "unavailable": "refuse" } },
    { "capability": "compose@1", "reads": ["need", "selection"], "writes": ["answer"] } ] }
```

| ID | Rule |
|---|---|
| PL-P01 | A pipeline is an entity: an ordered list of stages. Each stage is a capability `ref@n` with static `params`. |
| PL-P02 | Params are static, written in the pipeline block, validated against the capability's `params` schema when the pipeline is validated — before any run. Anything that varies per run is a context field, not a param. |
| PL-P03 | Data flows through a run context with named fields. A stage declares `reads` and `writes`. Validation checks that every field read was written by an earlier stage and that no field has two writers. There is no implicit data passing. At run time the fields a stage actually changed must be a subset of its `writes`; otherwise the stage fails (PL-C07). |
| PL-P04 | Branching is limited to `on: {status: action}` on a stage. Every status in `on` must be one the stage's capability declares (PL-C07); validation checks it. Actions: `continue`; `fallback: <capability>` — one alternative stage run in place, then continue; the fallback capability must write the same fields as the stage it replaces, checked by validation; `escalate` — stop and wait for a human; `refuse` — stop with a refusal. |
| PL-P05 | No backward jumps, loops or gotos. A fallback stage has no `on` of its own, so recursion is impossible. |
| PL-P06 | Any pipeline revision may run in `shadow` or on the bench. It drives execution only as the revision named by a `live` status fact (TR-F05), written by the owner (TR-F06) and admitted by apply only with a report that meets the pipeline's targets (DP-L06, BN-G02). |

## Runs

| ID | Rule |
|---|---|
| PL-R01 | A run is a `runtime` commit (LG-R05): `pipeline@n`, input fingerprint, execution tuple (code hashes of capabilities, `judge@n`, models), the knowledge commit it read (PL-K05), the tape of its ports (PL-K01), the outcome of every stage (PL-C07), and the run outcome — the outcome of the last stage, the dispatch action that stopped the run (`escalated`, `refused`), or `error`. A failed run is recorded too: its tape up to the failure and no partial output, so paid judge answers stay available for memoization. If a `fallback` ran, the run outcome says so, and so does the output of `solve` (LN-O01): degradation is never shown as normal. The environment (`node`, `icu`) is recorded outside the execution tuple. |
| PL-R02 | Replay is a run on the `recorded` adapters (PL-K02): the same execution tuple and the same tape give the same outcome. DP-T01 is the case of one decision. A missing recorded answer is an error, never a fall-through to the service. Replay writes nothing and reports the first stage whose outcome differs. A run whose capability code no longer exists replays as `code-changed`, not as an error. |
| PL-R03 | There are no suspended runs. `escalate` ends the run with status `escalated` and a question event. The human's answer is a participant event. Continuing is a new run with the answer as input and a reference to the previous run; if its execution tuple differs from the escalated run, the question is asked again. The runtime keeps no waiting state. |
| PL-R04 | The `llm` port is recorded like every port (PL-K01) and memoized like the judge (PL-K03); retries stay inside the capability (DP-T04). LLM output is generation with basis `inferred`; it never becomes knowledge (TR-I02) and is checked by schema in the pipeline. Block text in an LLM prompt is data, not instructions: code wraps it in delimiters carrying `ref@n`; the model never produces them. Block references in LLM output must be a subset of the references in its input field — a closed world checked by code, the mirror of DP-M06. |

## Recording

| ID | Rule |
|---|---|
| PL-K01 | Every port — `judge`, `llm`, `source`, `clock`, `ids` — goes through one recording module. Each run has a tape: the ordered answers of its ports. The tape is part of the run record (PL-R01). Every answer carries its cost and time (`usd`, `ms`, `tokens` where known) — the source of cost metrics (BN-M02). `clock` answers integer UTC milliseconds. |
| PL-K02 | Every port has three adapters: `service` (the real service), `recorded` (answers from a tape), `fixture` (answers written by hand, kept in git). Which adapter serves a port is chosen only in `setup` (PL-A01). Evidence (LG-R02) is a cut of a tape. One set of contract tests per port runs against all three adapters (ST-T01). |
| PL-K03 | Memoization (DP-T03) is a lookup in earlier tapes, enabled only for ports that declare it: `judge` and `llm`. `clock`, `ids` and `source` are recorded for replay but never memoized. The `llm` memo key is `(model@version, prompt_hash, schema_hash, input_hash, params)`; the `judge` key is DP-T03. |
| PL-K04 | Two independent axes: where an answer comes from is the adapter (PL-K02); whether a result drives execution is the `live` fact (DP-L01, PL-P06). Neither implies the other. |
| PL-K05 | Stages read `knowledge` through a read-only view pinned to the knowledge commit at run start. It is not a recorded port: the commit reference in the run record (PL-R01) makes the reads reproducible. |

## Ports and assembly

| ID | Rule |
|---|---|
| PL-A01 | **`setup`** is a block in `knowledge`: which adapter serves each port, pinned by revision, including the answer source (PL-K02). It is behaviour: versioned, and changing it is an owner act. Which `setup` is active is decided by its `live` fact (TR-F05), never by a naming convention. `setup` chooses only where answers come from; the model is part of `judge@n` (PL-C09). |
| PL-A02 | **`bindings`** is local configuration: service endpoints and keys via `{"$env": "…"}`. Secrets never enter the ledger (LG-A06). The rule for what goes where: anything that changes a result or a cost for the same ledger belongs in the ledger; `bindings` holds only what never does. |
| PL-A03 | Start-up checks run in named phases, stopping at the first refusal: (1) configuration schema, with a secret literal refused (LG-A06); (2) open store and verify the hash chain (LG-C04, LG-G01); (3) `setup` — hashes of capabilities and adapters match their blocks (PL-C01), model ids are exact (PL-C09); (4) `bindings` — every port has an endpoint and key. A refusal names the phase and the field path. |
| PL-A04 | An adapter error is `{adapter, code, status?, retryable}`, never the body or headers of the vendor's answer, so no secret or payload leaks into a tape. |

## Entry point

| ID | Rule |
|---|---|
| PL-E01 | Every external operation that reads or decides is a pipeline run: `solve` (blocks for a need), import, bench. In S0 import is a service command (LG-B07). |
| PL-E02 | The CLI is thin: `lattice run <pipeline> --input <file>` plus service commands (`init`, `apply`, `verify`, `export`, `upgrade`). The service commands are the write path (apply, LG-A01), the codec (LG-B05) and the `std` update (LG-G02); there is no other logic outside pipelines, so everything else is recorded and replayed the same way. Every slice leaves a CLI command for the owner's manual acceptance (SL-T06). |
