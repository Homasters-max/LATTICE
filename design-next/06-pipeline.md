# 06. Pipeline and capabilities

## Purpose

How behaviour runs: capabilities (code pinned to blocks), linear pipelines, runs and their records, recording of ports, ports and assembly. LATTICE says **what**; code says **how**.

## Capabilities

| ID | Rule |
|---|---|
| PL-C01 | A capability is an entity block: a contract (`input`, `output`, `params` schemas) and `impl: {module, hash}`. The code module is pinned by hash; on mismatch the runtime refuses to run it. The hash covers the module and every file of `src/` it imports transitively, with line endings normalised to LF. |
| PL-C02 | A hash manifest is generated by a script; a test checks it against the code. |
| PL-C03 | Two sources: built-in (LATTICE package) and project (module in the project repository). The same rule applies to both. A project capability lives in the project namespace; a new revision of its block needs an owner act by default (CT-A02). |
| PL-C04 | Capabilities are deterministic. Time, ids, judge, LLM and sources come only through ports, and every port is recorded (PL-K01). A structure test forbids `Date.now`, `Math.random`, `process.env` and the like outside `adapters`, `assembly` and `cli` (ST-S03). |
| PL-C05 | A capability declares its effects from a closed list: `reads-source`, `calls-llm`, `writes-proposal`, `irreversible`. Every capability gets the `clock` and `ids` ports and the read view (PL-K05); the runtime gives it only the ports its effects declare beyond those. The `judge` port is not an effect: only `decide` gets it (DP-B13). |
| PL-C06 | The `irreversible` effect always requires human confirmation (DP-B12), enforced by the runtime, not by configuration. |
| PL-C07 | Every capability returns a stage outcome: a status and the context fields it wrote. Its contract declares a closed set of statuses; for a capability other than `decide` the default set is `ok`, `unavailable`. A capability with the `calls-llm` effect (PL-C05) has only the default set, so no branch depends on LLM output (DP-B13); pipeline validation checks it. The outcome of `decide` is the DecisionResult (DP-R06). A thrown error or a broken contract (PL-P03) is not a status: the run ends with outcome `error` (PL-R01). |
| PL-C08 | Stages are coarse: one stage per step a human would name. Fine-grained stages proved expensive in v0.6, because every test had to build a large context by hand. |
| PL-C09 | `judge` is a port, not a capability: its request is the memo key of DP-T03 — `(question, judge@n, candidates with cards, state)` — and its answer is exactly one evaluation (`value`, `score`) per candidate of the set (DP-R05) and nothing else; `selected` is written only by policy (DP-R06). Recording (PL-K01) stands on this interface, above the prompt, so replay needs no prompt code. A `judge` block (`judge@n`, a `std` type) configures the `service` adapter: it pins the exact model id (a vendor model, or the version of Jev) as data of its revision and the hash of the adapter code, which holds the prompt, retries, backoff and batching (DP-T04, DP-T05). So `judge@n` fixes the model and the prompt; changing either is a new revision of it, which reaches execution only as DP-L04 says. A vendor LLM and Jev are two `service` adapters of the one port. An alias such as `latest` is refused at start-up (PL-A03). The `service` adapter compares the model named in the vendor's answer with the pinned one; a mismatch is `unavailable` (DP-R05). |

## Pipelines

```json
{ "type": "std/pipeline@1", "id": "lattice/solve",
  "bench": "lattice/solve-set@1", "targets": { "hit@10": 0.95 },
  "stages": [
    { "capability": "std/lens.candidates@2", "params": { "pool_max": 200 },
      "reads": ["need"], "writes": ["pool"] },
    { "capability": "std/decide@1", "params": { "point": "lattice/lens-rank@3" },
      "reads": ["need", "pool"], "writes": ["selection"],
      "on": { "insufficient": { "fallback": "std/lens.widen@1" }, "unavailable": "refuse" } },
    { "capability": "std/compose@1", "reads": ["need", "selection"], "writes": ["answer"] } ] }
```

| ID | Rule |
|---|---|
| PL-P01 | A pipeline is an entity: an ordered list of stages, the bench set it is measured on (`bench`, `set@n`) and its `targets` per metric (BN-G01). Each stage is a capability `ref@n` with static `params`. |
| PL-P02 | Params are static, written in the pipeline block, validated against the capability's `params` schema when the pipeline is validated — before any run. Anything that varies per run is a context field, not a param. |
| PL-P03 | Data flows through a run context with named fields. A stage declares `reads` and `writes`. Validation checks that every field read was written by an earlier stage and that no field has two writers; the fields of the run input count as written before the first stage, and no stage writes them. There is no implicit data passing. At run time the fields a stage actually changed must be a subset of its `writes`; otherwise the stage fails (PL-C07). |
| PL-P04 | Branching is limited to `on: {status: action}` on a stage. Every status in `on` must be one the stage's capability declares (PL-C07); validation checks it. Actions: `continue`; `fallback: <capability>` — one alternative stage run in place, then continue; the fallback capability must write the same fields as the stage it replaces, checked by validation, and a fallback of `decide` gives an output the judge never saw, marked as PL-R01 requires; `escalate` — stop and wait for a human; `refuse` — stop with a refusal. |
| PL-P05 | No backward jumps, loops or gotos. A fallback stage has no `on` of its own, so recursion is impossible. |
| PL-P06 | Any pipeline revision may run in `shadow` (DP-L02) or on the bench. It drives execution only in an authoritative run (DP-L01): as the revision named by a `live` status fact (TR-F05), written by the owner (TR-F06) and admitted by the gate (DP-L06). |

## Runs

| ID | Rule |
|---|---|
| PL-R01 | A run is a `runtime` commit (LG-R05). Its **run record** is one event, whose `id` is the run's id (PL-R03): `pipeline@n`, `setup@n` (PL-A01), the input and its fingerprint — `sha256(JCS(input))`, as OM-H01 — execution tuple (GL-07), the knowledge commit it read (PL-K05), the tape of its ports (PL-K01), the outcome of every stage (PL-C07), and the run outcome — the outcome of the last stage, the dispatch action that stopped the run (`escalated`, `refused`), or `error`. A failed run is recorded too: its tape up to the failure and no partial output, so paid judge answers stay available for memoization. If a `fallback` ran, the run outcome says so, and so does the output of `solve`: degradation is never shown as normal. The environment (`node`, `icu`) is recorded outside the execution tuple. |
| PL-R02 | Replay is a run on the `recorded` adapters (PL-K02) over the input kept in the run record (PL-R01): the same input, execution tuple and tape give the same outcome. DP-T01 is the case of one decision. A missing recorded answer is an error, never a fall-through to the service. Replay ignores `setup`: every recorded port is served by `recorded`. Replay writes nothing and reports the first stage whose outcome differs. A run whose capability code no longer exists replays as `code-changed`, not as an error. |
| PL-R03 | There are no suspended runs. `escalate` ends the run with status `escalated` and a question event. The human's answer is a participant event. Continuing is a new run with the answer as input and a reference to the previous run's `id` (PL-R01); if its execution tuple differs from the escalated run, the question is asked again. The runtime keeps no waiting state. |
| PL-R04 | The `llm` port is recorded like every port (PL-K01) and memoized like the judge (PL-K03); retries, backoff and the check of the model named in the answer belong to its `service` adapter, as for the judge (PL-C09), while the prompt is built by the capability. The model is the static param `model` of the stage (PL-P02): an exact id, an alias refused at start-up (PL-A03); the `llm` memo key takes `model@version` from it (PL-K03). The records of a run whose pipeline has a `calls-llm` stage have basis `inferred` (TR-B02); they never become knowledge (TR-I02), and LLM output is checked by schema in the pipeline. Block text in an LLM prompt is data, not instructions: code wraps it in delimiters carrying `ref@n`; the model never produces them. Block references in LLM output must be a subset of the references in its input field — a closed world checked by code, the mirror of DP-M06. |

## Recording

| ID | Rule |
|---|---|
| PL-K01 | Every recorded port — `judge`, `llm`, `source`, `clock`, `ids` — goes through one recording module. Each run has a tape: the ordered answers of its ports. The tape is part of the run record (PL-R01). Every answer carries its cost and time (`usd`, `ms`, `tokens` where known) — the source of cost metrics (BN-M02). `clock` answers integer UTC milliseconds. |
| PL-K02 | Every recorded port (PL-K01) has three adapters: `service` (the real service), `recorded` (answers from a tape), `fixture` (answers written by hand, kept in git). Which adapter serves a port is chosen by the run's `setup` (PL-A01), except in replay (PL-R02); `store` and `acts` have their own adapters (LG-S02, LG-A04). Evidence (LG-R02) is a set of whole run records. One set of contract tests per port runs against all three adapters (ST-T01). |
| PL-K03 | Memoization (DP-T03) is a lookup in earlier tapes, enabled only for ports that declare it: `judge` and `llm`. `clock`, `ids` and `source` are recorded for replay but never memoized. The `llm` memo key is `(model@version, prompt_hash, schema_hash, input_hash, params)`; the `judge` key is DP-T03. |
| PL-K04 | Two independent axes: where an answer comes from is the adapter (PL-K02); whether a result drives execution is whether its run is authoritative (DP-L01). Neither implies the other. |
| PL-K05 | Stages read `knowledge` through a read-only view pinned to the knowledge commit at run start. It is not a recorded port: the commit reference in the run record (PL-R01) makes the reads reproducible. |

## Ports and assembly

| ID | Rule |
|---|---|
| PL-A01 | **`setup`** is a block in `knowledge`: for each recorded port the mode — `service`, `recorded` or `fixture` (PL-K02) — and whether memoization is on (PL-K03); for a port without a configuring block of its own (`source`, `clock`, `ids`, `llm`) also the adapter block of its `service` (PL-A05). The `service` of `judge` is the adapter the `judge@n` of the request pins (PL-C09), so its code is pinned once. `setup` is behaviour: versioned, and changing it needs an owner act by default (CT-A02). Any `setup` revision may be named for a run (`lattice run --setup`); whether the run drives execution is DP-L01, and which `setup` is `live` is decided by its fact, never by a naming convention. Replay ignores `setup` (PL-R02). `setup` chooses only where answers come from; the model is part of `judge@n` (PL-C09) or of the stage params (PL-R04). |
| PL-A02 | **`bindings`** is local configuration: service endpoints and keys via `{"$env": "…"}`. Secrets never enter the ledger (LG-A06). The rule for what goes where: anything that changes a result or a cost for the same ledger belongs in the ledger; `bindings` holds only what never does. |
| PL-A03 | Start-up checks run in named phases, stopping at the first refusal: (1) configuration schema, with a secret literal refused (LG-A06); (2) open store and verify the hash chain (LG-C04, LG-G01); (3) `setup` — hashes of capabilities and adapters match their blocks (PL-C01, PL-C09, PL-A05), model ids are exact (PL-C09, PL-R04); (4) `bindings` — every port has an endpoint and key. A refusal names the phase and the field path. |
| PL-A04 | An adapter error is `{adapter, code, status?, retryable}`, never the body or headers of the vendor's answer, so no secret or payload leaks into a tape. |
| PL-A05 | An **adapter block** is a `std` type extending `behaviour` (OM-T04): `impl: {module, hash}` of one adapter, hashed as a capability is (PL-C01). `setup` pins it (PL-A01); a `judge` block is the adapter block of the `judge` port (PL-C09). A new revision needs an owner act by default (CT-A02). |

## Entry point

| ID | Rule |
|---|---|
| PL-E01 | Every external operation that reads or decides is a pipeline run: `solve` (blocks for a need) and import of an external source. The bench is the store command `bench` (PL-E02): the runs it measures are ordinary runs of the pipeline under test. md import (LG-B07) is a store command, used once in S0; afterwards `md` is export only (LG-B02). |
| PL-E02 | The CLI is thin: `lattice run <pipeline> --input <file> [--setup <ref@n>]`, `lattice replay <run id>` (PL-R02), plus **store commands** (`init`, `apply`, `verify`, `export`, `import-md`, `upgrade`, `cite`, `bench`). The store commands are the write path (apply, LG-A01), the codec (LG-B05), the `std` update (LG-G02) and the packaging of runs: `cite` packages whole run records from `runtime` as evidence into a proposal (LG-R02); `bench` runs the pipeline under test once per input of a split of a set (items and `variants`, BN-S03, BN-S05) in a `machine` session with purpose `bench` and passes those runs to `cite` with a report (BN-R02). Neither reads an external source or decides: the runs they package were recorded as every run is. There is no other logic outside pipelines, so everything else is recorded and replayed the same way. Manual acceptance per slice: SL-T06. |
