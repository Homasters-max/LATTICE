### E-01 · Смена версии ядра на существующем хранилище не спроектирована

- **Вопросы:** Q56, Q70, Q01 · **Уровень:** EVOLUTION · **Класс:** F
- **Ответ дизайна:** KR-16 — `domains/10-kernel.md:214-216` — «хэш генезиса — константа версии ядра, сверяется при
  открытии хранилища»; SL-04 — `05-slices.md:66` — смена генезиса «до первой записи реальных данных … новая
  константа и пересчёт фикстур»; `10-kernel.md:86-87` — версия ядра объявляет, какой формат читает. Путь «хранилище
  с данными → ядро v2» не описан; искал: «версия ядра», «новой версии ядра», «смена генезиса», «хэш генезиса»,
  «обновление ядра», «миграц» по всему `design/`.
- **Наблюдение:** дизайн делает версию ядра единственным путём эволюции для всего замороженного (примитивы, проверки
  ядра, типы генезиса — `04-architecture.md:10`), сам ожидает такие смены (KR-11 `10-kernel.md:270` — «сигнал
  пересмотра ядра»; ADR-29 `:23` — гейт «версия ядра»; ADR-33 `:104` — второе пространство упирается в `owner`), но у
  ядра нет аналога коммита обновления `std` (CT-10): кто и каким коммитом пишет `core/<тип>@2` в хранилище, где генезис
  v1 уже записан сессией `core/genesis`, и что делает `open()` при несовпадении хэша генезиса.
- **Контрсценарий:** первый запуск прошёл, журнал WARRANT содержит реальные данные (граница SL-04 пройдена) → замер
  R8 требует поле в `core/trust-policy.calibration` (или второе пространство, или новый примитив по RL-14) → выходит
  ядро v2 с другим генезисом → `open()` сверяет хэш генезиса журнала с константой v2: либо отказ (хранилище проекта
  больше не открывается новым кодом), либо принимает — и тогда `core/trust-policy@2` в журнале нет, а записать его
  нечем: генезис пишет код ядра при `init`, у `owner` исключения только для `core/session` и первого пространства
  (`13-rules.md:61`), владельца пространства `core` в хранилище проекта нет.
- **Инварианта:** P9 / VI-04 («валидатор меняется только версией ядра» — `00-vision.md:107`) — механизм, на который
  ссылается принцип, не определён для хранилища с данными; неявная: «данные v1 открываются следующей версией ядра».
- **Последствие:** каждая отсрочка, которая по факту требует версии ядра (новый примитив, поле типа генезиса, второе
  пространство — E-02, карта отсрочек), на деле блокирует проект с данными или требует пересоздания хранилища
  (потеря истории, доверия, обучения).
- **Тяжесть:** S2 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 7 (ADR, затронуты 10, 12, 13, 15, 30): «обновление ядра» по образцу CT-10 —
  генезис v2 как дельта (новые ревизии `core/*` под сессией `core/genesis-<версия>`, пропускаемой `owner` по списку
  хэшей генезиса, которые версия ядра признаёт), `open()` принимает журнал с генезисом из этого списка; `revalidate`
  — уже есть (RL-12).
- **Когда обязательно:** до первого запуска (граница SL-04: после неё генезис не пересчитать).

### E-02 · Замороженное ядро несёт семантику bench, run, lens и compose

- **Вопросы:** Q01, Q03, Q56 · **Уровень:** OWNERSHIP / EVOLUTION · **Класс:** A (и B — два ответа на «что знает ядро»)
- **Ответ дизайна:** RL-08 — `domains/13-rules.md:167` — гейт в ядре, «ядро не знает смысла фактов обучения»;
  `10-kernel.md:220-222` — «что такое потребность или решение — знают данные `std`; исключение — примитив
  `learning-gate`: он читает вердикт, `std/bench-run` и план стенда»; ADR-28 `:22-26` отверг поля `pipeline`/`ports` в
  `core/namespace`, потому что тип генезиса с закрытой схемой делает «новый порт — новая версия ядра».
- **Наблюдение:** в периметре замороженного ядра — не одно исключение, а три группы чужой семантики: (1) примитив
  `learning-gate` (`13-rules.md:85`) читает `std/verdict.execution`, значения `purpose` (`bench`, `simulate`),
  кортеж из раздела `executions`, `std/bench-run.verdict/tuple`, `std/bench-plan.kind/base` и «регрессионный план
  владельца — последний по `seq`» (`23-bench.md:29-30`, `:146-147`); (2) тип генезиса `core/trust-policy`
  (`10-kernel.md:210`, схема `core` закрыта и `hard` — `:152`) содержит параметры lens (`lens`), compose
  (`candidates`) и run (`calibration`, `removal_window`) — `14-trust.md:104-118`; (3) типы генезиса `core/snapshot`,
  `core/member` — модель решения compose (владелец — 21, `04-architecture.md:129`, `:135`). Довод ADR-28 против (2) и
  (3) применён не был. Списка «поля `std`, которые читает ядро» нет — `std` меняется пакетом (CT-10), ядро — версией.
- **Контрсценарий:** (а) 22 «Вне объёма» `used[].evidence` (`22-run.md:457-458`: «политика сможет весить такие
  вердикты выше») или пересмотр ADR-20 по замеру R8 → новый ключ в `core/trust-policy.calibration` → новая ревизия
  типа генезиса → новая версия ядра → E-01. (б) Сопровождающий выпускает `std` с `std/bench-plan@2` (`kind: canary` —
  отложенная раскатка ADR-22 `:47-48`); совместимость схемы (`10-kernel.md:152`) это допускает → `lattice update`
  проходит → гейт ядра v1 такого плана не знает → вердикты по новой настройке молча ждут `pass` вечно
  (`22-run.md:325-327`), в отчёте только «ждёт».
- **Инварианта:** P10/T21 и RL-08 («ядро не знает смысла фактов обучения»); ADR-28 (довод против полей верхних
  доменов в типах генезиса); KR-11 («малое замороженное ядро, остальное — данные»).
- **Последствие:** эволюция стенда, политики обучения и модели решения — то, что первый запуск прямо обещает
  пересмотреть (`01-first-run.md:127`), — идёт через версию ядра; два канала релиза (`std`-пакет и ядро) связаны
  неявно; другой runtime не может учить систему, не повторив формат `bench-run`/`execution` LATTICE.
- **Тяжесть:** S2 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 1–2: (а) в `04-architecture.md` §1 перечислить «поля `std`, которые читает
  замороженное ядро» (`std/verdict.execution`, `std/bench-run.{plan,tuple,verdict}`, `std/bench-plan.{kind,base}`,
  значения `purpose`) и объявить их форму частью версии ядра; исправить «Почему» RL-08; (б) перенести `lens`,
  `candidates`, `calibration` из `core/trust-policy` в `std`-тип политики (как ADR-28 для `setup`) — ступень 7, до
  фиксации генезиса (SL-04).
- **Когда обязательно:** до первого запуска (SL-04 — последний дешёвый момент менять генезис).

### E-03 · «Универсальный» конвейер знает только потребности; это не записано как отсрочка

- **Вопросы:** Q02, Q59, Q56 · **Уровень:** EXECUTION / EVOLUTION · **Класс:** A (и F — неявная отсрочка)
- **Ответ дизайна:** P12 «один контракт стадии» (`00-vision.md:76`); AR-02 — `04-architecture.md:253` — новая
  версия конвейера без релиза, «пока стадии — существующие `builtin`»; 22 «Вне объёма» — только граф, параллельность,
  запись частями (`22-run.md:452-461`); ADR-18 — граф стадий «новой версией интерпретатора».
- **Наблюдение:** у стадии один тип входа и выхода — `std/ctx@1` (`13-rules.md:101`), а `std/ctx` — это модель
  compose: `needs[]` с `candidates`, `recall`, `selection`, `solution` (`22-run.md:86-105`). Интерпретатор жёстко
  строит `ctx = {request, run, needs: []}` и собирает коммит только из `needs[].rows` (`22-run.md:152`, `:160`);
  контракт будущего `exec` — «проекция `ctx` по `reads`» (`22-run.md:240-241`); вердикт и обучение определены только
  для пары `(execution, solution)` и членов решения (`22-run.md:271-298`, §6); порт `source` задаёт места только
  `doc | code | test` (`21-compose.md:217`). То есть «конвейер как данные» — это перестановка и параметры стадий
  одного сценария «задача → потребности → решения», а цикл обучения существует только для него. В отсрочках
  (22, 21, 20 «Вне объёма») форма `ctx` и единица работы не названы — граф назван, а он на это не отвечает.
- **Контрсценарий:** второй проект — анализ безопасности (Q59 п. 4): единица работы — актив/находка, выход —
  много фактов о разных объектах, вердикт — «находка подтверждена/ложная». По правилам дизайна: стадии проекта — только
  `builtin` (RN-10, `exec` отложен) → релиз пакета LATTICE; строки вне `needs[].rows` рантайм не коммитит → находки
  приходится выдавать за «потребности»; вердикт на находку в `std/verdict@1` не выражается (`solution`, `used/unused`
  — члены решения) → обучение не работает; «пакет» `deliver` — нормы по потребностям. Итог: нужны `std/ctx@2`, новый
  интерпретатор и новые типы вердикта/обучения — ровно то, что Q59 называет «универсальность не доказана».
- **Инварианта:** видение — «универсальная независимая система» (`README.md:3`), P12; неявная: «новый класс задач —
  данные `std`/проекта + адаптер, без правки интерпретатора».
- **Последствие:** второй проект другого класса — не конфигурация, а новая версия run (и, через E-02, возможно ядра);
  данные v1 не портятся, но заявленная универсальность держится только на тексте.
- **Тяжесть:** S2 · **Уверенность:** высокая (факты), средняя (тяжесть)
- **Минимальное разрешение:** ступень 1 + 5: в `00-vision.md` сузить заявление v1 — «универсальна по корпусам блоков,
  выдаваемых по потребности»; в 22 «Вне объёма» — отсрочка «конвейер с единицей работы ≠ потребность
  (`std/ctx@2`, вердикт по объекту работы)» с триггером «второй конвейер, чья единица — не потребность». Дёшево уже
  сейчас: коммит вызова собирает и верхнеуровневые `ctx.rows`, а не только `needs[].rows`.
- **Когда обязательно:** до второго проекта (формулировка видения — до первого запуска, E-07).

### E-04 · Жизнь источника после загрузки: исчезновение и перенумерация блоков не определены

- **Вопросы:** Q58, Q70, Q57 · **Уровень:** EVOLUTION / PROVENANCE · **Класс:** F (и A — схема `id` адаптера задаёт identity)
- **Ответ дизайна:** T129 — `02-glossary.md:175` — `source.load()` — «первичная загрузка и обновление»; контракт —
  `load(): AsyncIterable<RevisionInput>` (`21-compose.md:211`), только ревизии; `30-adapters.md:182` — повторный
  `load` пишет изменённое и снимает исчезнувшие *расхождения*; `10-kernel.md:96` — внешнее имя «стабильное»; id норм —
  `REQ-…`, `SCN-…`, `ADR-…#п` (`30-adapters.md:168`). Искал: «исчез», «удалён из источника», «нет в источнике»,
  «повторный load», `retire` + `load` — ответа про исчезнувший блок нет.
- **Наблюдение:** истина норм — репозиторий WARRANT, LATTICE держит их копии-ревизии. Контракт загрузки не умеет
  сказать «блока больше нет», а схема `id` с номером пункта (`ADR-…#п`) не стабильна при правке документа: вставка
  пункта даёт тому же `id` другое содержание. Статус snapshot'а меняется только от версий членов (T86,
  `02-glossary.md:153`) — исчезновение в источнике его не трогает.
- **Контрсценарий:** после первого запуска в WARRANT удалена норма `REQ-VER-003` и вставлен пункт в `ADR-0012` →
  `lattice load`: для `REQ-VER-003` парсер ничего не отдаёт → ни строки, норма жива в `latest`, в пулах и в
  решениях; snapshot её решения `fresh` → `recall` выдаёт её без LENS (`21-compose.md:74`) как проверенный блок с
  прежним доверием; `ADR-0012#3` получает текст бывшего `#2` новой ревизией — ссылки `follow` (решения, эталоны без
  `@n`) молча указывают на другой пункт, сводка вердиктов блока (`14-trust.md:134-135`) продолжается на другом
  содержании. Что делает `deliver` при `source.text` исчезнувшего блока, контракт не говорит.
- **Инварианта:** P6 «закрытый мир» из проверенных блоков; KR-01/T04 «`id` — тот же объект во времени»
  (`11-identity-grain.md:12-17`); P8 (тихих подмен нет).
- **Последствие:** каталог тихо расходится с источником; повтор (`recall`) закрепляет устаревшее; «проверено» в пакете
  относится к тексту, которого в проекте уже нет.
- **Тяжесть:** S2 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 1–2: в контракт `Source` (21 §8) — «загрузка отдаёт полный перечень `id`
  источника»; хост пишет для отсутствующих `std/load-finding {kind: missing}` (механизм ADR-10 уже есть), LENS/lint
  помечают, владелец решает `core/retire`; в 30 §5 — требование к схеме `id` адаптера: устойчивый якорь, не порядковый
  номер пункта.
- **Когда обязательно:** до первого запуска (загрузка R1 фиксирует схему `id` норм WARRANT).

### E-05 · «Член удаляется только окном» держит хост: строка без `from` обходит гейт и окно

- **Вопросы:** Q03, Q69 · **Уровень:** OWNERSHIP · **Класс:** E (граница держится текстом/хостом)
- **Ответ дизайна:** `22-run.md:413-415` (инвариант 5) — «Писатель с допуском, опустивший `from`, пишет собственный
  голос без `derived`: эту границу держит хост, а не коммит (T-16)»; инвариант 7 `:417-418` — «член удаляется только
  окном `removal_window`»; ADR-29 `:6-9` — барьер «держится в коммите, а не в коде `run`»; `21-compose.md:55-56` —
  правила типов проверяет «коммит любого писателя».
- **Наблюдение:** гейт `learning-gate` срабатывает только на строках с `from` (`13-rules.md:85`, параметр `from?`), а
  окно удаления (3 из 5 по группам, ADR-20) — логика кода `learn`, не правило типа. Допуск на `std/member` у агентов
  проекта — штатная настройка (`15-catalog.md:66-68`). Значит, удаление членства (`value: false`) любым держателем
  допуска проходит коммит без гейта, без окна и без групп; сессия `learn` с любым одним вердиктом в `from` тоже
  проходит гейт без окна.
- **Контрсценарий:** агент WARRANT с допуском `{create: ["std/member", …]}` через API пишет
  `std/member {of: {group: S, member: M}, value: false, reason}` без `from` → проверки: `owner` (допуск есть),
  `solution-size` (членов меньше), `learning-gate` (нет `from` — не применяется) → принят; по ADR-6 текущий факт —
  последний среди допущенных → M вне решения; следующий `recall` выдаёт решение без M. Ни окна, ни `bench-run pass`,
  ни второй группы.
- **Инварианта:** 22 инвариант 7; ADR-20; T-16 «инвариант держат тип и коммит»; ADR-29 «для любого писателя».
- **Последствие:** главная защита от одиночного ошибочного удаления (асимметрия ADR-20) — свойство кода `learn`, а не
  журнала; E3 первого запуска проверяет код `learn`, а не инвариант.
- **Тяжесть:** S2 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 3 (существующие примитивы): правило типа `std/member` —
  `schema {required: [from]}` с `when: {path: value, eq: false}` (как у `std/gap`, `21-compose.md:66`) — удаление
  только строкой обучения, значит только за гейтом; окно — признать границей хоста явно в 22 §6 и ADR-20 (или
  параметр гейта «число групп в окне»).
- **Когда обязательно:** до среза S8.

### E-06 · Пустое решение «устаревает при изменении области» — не выразимо ни в `core/snapshot`, ни в ledger

- **Вопросы:** Q03, Q58 · **Уровень:** SEMANTICS / OWNERSHIP · **Класс:** A (и B)
- **Ответ дизайна:** `21-compose.md:163` — «пустое решение допустимо: snapshot закреплён на версии пула области,
  устаревает при любом изменении области»; тело `core/snapshot` — `{of: solution, members: [ref@n], links}`
  (`21-compose.md:25`, T85 `02-glossary.md:152`); статус — `stale`, только если «изменились версии членов» (T86
  `:153`); статус считает раздел `snapshots` журнала (`12-ledger.md:90`); сводка доверия решения — «наименьшее
  основание среди членств» (`14-trust.md:132-133`).
- **Наблюдение:** у пустого snapshot'а нет поля «версия пула/области», а тип — генезис с закрытой схемой
  (`10-kernel.md:152`, `:210`); вычислить «изменилась область» проекция 12 может, только зная `std/need.scope`,
  членство домена и пул — это знание compose/lens ниже по матрице (`04-architecture.md:26`). Доверие пустого решения
  (минимум по пустому множеству) не определено — `recall` решает «доверие ок» по-разному у разных исполнителей.
- **Контрсценарий:** потребность N → `gap absent`, пустое решение S, snapshot `{of: S, members: [], links: []}` →
  владелец по сигналу добавляет блок B в домен → версии членов S не менялись (членов нет) → статус `fresh` → при
  чтении «пусто = доверие ок» `recall` выдаёт «нет в каталоге» без LENS (`21-compose.md:74`) бессрочно; сигнал
  `gap` исправлен, а честный отказ стал ложным.
- **Инварианта:** P6 «честный выход»; CP-07 (C чинит каталог); 21 §5 — обещанное поведение.
- **Последствие:** замыкание «пробел → владелец добавил блок → система его находит» не выполняется для повторов.
- **Тяжесть:** S2 · **Уверенность:** средняя (зависит от прочтения доверия пустого решения)
- **Минимальное разрешение:** ступень 1: пустое решение не хранится как snapshot для `recall` — `recall` отдаёт
  `fresh` только непустым решениям, пустое всегда идёт через LENS (строка в 21 §3); иначе — поле версии пула в
  `core/snapshot` (генезис, до SL-04).
- **Когда обязательно:** до среза S7.

### E-07 · Первый запуск не может опровергнуть заявленную универсальность (E7 и «обе половины»)

- **Вопросы:** Q02, Q59 · **Уровень:** PROVENANCE (доказательство) · **Класс:** — (заявление сильнее проверки)
- **Ответ дизайна:** E7 — `01-first-run.md:31` — «второе пространство (малый справочник) на том же `std`; ноль правок
  ядра и `std`; только адаптер `source` и конфигурация»; R12 `:88`; AD-04 — `30-adapters.md:255` — «E7 — единственная

  конвейера» — `00-vision.md:84-85`, `01-first-run.md:15-16`.
- **Наблюдение:** (1) малый справочник через `source-files` — это файлы → `std/knowledge` (`30-adapters.md:192-195`),

  отклонён `owner` (ADR-33) → исполнитель либо признаёт E7 FAIL, либо правит ядро (запрещено критерием), либо
  тихо делает `init` второго хранилища — и тогда получает PASS, который в отчёте (`01-first-run.md:122`) читается как
  «универсальность доказана», хотя проверено только «второй корпус документов».
- **Инварианта:** P11 (решения — по данным: доказательство должно мочь провалиться); видение `README.md:3`.
- **Последствие:** отчёт первого запуска выдаёт доказательство, которое сильнее измеренного; решения о развитии
  (второй проект другого класса) опираются на E7 PASS.
- **Тяжесть:** S3 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 1: E7 переименовать в «второй корпус (второе хранилище, `init`) без правки
  ядра и `std`»; в R12 — явный `init`; в `00-vision.md:84-85` и `01-first-run.md:15-16` — «способности — как стадии
  конвейера; как члены решений — после `exec`»; ограничение универсальности v1 — ссылкой на E-03.
- **Когда обязательно:** до первого запуска.

### E-08 · Без порта `composer` нет ни одной единицы работы; базовые линии стенда не выражаются настройкой

- **Вопросы:** Q01 · **Уровень:** EXECUTION · **Класс:** A (LLM-стадия задаёт единицу работы)
- **Ответ дизайна:** «Базовая линия — тоже ревизия настройки (конвейер из одной стадии BM25 и т. п.), её кортеж
  закреплён так же» — `23-bench.md:35-36`; базовые линии E1 — (a) «BM25 по документам целиком», (b) «BM25 в домене»,
  (d) «по полному тексту блока» — `01-first-run.md:64-66`; «запасной режим — отдельная ревизия `std/setup`»
  (`30-adapters.md:61-62`).
- **Наблюдение:** потребности (`needs[]`) создаёт только стадия `frame` — это Composer (`21-compose.md:114`); запрос
  несёт лишь `task`, `scope` (`22-run.md:88`), интерпретатор стартует с `needs: []` (`22-run.md:152`). `contract`
  требует, чтобы каждое чтение было записано раньше (`13-rules.md:119-121`): `bm25` читает `needs[].norm`,
  `needs[].pool` — без `frame`, `normalize`, `pool` конвейер из одной стадии не публикуется. Стадии «BM25 по
  документу целиком» (не по карточкам пула) в перечне нет (`20-lens.md:76-88`). `Deps.judge` обязателен
  (`22-run.md:131`), хотя конвейер без judge заявлен как законная настройка.
- **Контрсценарий:** R3 требует записать базовые линии как `baselines: [{name, setup: ref@n}]` плана
  (`23-bench.md:20`) → владелец пишет `setup` «BM25 по документам» → публикация конвейера отклонена `contract`, либо
  он включает `frame` (LLM Composer — цена и недетерминизм в «бесплатной» базовой линии E1), либо линия считается вне
  системы — и тогда «кортеж базовой линии закреплён» (BN-01) неправда. Два исполнителя сделают по-разному, и E1
  сравнивает LENS с разными «BM25».
- **Инварианта:** BN-01 (базовая линия — ревизия настройки с кортежем); ответ на Q01 «что остаётся без LLM» — ничего:
  без Composer нет потребности, без потребности — вызова.
- **Последствие:** «Composer — порт, заменяемая технология» (VI-02) верно только между LLM; детерминированного входа
  в систему нет, и базовые линии первого запуска не определены.
- **Тяжесть:** S3 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 1: в 21 §4 — детерминированная стадия `frame.single` («задача = одна потребность
  в заданной области», `determinism: deterministic`) и в 20 §4 — стадия `bm25.doc`; порты в `Deps` — только те, что
  есть в `setup.ports`.
- **Когда обязательно:** до среза S9 (регрессионный план) и R3.

### E-09 · «Runtime не создаёт и не правит блоки» держится честностью кода стадии

- **Вопросы:** Q03 · **Уровень:** OWNERSHIP · **Класс:** — (граница только текстом)
- **Ответ дизайна:** роли — «Runtime … не создаёт и не правит блоки» (`00-vision.md:56`); «не создавай блоков — нет
  операции записи блока у Composer; `check` п. 1» (`21-compose.md:155`); RN-09 — «коммит собирается без знания
  типов; граница контракта держится кодом» (`22-run.md:433`); рантайм сверяет изменённые пути с `writes`
  (`22-run.md:155`).
- **Наблюдение:** `writes` ограничивает пути `ctx`, но не типы строк в `rows`: стадия с `rows` в `writes` может
  положить в коммит вызова ревизию любого типа (`22-run.md:117-121`), коммит пишет сессия вызывающего. Когда
  вызывающий — агент с допуском только на `std/need…` (`15-catalog.md:66-68`), чужой тип остановит `owner`. Когда
  вызывающий — владелец (вызов R10b в основном журнале, приёмка срезов «показ CLI владельцу», `05-slices.md:52`) —
  `owner` пропускает всё, и граница «рантайм не правит блоки» не держится ничем. С `exec` (код проектов, «дополнение по
  `writes`», `22-run.md:240-241`) тот же путь открыт чужому коду.
- **Контрсценарий:** владелец запускает `lattice solve --as <владелец>`; ошибка в `materialize` (или способность
  `exec`) кладёт в `rows` ревизию `warrant/REQ-VER-007` с `expect` из `view` → шаги коммита: `owner` — владелец,
  схема `warrant/norm` — проходит → норма изменена внутри коммита вызова среди сотен строк оценок; основание новой
  ревизии — «+» человека-владельца → `declared`.
- **Инварианта:** роль Runtime (00-vision); P4 «тело говорит владелец» — здесь тело «говорит» код от имени владельца.
- **Последствие:** правка блока без намерения владельца, с высшим основанием; обнаружима только разбором коммита.
- **Тяжесть:** S3 · **Уверенность:** средняя (в v1 стадии — только `builtin` под `impl.pins`)
- **Минимальное разрешение:** ступень 2 (граница): способность объявляет типы строк (`rows: [std/pool, std/card]`), рантайм
  сверяет их, как пути (RN-09); коммит вызова (`key` = id вызова) не принимает ревизий типов с `card`.
- **Когда обязательно:** до `exec` (способностей проектов); текст — до S6.

### E-10 · Валидатор «заморожен», но читает проекции кода системы, версия которых в коммит не пишется

- **Вопросы:** Q01, Q03 · **Уровень:** PROVENANCE / EVOLUTION · **Класс:** D
- **Ответ дизайна:** ADR-32 `:8-9` — проверки ядра — замороженное ядро, «им нужен индекс»; `00-vision.md:87-90` —
  иначе «система сможет поменять собственный валидатор посреди работы»; маркер несёт только `kernel`
  (`12-ledger.md:27`); проекции индекса — код домена 12 (слой «код системы», обычные релизы — `04-architecture.md:11`,
  `12-ledger.md:97-100`); `revalidate` сравнивает «`kernel` записанный и текущий» (`13-rules.md:144`, RL-12 `:171`).
- **Наблюдение:** что «текущий факт», «живая сущность», «ключ зерна в области», «алиас в силе», «вызов жив» — решают
  проекции `facts`, `latest`, `grain`, `aliases`, `executions` (`12-ledger.md:80-92`); `owner`, `grain-unique`,
  `count`, `learning-gate` судят по ним. Проекции меняются релизом ledger без смены `kernel`, и их версия в коммит не
  записывается — только в кэш индекса, которого до триггера LG-09 нет (`12-ledger.md:116`).
- **Контрсценарий:** релиз ledger исправляет в проекции `facts` выбор «последний среди допущенных» (ADR-6) → те же
  строки: до релиза `count` для `solution-size` видел 7 действующих членов, после — 8 → коммиты с одинаковым
  `kernel: 1` получают разные вердикты; `revalidate` показывает равные `kernel` и расхождение объяснить не может;
  сравнение «против сохранённого индекса прежней версии проекции» (`12-ledger.md:109-111`) нечем сделать — кэша нет.
- **Инварианта:** P9/VI-04 («валидатор меняется только версией ядра»); RL-12 (повторимость проверки).
- **Последствие:** провенанс проверки коммита неполон: «прошёл проверки ядра версии k» не определяет результат.
- **Тяжесть:** S3 · **Уверенность:** средняя
- **Минимальное разрешение:** ступень 2: в перечень `04-architecture.md` §1 внести «проекции, которые читают проверки
  ядра» (`revisions`, `latest`, `grain`, `aliases`, `facts`, `keys`, `executions`) — их код версионируется `kernel`;
  тогда `kernel` маркера снова определяет валидатор.
- **Когда обязательно:** до среза S1 (формат маркера и слой проекций).

### E-12 · Одна настройка на пространство и одно пространство на проект: второй сценарий связан общим гейтом

- **Вопросы:** Q57 · **Уровень:** EVOLUTION · **Класс:** —
- **Ответ дизайна:** ADR-28 `:5-6` — `std/setup` «один на пространство имён (зерно без измерений)», тело — один
  `pipeline` и `ports`; проект — одно пространство (`15-catalog.md:24`, ADR-33 `:104` — второе проектное пространство
  в хранилище невозможно); совпадение `pass` — по `setup@n` (`22-run.md:78-79`, ADR-29).
- **Наблюдение:** оптимизация «одна атомарная ревизия на конвейер и модели» (PF-02) превращается в ограничение, как
  только в проекте нужен второй конвейер: либо он не выражается (одно поле `pipeline`), либо живёт в той же ревизии, и
  любая правка одного сценария меняет `setup@n` обоих. Второе пространство — через ядро (E-01, E-02). Отсрочки нет
  ни в 22, ни в ADR-28.
- **Контрсценарий:** WARRANT добавляет сценарий «проверить PR по нормам» (другой конвейер, та же модель judge) →
  `std/setup` может держать один `pipeline` → владелец выбирает: либо `std/setup@2` с несколькими конвейерами — тогда
  смена порога в `solve` даёт новый `setup@n`, и вердикты по неизменному второму сценарию ждут нового `bench-run pass`
  (гейт по кортежу, `22-run.md:325-327`) — полная регрессия `test` ради чужой правки; либо второй проект-хранилище —
  без общей памяти и доверия с первым (LG-11).
- **Инварианта:** ADR-22 «одна политика проверки» — предполагает одну настройку; видение «Работает в нескольких
  проектах» / переиспользование (`00-vision.md:23`).
- **Последствие:** рост проекта по сценариям упирается в модель «одна настройка»; стоимость стенда растёт с числом
  сценариев, а не с числом изменений.
- **Тяжесть:** S3 · **Уверенность:** средняя
- **Минимальное разрешение:** ступень 5: отсрочка в 22 «Вне объёма» — «несколько конвейеров в пространстве: зерно
  `std/setup` = `[name]`, кортеж гейта — по `setup@n` + имени конвейера» с триггером «второй конвейер в проекте»;
  изменение — `std`-уровня (перезерновка по GR-03), ядро не задевает.
- **Когда обязательно:** по триггеру «второй конвейер в проекте».

### E-13 · Какие типы истекают сегментом — таблица в коде ledger; проект не может объявить свои события

- **Вопросы:** Q59, Q57 · **Уровень:** EVOLUTION · **Класс:** A (и F)
- **Ответ дизайна:** ADR-3 `:5-6`, `:16-17` — события «`std/measurement`, `std/execution` и подобные» — в сегменты
  «по типу»; «рекомендация — таблица в 12-ledger, не поле `core/type` (поле расширило бы ядро)»; таблица
  `12-ledger.md:38-41` — два `std`-типа.
- **Наблюдение:** принадлежность типа сегменту — знание кода системы (ledger), а не данных; «и подобные» не
  определено. Проект с потоком событий (Q59 п. 3 data engineering — прогоны по датасетам; п. 4 — сканы) не может
  объявить свой тип событий исполнения данными: либо строки навсегда в основном журнале (рост, p95 пересборки,
  LG-09), либо релиз LATTICE с именем проектного типа в таблице ledger — код системы знает проект (против P10 «всё
  проектное — в пространстве проекта и его адаптере»).
- **Контрсценарий:** проект `acme` пишет `acme/scan-event` (тысячи на прогон) → таблица 12 §1 его не знает → основной
  журнал, сроков нет → через месяцы p95 пересборки при каждом `open()` (кэша до LG-09 нет, `12-ledger.md:116`)
  срабатывает триггер хранилища не из-за данных проекта, а из-за телеметрии; обратный путь — выпуск пакета ради
  имени чужого типа.
- **Инварианта:** P10; ADR-3 (события исполнения не копятся вечно).
- **Последствие:** точка расширения «свои события исполнения» закрыта для проектов; второй событийный потребитель
  упирается в релиз кода системы.
- **Тяжесть:** S3 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 1: сегментный тип — наследник `std`-маркера (например, `std/execution-event`,
  проверка по цепочке `extends`, как номинальная совместимость RL-05); таблица 12 §1 — по маркеру; ядро не
  расширяется.
- **Когда обязательно:** до второго проекта (данные v1 не затрагиваются: сегменты до замера не истекают).

### E-14 · В сквозной цепочке нет звена «Результат»: вердикт — утверждение без следа исхода

- **Вопросы:** Q69 (и Q70) · **Уровень:** PROVENANCE · **Класс:** E (корень доверия — добросовестный потребитель)
- **Ответ дизайна:** «вердикт по результату возвращается в LATTICE и меняет доверие» — `00-vision.md:5-6`, «каждый раз
  узнаёт, что сработало» — `:9`; вердикт — «диагноз потребителя» (`22-run.md:271-273`); «верни вердикт — кодом не
  принуждается (потребитель внешний)» (`21-compose.md:156`); след использования `used[].evidence` — «Вне объёма, когда
  появится его источник» (`22-run.md:457-458`); живые вердикты агентов — «следующий этап» (`01-first-run.md:93-96`).
- **Наблюдение:** в журнале есть выдача (`std/execution`, пакет) и есть вердикт, но нет результата работы
  потребителя — ни ссылки на коммит/тест, ни места. Переход Execution → Result → Verdict держится на «потребитель честно
  и верно оценил», а в первом запуске — на вердиктах, выведенных из эталона. Поля под след в `std/verdict@1` нет, поэтому
  вердикты v1 нельзя будет потом перевзвесить по следу, даже когда он появится.
- **Контрсценарий:** агенты двух моделей (две группы, ADR-26) используют пакет, задача у обоих проваливается по другой
  причине, оба возвращают `complete` с `used` по всем членам → `std/learned-assert` +1 от двух групп → членства и
  подсказки `observed` (`14-trust.md:75`) → в карточку и `recall` без LENS. Позже вводится `used[].evidence` —
  вердикты v1 без следа не отличить от подтверждённых исходом; переоценить их нечем.
- **Инварианта:** видение «узнаёт, что сработало»; P5 «доверие вычисляется» — вычисляется из самоотчётов.
- **Последствие:** канонические членства и `observed` в v1 растут из утверждений о результате, которые журнал не
  может сопоставить с результатом; отсрочка `evidence` оставляет данные v1 без пути переинтерпретации.
- **Тяжесть:** S3 · **Уверенность:** средняя (пересекается с ролью B — эпистемика вердикта)
- **Минимальное разрешение:** ступень 5: уже в `std/verdict@1` — необязательное поле `evidence: [Place | ref]` (не
  взвешивается политикой, пока нет решения), чтобы данные v1 были переинтерпретируемы; в 00-vision «узнаёт, что
  сработало» → «узнаёт, что потребитель счёл сработавшим».
- **Когда обязательно:** до среза S8 (форма `std/verdict@1`).

### E-15 · Смысл вопросов judge («та же потребность?», «одно и то же?») живёт в коде, а не в данных

- **Вопросы:** Q58 · **Уровень:** SEMANTICS · **Класс:** A
- **Ответ дизайна:** слой `std` содержит «промпты стадий» (`04-architecture.md:12`); промпты Composer — в `params`
  стадий (`21-compose.md:224-225`, `:281`); у judge «вопросы атомарные; композиция — в коде стадий»
  (`20-lens.md:122`), «`prompt_hash` — от шаблона вопроса адаптера» (`20-lens.md:125-126`, `30-adapters.md:131`);
  идентичность — `code` и `prompts` кортежа (`22-run.md:72-76`), `calibrated_for` (RN-10).
- **Наблюдение:** текст утверждений для `verify` (решает повтор — названное исключение ADR-13 — и кандидатов в алиас)
  формирует код `builtin`-стадии, обёртку — шаблон адаптера; ни то, ни другое не данные LATTICE. Смена распознаётся
  (хэши в кортеже, отказ по `calibrated_for`), поэтому тихого нарушения нет, но P9-перечень «промпты стадий — данные
  `std`» верен только для Composer.
- **Контрсценарий:** владелец хочет уточнить формулировку «та же потребность?» (ложные повторы на стенде E2) → ревизией
  `std/setup` это сделать нельзя, нужен релиз пакета (`code`) или адаптера (`prompts`) → затем новая калибровка
  `same_hi/lo` — путь другой, чем у промптов Composer, при том же смысле «поменять промпт».
- **Инварианта:** P9 (самоописание данных) — формулировка перечня.
- **Последствие:** два класса промптов с разной эволюцией; ожидание «всё поведение — данные» неверно для judge.
- **Тяжесть:** S4 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 1: в `04-architecture.md` §1 (строка `std`) и 20 §5 — «промпты Composer — данные
  `params`; формулировки вопросов judge — код стадий, шаблон — адаптер; идентичность — `code`, `prompts`».
- **Когда обязательно:** до среза S5.

## Сомнения и справки

- **E-02:** закрыты ли вложенные объекты `core/trust-policy` (`calibration.verdict_weights: {…}`) — от этого зависит,
  нужна ли версия ядра для нового ключа веса или только для нового раздела. Нужен текст схемы генезиса (в `design/`
  её нет).
- **E-01:** не видел `integration/` и `research/analysis/arch-changes.md` (T-10 «периметр ядра») — возможно, путь смены
  ядра обсуждался там и не был перенесён в `design/`; в `design/` его нет.
- **E-06:** не нашёл, как `recall` трактует доверие решения без членов; если принять «пустое — всегда через LENS»,
  находка снимается одной строкой в 21 §3.
- **Пересечения:** E-05 — с ролями B/D (гейт, допуски); E-14 — с B (эпистемика вердикта); E-06 — с C (`recall`);
  E-10 — с A (провенанс проверки, `revalidate`). Корень в каждом случае — заявление видения/архитектуры (зона E).
- Не читались: `03-python-lessons.md`, `proposals/PF-config*.md` (нормой не являются; PF внесены в v0.4).
