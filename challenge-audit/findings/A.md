## Находки

### A-01 · Статус snapshot'а не видит смены состава — `recall` отдаёт невыученное

- **Вопросы:** Q05, Q10 · **Уровень:** SEMANTICS · **Класс:** D
- **Ответ дизайна:** T86 — `02-glossary.md:153` — «`stale` (изменились версии членов) · `broken` (член не найден)»;
  путь `recall` — `21-compose.md:74-75`: `fresh` → `deliver` без LENS, новый snapshot — только на ветке `stale`;
  обучение меняет состав фактами «без новых версий решения» — `21-compose.md:48-49`; `22-run.md:338`, `:349-352`.
- **Наблюдение:** snapshot — значение «что выдано»; статус сравнивает только версии его членов с текущими. Смена
  **состава** решения (добавление `found_by: verdict`, удаление окном `removal_window`) статус не меняет, а `recall`
  на `fresh` новый snapshot не строит. Где сказано, что выдача повтора строится из текущих `std/member`, — не найдено
  (искал: `snapshot`, `fresh`, `новый snapshot`, `состав`, `recall` по всему `design/`).
- **Контрсценарий:** решение S, snapshot N1 = {X@4, Y@2}. Вердикт `incomplete` + `add: Z@1` → `learn` пишет
  `std/member {S, Z@1, true}`; три группы закрывают окно по Y → `std/member {S, Y@2, false}`. Версии X, Y не менялись →
  N1 `fresh`. Следующий перефраз → `recall` → `deliver` N1 = {X@4, Y@2}: Z не выдаётся, удалённый Y выдаётся;
  вердикты на N1 (`used ∪ unused ⊆ snapshot.members`, `22-run.md:292`) продолжают писать голоса на удалённое членство.
- **Инварианта:** неявная: «выдача повтора отражает действующий состав решения»; E3 «Учится» (`01-first-run.md:27`).
- **Последствие:** контур обучения не доходит до потребителя; голоса копятся на выведенных членствах; E3 меряет либо
  ноль, либо (если `select-F1` считать по фактам, а не по пакету) доказывает выученное, которого потребитель не видит.
- **Тяжесть:** S2 · **Уверенность:** средняя (высокая — что определение T86 не покрывает состав; средняя — что
  реализация не пересоберёт snapshot сама)
- **Минимальное разрешение:** ступень 1 (определение) — T86 и `12-ledger.md:90`: `stale` также когда множество
  действующих `std/member`/`std/link` решения ≠ `members`/`links` snapshot'а; ветка `stale` уже строит новый snapshot.
- **Когда обязательно:** до среза S7 (повтор) / до E3 первого запуска.

### A-02 · Писатель выбирает старую `type@n` и обходит новые правила и `writers`

- **Вопросы:** Q38, Q68, Q06 · **Уровень:** OWNERSHIP · **Класс:** B
- **Ответ дизайна:** `10-kernel.md:28` — `type` — закреплённая ссылка, «ревизия проверялась правилами именно этой
  версии типа»; `13-rules.md:37-39`, `:130`, `:148` — строка проверяется правилами «своего `type@n`»; закреплённая
  ссылка разрешается «всегда» — `10-kernel.md:117`; `core/retire` на `id@n` запрещает только **исполнение** —
  `15-catalog.md:112`. ADR-12:9 закрывает ту же дыру для наследника («иначе наследник управляющего факта обходит ADR-6»),
  но не для прежней версии самого типа.
- **Наблюдение:** нигде не требуется, чтобы **новая** строка ссылалась на последнюю живую версию своего типа (искал:
  `type@n`, `последн… верси… типа`, `устаревш… верси…`, `старой версии типа`, `retire … тип`). `Draft.type` — строка
  (`12-ledger.md:131`); шаг 1 коммита заголовок `type` не нормализует (`12-ledger.md:53-55`). Значит правило, `writers`,
  `inForce`, `schema: hard`, добавленные в `T@n+1`, действуют только на тех, кто сам выбрал `T@n+1`.
- **Контрсценарий:** (1) владелец WARRANT сужает `writers` своего типа факта `warrant/…@1: grant` → `@2: owner` (или
  поднимает `schema` `soft` → `hard` по лестнице `13-rules.md:51-52`). Агент с допуском пишет строку с
  `type: warrant/…@1` — `owner` сверяет `writers` `@1`, схема `@1` — `soft`; коммит проходит. (2) `update` приносит
  `std/member@2` с `solution-size max: 5`; `materialize` или `learn` пишет строки под `std/member@1` (`max: 7`); у
  `select` «закреплённая версия `std/member`» (`21-compose.md:68`) нигде не закреплена — промпт и коммит читают разные
  `max`. Отзыв `core/retire` на `T@1` запись не останавливает.
- **Инварианта:** ADR-6 (права — в типе), лестница схемы RL-02, `13-rules.md` инвариант 1 (формально держится — по
  выбранной писателем версии).
- **Последствие:** ужесточение типа или правила — только декларация; «инвариант держит тип, а не стадия» (T-16) сводится
  к честности писателя; две версии одного контракта живут одновременно.
- **Тяжесть:** S2 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 2 (граница) — проверка ядра `kind`/`ref-policy` расширяется: `type` новой строки —
  последняя живая версия типа, или версия без `core/retire` на `T@n` (тогда «отзыв версии типа» = запрет записи под
  ней); `materialize`/`select` читают `solution-size` той версии, которой пишут. Проверка ядра — замороженное ядро: до
  первых данных (SL-04).
- **Когда обязательно:** до первого запуска (заморозка ядра, SL-04).

### A-03 · Член решения — ревизия или объект: противоречие и неопределённый ключ

- **Вопросы:** Q09, Q08, Q06 · **Уровень:** SEMANTICS · **Класс:** B
- **Ответ дизайна:** `21-compose.md:23` — `std/member {of: {group, member: блок@n}}`, ключ `[group, member]`; пример
  `10-kernel.md:172` — `member: REQ-VER-007@4`. Против: `15-catalog.md:100-101` — «Решение ссылается на норму **без
  версии**; snapshot при выдаче закрепляет версии». `22-run.md:357-358` — при смене версии члена «отвечает — новый
  snapshot, **доверие не меняется**»; `14-trust.md:132` — «доверие каждого членства отдельно».
- **Наблюдение:** (а) два места по-разному говорят, на что ссылается состав. (б) Если член — `блок@n`, не определено,
  входит ли версия в ключ факта (`10-kernel.md:187-188` — ключ по ролям, нормализация закреплённой ссылки не задана;
  искал `ключ факта`, `key`, `@n`, `нормализ`).
- **Контрсценарий:** решение S, `std/member {S, X@4, true}`, доверие `observed`. Владелец правит X → X@5; `recall` →
  `stale` → `recheck` «отвечает» → новый snapshot {X@5}. Чтение 1 (версия в ключе): для X@5 нужен новый факт
  `{S, X@5}` — его доверие с нуля (`unresolved`/`inferred`), `recall` на следующем повторе отдаёт «не подтверждено»
  (`14-trust.md:157`), вопреки «доверие не меняется»; старый `{S, X@4, true}` остаётся действующим — `count` считает
  X дважды, 7 мест съедаются ревизиями. Чтение 2 (ключ по `id`): запись `{S, X@5, true}` при текущем `{S, X@4, true}`
  — no-op по «тот же ключ и `value`» (`10-kernel.md:43`), закрепление X@5 тихо теряется, snapshot и состав расходятся.
- **Инварианта:** `21-compose.md` инвариант 1 (≤ `max` действующих), TR-01/§5 (доверие членства), KR-03 (no-op).
- **Последствие:** каждая правка нормы либо обнуляет накопленное вердиктами доверие состава и раздувает `count`, либо
  тихо съедает новое закрепление; два добросовестных исполнителя построят несовместимые журналы (ключ — формат данных).
- **Тяжесть:** S2 · **Уверенность:** высокая (противоречие по цитатам)
- **Минимальное разрешение:** ступень 1 (определение) — в 10 §7: ключ факта нормализует ссылки ролей до `id` (версия —
  атрибут факта, не identity); смена `блок@n` → `@n+1` — новый факт того же ключа (не no-op, т. к. `of` отличается) —
  правило no-op уточнить «тот же `of` и `value`»; доверие членства — по ключу; `15-catalog.md:100` привести к 21.
- **Когда обязательно:** до среза S3 (факты и доверие) — ключ входит в формат индекса `facts`.

### A-04 · Слияние потребностей: столкновение ключей фактов и отказ `solution-size`

- **Вопросы:** Q08, Q06 · **Уровень:** EVOLUTION · **Класс:** B
- **Ответ дизайна:** `11-identity-grain.md:110-112` — факты о A «учитываются как факты о B», `merge` перепроверяет
  hard-правила этих фактов «на разрешённом виде — в том же коммите»; `21-compose.md:174-176` — «при слиянии потребностей
  их решения алиасятся тем же коммитом; состав после объединения > `max` → **находка** «разбить»»; `solution-size` —
  hard (`21-compose.md:60`), инвариант 1 — `21-compose.md:243-244`.
- **Наблюдение:** (а) если перепроверка `count` идёт на разрешённом виде, объединение > 7 — **нарушение**, коммит
  слияния отклонён, «находки» не будет; если не идёт — инвариант 1 нарушен в журнале. (б) Не определено, что делает
  индекс `facts` (`12-ledger.md:87`), когда после алиаса SA→SB два факта сводятся к одному ключу: `{SA, X@4}` и
  `{SB, X@4}` с разными `value` (искал: `ключ`, `алиас`, `разрешённ`, `столкнов`, `коллиз` в 11, 12, 21).
- **Контрсценарий:** NA и NB — дубли; SA = {X@4, Y, Z, U}, SB = {X@4, V, W, Q, R}; в SB окно удаления уже записало
  `{SB, X@4, false}` (seq 900), в SA `{SA, X@4, true}` (seq 500). Владелец подтверждает кандидата: `core/alias NA→NB`
  + `core/alias SA→SB`. Разрешённый состав = 8 уникальных + X дважды; `count` на разрешённом виде → 9 > 7 → слияние
  отклонено; дубль потребностей остаётся, вопреки CP-09. Если перепроверки нет — по ключу `[SB, X@4]` текущим становится
  последний по `seq` (`false`), X тихо выпадает; после `split` возвращается, но вердикты, собранные в период слияния на
  SB, уже учтены обучением и не откатываются.
- **Инварианта:** `11-identity-grain.md` GR-05 («обратимо»), `21-compose.md` инвариант 1, KR-13 (текущий — последний
  по ключу).
- **Последствие:** главный путь устранения дублей потребностей либо блокируется, либо портит состав; «обратимость»
  слияния не распространяется на обучение, выполненное в период слияния.
- **Тяжесть:** S2 · **Уверенность:** высокая — для (а); средняя — для (б)
- **Минимальное разрешение:** ступень 1 (определение) — в 11 §4: ключи фактов при слиянии сравниваются по разрешённым
  ролям; при столкновении текущим остаётся факт канонического, факт алиаса — историей; `count` на `merge` — только
  `soft`-находка «разбить» (как пишет 21) либо план слияния обязан нести `value: false` для лишних членов. В 22 §6 —
  строка «обучение в период слияния при `split` не откатывается» (явно).
- **Когда обязательно:** до среза S7 (кандидаты потребностей) / до E5.

### A-05 · Правка `core/actor` задним числом перегруппировывает всю историю голосов

- **Вопросы:** Q07, Q04 · **Уровень:** PROVENANCE · **Класс:** D
- **Ответ дизайна:** `core/actor` — **сущность** `{kind, name, model?}` (`14-trust.md:18`); `core/session` —
  `{actor: ref | null, …}` без `kind`/`model` (`14-trust.md:19`); группа `agent` — `(kind, model)`, вид и модель
  «из реестра» (`14-trust.md:22-26`, `:37-38`; ADR-26:7-8 — «детализацию `model` задаёт владелец»); вердикт: «вид и
  модель участника — из реестра, в теле их нет» (`22-run.md:285`); `trust()` — функция журнала (`14-trust.md:175`).
  ADR-25:28 — «Откат необратим: меняется смысл `kind` уже записанных `actor`».
- **Наблюдение:** что такое «тот же участник» при смене модели агента, не определено (для `machine` определено:
  `software` → новая сессия, `14-trust.md:35-36`). Закреплена ли `session.actor` (`actor@n`) — не сказано (искал:
  `actor@`, `session.actor`, `смен… модел…`, `(kind, model)`). Если ссылка следующая или группа читается из текущей
  ревизии — ревизия реестра переписывает группы, веса и `declared` всех прошлых голосов.
- **Контрсценарий:** участник `warrant/ACT-coder {kind: agent, model: m1}` полгода пишет вердикты; подсказки и членства
  дошли до `observed` голосами групп `(agent, m1)` и `(agent, m2)` (второй агент `ACT-review`). Агент переходит на m2;
  владелец, как велит ADR-26, правит `ACT-coder@2 {model: m2}`. Пересчёт: все прошлые сессии ACT-coder — группа
  `(agent, m2)`, совпадает с ACT-review → `groups` падает, `std/cue` (`inForce {basis: observed}`, `14-trust.md:160`)
  выходят из силы, карточки теряют подсказки, `recall` — «не подтверждено». Обратный случай: правка `kind: agent →
  human` превращает прошлые «+» в `declared`, прошлые «−» — в решающие `overruled`.
- **Инварианта:** `14-trust.md` инвариант 2 (независимость — по группам), TR-08 (доверие не меняется со временем без
  новых голосов — неявно), P5.
- **Последствие:** канон (журнал) цел, но вывод о независимости подтверждений — функция **текущего** реестра, а не
  того, кто голосовал; нарушение не видно (у `trust()` есть `policy@version`, версии реестра нет).
- **Тяжесть:** S2 · **Уверенность:** средняя (зависит от толкования `session.actor`)
- **Минимальное разрешение:** ступень 1 (определение) — `core/session.actor` — закреплённая ссылка `actor@n` на момент
  открытия; группа и вес — по ревизии в сессии; смена модели агента — новая ревизия участника, прошлые сессии не
  перегруппировываются (как `software` у `machine`). Строка в 14 §1 и T53.
- **Когда обязательно:** до среза S3.

### A-06 · Нет протокола смены версии ядра на существующем журнале

- **Вопросы:** Q39 · **Уровень:** EVOLUTION · **Класс:** F
- **Ответ дизайна:** хэш генезиса — константа версии ядра, «сверяется при открытии хранилища» (`10-kernel.md:214-215`,
  `12-ledger.md:72`, KR-16); «каждая версия ядра объявляет константой кода, какой формат пишет и какие читает»
  (`10-kernel.md:86-87`); SL-04 (`05-slices.md:66`) — «до того [первого запуска] смена генезиса — новая константа и
  пересчёт фикстур»; `revalidate` — «код старых примитивов не хранится» (RL-12, `13-rules.md:171`); примитивы и
  проверки ядра «растут только с его версией» (`13-rules.md:87`); ядро меняется «только версией кода ядра»
  (`10-kernel.md:210`).
- **Наблюдение:** что происходит **после** первых данных, когда выходит ядро v2 (новый примитив по RL-14, новая
  проверка, новое поле генезис-типа), не описано: открытие журнала v1 ядром v2 по KR-16 — расхождение хэша генезиса;
  как ревизии генезис-типов `core/*@2` попадают в журнал (кто пишет — `core/genesis`? по какому `owner`?) — нет;
  «какие форматы читает» есть только для формата строк, не для генезиса. Искал: `версия ядра`, `хэш генезиса`,
  `миграц`, `новая версия ядра`, `SL-04`, `KR-11` по всему `design/`.
- **Контрсценарий:** первый запуск идёт полгода на ядре v1. Стенд показывает, что нужен новый примитив (критерий RL-14 —
  «тот же выход в нескольких пространствах») или новый параметр политики (A-08). Выпуск ядра v2 меняет генезис → `open()` журнала WARRANT
  отказывает; либо реализация «временно» отключает сверку хэша / дописывает `core/type@2` от `core/genesis` в середине
  журнала — тот самый «валидатор меняется посреди работы», от которого защищает P9 (`00-vision.md:89`).
- **Инварианта:** KR-16, P9/VI-04, LG-01 (журнал только растёт).
- **Последствие:** «заморожено» превращается в долг: либо ядро не развивается вовсе, либо первое же развитие делается
  внештатно, без провенанса; `revalidate` старых коммитов на новом ядре смешивает вердикты двух ядер.
- **Тяжесть:** S2 · **Уверенность:** высокая (пробел), средняя (что понадобится в пределах жизни v1)
- **Минимальное разрешение:** ступень 7 (ADR) — «переход ядра»: ядро vN объявляет множество принимаемых хэшей генезиса
  (как форматы); новые ревизии генезис-типов пишет сессия `core/genesis` отдельным коммитом с `kernel = vN` и `key =
  kernel:vN`; проверки ядра — по `kernel` маркера. Ступени 1–5 не хватает: затронуты 10, 12, 13 и P9.
- **Когда обязательно:** до первого запуска — зафиксировать принцип (хотя бы «принимаемые хэши генезиса»), протокол —
  до первой версии ядра после первых данных.

### A-07 · Гейт принимает `base` на любой регрессионный план владельца, а не на действующий

- **Вопросы:** Q10, Q06 · **Уровень:** OWNERSHIP · **Класс:** D
- **Ответ дизайна:** «Действующий [регрессионный план] — последний по `seq` среди записей владельца» (`23-bench.md:28-30`);
  регрессия — «`base` на **действующий** регрессионный план» (`23-bench.md:115-116`); но гейт — «по плану с `base` на
  регрессионный план владельца» (`13-rules.md:85`; `23-bench.md:123-125`; инвариант 4 — `23-bench.md:146-147`;
  ADR-29:8); ротация изношенного `test` — «новый регрессионный план» (`23-bench.md:131-132`), прежний не выводится.
- **Наблюдение:** правило коммита (единственный барьер необратимого обучения) не требует, чтобы `base` был
  действующим; события-планы не имеют «текущего» в индексе `facts` — «последний среди записей владельца» считает не
  ядро. «Владелец» — на момент записи плана или текущий — тоже не сказано (искал: `действующ`, `регрессионный план`,
  `base`, `владельца`, `supersedes`).
- **Контрсценарий:** в марте владелец пишет регрессионный план R1 (мягкий δ, 40 вопросов); в июне — R2 (строже, новый
  `set@n`, R1 изношен). Предлагающий новую ревизию `setup@6` пишет план `candidate` с `base: R1` — BN-07 запрещает ему
  выбирать вопросы и порог, но выбрать **какой из планов владельца** ему никто не запрещает. `pass` по R1 → гейт
  открыт → вердикты на `setup@6` учат. Второй вариант: после `transfer` владения (`15-catalog.md:71-75`) все планы
  прежнего владельца — «не владельца» при текущем прочтении → гейт закрыт для всех кортежей, обучение останавливается
  без сигнала (вердикты «ждут `pass`»).
- **Инварианта:** BN-07 (предлагающий не выбирает порог и вопросы), ADR-29.
- **Последствие:** барьер стенда ослабляется выбором исторического `base`; либо смена владельца тихо останавливает
  обучение.
- **Тяжесть:** S2 · **Уверенность:** высокая (расхождение формулировок по цитатам)
- **Минимальное разрешение:** ступень 1 (определение) — в 13 §2 `learning-gate` и 23 инвариант 4: `base` — действующий
  на `seq` плана `candidate` регрессионный план (последний по `seq` среди планов `kind: regression`, записанных
  тем, кто был владельцем на момент записи плана).
- **Когда обязательно:** до среза S9 (гейт) / до E6.

### A-08 · Замороженное ядро держит форму данных `std`, которые меняются релизами

- **Вопросы:** Q37, Q39 · **Уровень:** OWNERSHIP · **Класс:** B
- **Ответ дизайна:** примитив `learning-gate` «читает вердикт, `std/bench-run` и план стенда» — названное исключение
  (`10-kernel.md:220-222`); его логика — `13-rules.md:85` (поля `verdict.execution`, `bench-run pass`, `base`
  регрессионного плана, `purpose: bench`/`simulate`); значения `purpose` резервируют домены 14, 22, 23
  (`14-trust.md:31-34`); `std` — «как любые данные: версии» (`10-kernel.md:211`). `core/trust-policy` — тип генезиса
  (`10-kernel.md:210`), его схема общая — «обязательна, закрыта и `hard`» (`10-kernel.md:152`), а значения `lens`,
  `candidates`, `calibration` «задают их потребители» 20, 21, 22 (`14-trust.md:120-121`).
- **Наблюдение:** семантика правила живёт в двух местах с разным темпом изменений: код примитива (заморожен, меняется
  версией ядра) и форма `std`-типов/значения `purpose`/параметры политики (меняются релизами `std`). Какая сторона
  главная при расхождении — не сказано (искал: `learning-gate`, `std/verdict@`, `bench-plan`, `purpose`,
  `trust-policy`, `schema`).
- **Контрсценарий:** (1) релиз `std` вводит `std/verdict@2` с полем `executions: [ref]` (вердикт на пакет из двух
  вызовов) или `std/bench-plan@2` с `kind: regression-v2`; гейт ядра v1 читает `from.execution`/`base` по старой форме:
  строки обучения от `@2` либо все отклоняются (вердикты «ждут `pass`» навсегда, `22-run.md:325-326`), либо гейт читает
  пустое и пропускает — зависит от реализации. (2) Стенд требует нового параметра обучения (`calibration.add_window`);
  закрытая схема генезис-типа `core/trust-policy@1` его отвергает → новая версия ядра → A-06.
- **Инварианта:** RL-08 («ядро не знает смысла фактов обучения»), T-10/KR-11 (малое ядро), ADR-29.
- **Последствие:** `std` фактически заморожен в частях, которые читает гейт и которые описывает `core/trust-policy`;
  эволюция обучения и калибровки упирается в версию ядра без протокола (A-06).
- **Тяжесть:** S3 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 2 (граница) — в 13 §2 у `learning-gate` перечислить закреплённые версии
  `std`-типов, которые он читает (`std/verdict@1`, `std/bench-run@1`, `std/bench-plan@1`), и правило: новая версия
  этих типов в `std` совместима по читаемым путям (проверка совместимости схемы уже есть — дописать пути гейта);
  `core/trust-policy` — схема открыта для полей потребителей (`additionalProperties` по подразделам) либо перенести
  форму параметров в `std`-тип, на который ссылается политика.
- **Когда обязательно:** до первого запуска (заморозка генезиса, SL-04).

### A-09 · Проверки внутри коммита: префикс или итог — от порядка строк зависит исход

- **Вопросы:** Q68 · **Уровень:** EXECUTION · **Класс:** B
- **Ответ дизайна:** шаг 5 коммита — «на состоянии «индекс + **уже принятые** строки этого коммита»»
  (`12-ledger.md:60`); LG-03 — «на состоянии **с учётом строк** того же коммита» (`12-ledger.md:192`); смена зерна —
  «версия типа + факты `core/alias` — всё или ничего» (`11-identity-grain.md:95`), `regrain-plan` требует план у
  строки типа (`13-rules.md:69`); цепочка `extends` — «с учётом строк коммита» (`10-kernel.md:250`).
- **Наблюдение:** «уже принятые» = префикс (строки выше по порядку), «с учётом строк» = итоговое состояние. Порядок
  строк в `Draft[]` нигде не нормирован (искал: `порядок строк`, `уже принятые`, `с учётом строк`, `Draft[]`). Для
  относительных правил (`count`, `grain-unique`, `regrain-plan`, `learning-gate`) ответ зависит от прочтения.
- **Контрсценарий:** решение S из 7 действующих членов. Вердикт `incomplete` + `add: Z`, этот же вердикт замыкает
  окно удаления Y. `learn` готовит `[{S, Z, true}, {S, Y, false}]` одним коммитом (`key = learn:<verdict>`,
  `22-run.md:322`). Префикс: строка Z видит 8 > 7 → нарушение `solution-size` → весь коммит отклонён; `learn`
  повторяет — тот же отказ; вердикт навсегда «ждёт» (`22-run.md:325-326`), и удаление Y тоже не записано. Итог:
  7 → проходит. Обратный порядок строк — проходит при обоих прочтениях. Аналогично: план слияния, записанный до строки
  новой версии типа, при префиксном прочтении проверяется ещё по старому зерну.
- **Инварианта:** LG-03, RL-11 (детерминированный отказ), неявная: «исход коммита не зависит от порядка строк».
- **Последствие:** два исполнителя примут/отклонят один и тот же коммит; `revalidate` на другом порядке даст другой
  вердикт; обучение молча теряет вердикты.
- **Тяжесть:** S3 · **Уверенность:** высокая (расхождение формулировок), средняя (сценарий зависит от `learn`)
- **Минимальное разрешение:** ступень 1 (определение) — в 12 §2 и 13 §4: построчные проверки (`owner`, `schema`,
  `ref-*`, `kind`) — на префиксе, относительные (`count`, `grain-unique`, `unique-within`, `regrain-plan`,
  `acyclic`) — на итоговом состоянии коммита; одна фраза и тест «перестановка строк не меняет исход».
- **Когда обязательно:** до среза S1 (коммит) — это контракт `commit`.

### A-10 · Относительное hard-правило запирает данные, нарушающие новую версию правила

- **Вопросы:** Q38 · **Уровень:** EVOLUTION · **Класс:** D
- **Ответ дизайна:** старые ревизии «остаются валидными по своей версии» (`11-identity-grain.md:122-124`); коммит
  проверяется один раз (`12-ledger.md:181`, инвариант 3); `count` — «число действующих фактов … где в роли `role` тот
  же объект, что у проверяемой строки» (`13-rules.md:84`); `solution-size` без `when` (`21-compose.md:60`), `max`
  «калибрует стенд»; `when` — механизм условия (`13-rules.md:46-48`).
- **Наблюдение:** «валидно по своей версии» верно для построчных правил, но `count`/`grain-unique`/`unique-within`
  считают по **всему текущему состоянию** — новая версия правила судит новую строку по старым данным. `solution-size`
  проверяется и на строке удаления `value: false`. Что делать с группами, уже превышающими новый `max`, — не сказано
  (искал: `max`, `solution-size`, `revalidate`, `план`, `раздут`, `большие группы`; lint лишь находит «большие группы»,
  `13-rules.md:135`).
- **Контрсценарий:** стенд калибрует `max` 7 → 5: новая версия `solution-size@2` + `std/member@2`. Решение S имеет 7
  действующих членов под `@1`. Окно удаления замыкается по Y → `learn` пишет `{S, Y, false}` под `std/member@2` →
  `count` = 6 > 5 → отказ. Ни одно одиночное удаление не проходит, пока их не станет два одним коммитом (а с префиксным
  прочтением A-09 — не пройдёт и так). Состав S заморожен в нарушающем состоянии, обучение по нему остановлено; `learn`
  повторяет без конца. Тот же тупик — после слияния потребностей (A-04).
- **Инварианта:** `21-compose.md` инвариант 1; RN-05 (удаление окном); неявная: «удаление всегда уменьшает нарушение».
- **Последствие:** ужесточение правила (обычная калибровка) блокирует именно то действие, которое вернуло бы данные в
  норму; смешение «старые данные валидны по версии» и «проверка по текущему состоянию».
- **Тяжесть:** S3 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 1 (определение) — `solution-size` с `when: {path: value, eq: true}` (механизм
  есть); в 13 §1 фраза: относительное правило проверяет строку, только если она не уменьшает нарушение; смена `max` —
  с отчётом `lint` о группах сверх нового `max` (он уже есть).
- **Когда обязательно:** до среза S8 (обучение).

### A-11 · Смена `grain_scope` обходит `regrain-plan` — тихие дубли в расширенной области

- **Вопросы:** Q07 · **Уровень:** SEMANTICS · **Класс:** D
- **Ответ дизайна:** `regrain-plan` — «при любом изменении **состава или порядка** измерений» (`11-identity-grain.md:93-94`;
  `13-rules.md:69`; GR-03); индекс `grain` — по `(namespace, тип, hash)`, `store` — одна сущность на хранилище
  (`11-identity-grain.md:42-45`, ADR-27); ADR-27:15-16 — смена области «меняет область проверки задним числом».
- **Наблюдение:** `grain_scope` — поле `core/type` рядом с `grain`, но в условие перезерновки не входит (искал:
  `grain_scope`, `область зерна`, `regrain-plan`, `перезерновка`). `grain-unique` проверяет только строки коммита
  (`13-rules.md:63`) — живые сущности, ставшие дублями после расширения области, никто не проверит.
- **Контрсценарий:** `std`-тип справочника (единица, термин) с областью по умолчанию; в `std` и в `warrant` есть
  сущности с ключом `kg`. Релиз `std` ставит `grain_scope: store` (ровно рекомендация ADR-27 для справочников).
  `update` публикует тип без плана (`regrain-plan` не сработал: состав `grain` тот же) → в хранилище две живые
  сущности с одним ключом в одной области; индекс `grain` (`ключ → id`) хранит одну из них — какую, решает порядок
  пересборки; `ensure(kg)` возвращает её, ссылки проекта ведут на другую. P8 «ни одного тихого дубля» нарушено тихо.
  Обратная смена `store → namespace` безопасна.
- **Инварианта:** P8; `11-identity-grain.md` инварианты 1 и 4.
- **Последствие:** канон содержит запрещённый дубль без следа; `rebuild` детерминирован, но выбирает «победителя»
  порядком, а не решением владельца.
- **Тяжесть:** S3 · **Уверенность:** высокая (пробел), низкая (что `std` сменит область в v1)
- **Минимальное разрешение:** ступень 1 (определение) — в GR-03/`regrain-plan`: «изменение состава, порядка **или
  расширение `grain_scope`**»; одна фраза в 11 §3 и 13 §2.
- **Когда обязательно:** до среза S2 (типы и зерно).

### A-12 · После истечения сегмента строка обучения теряет доказательство прохода гейта

- **Вопросы:** Q62, Q04 · **Уровень:** PROVENANCE · **Класс:** D
- **Ответ дизайна:** строки обучения несут `from` (вердикт) и `policy@rev` (`22-run.md:304-306`), гейт читает кортеж
  через `verdict.execution` из раздела `executions` живых сегментов (`13-rules.md:85`, `12-ledger.md:92`, ADR-3:9-11);
  за горизонтом `revalidate` по гейту — «не проверяемо» (`22-run.md:388-391`, RN-17); копию `setup@n` в вердикт
  отвергли: «значение писал бы код `verdict()`» (`22-run.md:459-460`). `execution.bench` — тоже в сегменте
  (`22-run.md:203`).
- **Наблюдение:** гейт отвечает на вопрос «по какому `bench-run pass` принята строка», но ответ нигде не
  записывается: ни в строке обучения, ни в вердикте. После истечения цепочка `строка → вердикт → вызов → кортеж →
  bench-run` рвётся на втором звене навсегда, хотя сама строка и её доверие вечны. Аргумент 22:459 касается вердикта,
  а не строки обучения, которую пишет `learn` после проверки гейтом.
- **Контрсценарий:** горизонт — 90 дней (замер). Март: вердикт на вызов с `setup@3`, `learn` пишет `std/member {…,
  from: V}` за `bench-run` B7. Май: выясняется, что регрессионный план B7 был слабым (или `code` в B7 записан с
  ошибкой). Июль: вызов истёк. Вопрос владельца «какие членства выучены под B7 / под `setup@3`?» — ответа в журнале нет;
  `revalidate` — «не проверяемо»; отличить строки, прошедшие гейт, от строк, записанных писателем с допуском без `from`
  (инвариант 5, «держит хост», `22-run.md:414-415`), тоже нельзя.
- **Инварианта:** RN-04 «основание факта восстанавливается по вызову» (`22-run.md:428`) — верно только до горизонта;
  LG-08 (всё, что влияет на результат, — в журнале).
- **Последствие:** провенанс обучения — функция срока хранения; откат выученного по одному прогону стенда невозможен
  после горизонта.
- **Тяжесть:** S3 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 1 (определение) — строка обучения несёт `bench: ref` (тот `bench-run pass`,
  который засчитал гейт), `learning-gate` проверяет, что его `tuple` совпадает с кортежем вызова; `bench-run` лежит в
  основном журнале и не истекает. Новых механизмов нет — поле и одна проверка в существующем примитиве.
- **Когда обязательно:** до среза S8; обязательно до первого истечения сегмента (замер горизонта).

### A-13 · Истечение сегмента не меняет `seq` — кэш индекса и `executions` расходятся с пересборкой

- **Вопросы:** Q62, Q04 · **Уровень:** EXECUTION · **Класс:** F
- **Ответ дизайна:** кэш индекса принимается по `projection` и `seq` хвоста (`12-ledger.md:114-116`); `seq` — пропуски
  допустимы, «истёкший сегмент» (`12-ledger.md:154`); «истёк сегмент — записи раздела [`executions`] исчезают» (ADR-3:9-11);
  механизм истечения отложен — «Вопросы» 2 (`12-ledger.md:216-218`), рекомендация — `expire(segment)` по команде.
- **Наблюдение:** истечение меняет журнал, не двигая хвост: `loadIndex` примет кэш с живыми записями `executions`
  истёкшего сегмента. Отложенный вопрос 2 перечисляет только хэш коммита; согласованность кэша и раздела `executions`
  в нём не названа (искал: `expire`, `истечен`, `IndexBlob`, `loadIndex`, `executions`).
- **Контрсценарий:** включён кэш (LG-09) и истечение (вопрос 2). `expire(seg-7)`; процесс A открывает хранилище —
  кэш с `seq` = хвосту принят, в `executions` есть вызовы seg-7 → `learn` по вердикту истёкшего вызова проходит гейт и
  `ref-exists`. Процесс B (без кэша, другая машина) пересобирает индекс → тот же коммит отклонён «вызов истёк».
  `rebuild --check` покажет расхождение раздела `executions` — но уже после принятого коммита.
- **Инварианта:** `12-ledger.md` инвариант 2 (`rebuild(ledger) == index`), LG-07.
- **Последствие:** принятие строки обучения зависит от того, был ли кэш, — недетерминизм в каноне (принятая строка
  необратима).
- **Тяжесть:** S3 · **Уверенность:** высокая (сценарий — при двух отложенных триггерах одновременно)
- **Минимальное разрешение:** ступень 5 (замер с наблюдаемым триггером) — в отложенный вопрос 2 дописать условие:
  `expire` инвалидирует кэш индекса (эпоха сегментов в `IndexBlob`) и пересобирает `executions`.
- **Когда обязательно:** по триггеру «включается истечение сегментов» (вопрос 2) — если кэш LG-09 к тому времени включён.

### A-14 · Цель голоса и вердикта — следующая ссылка: «основание на ревизию» не держится

- **Вопросы:** Q09 · **Уровень:** PROVENANCE · **Класс:** D
- **Ответ дизайна:** «Основание — на одну ревизию или факт» (`14-trust.md:49-52`); `core/assert.target` — «любой факт
  или ревизия», ссылка в примере — без версии (`14-trust.md:46`); раздел индекса `trust` — «цель (факт или ревизия)»
  (`12-ledger.md:89`); вердикт: `used`/`unused` — **следующие** ссылки (`22-run.md:279`), при этом
  `used ∪ unused ⊆ snapshot.members`, а члены snapshot'а закреплены `ref@n` (`22-run.md:292`, `21-compose.md:25`);
  ссылки на нормы (`refs: follow`) могут быть следующими (`15-catalog.md:94`).
- **Наблюдение:** что значит голос/вердикт по `X` без версии — на ревизию в момент записи или «на объект вообще» — не
  сказано; как сравнивать `X` с `X@4` в подмножестве — тоже (искал: `target`, `@n`, `закреп`, `used`, `следующ`).
- **Контрсценарий:** выдан snapshot {X@4}. Владелец правит X «в противоположную сторону» → X@5. Потребитель
  возвращает вердикт `used: [X]`: (а) `X` разрешается в X@5 ∉ snapshot → вердикт отклонён (RL-11), сигнал потерян;
  (б) сравнение по `id` → принят, `learn` пишет `confirm` на членство — какое, X@4 или X@5 (A-03)? Параллельно:
  утверждение `core/assert {target: X, +1}` от марта: если индекс хранит цель как `X`, поддержка «перетекает» на X@5 с
  противоположным смыслом; если разрешает при коммите — на X@4, как и заявлено, но это нигде не записано.
- **Инварианта:** TR-09 / «основание — на одну ревизию» (`14-trust.md:49`); KR-07 (форма ссылки).
- **Последствие:** доверие к норме может пережить смену её смысла; вердикты по отредактированным блокам теряются или
  относятся не к той ревизии.
- **Тяжесть:** S3 · **Уверенность:** средняя
- **Минимальное разрешение:** ступень 1 (определение) — цель `core/assert` и элементы `used`/`unused`/`add` —
  закреплённые `id@n` (правило `ref-exists {pinned: true}` в типах `core/assert`, `std/verdict`) либо: следующая цель
  разрешается при коммите и индекс хранит `id@n`; одна фраза в 14 §2 и 22 §5.
- **Когда обязательно:** до среза S3 (доверие) и S8 (вердикт).

### A-15 · «Один `std/setup` на пространство» против базовых линий-настроек

- **Вопросы:** Q06 · **Уровень:** SEMANTICS · **Класс:** B
- **Ответ дизайна:** `std/setup` — «один объект на пространство имён» (`22-run.md:58-59`, T126 `02-glossary.md:172`,
  ADR-28); рантайм берёт `view.get(<пространство>/setup)` (`22-run.md:147`); «Базовая линия — тоже ревизия настройки
  (конвейер из одной стадии BM25 и т. п.), её кортеж закреплён так же» (`23-bench.md:37-38`); план — `baselines:
  [{name, setup: ref@n}]` (`23-bench.md:20`). Правила или зерна, держащего единственность, нет (искал: `один на
  пространство`, `<пространство>/setup`, `grain`, `std/setup`).
- **Наблюдение:** два прочтения: (а) базовая линия — ревизия **того же** `warrant/setup` — тогда запись базовой линии
  меняет действующий конвейер рабочих вызовов; (б) отдельный объект `std/setup` — тогда «один на пространство» ложно, а
  «действующий» определяется локальным именем `setup` — соглашением об имени (ср. «тип из `id` не выводится никогда»,
  `10-kernel.md:113`; `name` — «для типов и объектов ядра/библиотек», `10-kernel.md:97`).
- **Контрсценарий:** владелец готовит кампанию E1 с четырьмя базовыми линиями. По (а) пишет `warrant/setup@5 =
  BM25-only` для плана — с этого `seq` все рабочие `solve` идут без judge и Composer до следующей ревизии; `recall`
  пропадает, пакеты «не проверено стендом». По (б) реализация, которая держит единственность зерном типа (буква T126),
  отклоняет вторую настройку — базовые линии не записать.
- **Инварианта:** ADR-28 (одна настройка — действующая), T126.
- **Последствие:** «что исполняется сейчас» держится именем, а не моделью; одно из прочтений портит рабочий журнал.
- **Тяжесть:** S3 · **Уверенность:** средняя
- **Минимальное разрешение:** ступень 1 (определение) — «действующая настройка» = объект, на который указывает поле
  `setup` в `core/namespace` (или фиксированное локальное имя `setup`, записанное как правило в T126); прочие
  `std/setup` пространства — базовые линии и кандидаты, их рантайм рабочих вызовов не читает.
- **Когда обязательно:** до среза S9 (самоописание) / до E1.

### A-16 · `bench-run pass` — событие, работающее бессрочным допуском; отозвать нельзя

- **Вопросы:** Q05, Q10 · **Уровень:** SEMANTICS · **Класс:** D
- **Ответ дизайна:** `std/bench-run` — событие `{plan, tuple, results, metrics, verdict: pass|fail|invalid, copy}`
  (`23-bench.md:20`); гейт — «есть `bench-run pass`» на кортеж (`13-rules.md:85`, ADR-29:8-11); копию «хранят, пока её
  не удалит владелец», без копии `replay` — `expired` (`23-bench.md:84-85`); правка плана — новый план с `supersedes`
  (`23-bench.md:24`); у прогона такого механизма нет (искал: `bench-run` × `retire`, `отзыв`, `отмен`, `supersedes`,
  `invalid`).
- **Наблюдение:** по категориям Q10 `bench-run` — «что произошло», а гейт читает его как «что действует сейчас»
  (допуск к обучению для всех будущих вердиктов этого кортежа). Смотрит ли гейт на `core/retire` прогона — не
  сказано; `invalid` ставится только при записи. После удаления копии `bench-run` — запись о
  прошлом, которую нельзя перепроверить (`copy` — хэш того, чего нет).
- **Контрсценарий:** прогон B7 `pass` для `setup@3`. Через месяц владелец находит, что эталоны регрессионного набора
  были размечены с ошибкой (или копия кампании собрана на неверном `state`). Пишет новый план и получает `fail` B9 на
  тот же кортеж. Гейт ищет «есть `pass`» — B7 по-прежнему есть → каждый новый вердикт на вызовы `setup@3` учится; `fail`
  B9 ничего не отменяет. `core/retire` на B7 — поведение гейта не определено.
- **Инварианта:** ADR-29 (барьер на необратимом переходе), T-16.
- **Последствие:** ошибочный `pass` продолжает открывать необратимое обучение; последующий `fail` того же кортежа не
  барьер.
- **Тяжесть:** S3 · **Уверенность:** высокая (пробел), средняя (толкование «есть `pass`»)
- **Минимальное разрешение:** ступень 1 (определение) — в 13 §2 у `learning-gate`: засчитывается **последний** по `seq`
  прогон на кортеж по действующему регрессионному плану, и только живой (без `core/retire`); `fail` после `pass`
  закрывает гейт.
- **Когда обязательно:** до среза S9 (гейт) / до E6.

### A-17 · Три текстовых расхождения в определениях правила и зерна

- **Вопросы:** Q37, Q07 · **Уровень:** SEMANTICS · **Класс:** B
- **Ответ дизайна / наблюдение:**
  1. T41 — правило «…параметры, **к каким типам применяется**» (`02-glossary.md:73`); по 13 §1 правило такого поля не
     имеет — тип закрепляет правила (`13-rules.md:27-31`). Кто связывает: правило → типы или тип → правила.
  2. «Измерения `grain` — `required` в `schema` типа (правило `schema`, hard)» и тут же «тип, у которого измерение не
     обязательно, получает … soft» и «отсутствующее входит в ключ как `null`» (`11-identity-grain.md:39-41`, GR-09):
     обязательность измерения — требование к типу (hard при публикации) или рекомендация (lint)?
  3. «ключ A, пока она была алиасом, оставался в индексе `grain`» (`11-identity-grain.md:115`) против «`grain` … id
     (только живые)» (`12-ledger.md:85`) и T35 «живая — … не является алиасом» (`02-glossary.md:53`).
- **Контрсценарий:** (2) реализация A публикует проектный тип с необязательным измерением (находка lint), реализация
  B отклоняет публикацию — один и тот же журнал принят одной и отвергнут другой; (3) реализация, держащая ключ алиаса в
  индексе, отвечает на `ensure` ключа A алиасом A, другая — каноническим B, после `split` у них разный `grain`.
- **Инварианта:** KR-01/P12 (один механизм); `11-identity-grain.md` инвариант 1.
- **Последствие:** расхождение реализаций на уровне принятия коммита и содержимого индекса.
- **Тяжесть:** S4 · **Уверенность:** высокая
- **Минимальное разрешение:** ступень 1 — T41: «…параметры; типы закрепляют правила полем `rules`»; 11 §1: «измерения
  `grain` должны быть `required` — иначе находка lint; ядро не отклоняет»; 11 §4: «ключ A возвращается в индекс
  `grain` при `split`; пока A — алиас, в индексе только B».
- **Когда обязательно:** до среза S2.

## Сомнения и справки

1. **A-01** — тяжесть зависит от того, как 23 считает `select-F1` и `calibration-Δ` на ветке `recall` (по пакету или
   по фактам состава). Если по фактам — E3 доказывает то, чего потребитель не получает (кандидат в S1). Нужна справка
   владельца 23-bench.
2. **A-02** — принимает ли `Draft.type` ссылку без версии (разрешается в последнюю): в 12 §5 тип `string`; если
   рантайм всегда подставляет последнюю, риск остаётся для писателей CLI/API.
3. Для роли B: гейт пропускает вердикты сессий `purpose: simulate` «только в копии» (`13-rules.md:85`), но ядро не
   может отличить копию от основного журнала — в основном журнале такая сессия лишь находка (`23-bench.md:88-90`).
   Строка обучения по вердикту «симулятора» в основном журнале проходит hard-гейт.
4. Для роли B (Q63): строка обучения несёт `policy@rev`, а `trust()` и `inForce {basis}` считаются по текущей
   политике — два времени политики в одном выводе.
5. Для роли C: `replay` строит `view` пересборкой префикса **текущим** кодом проекций (`22-run.md:139-140`); версия
   проекции, которой шёл вызов, в кортеж не входит.
6. Q11 (сводка): `core/member`, `std/link` `{value: false}` — прекращение действия факта; `core/alias {value: false}` —
   отмена слияния; `std/distinct` — решение владельца «не одно» (снимается `value: false`); `reliability < 0` —
   голос, факт не заканчивает; `std/gap absent` — событие «на `seq` не найдено» (не закрывается, устаревает вместе с
   областью); `core/retire` — прекращение жизни объекта или версии. Смешения не найдено.
7. Q12: `none` пишется «как `unused` для каждого члена» (`22-run.md:337`) — отрицательный голос членствам по сигналу
   уровня задачи; роли B — проверить, не превращает ли это «задаче не понадобилось» в «член лишний».
8. Не читал `research/`, `integration/` (на них ссылаются ADR-26:20, ADR-31:18) — для выводов не понадобились.
