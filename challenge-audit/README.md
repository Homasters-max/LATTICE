# Challenge-аудит design v0.4 — старт сессии

Архитектурный аудит «на слом» каталога `design/` (v0.4, тег `design-v0.4`). Не проверка согласованности ссылок и
формулировок (её сделали аудиты C1 и F) — а поиск мест, где **принятое решение не выдерживает контрсценария**:
скрытые допущения, двойные источники истины, замкнутые эпистемические контуры, временные нестыковки, решения, которые
станут ограничением у второго потребителя.

**Точки входа:**

- **Ведущий** (новая сессия Claude, запущенная пользователем) — этот файл, потом `STATE.md`, дальше по шагам ниже.
- **Аудитор-субагент** — промпт из `ROLES.md` §«Промпт»; он ведёт в `AUDITOR.md` → свой раздел `ROLES.md` →
  `QUESTIONS.md`. Этот README аудитор не читает.

## Комплект

| Файл | Кто читает | Что внутри |
|---|---|---|
| `README.md` | ведущий | этот регламент |
| `STATE.md` | ведущий | где остановились, промахи прогона |
| `ANALYSIS.md` | человек | разбор исходного вопросника: что сохранено, что исправлено, что добавлено |
| `AUDITOR.md` | ведущий, все аудиторы | правила аудитора: мышление, доказательства, формат находки, тяжесть, запреты |
| `QUESTIONS.md` | все аудиторы | банк вопросов v2: Q01–Q70, поправки посылок, якоря в `design/`, роль-владелец |
| `ROLES.md` | ведущий, каждый аудитор — свой раздел | 5 ролей, их вопросы, чтение, обязательные артефакты; шаблон промпта |
| `REPORT-TEMPLATE.md` | ведущий | структура итогового отчёта |
| `findings/<A…E>.md` | пишут аудиторы | сырые находки ролей |
| `REPORT.md` | пишет ведущий | итоговый подробный отчёт |
| `LATTICE-Architectural-Challenge-Questions.md` | никто (история) | исходный вопросник; в нём ложные посылки — норма аудита этот комплект, аудиторы его **не читают** |

## Границы (жёстко)

- Аудируется **только** `design/` (включая `adr/`, `domains/`, `proposals/`). Правок в `design/` нет.
- Другие папки проекта (`research/`, `integration/`, `batch/`, черновики в корне, `D:\kb`) — **только по запросу
  пользователя**. Нужна справка оттуда — ведущий спрашивает пользователя, аудитор пишет в находке «нужна справка из …».
- **Навыки (Skill tool) не используются** — ни ведущим, ни аудиторами. Веб — нет.
- Пишут только в `challenge-audit/`: аудитор — свой `findings/<роль>.md`; ведущий — `STATE.md`, `REPORT.md`.

## Регламент ведущего

**Шаг 0. Подготовка (ведущий, ~5 мин).** Прочитать `README.md`, `STATE.md`, `AUDITOR.md`, `ROLES.md` (целиком) и
заголовки `QUESTIONS.md`. `design/` целиком **не читать** — контекст ведущего нужен для сверки и синтеза. Записать в
`STATE.md`: старт, ревизия (`git log -1 --format=%h -- design`).

**Шаг 1. Волна аудиторов.** Одним сообщением запустить 5 агентов (`subagent_type: general-purpose`, фоном) — роли
A–E из `ROLES.md`, промпт — шаблон из `ROLES.md` §«Промпт» с подставленной ролью. Пока идут — ничего не читать из
`design/` (не дублировать работу). Всего агентов в аудите — **5**; новых не порождать.

- Сбой агента (лимит 429, обрыв) — **возобновить его же** через `SendMessage` («продолжи с места остановки; уже
  записанное в `findings/<роль>.md` не переписывай»), а не запускать новый. Записать промах в `STATE.md`.
- Уточнение по находке — тоже `SendMessage` тому же аудитору.

**Шаг 2. Приём.** Каждый агент возвращает сводку ≤ 15 строк; находки — в файле. Проверить у каждого файла:
все вопросы роли есть в таблице покрытия; у каждой находки есть «Ответ дизайна» с адресом и «Контрсценарий». Нет —
`SendMessage` с требованием дополнить (один раз), иначе пометить находку «не подтверждена».

**Шаг 3. Сверка (ведущий, обязательна).**

1. **Дедупликация.** Один корень — одна находка итога; в ней ссылки на все сырые ID (`A-04 = D-11`).
2. **Проверка S1 и S2 — каждой.** Прочитать цитируемые строки `design/`; `Grep` по `design/` ключевых терминов
   находки — нет ли ответа в другом файле (ADR, глоссарий, «Вне объёма» другого домена). Итог: подтверждена /
   понижена (с причиной) / отклонена (с причиной и адресом ответа).
3. **S3–S4** — выборочно, не меньше одной на роль.
4. **Противоречия между ролями** (A считает решённым, B — дырой) — разобрать по источнику, итог записать.
5. Отклонённое не удалять: раздел «Отклонено при сверке» отчёта — видно, что проверено.

**Шаг 4. Отчёт.** `REPORT.md` по `REPORT-TEMPLATE.md`: подробный, с адресами. Матрица покрытия — все Q01–Q70.
Решения предлагать по лестнице `AUDITOR.md` §6 (сначала определение/граница, механизм — последним).

**Шаг 5. Закрытие.** Обновить `STATE.md` (итог, промахи, что дальше). В чат: 10–15 строк — сколько находок по
тяжести, топ-5, ссылка на `REPORT.md`. **Остановиться.** Внедрение в `design/` — отдельное решение пользователя.

## Ожидаемый объём

- Сырых находок: ≤ 20 на роль (≤ 100 всего) + таблицы покрытия.
- После сверки: ориентир 30–50 находок итога; S1 — единицы (если S1 больше 5 — перепроверить шкалу).
- Сессия ведущего: чтение ~1,5–2 тыс. строк (находки + выборочные цитаты), не весь дизайн.

## Условия остановки раньше

- Три и более агента упали и не возобновляются — остановиться, записать `STATE.md`, сообщить пользователю.
- Аудитор просит справку из другой папки и без неё ключевой вопрос не решается — спросить пользователя, не читать самому.
