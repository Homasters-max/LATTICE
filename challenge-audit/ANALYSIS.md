# Разбор исходного вопросника и что доработано

Исходник: `LATTICE-Architectural-Challenge-Questions.md` (59 вопросов + «Universal Auditor Skill»). Сверен с
`design/` v0.4: README, 00-vision, 01-first-run, 02-glossary (T01–T176), 04-architecture, 05-slices, индекс ADR,
выборочно домены 14, 22, 23, 30 (модель доверия, вердикт, эталоны, хост), разделы «Вопросы для grilling» и «Вне
объёма» всех доменов.

## 1. Что в исходнике сильное — сохранено

- **Установка «сломать, а не подтвердить»** и главный вопрос «что должно быть истинно без реализации, LLM, Jev,
  индексов, кэшей, пользователя» — сохранены дословно (`AUDITOR.md` §1).
- **Пять уровней** SEMANTICS → OWNERSHIP → PROVENANCE → EXECUTION → EVOLUTION и правило «аудит неполон, если проверен
  один» — сохранены, добавлено, где в дизайне обычно ответ (§3).
- **10 системных вопросов**, **4 класса скрытых проблем** (leakage, duplicate authority, closed loop, temporal),
  **правило «не усложнять»**, **сквозная цепочка** Need → … → New canonical fact — сохранены.
- **Универсальная модель объекта** (11 полей) — сохранена как «паспорт», но только для ключевых объектов ролей.
- Нумерация вопросов Q01–Q59 — сохранена для трассировки.

## 3. Чего в исходнике нет — добавлено (Q60–Q70)

Найдено при чтении дизайна; каждое — гипотеза для аудита, не вывод.

| Q | Тема | Почему (что видно в дизайне) |
|---|---|---|
| Q60 | **Корень аутентификации** | участника называет `--as` / `LATTICE_ACTOR` (30 §3); писатели — агенты, задающие своё окружение; на «хост честно передаёт личность» (14, 15 «Вне объёма») стоят `declared`, `overruled`, декларант, вердикт владельца R10b |
| Q61 | **`composer-caller` — контур в одном агенте** | вызывающий агент — Composer, потребитель и автор вердикта; группа `(agent, model)` одна |
| Q62 | **Истечение сегментов против пересборки и гейта** | события исполнения истекают (ADR-3), гейт читает `verdict.execution` (ADR-29); 12 «Вопросы» 2: хэш коммита с истёкшими строками перепроверить нельзя |
| Q63 | **Смена политики доверия задним числом** | `trust()` — вычисление; строка обучения несёт `policy`, остальное — ? |
| Q64 | **Дрейф калибровки** | `calibrated_for` = `{adapter, model, prompt_hash}`, но не состояние корпуса и шаблона карточки |
| Q65 | **Узкое горло владельца** | алиасы, эталоны, план, решающее «−» — только владелец/декларант |
| Q66 | **`recall` — исключение ADR-13** | «та же потребность» по judge без LENS; при отсутствии вердикта ошибку ничто не ловит? |
| Q67 | **Проводка «не влияет на результат»** | AR-09; эндпоинт может вести «ту же модель» на другое развёртывание |
| Q68 | **Самоописание без самоподмены** | P9: правила — данные; может ли коммит менять правила собственной проверки |
| Q69 | **Сквозная цепочка** | в исходнике — «финальный критерий», но не задание; теперь обязательный артефакт роли E |
| Q70 | **Отложенное, но несущее** | все «Вне объёма» и отложенные вопросы — проверить, безопасна ли отсрочка |

Добавлены классы **E. Implicit trust root** и **F. Deferral hazard** — два вида дыр, которые у зрелого дизайна
встречаются чаще, чем «забыли решить».

## 4. Роли — почему так

Разрез **по видам риска**, а не по файлам: каждая роль владеет классом вопросов целиком (иначе «самоподтверждение»
разорвано между trust, run и bench и никто его не видит). Домены читаются 2–3 ролями с разных сторон — пересечения
намеренны, их сводит ведущий. Пять ролей — верх заданного диапазона 3–5: при трёх роли B+C или D+E слились бы, и
артефакты (карта контура, таблица детерминизма, модель угроз) не поместились бы в контекст одного агента.

| Роль | Почему отдельно |
|---|---|
| A онтолог | SSOT, идентичность, правила — фундамент; ошибки здесь каскадом ломают всё выше |
| B эпистемолог | доверие + обучение + стенд — одна петля; делить её — терять класс C |
| C инженер решения | LENS/Composer/рантайм — где LLM и judge касаются смысла; детерминизм |
| D противник | модель угроз, сбои, владение, масштаб — взгляд «как сломать снаружи» |
| E скептик | проверяет утверждения видения целиком и делает сквозные артефакты, которые не принадлежат домену |

Верификацию S1/S2 делает ведущий (чтение цитат + `Grep` ответа), а не шестой агент: остаёмся в лимите 3–5, а сверка
требует взгляда поверх всех ролей.

## 5. Риски самого аудита

- **Ложные находки** из-за неполного чтения — главный риск; закрыт правилом «ответ дизайна с адресом» и обязательной
  сверкой S1/S2.
- **Инфляция тяжести** — закрыта критериями S1 и порогом «больше трёх S1 у роли — перепроверить».
- **Уход в «добавить механизм»** — закрыт лестницей разрешения (§6).
- **Контекст ведущего** — ведущий не читает `design/` целиком; сырые находки ≤ 20 на роль.
- **Обрыв агентов (429)** — постепенная запись в файл + возобновление тем же агентом через `SendMessage`.
