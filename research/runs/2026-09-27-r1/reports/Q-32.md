**Выводы**

```text
C-1. Закреплять rule@n в type@n — да; ошибочная версия правила находит задетые ревизии через индекс потребителей.
  Опора: E-1, E-2, E-3 (правило — версионируемая политика, исход восстановим) · E-8 (от негодной зависимости — к
    задетым результатам)
  Отношение к дизайну: СОГЛАСУЕТСЯ — RL-04; ссылки на правила только закреплённые (design/domains/15-catalog.md:52-58),
    `id@n` разрешается всегда (design/domains/10-kernel.md:72). Цепочка «rule@n → type@n → ревизии» уже есть в индексе
    `consumers` (design/domains/12-ledger.md:80), но как запрос не описана.
  Где в дизайне: design/domains/13-rules.md:24-26, :89
  Действие: в 13-rules §4 — строка «ошибка в rule@n: `consumers(rule@n)` → типы → их ревизии; lint выдаёт их владельцам».
  Неверен, если: —
  Уверенность: высокая · Цена отката: высокая

C-2. Кортеж проверки шире версии правила: ещё код примитива, правила родителя и состояние до коммита.
  Опора: E-4 (закреплять все части кортежа) · E-6 (изменение алгоритма ломает опору на прежние результаты)
  Отношение к дизайну: ПРОПУСК. Вердикт hard-правила = f(rule@n, код примитива, правила родителя, состояние)
    (design/domains/12-ledger.md:20-24). Состояние восстановимо: индекс — функция префикса журнала
    (design/domains/12-ledger.md:50-53). Код примитива — нет: ядро меняется версией кода (design/00-vision.md:86-87),
    а в строках и метке коммита версии ядра нет; исправленный `schema` иначе оценит старые тела. Правила родителя —
    не ясно: `extends` наследует правила (design/domains/10-kernel.md:97), но что `extends` обязан быть `T@n`, сказано
    только косвенно (типы — `refs: pin`, design/domains/15-catalog.md:54). Если родитель следующий — правила ребёнка
    меняются без новой версии ребёнка, и RL-04 не держится.
  Где в дизайне: design/domains/12-ledger.md:20-24; design/domains/10-kernel.md:97; design/domains/13-rules.md:25-26
  Действие: (1) метка коммита (`commit`) несёт версию ядра; (2) в 10-kernel: `extends` — только закреплённая ссылка
    `id@n`, правило `ref-policy` для `core/type` — безусловное (Q-29 C-3); (3) в 13-rules «Операции» —
    `revalidate(commit)`: индекс на seq до коммита + правила из `type@n` строк; расхождение с версией ядра из метки —
    явное предупреждение, а не тихий другой ответ.
  Неверен, если: ядро не меняет семантику примитивов между версиями (тогда хватит правила «примитив меняется только
    расширением» — но это тоже надо записать).
  Уверенность: средняя (механизм — рассуждение по дизайну, принцип — E-4) · Цена отката: высокая

C-3. Цена закрепления — каскад версий; его режет определение совместимости без версии.
  Опора: E-5 (каждый базис стоит) · E-7 (потребитель переходит сам; параллельные версии — цена)
  Отношение к дизайну: ПРОПУСК. Правка правила типа `std/ctx` → `std/ctx@2` (design/domains/13-rules.md:25-26) →
    контракты всех стадий закреплены на `std/ctx@1` (design/domains/13-rules.md:59, design/domains/22-run.md:17) →
    новые версии 17 стадий и конвейера → регрессия стенда (design/domains/22-run.md:39-40). Потребитель переходит сам
    (design/domains/15-catalog.md:47-48) — по E-7 это верно, но глубина каскада нигде не оценена. Если `compatible`
    сравнивает id типа без версии (versions одного id — один тип, Q-05 C-2), правка правила не трогает контракты.
  Где в дизайне: design/domains/13-rules.md:59-63, :80; design/domains/22-run.md:39-40
  Действие: решить вместе с Q-33 C-3: `compatible(out, in)` — по id типа без версии (+ `extends`); закрепление
    `@n` в контракте — для воспроизведения, не для совместимости. В 15-catalog — lint «новая версия типа, на
    старой закреплено N способностей».
  Неверен, если: версии одного id типа меняют смысл тела (тогда нужна сверка версий — но это запрещает Q-05 C-2).
  Уверенность: средняя · Цена отката: высокая
```
