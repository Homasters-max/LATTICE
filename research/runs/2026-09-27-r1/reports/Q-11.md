## Q-11. Можно ли менять тип (классификацию) сущности, сохраняя её идентичность?

- **Место в дизайне:** KR-10 «смена типа сущности — новая версия с другим `type`; `id` не меняется»
  `design/domains/10-kernel.md:169#68f38c`; `type` — закреплённая ссылка на ревизию типа, `version` — только следующий
  `design/domains/10-kernel.md:25-27#658a97`; виды объектов по флагам `design/domains/10-kernel.md:36-44#36ed29`; хэш включает id
  типа `design/domains/10-kernel.md:48#7fa2d3`; инварианты 1–4 `design/domains/10-kernel.md:150-153#a866cd`. Примитивы
  `ref-type` (цель — нужного типа или наследника), `ref-policy`, `roles` `design/domains/13-rules.md:35-37#5dc425`; ревизия
  проверяется правилами своего `type@n` `design/domains/13-rules.md:25-26#0b4e82`. Следующие ссылки видят новую версию
  `design/domains/15-catalog.md:68#8c0b18`; snapshot при изменении — `stale` `design/domains/15-catalog.md:60-61#271883`.
  Python-урок: `__class__` сохраняет identity `design/03-python-lessons.md:21#e5b2b7`, в LATTICE смена — новой версией под
  правилами нового типа `design/03-python-lessons.md:37#ecdaee`. Зерно — от типа, identity от зерна не зависит
  `design/domains/11-identity-grain.md:10-20#6b0f5b`.
- **Уже исследовали:** `research/2026-09-27-record-versioning.md` C-3 — перевод на **новую версию того же** типа с тем же
  телом отбрасывается как no-op; здесь не повторяется. Смена на **другой** тип no-op не даёт: хэш берёт id типа (:48).
- **Цена отката:** высокая → L2.
- **Глубина:** L0 (7 выдач) → L1 (9 разделов 7 карточек) → L2 (`related` TERM-395: PAT-146, PAT-147 — описания из
  пакета, не открывались: вид «значение» уже разобран в `research/2026-09-27-identity-kinds.md`; карта
  `maps/map-identity.md` — про identity участников и делегирование, не про объекты; не использована). Главы kddd24-ch11,
  hew19-ch08 не открывались (не L3).
- **Бюджет:** запросы сборщика 1 + 5 узких (лимит превышен сборщиком на 1, R-1) · добор куратора 1 (S-7, пакет не

- **Статус:** отвечен (C-1, C-3, C-4); C-2 — рассуждение на инвариантах дизайна.

```text
C-1. Сохранять id при смене классификации верно.
  Опора: E-1 (сущность — явный id при изменяемом остальном)
  Отношение к дизайну: СОГЛАСУЕТСЯ — KR-10, инвариант 1; тот же принцип у зерна (11-identity-grain:10-20).

  Действие: не требуется.
  Неверен, если: смена типа меняет вид объекта (см. C-2).
  Уверенность: высокая · Цена отката: высокая

C-2. Смена типа допустима только между типами одного вида.
  Опора: рассуждение на инвариантах дизайна (база молчит, G-1). Инвариант 2: у mutable:false только version 1 —
    переход сущности в тип события даёт событие с version > 1. Инвариант 3: у значения id = хэш — переход в тип
    с identity: content невозможен при неизменном id. Python, на который ссылается урок, тоже не позволяет
    присвоить __class__ несовместимого устройства (рассуждение, не из базы).
  Отношение к дизайну: ПРОПУСК — KR-10 говорит только «новая версия с другим type».
  Где в дизайне: design/domains/10-kernel.md:151-152, :169; design/03-python-lessons.md:21
  Действие: 10-kernel, инварианты: «новая ревизия сущности может сменить type только на тип с теми же identity и
    mutable» — проверка кодом ядра при коммите (как immutable, 13-rules).
  Неверен, если: понадобится «заморозить» сущность в событие — тогда это новый объект со ссылкой на старый, а не
    смена типа.
  Уверенность: высокая · Цена отката: высокая

C-3. Новая ревизия проверяется правилами нового типа, но потребители — нет.
  Опора: E-5 (смена типа тянет пересмотр всего, что завязано на старый) · E-6 (реакция — в одном месте)
  Отношение к дизайну: ПРОПУСК. ref-type проверяется при коммите объекта, который ссылается; следующая ссылка из
    чужого объекта после смены типа цели начнёт указывать на объект не того типа, и никто этого не проверит.
    То же для текущих фактов: roles объявляет типы объектов ролей (13-rules:37) — членство или связь с
    переклассифицированным объектом становятся неверными задним числом. Закреплённые ссылки не страдают — они
    видят старую ревизию.
  Где в дизайне: design/domains/13-rules.md:35-37; design/domains/15-catalog.md:68; design/03-python-lessons.md:37
  Действие: 10-kernel / 13-rules: смена type — отдельное событие индекса. Смена вниз по extends (на наследника
    текущего типа) безопасна для потребителей: ref-type принимает наследника, правила только добавляются (Q-10 C-1).
    Смена в сторону или вверх — коммит проверяет ref-type и roles у текущих потребителей из индекса (hard), либо
    потребители получают lint-находку, как stale у snapshot (15-catalog:60-61) — выбрать.
  Неверен, если: следующие ссылки с ref-type на сущности не используются (всё закреплено) — тогда риск только у фактов.
  Уверенность: средняя · Цена отката: высокая

C-4. Смена типа — не способ выразить состояние, дрейфующую категорию или одновременные роли.
  Опора: E-4 (классификация — по поведению) · E-3 (дрейфующие категории — справочник, не жёсткое деление) · E-2
    (одна идентичность — несколько контекстов сразу) · E-7 (атрибут связи)
  Отношение к дизайну: ПРОПУСК — у KR-10 нет критерия, когда менять тип, а когда поле или факт.
  Где в дизайне: design/domains/10-kernel.md:169
  Действие: в KR-10 дописать критерий: тип меняют, когда меняются правила, роли или зерно (поведение объекта в
    LATTICE); статус жизненного цикла — поле или факт; категория, чьи границы меняются, — ссылка на объект-категорию
    (ANT-121); несколько классификаций одновременно — факты о том же id (как членство), не смена type.
  Неверен, если: у категорий действительно разные правила и объект не бывает в двух сразу — тогда смена типа уместна.
  Уверенность: средняя · Цена отката: высокая
```
