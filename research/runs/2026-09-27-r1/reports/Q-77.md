C-2. Для runtime различие скрыть нельзя — ответ агента приходит в другом процессе.
  composer-caller отдаёт задание, а вызывающий агент отвечает командой (design/domains/30-adapters.md:59-60) —
  новым запуском CLI. Runtime же проходит стадии в одном цикле и коммитит в конце (design/domains/22-run.md:68-75);
  run<T>() обещает Promise<{output}> (design/domains/30-adapters.md:25-28). Выполнить оба обещания в одном процессе
  нельзя; в списке команд нет той, которой агент отвечает (design/domains/30-adapters.md:77-88). Деталь «ответ придёт
  позже» нужна runtime и CLI — сокрытие за одной сигнатурой даёт ложную абстракцию (E-4, E-8); по базе её делают
  явной частью интерфейса (E-5). Агент и вызов API различаются операционно (минуты против секунд, доступность
  человека-оператора против сервиса) — это случай асинхронной связи с обратным каналом (E-6).
  Механизм без нового состояния: фиктивный composer уже отвечает из фикстуры по (kind, hash входа)
  (design/05-slices.md:39). composer-caller — та же фикстура, которую заполняет агент:
    1. run() ищет ответ в cache/composer по (kind, hash входа); есть — возвращает {output, meta};
    2. нет — возвращает {pending: {kind, input, schema, key}};
    3. runtime на pending останавливается без коммита (RN-03 цел) и отдаёт
       {status: "needs-answer", execution, task} (solve --json);
    4. lattice answer <execution> <json> проверяет ответ схемой, пишет в кэш по key и перезапускает прогон;
       стадии до этого места повторяются из кэша judge почти бесплатно (Q-65 C-1).
  Опора: E-4, E-8 (против скрытия) · E-5 (сделать явным) · E-6 (асинхронно) · E-3
  Отношение к дизайну: ПРОПУСК
  Где в дизайне: design/domains/30-adapters.md:25-28; design/domains/30-adapters.md:59-60;
    design/domains/30-adapters.md:77-88; design/domains/22-run.md:68-75
  Действие: 30-adapters: Composer.run → Promise<{output, meta} | {pending: Task}>; раздел composer-caller — шаги 1–4;
    CLI + «lattice answer <execution> <файл|json>»; 22-run §3: pending — не ошибка стадии, прогон «ждёт ответа»,
    журнал не пишется.
  Неверен, если: агент вызывает LATTICE как библиотеку в своём процессе (тогда достаточно обратного вызова, pending
    не нужен).
  Уверенность: высокая · Цена отката: высокая

C-3. Чего избегать: ждать агента внутри run() и пропускать его ответ мимо проверки.
  Блокирующее ожидание (stdin, опрос файла) склеивает время агента со временем стадии: бюджет ms, проверяемый после
  каждой стадии (design/domains/22-run.md:72), теряет смысл, а обрыв ожидания неотличим от сбоя. Ответ агента — вход
  извне, как и ответ модели: он проходит ту же схему и закрытый мир (design/domains/30-adapters.md:61), иначе режим
  агента станет обходом AD-05. Pending без обратного канала прячет, что ответа нет (E-7): статус «ждёт ответа» должен
  быть виден в выводе solve.
  Опора: E-7 (граница) · E-5
  Отношение к дизайну: ПРОПУСК
  Где в дизайне: design/domains/30-adapters.md:59-61; design/domains/22-run.md:72
  Действие: 30-adapters composer-caller + «не ждёт в процессе; ответ проходит схему и check, как ответ модели».
  Неверен, если: —
  Уверенность: средняя · Цена отката: высокая

C-4. Режим «агент» — свойство вызова, не проекта.

  Опора: E-2 · рассуждение

  Неверен, если: —
